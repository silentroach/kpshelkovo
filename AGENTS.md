# AGENTS.md

Руководство для AI-агентов на уровне всего workspace.

## Жизненный цикл изменений

### Выбор маршрута

- Основной вход — обычный запрос владельца. Сам выбери маршрут и подключи методы и предметные skills; slash-команда не обязательна.
- OpenSpec используй для новой функциональности, изменения правил поведения и существенных технических изменений, включая инфраструктуру. Маршрут: задача → исследование и обсуждение → согласованный change → разрешение реализации → самостоятельная работа → проверки → PR → человеческое ревью и merge.
- Контент, редактура документации и specs без изменения смысла, очевидные мелкие исправления известного поведения и совместимые механические обновления идут коротким путём с предметными правилами. Если исправление бага требует нового решения о поведении, подготовь change. Примеры выбора маршрута и объёма артефактов — в [docs/development.md](/docs/development.md#объём-работы-и-проверок).
- На маршруте OpenSpec используй штатную схему `spec-driven`. Начни с `pnpm exec openspec context --json` и `pnpm exec openspec list --json`, найди текущий change и затронутые основные specs. Затем подключи подходящий штатный OpenSpec skill.
- Все терминальные вызовы OpenSpec выполняй через `pnpm exec openspec` из корня workspace. Это правило относится и к примерам в сгенерированных skills, командах и подсказках CLI: перед исполнением добавляй `pnpm exec`. В ответах используй списки, даже когда upstream-шаблон предлагает таблицу.

### Владельцы информации

- GitHub issue хранит проблему, исходные материалы, приоритет, обсуждение, координацию и ссылки.
- `openspec/changes/<change>/` хранит единственную актуальную версию объёма, требований, технического подхода и задач изменения. После согласования в issue остаются резюме и ссылки, а не вторая спецификация. Пункты `tasks.md` автоматически в issues не превращаются.
- `openspec/specs/` хранит накопленные требования после завершённых изменений. Перед подготовкой, правкой и синхронизацией specs прочитай раздел [«Отбор требований для specs»](#отбор-требований-для-specs). Пополняй specs по мере работы над областью, сверяя код, тесты и прежние решения.
- `docs/decisions/` хранит долговечные архитектурные решения и причины выбора. `design.md` change ссылается на действующие ADR; новый ADR нужен для значимого долговечного выбора. Историческое обоснование ADR не заменяет действующие рабочие инструкции.
- Продуктовые документы, дизайн-гайд и `GLOSSARY.md` хранят общие правила своих областей. Термины уточняй в существующем глоссарии, архитектурные решения — в существующей серии ADR.
- PR хранит реализацию, результаты проверок и оставшуюся ручную приёмку. По умолчанию самостоятельная задача — один issue, один change и один PR. Большая инициатива может объединять несколько изменений; для мелкой прямой правки issue создаётся по необходимости.
- Документы OpenSpec пиши по-русски, сохраняя обязательные заголовки, `Requirement`, `Scenario`, `SHALL`/`MUST`, `WHEN`/`THEN` и технические идентификаторы.

### Согласование и передача

- Покажи подготовленные артефакты и получи явное разрешение владельца на реализацию. Исходная просьба решить задачу не одобряет ещё не подготовленный change.
- Сохрани согласованные артефакты в рабочей ветке. После разрешения оставь в issue короткую отметку со ссылкой на соответствующий коммит. Документы и реализация обычно входят в один PR; отдельный PR для согласования не требуется.
- Новая сессия читает change, отметку разрешения и фактическое состояние ветки, включая незакоммиченные файлы. Продолжай по `tasks.md`, сверяя отметки с результатом, а не по памяти предыдущего разговора. Если разрешение не удаётся подтвердить, уточни его у владельца.
- После разрешения самостоятельно доводи работу до PR. Повторное обсуждение нужно при изменении поведения, согласованного объёма или существенного архитектурного решения.
- Перед реализацией незапланированного отдельного механизма, существенного обходного решения или заметного расширения задачи вызови `advisor` по [протоколу консультации](/docs/development.md#консультация-с-advisor). Это правило действует для OpenSpec и короткого пути; при других сомнениях консультация добровольна, для обычной мелкой правки не обязательна. Разбери рекомендацию до реализации; если обязательная консультация недоступна, сообщи причину владельцу и согласуй дальнейший путь.
- Перед реализацией крупного обходного решения обсуди его с владельцем, даже если оно укладывается в согласованное поведение и обе модели его поддержали: покажи реальный случай, причину обхода, цену поддержки и более простой вариант, включая отказ от необязательного эффекта. Реализуй обход после явного согласования.
- Согласованный объём имеет приоритет перед предложениями упрощения. Исправления и упрощение собственной реализации выполняй внутри текущего изменения. Самостоятельный рефакторинг вне его объёма оформляй отдельно. Методы grilling, исследования и качества помогают этому маршруту, а не вводят собственный жизненный цикл.
- Явные указания владельца о рабочей копии, ветке и публикации, а также ограничения текущего инструмента сохраняют силу. Если commit, push или PR ещё не разрешены, подготовь результат локально и явно укажи, каких опубликованных ссылок пока нет; не выдумывай коммит согласования.

### Проверки и завершение

- Перед PR выполни три части приёмки: структурную валидацию OpenSpec; проверку результата по требованиям и сценариям с подходящими typecheck, тестами, сборкой или браузером; ревью всего актуального diff с исправлениями и упрощениями. Для короткого пути требования задаёт запрос или issue. В ревью включай staged, unstaged и новые файлы, а не только последний коммит.
- Структуру проверяй `pnpm openspec:validate`. Наличие всех артефактов и успешная валидация не доказывают готовность реализации.
- Обычное завершение: реализация → проверки → синхронизация основных specs и архивирование change в той же ветке → PR. Используй штатные sync/archive workflows; код, основные specs и архив должны попасть в основную ветку вместе. В PR кратко укажи выполненные проверки, результаты и оставшуюся ручную приёмку.
- Если нужна приёмка на production, согласуй её до реализации: PR использует `Refs`, issue закрывается после проверки. Если production-проверка завершает сам change, архивирование тоже откладывается до завершающего изменения документов. В обычном случае PR использует `Closes` для своей задачи.
- Собственная проверка агента предшествует PR; человеческое ревью и merge выполняет владелец. GitHub-детали — в `project-issues`.

### Отбор требований для specs

Эти правила действуют при подготовке delta specs, их переносе в `openspec/specs/` и ревью основных спецификаций. Жизненный цикл изменения — в разделе [«Жизненный цикл изменений»](#жизненный-цикл-изменений).

- Перед добавлением или сохранением каждого требования ответь: чьё ожидание оно защищает, зачем понадобится после завершения задачи и по какому наблюдаемому результату отличить соблюдение от нарушения. В основных specs оставляй только обоснованные долгоживущие правила продукта, редакционной модели или публичного контракта; описание текущего кода само по себе недостаточно.
- Delta specs готовь сразу как будущий основной контракт. Разовые миграции, текущие количества и списки записей, старые форматы и условия конкретного релиза описывай в `design.md`/`tasks.md`, результаты — в PR. Если совместимость со старым форматом остаётся обязательством для потребителей, это долгоживущее требование.
- Сценарий фиксирует существенное различие поведения: воспроизводимое условие и конкретный результат. Используй обобщённые данные; реальные названия, даты и slug нужны только когда они сами являются контрактом. Слова «раньше», «прежний набор» и «после миграции» требуют явной точки сравнения. Способ проверки и тестовые fixtures принадлежат задачам и тестам.
- Не переписывай в specs схемы полей, код, ADR и тестовые матрицы. Обычные проверки типов, пустых строк и диапазонов оставляй схемам и тестам; в spec сохраняй значимые ограничения и ошибки предметной области. Точные имена публичных полей, URL и идентификаторов уместны, когда от них зависит внешний потребитель.
- Перед sync/archive и при ревью основных specs повтори отбор: убери дубли и разовые условия, сохрани существенные инварианты и согласованное поведение. Если сокращение меняет смысл требования, согласуй изменение; редакторское сокращение спецификации само по себе не повод удалять защитную валидацию или регрессионные тесты.

### Установка и обновление инструментов

- Восстановление, регенерация и откат описаны в [docs/development.md](docs/development.md). Используй проектный bootstrap; глобальные skills и их lock-файлы не меняй.
- Сгенерированную интеграцию обновляй штатно через `pnpm openspec:generate`; проектные дополнения храни в правилах и OpenSpec config. Внешние skills устанавливай в исходном upstream-виде; несовместимый с политикой метод исключай из проектного набора по согласованию с владельцем.
- Обновление OpenSpec: release notes и миграции → точная версия и lock-файл → регенерация → проверка совместимости с этой политикой → валидация и подходящие проверки → человеческое ревью. Совместимое механическое обновление идёт коротким путём; изменение процесса требует change. Откат возвращает весь PR: пакет, lock-файл, параметры и инструкции.

## Структура репозитория

```text
apps/
  www/       # единое Astro-приложение kpshelkovo.online
  media/     # статическая 404 для media.kpshelkovo.online
packages/    # shared утилиты и UI
docs/        # документация, дизайн-гайды и ADR
ops/         # nginx и deploy-инфраструктура
scripts/     # build/deploy helper scripts
```

## Локальные инструкции

- Перед работой в `apps/www` обязательно читать `apps/www/AGENTS.md`.
- Для устойчивых названий, терминов, юрлиц и написаний сверяться с корневым `GLOSSARY.md`. Добавлять туда общую терминологию проекта и названия, для которых необходимо закрепить написание или различение. Появление карточки подрядчика, канала или места само по себе не повод пополнять глоссарий.
- Данные новостей лежат в `apps/www/src/data/news`: авторы в `authors/*.yaml`, статьи в `articles/**/*.md`, выжимки архивов в `summaries/YYYY/index.md` и `summaries/YYYY/MM.md`; при добавлении или редактировании новостей обязательно использовать skill `news-maker`.
- Перед изменением поискового кода, разметки индексирования, metadata, правил корпуса, весов, настроек или версии Pagefind, поисковых тестов и `search_aliases` использовать skill `site-search`. Релевантность оценивать вручную по затронутым запросам до/после; обычное пополнение материалов по действующим правилам само по себе не требует поисковой приёмки.
- Данные статуса сервисов лежат в `apps/www/src/data/status/incidents/**/*.md`; перед добавлением или редактированием читать локальный `apps/www/src/data/status/incidents/AGENTS.md`.
- При визуальной сверке генпланов с контурами НСПД следуй `docs/parcel-updates.md`: проверь снимки, привязку и временное HTML-наложение, затем изучи увеличения до записи связей.
- При подготовке координат в градусах для публикации ограничивай результат вычислений и публичные копии восемью знаками после запятой; внешние снимки и редакционные исходники сохраняй без округления. Контракт — [public-coordinate-precision](openspec/specs/public-coordinate-precision/spec.md).
- Перед загрузкой, заменой, удалением или проверкой публичных файлов в `kps-public` обязательно использовать skill `public-media-publisher`.
- Если меняются shared стили, примитивы ссылок или URL-утилиты, проверить все затронутые разделы в `apps/www`.
- При изменении клиентских импортов, условий загрузки или сборки сравни состав и размеры по [инструкции анализа бандлов](docs/development.md#анализ-клиентских-бандлов); сохраняй актуальные YAML-отчёты вместе с изменением.
- Архитектурные решения искать и фиксировать в `docs/decisions`; список ADR лежит в `docs/decisions/README.md`.
- Публичные Markdown/llms-документы генерировать через `@shelkovo/markdown` AST API или app-helper поверх него; не собирать целый документ локальным `lines.join('\n')`.
- В генераторах создавать ссылки, списки, абзацы и inline-код напрямую через `md`; не собирать Markdown-шаблон, чтобы затем распарсить его в AST. `parseMarkdownFragment` использовать для вставки существующего редакционного Markdown.
- В публичных Markdown/llms-документах не использовать Markdown-таблицы; если нужна структурированная выдача, писать обычными списками.
- Форматирование автоматически запускается при коммите: Prettier для `.astro`, oxfmt для остальных поддерживаемых файлов, включая Svelte.
- В документации и ответах не использовать markdown-таблицы; писать списками.
- Во внутренней документации репозитория и собственных агентских инструкциях ссылки на файлы пиши от корня с начальным `/`: `[дизайн-гайд](/docs/design/design-code-shelkovo.md)`. Ссылки на раздел того же файла оставляй в виде `#якорь`. Для материалов сайта и публичных Markdown/llms следуй их URL-контрактам.

## Роутинг news/status/events

- В `/status` добавляй доступность сервисов: электричество, вода, интернет, дамба, аварии, временные отключения, окна плановых или внеплановых работ, восстановление и фактическую длительность перебоя.
- В `/events` добавляй датированные мероприятия для жителей: досуг, спорт, собрания, встречи и совместные дела, включая соседние посёлки. Перед добавлением, уточнением, отменой или ревью читай `apps/www/src/data/events/AGENTS.md`; данные лежат в `apps/www/src/data/events/YYYY/MM/*.md`.
- В `/news` добавляй редакционные материалы с самостоятельной новостной ценностью: отчеты ОК Комфорт, тарифы, документы, итоги собраний и голосований, строительные этапы, изменения правил и полезные инструкции. Новость о мероприятии ссылается на общую запись `events`; отдельная новость на каждый сеанс не нужна.
- Если источник опубликован в Domyland или Telegram как `news`, маршрутизируй по смыслу, а не по названию канала: сообщение о временном отключении сервиса идет в `/status`.
- Если один источник содержит и сервисный перебой, и широкий контекст, добавляй отдельную status-запись для перебоя; новость делай только если остается самостоятельная польза вне таймлайна статуса.

## Skills

- При любой разработке подключай скилл `ponytail`
- При выборе визуального направления, создании или пересмотре композиции страниц подключай `design-taste-frontend` (Taste). Для плотных таблиц и рабочих экранов вне основной области upstream применяй только подходящие общие приёмы иерархии и композиции.
- При создании или изменении конкретного движения подключай `animate`; сначала определи назначение и частоту движения. Для физики жестов, инерции и прерываемых взаимодействий подключай `apple-design` по его предметной области.
- При создании, изменении или анализе Svelte-компонентов и модулей подключай `svelte-core-bestpractices` вместе с `svelte-code-writer`: первый задаёт инженерные приёмы, второй — работу с документацией и autofixer.
- При создании или редактировании любых русскоязычных текстов сайта подключай `humanizer-ru`: статьи, справочные материалы, тексты интерфейса, заголовки, описания и подписи. Для нового текста сначала подготовь черновик, затем отредактируй его по скиллу с учетом жанра. Исключение — страницы `/kb`, которые только дословно воспроизводят сканы: сохраняй текст источника; собственные пояснения на таких страницах редактируй по скиллу. ADR и внутренняя техническая документация под это правило не подпадают.
- Добавляешь или правишь новость сайта - подключай `news-maker`
- Меняешь внутрисайтовый поиск, Pagefind или `search_aliases` - подключай `site-search`
- Публикуешь или меняешь файлы в `kps-public` или ссылки `media.kpshelkovo.online` - подключай `public-media-publisher`
- Меняешь/изучаешь конфиги nginx в папке ops - `nginx-expert`

## Видимые тексты

- Писать живым языком без канцелярита: активный залог вместо пассивов и отглагольных существительных (`залатали ямы`, а не `проведен ямочный ремонт`).
- Помогать читателю сканировать текст: выделять ключевые факты жирным, дробить длинный текст заголовками, ставить ссылки на связанные материалы.
- При пересказе источника фиксировать его сообщение и только проверяемые релевантные пробелы: не назван срок или статус, нет ответа на прямо заданный вопрос, нет запрошенного подтверждения. Молчание источника по остальным деталям плана не превращать в отдельные утверждения или перечни.
- Не дописывать в материал, какие посторонние вопросы источник не осветил. Отсутствие ответа упоминать только тогда, когда этот пробел непосредственно важен для темы страницы и помогает читателю правильно понять приведённый факт; не придумывать дополнительные ожидания от источника.
- Факты и обещания различай атрибуцией и глаголами: «ОК обещала закончить до 31 октября», «компания сообщила о начале работ». Убирай пояснения вида «это X, а не подтверждение Y», «не означает, что…», «не следует считать…», если читатель не рискует существенно неверно понять факт. Перед завершением проверяй на такие оговорки и текст сайта, и свой ответ.
- Эмоджи допустимы, когда уместны по тону и помогают восприятию.

## Дизайн

- Начинай визуальную работу с brief: задача читателя, реальный материал и осмотр текущего интерфейса. Задача читателя, доступность, полнота фактов и редакционные правила имеют приоритет над маркетинговыми ограничениями Taste.
- Сохраняй необходимые строки таблиц, источники, даты, цитаты и смысл текста; числа из источника не заменяй ради визуального разнообразия. Русские тире и диапазоны оформляй действующим типографом и редакционными правилами, включая `humanizer-ru`.
- [Дизайн-гайд](/docs/design/design-code-shelkovo.md) — отправная точка для визуальных решений, палитры и UI-правил. Предлагай улучшения шрифтов, палитры, плотности и композиции с обоснованием пользы для задачи; согласованные изменения записывай в этот же гайд одновременно с UI.
- Перед добавлением нового семейства, стиля или веса шрифта сначала обновить Font Budget в [дизайн-гайде](/docs/design/design-code-shelkovo.md#font-budget) и проверить сетевые запросы на ключевых страницах; не добавлять локальные начертания для одного компонента.
- Числовые dials, обязательные изображения и dual-mode из Taste сами по себе не расширяют объём задачи. Изображения подбирай по смыслу материала и публикуй по проектным правилам.
- Skills следуют проектному [жизненному циклу](#жизненный-цикл-изменений) и [владельцам информации](#владельцы-информации); компоненты остаются в существующих app/package-каталогах. Block library из Taste — upstream-справочник, а не новое проектное хранилище.
- За правилами `title` и `description` страниц идти в `docs/page-meta.md`.
- В `AGENTS.md` держать процессные и архитектурные правила, а не подробный дизайн-гайд.

## Упоминания людей

- Людей в материалах упоминать через `@person-id`, `@person-id:case` или `[видимый текст](@person-id)`.
- `@person-id` использовать, когда в тексте нужно показать каноническое имя человека в именительном падеже.
- `@person-id:case` использовать, когда нужно показать имя человека в другом падеже.
- `[видимый текст](@person-id)` использовать, когда видимым текстом должна остаться авторская фраза: роль, описание или часть предложения.
- Поддерживаемые падежи: `nom`, `gen`, `dat`, `acc`, `ins`, `prep`.
- Если падеж не указан, используется `nom`: `@kirill-shchemelinin` → именительный.
- Если в материале нужен другой падеж, сначала добавить соответствующую форму в данные человека, затем использовать ее в тексте: `@kirill-shchemelinin:gen`.
- Не использовать `[видимый текст](@person-id:case)`: в ссылочном формате грамматика живет в видимом тексте, а не в `name_cases`.
- Формы имени хранить в человеке как источник истины; не полагаться на автосклонение при рендере.
- Build должен проверять все `@person-id:case` в материалах: человек обязан существовать, а запрошенная форма склонения обязана быть заполнена.
- Нельзя молча fallback-ать на `nom`, если явно запрошен другой падеж и формы нет; build должен падать или выдавать явную ошибку.

## Правила Typescript

- по максимуму используй `readonly` для иммутабельности там, где она уместна
- для тривиальных helper-ов с единственным `return` предпочитай однострочные `const`-стрелки (`const fn = (): T => expr`) вместо `function fn() { return expr; }`
- не храни типы и интерфейсы вместе с кодом, лучше вынеси их в отдельный модуль
- не используй null вообще никогда, только undefined и optional свойства
- если параметр функции можно опустить, пиши `param?: T`, а не `param: T | undefined`; union с `undefined` оставляй для случаев, где аргумент обязателен семантически
- не писать `...(value ? { field: value } : {})` только ради optional-поля: если `undefined` допустим и отсутствие ключа не является контрактом, присваивай `field: value` напрямую

## Тесты

- Не превращать разовую проверку доставки или наличия артефактов сборки в постоянный smoke-обход сайта в CI. Регрессию проверять коротким тестом конкретного поведения; не писать отдельные парсеры и универсальные валидаторы ради тестов.
- Если ожидаемый результат не супермелкий и важна точная строка/структура, предпочитай `toMatchInlineSnapshot() / toMatchSnapshot()` (в зависимости от размера снапшота) вместо длинного `toBe(...)`/`toEqual(...)`
- Если в строке важны неразрывные пробелы, в snapshot показывай их видимым символом, например через test-helper, который заменяет `\u00A0` на `·`.
- Не генерируй тесты, которые проверяют случайную статику: точный текст заголовков/лейблов, полный generated markdown/llms output, большие snapshots или Tailwind-классы. Исключение — когда это явно публичный контракт, аудируемые данные или важная типографика/форматирование. Для generated discovery/llms проверяй наличие стабильных URL, схем, фидов и отсутствие внутренних путей; для UI — поведение, доступность и data/URL-контракты, а не классы.
