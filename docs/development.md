# Окружение разработки

Правила работы с задачами находятся в разделе [«Жизненный цикл изменений»](/AGENTS.md#жизненный-цикл-изменений). Этот документ описывает установку и обслуживание инструментов; причины выбора процесса — в [ADR-038](/docs/decisions/038-openspec-development-workflow.md).

## Объём работы и проверок

Выбирай маршрут по `AGENTS.md`: например, исправление опечатки или удаление дословного дубля в spec идёт коротким путём, а изменение контракта публичного поля, даже в одной строке, требует change. На коротком пути достаточно самой правки и подходящих проверок; issue создаётся по необходимости.

Состав и оформление артефактов определяют штатные skills и инструкции OpenSpec, получаемые через `pnpm exec openspec instructions <artifact-id> --change <change> --json`.

Выбирай проверки по затронутому результату:

- Для редакторской правки specs нужны `pnpm openspec:validate`, сверка сохранности требований и ревью diff.
- При изменении агентских правил или интеграции добавь проверки из раздела [«Проверки»](#проверки).
- Для кода выбери подходящие typecheck, тесты, сборку или браузер. Предметные правила, например проверка поисковой релевантности или анализ бандлов, сохраняют силу.

Один актуальный результат проверки может подтверждать несколько задач. Повторяй запуск, когда изменились её входы или появились новые сомнения в результате; после исправлений проверяй затронутые места и связанные сценарии.

При возобновлении сессии сначала сопоставь сохранённые результаты с текущими файлами и условиями проверки. Перезапуск агента сам по себе не делает результат устаревшим. Перед повтором назови изменившийся вход или конкретный непроверенный риск; выбери самый короткий сценарий, который его проверяет. Закончи приёмку, когда согласованные требования подтверждены актуальными результатами, а не после ещё одного одинакового прогона.

Примеры накладных расходов и предложения для дальнейшего обсуждения собраны в [аудите OpenSpec от 29 сентября 2026 года](/docs/research/2026-09-29-openspec-audit.md).

## Чистый checkout

Нужны Git, Node.js 24+ и pnpm версии из `packageManager` в корневом `package.json`. Поддерживаемые среды проверки — macOS и Linux. Установка внешних skills требует доступа к GitHub.

Из корня репозитория выполни:

```bash
pnpm agents:setup
```

Команда устанавливает зависимости по frozen lock-файлу, восстанавливает проектный набор skills и генерирует интеграцию OpenCode. После установки или изменения инструкций **перезапусти OpenCode**: работающая сессия может хранить прежние skills в памяти.

- Собственные skills хранятся в Git под `.agents/skills/`.
- Внешние skills восстанавливаются в тот же каталог из `skills-lock.json` в исходном upstream-виде. Их версии задаются полными Git SHA в `ref`, содержимое — `computedHash`.
- Штатные skills и команды OpenSpec хранятся в `.opencode/skills/openspec-*/` и `.opencode/commands/opsx-*.md`. OpenCode также обнаруживает общий каталог `.agents/skills/`.
- Личные глобальные skills и их lock-файлы не участвуют в восстановлении. Установщик запускается с временным домашним каталогом, а генератор OpenSpec — с временным профилем.

Ревью, согласование объёма, ведение глоссария и ADR и упрощение собственной реализации выполняются по `AGENTS.md`. По решению владельца все методы, для которых готовились проектные patches, исключены из набора. Установка не изменяет исходники внешних skills.

Переустановка внешнего набора заменяет его проектные копии. Проектные дополнения хранятся в правилах, OpenSpec config и собственных skills. Bootstrap откажется работать, если в проектной установке остались неизвестные каталоги или дубли skills; сначала разбери их содержимое. Новые собственные skills должны быть добавлены в Git и разрешены в `.gitignore`.

### Setup-скрипт внешней среды

Если среда, например Codex, уже подготавливает pnpm через Corepack, её setup может вызывать общий bootstrap:

```bash
set -euxo pipefail
corepack enable
corepack prepare --activate
pnpm agents:setup
```

Запускай его из корня checkout. Он заменяет отдельные `pnpm install --frozen-lockfile` и `pnpm exec skills experimental_install -y`: bootstrap дополнительно проверяет полученный состав и хеши и восстанавливает интеграцию OpenSpec. На этапе #736 штатная OpenSpec-интеграция генерируется для OpenCode; общий каталог `.agents/skills/` доступен и другим поддерживающим его агентам. Штатные OpenSpec workflows для Codex требуют отдельного подключения этого инструмента.

## Проверки

Из корня workspace запусти `pnpm lint` для полной проверки исходного кода. Это ручная проверка **без автоисправлений**: команда не меняет файлы и завершится с ошибкой при замечаниях Oxlint, включая предупреждения. Для `.astro` и `.svelte` Oxlint проверяет поддерживаемые скриптовые блоки, но не разметку; typecheck и тесты запускай отдельно. В CI lint идёт перед ними в общем `test` job и при ошибке блокирует деплой, в том числе плановый.

Перед коммитом существующий хук запускает `lint-staged`: для staged JS/TS и скриптовых блоков `.astro`/`.svelte` он применяет только безопасный `oxlint --fix`. Форматирование (Prettier для `.astro`, oxfmt для остальных поддерживаемых файлов) выполняется последовательно с Oxlint: они не записывают один файл одновременно. Неисправленные ошибки и предупреждения останавливают коммит; `--fix-suggestions` и `--fix-dangerously` в хуке не используются. Остальные staged-файлы продолжают форматироваться по прежним правилам.

### Oxlint для агентов

Прямые вызовы Oxlint выполняй из корня с `--format=agent`, в том числе для отдельных файлов и с автоисправлением:

```bash
pnpm exec oxlint --format=agent --deny-warnings .
pnpm exec oxlint --format=agent --fix --deny-warnings .
# Разбери оставшиеся замечания вручную, затем отформатируй изменённые файлы.
pnpm exec oxlint --format=agent --deny-warnings .
```

Сначала применяй безопасный `--fix`. Он исправляет только нарушения с безопасным автофиксом; ненулевой код при оставшихся замечаниях означает, что работа продолжается. После ручных исправлений запускай проектные formatter-команды для изменённых файлов и проверку без записи. `pnpm lint` и CI остаются проверочными; `--fix-suggestions` и `--fix-dangerously` в стандартный порядок не входят.

Локальный плагин включает только `no-conditional-empty-object-spread` из anti-slop. У этого правила нет автофикса: выбирай между прямым optional-полем и условным добавлением свойства по контракту потребителей. Строгое ожидание теста само по себе не доказывает значимость отсутствия ключа; при необходимости поправь тест. Происхождение, лицензия и обновление — в [UPSTREAM.md](/tools/oxlint/UPSTREAM.md). `pnpm test:lint` проверяет правило через штатный RuleTester и выполняется также в начале `pnpm lint`.

В staged-вызовах `--no-error-on-unmatched-pattern` позволяет коммитить только исключённые upstream-файлы: если все переданные пути исключены, проверка завершается успешно. Полная `pnpm lint` сохраняет ошибку при отсутствии проверяемых файлов.

### Агентская интеграция

```bash
pnpm openspec:validate
pnpm skills:check
pnpm test:agent-tooling
```

- `openspec:validate` проверяет активные changes и основные specs в строгом режиме, затем завершённость задач архивов.
- `skills:check` напрямую сравнивает исходные хеши установленных внешних skills с lock-файлом. Кеш Python `__pycache__`, создаваемый при работе сканера humanizer, не считается изменением исходников.
- `test:agent-tooling` проверяет независимость генерации OpenSpec от глобального профиля и обнаружение изменённых, отсутствующих и лишних skills.

Набор skills устанавливается сначала во временный каталог. Ошибки штатного установщика, которые он только печатает, обнаруживаются по фактически полученным файлам и хешам. В рабочую копию попадает проверенное содержимое. Git SHA закрепляет восстанавливаемую ревизию; хеш без SHA этого не обеспечивает.

Эти проверки входят в workflow `Agent tooling` для изменений агентской интеграции, правил, скриптов и зависимостей. Проверки приложения выбираются отдельно по затронутой области. Успешная структурная валидация не доказывает выполнение требований change.

## Консультация с advisor

Условия вызова и согласования с владельцем заданы в [AGENTS.md](/AGENTS.md#согласование-и-передача). В первом вызове проектного subagent `advisor` передай:

- рабочую директорию, исходную задачу, ожидаемый результат и согласованные требования и ограничения;
- наблюдаемую проблему, подтверждающие факты и результаты уже выполненных проверок;
- ссылки на существенный код, change при его наличии, основные specs и решения.

Описывай проблему без своего готового решения: советник сначала самостоятельно исследует причины и предлагает подход. Результаты проверок передавай сразу, чтобы он мог использовать уже полученные факты.

Например:

> Вызови advisor по обнаруженной проблеме. Рабочая директория — `<путь>`, задача — `<нужный результат>`, ограничения — `<согласованные требования>`. Наблюдаем `<проблема и условия>`, факты и результаты проверок — `<наблюдения и источники>`. Исследуй `<пути к коду и требованиям>`, проверь необходимость вмешательства и предложи соразмерный подход с оценкой его цены.

После добавления или изменения профиля обнови контекст OpenCode либо перезапусти его. Вызывай `advisor` без переопределения модели: модель и вариант закреплены в [профиле](/.opencode/agents/advisor.md). При проверке установки подтверди discovery, фактические модель/вариант дочерней сессии и запрет штатного редактирования средствами runtime; самоописание модели этого не доказывает. Широкие исследовательские инструменты ограничены поведенческой инструкцией, а не полной песочницей. Проверки с возможной записью выполняет основной агент.

Советник самостоятельно проверяет существенные предположения по коду и документам; порядок исследования и состав заключения задаёт его профиль. После первого заключения можно обсудить своё предложение, рассмотренные варианты, возражения и дополнительные факты через продолжение с тем же `sessionID`. Если рекомендации достаточно, второй вызов не требуется. Фиксированного лимита раундов нет. Когда новых фактов и аргументов не осталось, прекрати повторение и зафиксируй расхождение.

Основной агент принимает решение и кратко объясняет выбор. Рекомендацию можно обоснованно отклонить в пределах согласованных требований и объёма. Существенный неразрешённый спор о цене, требованиях или крупном обходе вынеси владельцу с вариантами и рекомендацией. Разрешение на крупный обход получи по `AGENTS.md` до реализации. Если обязательная консультация недоступна, укажи конкретную причину и согласуй дальнейший путь с владельцем; самопроверку не представляй как независимое заключение.

## Ревью изменения в OpenCode

Для OpenSpec-изменения перед PR вызови из основной сессии проектного subagent `reviewer`. После добавления или изменения профиля перезапусти OpenCode или обнови контекст среды, чтобы он использовал актуальную инструкцию. Выбери целевую ветку и передай точный SHA базы, например `git merge-base HEAD origin/master`; укажи рабочую директорию, задачу и решения из issue, согласованный change, применимые основные specs, уже выполненные проверки и их ограничения.

Первый проход охватывает весь diff. При повторе после исправлений или sync/archive передай прежний отчёт, проверенное состояние (SHA и незакоммиченные правки, если они были) и все последующие изменения. Можно продолжить ту же сессию reviewer. Повтор проверяет новые изменения и их влияние на связанные сценарии; совокупный охват должен соответствовать всему итоговому diff. Если прежний охват или состояние нельзя восстановить, нужен полный проход. Порядок сравнения и состав отчёта задаёт [профиль reviewer](/.opencode/agents/reviewer.md).

Пример обращения к основной сессии:

> Вызови reviewer для change `add-opencode-reviewer` в текущей рабочей директории. Целевая ветка — `origin/master`, база — `<SHA из git merge-base HEAD origin/master>`. Передай issue, план, результаты проверок и попроси оценить весь diff, включая коммиты ветки, staged, unstaged и новые файлы. После отчёта разбери замечания и повтори ревью исправлений.

Reviewer использует `ponytail-review` как единый метод проверки качества: сначала сверяет требования и ищет регрессии, затем проверяет лишнюю сложность по пункту `Lean`. Находки входят в общий отчёт с отдельным блоком предложений упрощения. Профиль технически запрещает штатные edit/write/patch, но оставляет обычный доступ к остальным инструментам в пределах разрешений среды. Запрет записи через shell, браузер и внешние инструменты — поведенческая инструкция, а не песочница. Тесты и сборку запускает автор, он же проверяет и исправляет находки. Если reviewer недоступен, автор сам выполняет эти проверки, называет причину fallback и не выдаёт самопроверку за независимое ревью. Человеческое ревью и merge остаются у владельца.

## Анализ клиентских бандлов

Из корня репозитория запусти `pnpm bundle:analyze`. Команда заново собирает сайт и обновляет два отчёта в Git: `docs/bundle/client.yaml` с составом клиентских JS-чанков и `docs/bundle/assets.yaml` с размерами готовых JS/CSS-файлов, включая Brotli и gzip. Локальная диаграмма создаётся в `.cache/bundle/client.html`. Отчёты и диаграмма не попадают в публикуемый `dist/www`; обычный `pnpm build` их не обновляет.

В `assets.yaml` поле `bytes` всегда показывает размер оригинала. Поля `brotli` и `gzip` есть только для существующих `.br` и `.gz`: компрессор может не сохранить вариант, если он не меньше оригинала. При отдаче без сжатия используется размер `bytes`; отсутствие поля не означает нулевой размер.

Перед изменением клиентских импортов или сборки сохрани исходное состояние отчётов, после изменения повтори команду и посмотри `git diff -- docs/bundle/`. В YAML хеши имён чанков заменены на `XXXXXXXX`; одноимённые чанки получают номер перед ним. Сравнивай модули, точки входа и размеры готовых файлов, а не только названия чанков. После проверки сохраняй актуальные YAML вместе с изменением в Git; промежуточную историю снимков вести не нужно. Размеры модулей в `client.yaml` помогают найти зависимости, но не складываются в сетевой вес чанка и не заменяют проверку запросов страницы или Lighthouse.

## Регенерация OpenSpec

```bash
pnpm openspec:generate
```

Генератор запускает один штатный `pnpm exec openspec init --tools opencode --profile core --no-animation` из локального пакета; параметры закреплены в `scripts/openspec.mjs`. Он создаёт skills и команды со штатной схемой `spec-driven`. Временные `XDG_CONFIG_HOME` и `XDG_DATA_HOME` исключают влияние личного профиля, а после запуска удаляются.

Собственной схемы проекта нет. Сгенерированные файлы сохраняются без ручных правок и исключены из форматирования, включая обработку явно перечисленных staged-файлов. Дополнения живут в `AGENTS.md` и `openspec/config.yaml`.

Все терминальные примеры OpenSpec, включая upstream skills и подсказки CLI, исполняй через `pnpm exec openspec` из корня workspace.

## Обновление и откат

### OpenSpec

1. Прочитай [release notes и миграции](https://github.com/Fission-AI/OpenSpec/releases) выбранной версии.
2. Обнови точную версию `@fission-ai/openspec` в корневом `package.json` и `pnpm-lock.yaml` через `pnpm add -DwE @fission-ai/openspec@<version>`.
3. Выполни `pnpm openspec:generate` и просмотри весь generated diff, включая добавленные или удалённые workflows.
4. Проверь совместимость инструкций и конфигурации с действующей политикой `AGENTS.md`, затем выполни проверки из раздела выше и подходящие проверки затронутого кода.
5. Передай изменение владельцу на ревью. Dependabot предлагает OpenSpec отдельно от общей группы dev-зависимостей; обновление пакета само по себе не обновляет инструкции в Git.

Совместимое механическое обновление допускает короткий путь. Изменение процесса требует change. Откат возвращает весь PR обновления: пакет, lock-файл, настройки и инструкции. После отката восстанови окружение через `pnpm agents:setup` и проверь его; отдельно откатывать только npm-пакет нельзя.

### Внешние skills

Обновляй выбранный upstream в отдельном временном проекте штатным `skills` CLI из локально закреплённого пакета. В качестве источника используй `<owner>/<repo>#<full-git-sha>`, указывай `--agent opencode --skill <name> --yes`. Проверь совместимость метода с проектной политикой, сверь полученные `ref`, `skillPath` и `computedHash` и перенеси нужные записи в проектный lock. Затем выполни `pnpm skills:install` и `pnpm skills:check`.

Несовместимый метод исключай из набора по согласованию с владельцем. Для обновления установщика `skills` также сохраняй точную версию и проверяй совместимость lock-формата и алгоритма хеша. Глобальный набор этим способом не обновляется.

### Сканер humanizer-ru

`pnpm agents:setup` восстанавливает весь skill, включая сканер, но не устанавливает его Python-зависимости. Для сканера нужны Python 3.10+ и пакеты `razdel>=0.5`, `pymorphy3>=2.0`. Из корня checkout проверь запуск:

```bash
python3 .agents/skills/humanizer-ru/scripts/scan.py --help
```

Если сканер сообщает о нехватке зависимостей, создай отдельное окружение вне каталога skills:

```bash
python3 -m venv "$HOME/.venvs/kpshelkovo-humanizer"
"$HOME/.venvs/kpshelkovo-humanizer/bin/python" -m pip install 'razdel>=0.5' 'pymorphy3>=2.0'
source "$HOME/.venvs/kpshelkovo-humanizer/bin/activate"
python3 .agents/skills/humanizer-ru/scripts/scan.py --help
```

Активируй это окружение в терминале перед запуском агента, чтобы его `python3` видел зависимости. После обновления skill перезапусти агент. Окружение внутри `.agents/skills/` нарушит проверку состава или хеша и может быть удалено при переустановке.

Для новостей передавай `--genre news`, как описано в [news-maker](/.agents/skills/news-maker/SKILL.md). Сохрани исходный редакционный текст перед правкой и сравни его с чистовиком:

```bash
python3 .agents/skills/humanizer-ru/scripts/scan.py /path/to/after.md --genre news --before /path/to/before.md
```

В эти временные файлы переноси проверяемый видимый текст; YAML frontmatter сканер сам не исключает. Заголовок, summary и другие видимые поля проверяй как текст без служебных ключей. Код `1` означает найденные жёсткие запреты; при `--before` код `2` может означать расхождение фактов, поэтому читай отчёт и stderr. Ошибки запуска тоже дают код `2`.

В версии 3.31.3 Markdown-подзаголовки `##` снижают балл как «обвязка чата» даже с `--genre news`. Оценивай такие находки по [правилам видимых текстов](/AGENTS.md#видимые-тексты): полезные заголовки и акценты нужны читателю. Совпадение извлечённых фактов требует отдельной сверки смысла, особенно обещаний, условий и атрибуции.

Запуск локального `scan.py` использует ревизию из `skills-lock.json`. Предлагаемый upstream fallback `uvx ru-humanizer` загружает отдельный пакет из PyPI, чью версию этот lock не закрепляет. MCP-сервер и отдельный CLI для работы установленного skill не требуются.

## Шрифты при сборке

Общие определения в [fonts.ts](/packages/ui/fonts.ts) используют штатный `fontProviders.local()` Astro Fonts API. WOFF2 и Unicode-диапазоны берутся из установленных `@fontsource/fira-sans` и `@fontsource/pt-serif` в `/packages/ui`; точные версии пакетов и lock-файл закрепляют источник. После `pnpm install --frozen-lockfile` разрешение и копирование шрифтов работают без Fontsource API/CDN, в том числе с пустым font cache. Самой установке нужен npm registry либо заполненный pnpm store.

Astro читает локальные файлы на этапе сборки и публикует их внутри `build.assets`: `/static/fonts/` основного сайта и `/_media/fonts/` самостоятельной media 404. Пути разрешаются относительно пакета UI, поэтому приложениям и вложенным визуальным стендам не нужны прямые Fontsource-зависимости. Браузер получает шрифты с origin страницы.

Штатный build cache находится внутри `cacheDir`, заданного в [www config](/apps/www/astro.config.ts) и [media config](/apps/media/astro.config.ts):

- `node_modules/.astro/www/fonts/`;
- `node_modules/.astro/media/fonts/`.

Он хранит разрешённые описания font faces и бинарные файлы, в том числе используемые для расчёта метрик fallback. В dev Astro использует `<root>/.astro/fonts/` соответствующего хоста. CI сохраняет общий `node_modules/.astro` через существующий Astro cache; наличие кеша не требуется для доступа к шрифтам. Другие источники сборки сайта, например удалённые изображения, сохраняют собственные сетевые зависимости.

[Fonts.astro](/packages/ui/src/Fonts.astro) проверяет публичный `fontData` по общей матрице начертаний и количеству разных WOFF2 для каждого начертания. Штатный local provider не передаёт метки `subset`: соответствие локальных вариантов алфавитам и Unicode-диапазонам проверяет адресный тест. Отсутствие обязательного face, дублирующий файл вместо отдельного subset или отсутствующий локальный файл останавливают сборку. Не публикуй промежуточный результат неуспешной сборки.

При изменении подключения сверяй [Font Budget](/docs/design/design-code-shelkovo.md#font-budget), запускай адресный `font-budget.test.ts` и проверяй реальные запросы и отображение текста отдельно. Тест читает общие определения и локальные файлы без сети; готовые assets проверяет сборка. Все хосты подключают шрифты без preload; отсутствие предзагрузок подтверждай по HTML и реальным запросам в браузере. Для сравнения стоимости учитывай не только WOFF2 и внешний CSS, но и встроенный font CSS и сжатый HTML — их нет в отчёте клиентских бандлов.

Unit-тесты www отключают Fonts API в тестовой Astro-конфигурации и заменяют head-компонент пустым fixture: проверка разметки страниц не запускает обработку шрифтов. Проверки Font Budget и обязательной матрицы используют реальные общие определения и guard. Доставку, отсутствие preload и CSS подтверждают production-сборки и визуальные стенды с настоящим подключением.
