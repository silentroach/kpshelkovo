# Окружение разработки

Правила работы с задачами находятся в разделе [«Жизненный цикл изменений»](../AGENTS.md#жизненный-цикл-изменений). Этот документ описывает установку и обслуживание инструментов; причины выбора процесса — в [ADR-038](decisions/038-openspec-development-workflow.md).

## Чистый checkout

Нужны Git, Node.js 24+ и pnpm версии из `packageManager` в корневом `package.json`. Поддерживаемые среды проверки — macOS и Linux. Установка внешних skills требует доступа к GitHub.

Из корня репозитория выполни:

```bash
pnpm agents:setup
```

Команда устанавливает зависимости по frozen lock-файлу, восстанавливает проектный набор skills, генерирует интеграцию OpenCode и сверяет её с закреплённым генератором. После установки или изменения инструкций **перезапусти OpenCode**: работающая сессия может хранить прежние skills в памяти.

- Собственные skills хранятся в Git под `.agents/skills/`.
- Внешние skills восстанавливаются в тот же каталог из `skills-lock.json`. Их версии задаются полными Git SHA в `ref`, содержимое — `computedHash`.
- Проектные адаптации находятся в `.agents/skill-patches/`; bootstrap применяет их после проверки исходных хешей.
- Штатные skills и команды OpenSpec хранятся в `.opencode/skills/openspec-*/` и `.opencode/commands/opsx-*.md`. OpenCode также обнаруживает общий каталог `.agents/skills/`.
- Личные глобальные skills и их lock-файлы не участвуют в восстановлении. Установщик запускается с временным домашним каталогом, а генератор OpenSpec — с временным профилем.

Ревью, согласование объёма, ведение глоссария и ADR и упрощение собственной реализации выполняются по `AGENTS.md`. Отдельные `code-review`, `domain-modeling`, `idea-refine` и `code-simplification` исключены из проектного набора по решению владельца.

Переустановка внешнего набора заменяет его проектные копии. Перед ней перенеси нужные локальные адаптации в patches. Bootstrap откажется работать, если в проектной установке остались неизвестные каталоги или дубли skills; сначала разбери их содержимое. Новые собственные skills должны быть добавлены в Git и разрешены в `.gitignore`.

### Setup-скрипт внешней среды

Если среда, например Codex, уже подготавливает pnpm через Corepack, её setup может вызывать общий bootstrap:

```bash
set -euxo pipefail
corepack enable
corepack prepare --activate
pnpm agents:setup
```

Запускай его из корня checkout. Он заменяет отдельные `pnpm install --frozen-lockfile` и `pnpm exec skills experimental_install -y`: вызов обычного установщика после bootstrap перезапишет проектные адаптации. На этапе #736 штатная OpenSpec-интеграция генерируется для OpenCode; общий каталог `.agents/skills/` доступен и другим поддерживающим его агентам. Штатные OpenSpec workflows для Codex требуют отдельного подключения этого инструмента.

## Проверки

```bash
pnpm openspec:validate
pnpm openspec:check
pnpm skills:check
pnpm test:agent-tooling
```

- `openspec:validate` проверяет активные changes и основные specs в строгом режиме, затем завершённость задач архивов.
- `openspec:check` генерирует ожидаемые инструкции во временном проекте и сравнивает с рабочей копией. Ручные изменения, отсутствующие и лишние инструкции дают ошибку; проверка не исправляет файлы.
- `skills:check` снимает проектные patches с временных копий skills и сравнивает исходные хеши с lock-файлом. Кеш Python `__pycache__`, создаваемый при работе сканера humanizer, не считается изменением исходников.
- `test:agent-tooling` проверяет независимость генерации от глобального профиля и отрицательные случаи: расхождения инструкций, неполную установку и несовместимый patch.

Набор skills устанавливается сначала во временный каталог. Ошибки штатного установщика, которые он только печатает, обнаруживаются по фактически полученным файлам и хешам. В рабочую копию попадает проверенное содержимое. Git SHA закрепляет восстанавливаемую ревизию; хеш без SHA этого не обеспечивает.

Эти проверки входят в workflow `Agent tooling` для изменений агентской интеграции, правил, скриптов и зависимостей. Проверки приложения выбираются отдельно по затронутой области. Успешная структурная валидация не доказывает выполнение требований change.

## Регенерация OpenSpec

```bash
pnpm openspec:generate
pnpm openspec:check
```

Генератор использует штатные `init` и `update` из локального пакета. Параметры закреплены в `scripts/openspec.mjs`: `spec-driven`, профиль доставки `custom`, `delivery: both` и семь штатных workflows. Временный `XDG_CONFIG_HOME` исключает влияние личного профиля, а после запуска удаляется.

`custom` относится к выбору workflows, а не к схеме. Собственной схемы проекта нет. Сгенерированные файлы сохраняются без ручных правок и исключены из форматирования, включая обработку явно перечисленных staged-файлов. Дополнения живут в `AGENTS.md` и `openspec/config.yaml`.

Все терминальные примеры OpenSpec, включая upstream skills и подсказки CLI, исполняй через `pnpm exec openspec` из корня workspace. Например:

```bash
pnpm exec openspec context --json
pnpm exec openspec list --json
pnpm exec openspec status --change <change> --json
```

## Обновление и откат

### OpenSpec

1. Прочитай [release notes и миграции](https://github.com/Fission-AI/OpenSpec/releases) выбранной версии.
2. Обнови точную версию `@fission-ai/openspec` в корневом `package.json` и `pnpm-lock.yaml` через `pnpm add -DwE @fission-ai/openspec@<version>`.
3. Выполни `pnpm openspec:generate` и просмотри весь generated diff, включая добавленные или удалённые workflows.
4. Проверь совместимость инструкций и конфигурации с действующей политикой `AGENTS.md`, затем выполни проверки из раздела выше и подходящие проверки затронутого кода.
5. Передай изменение владельцу на ревью. Dependabot предлагает OpenSpec отдельно от общей группы dev-зависимостей; обновление пакета само по себе не обновляет инструкции в Git.

Совместимое механическое обновление допускает короткий путь. Изменение процесса требует change. Откат возвращает весь PR обновления: пакет, lock-файл, настройки и инструкции. После отката восстанови окружение через `pnpm agents:setup` и проверь его; отдельно откатывать только npm-пакет нельзя.

### Внешние skills

Обновляй выбранный upstream в отдельном временном проекте штатным `skills` CLI из локально закреплённого пакета. В качестве источника используй `<owner>/<repo>#<full-git-sha>`, указывай `--agent opencode --skill <name> --yes`. Сверь полученные `ref`, `skillPath` и `computedHash`, перенеси нужные записи в проектный lock и пересмотри связанные patches. Затем выполни `pnpm skills:install` и `pnpm skills:check`.

Для правки patch сравни закреплённые исходники и желаемую проектную копию с помощью `git diff --no-index`; пути patch должны начинаться с `.agents/skills/<name>/`. Проверяй прямое и обратное применение через bootstrap. Для обновления установщика `skills` также сохраняй точную версию и проверяй совместимость lock-формата и алгоритма хеша.

Patches содержат адаптации процесса, исправления недоступных указателей и сохранённые до перехода уточнения справки Turborepo. Если upstream уже включает исправление, удали соответствующий hunk при обновлении ревизии. Глобальный набор этим способом не обновляется.
