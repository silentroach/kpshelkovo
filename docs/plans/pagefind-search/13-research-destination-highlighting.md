# Задача 13: Исследовать подсветку совпадений на целевой странице

## Статус

Post-release backlog. Задача не входит в MVP, не блокирует выпуск и не обещает реализацию подсветки.

## Что подтверждает Pagefind

- `pagefind.options({ highlightParam: "highlight" })` добавляет поисковый термин в query parameter ссылок результатов.
- Целевая страница должна отдельно включить подсветку: можно обработать параметр своим кодом или импортировать сгенерированный `/pagefind/pagefind-highlight.js` и создать `PagefindHighlight` с тем же `highlightParam`.
- `PagefindHighlight` по умолчанию ищет внутри `[data-pagefind-body]`, а если marker отсутствует - внутри `document.body`. Он исключает `[data-pagefind-ignore]`, добавляет класс `pagefind-highlight` и минимальные стили; context, exclusions, класс и стили настраиваются.
- Документация Search API отдельно гарантирует HTML-экранирование для `excerpt` и `plain_excerpt`, но называет `content` и `meta` сырыми данными. Эта гарантия относится к рендерингу результата и не является заявлением о безопасности входного query parameter на целевой странице.
- Официальная документация не заявляет отдельных security- или accessibility-гарантий для destination highlighting.

## Вопросы исследования

- Дает ли подсветка достаточную пользу после перехода, особенно для длинных KB, встреч и регламента, или усложняет обычную навигацию без заметного выигрыша?
- Как параметр собирается для нескольких слов, существующего query string и URL с sub-result anchor; сохраняется ли ожидаемый фрагмент и корректно ли кодируются все значения?
- Допустимо ли отправлять поисковую фразу в URL целевой страницы? Такой переход передает query string nginx и может оставить его в access log, истории браузера, общей ссылке и Referer. Это требует отдельной проверки относительно утверждения ADR-025, что поисковые запросы остаются в браузере и не создают отдельный журнал.
- Нужен ли официальный `pagefind-highlight.js` или более узкая собственная реализация? Для обоих вариантов проверить ограничение длины, malformed encoding, повторяющиеся параметры и строки, похожие на HTML/script payload.
- Нужно ли загружать highlight asset только при наличии ожидаемого параметра, чтобы обычные переходы не получали новый JavaScript и не меняли DOM?
- Как ограничить `markContext`, чтобы не менять навигацию, элементы управления, скрытый текст, код и блоки с `data-pagefind-ignore`?
- Не ухудшает ли множество `<mark>` чтение screen reader, порядок фокуса, browser find, 200% zoom, forced colors и контраст? Документация Pagefind этого не гарантирует.
- Должна ли страница только подсветить совпадения или еще прокрутить к первому? Автоматическую прокрутку и перенос фокуса не принимать без отдельной accessibility-проверки.

## Возможные критерии приемки

Эти критерии становятся обязательными только после отдельного решения внедрять подсветку:

- Зафиксировано privacy-решение для query string и логов; при изменении предпосылок ADR-025 добавлена implementation note или новое решение.
- Ссылка результата корректно сохраняет canonical path, существующие параметры и sub-result anchor, а значение подсветки URL-encoded и ограничено по длине.
- Crafted URL не создает DOM injection, не ломает страницу и обрабатывается за ограниченное время.
- Подсветка затрагивает только согласованный content scope, не меняет ignored/UI-элементы и не загружает asset на обычном переходе без параметра.
- Без JavaScript или при ошибке highlight asset страница остается полностью читаемой и навигация работает.
- Цвета проходят contrast/forced-colors проверку; keyboard и screen-reader smoke не выявляют лишнего фокуса, шума или потери контекста.
- Production smoke подтверждает отсутствие нового внешнего origin и неожиданных CSP-ошибок.
