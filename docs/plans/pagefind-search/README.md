# План внедрения полнотекстового поиска Pagefind

## Статус

Задачи 01-11 реализованы в текущем незакоммиченном worktree и прошли локальную production-like проверку. Отметки ниже означают готовность реализации, а не production release.

Локальные критерии задачи 12 пройдены: переходы по `Enter` работают, холодный запрос загружает 145 102 байта при бюджете 300 КБ, а query-scoped result cache снижает warmed full-client p95 до 1,6 мс при бюджете 100 мс. Задача 12 остается незавершенной только из-за отложенных проверок dev-режима, public deploy, non-Chromium и реального screen reader. Поиск еще не развернут и не выпущен.

## Контекст

Архитектурное решение принято в [ADR-025](../../decisions/025-static-full-text-search-with-pagefind.md). Сайт остается статическим: Pagefind индексирует готовый HTML после Astro build, а поиск выполняется в браузере без Node API, поискового daemon и cron.

Цель первой версии - быстрый минималистичный поиск по каноническим содержательным страницам сайта. Pagefind используется как headless-движок; интерфейс строится в визуальной системе «Шелково Онлайн».

## Зафиксированные решения

- Pagefind запускается после `astro build` и пишет `/pagefind/` в тот же `dist/www`, что и HTML.
- Индексирование явное: страница попадает в корпус только через `search`-контракт `BaseLayout`.
- Контракт поддерживает `page` для обычных публикаций и `manual` для сложных инструментальных страниц.
- `data-pagefind-*` остаются в production HTML как декларативная разметка поискового контракта.
- В KB `index.md` означает hub, а обычный `<slug>.md` - конечную статью; поиск индексирует только конечные статьи.
- Индексируются ответы и самостоятельные материалы, а не все sitemap routes.
- Архивы, теги, повторяющие списки, 404, verification HTML и `noindex` не индексируются.
- В первой версии нет видимых фильтров и сортировки, отдельного `/search/`, typo correction и поисковой аналитики.
- UI использует JavaScript API Pagefind, а не готовый Pagefind Component UI.
- Pagefind загружается только при открытии поиска.
- Новости публикуют sort key `date` со значением `YYYY-MM-DD`, но MVP не передает `sort` в JavaScript API и сохраняет стандартное ранжирование по релевантности.

## Поведение в разработке

Обычный `pnpm dev` сам не строит поисковый индекс. Astro dev не создает полный каталог HTML, который Pagefind мог бы корректно просканировать.

Для полной локальной проверки предусмотрена явная подготовка:

```bash
pnpm search:prepare
pnpm dev
```

`pnpm search:prepare` делает актуальный Astro build, строит Pagefind в игнорируемый Git dev-кеш и не запускает постоянный server. Dev-only Vite middleware отдает этот кеш по production-пути `/pagefind/`, поэтому клиентский код не получает отдельную dev-конфигурацию URL.

В dev-режиме:

- если перед запуском выполнен `pnpm search:prepare`, поиск работает по подготовленному snapshot;
- после изменения контента или поисковой разметки snapshot нужно явно пересобрать и перезагрузить страницу;
- если dev-кеша нет, клиент не запрашивает отсутствующий `/pagefind/` и диалог показывает короткую developer-only подсказку про `pnpm search:prepare`;
- состояния результатов проверяются через маленький fake adapter в focused component test, а не через параллельный dev-корпус.

Не использовать последний production `dist` как молчаливый dev-index: устаревшая выдача создает ложное ощущение, что текущие изменения уже проиндексированы. Подготовленный snapshot хранится отдельно, создается только явной командой и не watch-ится. Не создавать отдельный JSON-корпус только для разработки.

## Поисковый документ

Минимальные metadata:

- чистый `title` без SEO-суффикса;
- `description`;
- стабильный `sectionId`;
- видимый `sectionLabel`;
- optional `publishedAt` в ISO-формате.

`sectionLabel` и `publishedAt` нужны для отображения, но не должны влиять на ranking. `sectionId` подготавливает внутренний фильтр, даже если видимые фильтры появятся позже.

Для новостей `publishedAt` также публикуется как `data-pagefind-sort="date"` в нормализованном ISO 8601 формате `YYYY-MM-DD`. Pagefind использует строковые sort values в алфавитном порядке, поэтому единый формат сохраняет хронологический порядок. Сам атрибут только делает sort key доступным: пока клиент не передает `{ sort: { date: "asc" | "desc" } }`, выдача остается отсортированной по релевантности.

Веса первой версии:

- title и HTML headings используют стандартные веса Pagefind;
- уникальный lead можно повысить до `2`;
- основной текст остается с весом `1`;
- служебные источники и метаданные при необходимости получают вес `0.5`;
- related lists, повторяющийся boilerplate и элементы управления исключаются.

## Состав первого корпуса

Включить:

- отдельные новости;
- отдельные инциденты статуса и уникальные части service pages;
- конечные страницы базы знаний без `noindex`; KB sources с именем `index.md` считаются хабами и исключаются;
- встречи и транскрипции;
- профили людей без backlinks;
- тексты отзывов без повторяющегося disclaimer;
- карточки полезных контактов;
- страницы поселков только по каноническим и видимым альтернативным названиям;
- полезный текст и таблицы регламента без калькуляторного шума.

Не включать:

- главную с повторяющейся лентой;
- news year/month/tag archives;
- section indexes, которые только перечисляют дочерние материалы;
- KB root и все hub/collection pages с source-файлом `index.md`;
- Compare landing, rating, explorer controls, тарифы и инфраструктурные факты;
- Markdown companions, JSON, RSS, ICS, OpenAPI, schemas и `llms.txt`;
- search UI;
- скрытые или непубличные данные.

## Целевой интерфейс

- Глобальный нативный `<dialog>` без отдельной search page.
- На desktop диалог шириной около `46rem` расположен ближе к верхней части viewport.
- На mobile диалог занимает экран, а поле остается сверху.
- Результаты показаны плоскими редакционными строками с тонкими разделителями, без сетки карточек.
- В строке есть section, optional date, title и excerpt.
- Title использует PT Serif, интерфейс и excerpt - Fira Sans.
- Активная строка использует спокойную `primary-soft-2`, совпадение - `accent-soft`.
- Доступны `Escape`, стрелки, `Enter`, обычный tab order, focus restoration и `aria-live`.
- Первая выдача ограничена восемью результатами с действием «Показать еще».

## Границы тестирования

Не добавлять тесты на случайную статику, точные CSS-классы, полный HTML, полный Pagefind index или точный порядок всей выдачи.

Достаточный набор:

- build smoke: Pagefind создал ожидаемые entrypoint, worker, metadata, index chunk и fragment;
- один focused test поискового клиента: нормализация результата и игнорирование устаревшего ответа;
- один focused component test диалога с fake adapter: focus, закрытие и основные состояния;
- production-like query matrix с несколькими реальными русскими запросами;
- ручная responsive и accessibility проверка диалога;
- финальные `pnpm typecheck` и `pnpm build`.

## Готовность к выпуску

- Обычные страницы не загружают `/pagefind/` до открытия поиска.
- Канонические материалы находятся, а исключенные routes отсутствуют.
- Русские формы `тариф`/`тарифы` и `вода`/`воды` находят ожидаемые материалы.
- Холодный типичный запрос укладывается в 300 КБ Pagefind-ресурсов.
- Поиск после загрузки движка укладывается в p95 100 мс на согласованном среднем мобильном профиле.
- Диалог работает на 320, 768, 1024 и 1440 px, с клавиатуры и при 200% zoom.
- Production nginx отдает все части индекса с подходящим кешированием и без CSP-ошибок.

## Вне плана

- Sphinx, Manticore, Typesense, Meilisearch или Node Search API.
- Серверная поисковая аналитика.
- Индексация PDF и других вложений вне HTML.
- Семантический/vector search.
- Публичный Search API.
- Отдельная страница поиска и shareable query URL.
- Автоматическое исправление опечаток.
