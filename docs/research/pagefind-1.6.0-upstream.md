# Pagefind 1.6.0: новые возможности и влияние на наш поиск

Дата: **2026-11-05**. Прочитаны diff PR через GitHub API и исходники тегов `v1.5.2`/`v1.6.0`. Ниже — выводы по исходникам и upstream-тестам; локальный поиск на новой версии не запускался.

## Краткий вывод

Обновление полезно прежде всего исправлением кеширования сетевых отказов и надёжности записи индекса. Из новых возможностей наиболее интересны достоверные многоточия обрезки и поисковые секции на обычных HTML-блоках. Объединение fragments стоит рассматривать только после измерений.

- [Релиз 1.6.0](https://github.com/Pagefind/pagefind/releases/tag/v1.6.0) опубликован 1 ноября 2026 года. У нас закреплена `1.5.2`: [package.json](/apps/www/package.json).
- Используем собственный интерфейс и JavaScript API, включая metadata weights для тегов и алиасов и дополнительный exact search для однословного запроса: [client.ts](/apps/www/src/lib/search/client.ts). Поэтому изменения движка относятся к нам, а изменения Component UI автоматически не применяются.
- Индекс строится через Node API из HTML и отдельных записей участков: [build-search-index.ts](/apps/www/scripts/build-search-index.ts). Это делает исправление service mode непосредственно применимым.

## Новые возможности

### `excerptEllipsis`: обозначение настоящей обрезки

- В `pagefind.options()` можно передать `excerptEllipsis: '…'`. Движок добавляет строку только с обрезанного края. По умолчанию опция отключена. Источники: [документация](https://pagefind.app/docs/search-config/#excerpt-ellipsis), [PR #1320](https://github.com/Pagefind/pagefind/pull/1320/files).
- Для нас это полезно в выдаче новостей и длинных расшифровок: фрагмент, начавшийся посреди предложения, получает понятное обозначение. Прежнее решение не добавлять многоточия объяснялось отсутствием достоверного признака обрезки; теперь решение принимает сам генератор. Источник прежнего ограничения: [design разделения контекста и excerpt](/openspec/changes/archive/2026-10-12-separate-search-heading-context/design.md).
- **Включение требует проверки выбора якоря.** [SearchDialog.svelte](/apps/www/src/components/search/SearchDialog.svelte) выбирает секцию только при равенстве основного и секционного excerpt. В `build_excerpt` многоточие зависит от `startcap`/`endcap`; основной excerpt ограничен страницей, секционный — своей секцией. Один текст может получить разные многоточия и перестать совпадать. Источники: [excerpt.ts v1.6.0](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/excerpt.ts), [sub_results.ts v1.6.0](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/sub_results.ts).
- Основная сессия подтвердила это отдельным запуском оригинального `build_excerpt` из тега `v1.6.0` в Node, без установки Pagefind в проект. Для текста `Начало документа здесь Найденный фрагмент секции Следующая часть документа`, окна `start=3`, `length=3`, подсветки позиции `4` и границ секции `[3, 6)`:
  - без опции оба результата: `Найденный <mark>фрагмент</mark> секции`;
  - с опцией основной: `… Найденный <mark>фрагмент</mark> секции …`, секционный: `Найденный <mark>фрагмент</mark> секции`;
  - нынешнее точное сравнение даст разные результаты и выберет canonical URL вместо якоря.
- Это обозначение окна слов, а не генератор целых предложений. CSS-обрезка отображаемых строк остаётся отдельным механизмом. Для внедрения нужно согласовать отображение многоточий с выбором секции и сохранить авторские многоточия.

### `data-pagefind-title`: секции без искусственных heading-элементов

- Любой индексируемый элемент с `id` и непустым `data-pagefind-title` может задавать подрезультат; значение атрибута становится его названием. API `sub_results` сохраняется. Источники: [документация](https://pagefind.app/docs/sub-results/#defining-a-sub-result-explicitly), [PR #1282](https://github.com/Pagefind/pagefind/pull/1282/files).
- Конкретный кандидат — Markdown-карты. Сейчас [editorial-maps-html.ts](/apps/www/src/lib/markdown/editorial-maps-html.ts) создаёт `h3` с ID внутри подписи. Новая версия позволяет рассмотреть `id` и `data-pagefind-title` на `figure`, сохранив видимую подпись обычной подписью. Это упрощает семантику и даёт естественную цель перехода в начале карты. Требуется сверить выдачу, подсветку и существующие ссылки.
- Другой кандидат — переход к конкретной выжимке отзыва в «Сарафане». В [ContactReviews.astro](/apps/www/src/components/contacts/ContactReviews.astro) текст отзывов уже индексируется, но отдельных ID у этих блоков нет. Для такого улучшения потребуются стабильные ID и осмысленные названия секций; само обновление пакета их не создаёт.
- Границы подрезультатов определяются последовательностью якорей, а не закрывающим HTML-тегом контейнера. Сохранить общее правило карты: соседний текст также может привести к выбору её секции. Источники: [sub_results.ts](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/sub_results.ts), [контракт поиска](/openspec/specs/search/spec.md).

### `maxFragments`: меньше файлов индекса

- Новый параметр объединяет несколько fragments в общий файл, ограничивая количество файлов на язык. В используемом нами Node API это `createIndex({ maxFragments: N })`; CLI/YAML-имя — `max_fragments`. Источники: [документация](https://pagefind.app/docs/config-options/#max-fragments), [Node types v1.6.0](https://github.com/Pagefind/pagefind/blob/v1.6.0/wrappers/node/types/index.d.ts), [PR #1020](https://github.com/Pagefind/pagefind/pull/1020/files).
- У нас много небольших custom records участков, поэтому это возможный эксперимент с доставкой индекса. Группы формируются по числу fragments, а не по тематике запроса; загрузка одной записи скачивает всю её группу. Меньше файлов не гарантирует меньший трафик или задержку. Источник: [формирование групп](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind/src/index/mod.rs), [загрузка групп](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts).
- Для текущей архитектуры со статической доставкой через nginx необходимость обходить лимит файлов не установлена. Перед включением сравнить холодный поиск участка и обычной статьи: число запросов, переданные байты и время до выдачи. Контекст доставки: [ADR-025](/docs/decisions/025-static-full-text-search-with-pagefind.md).

## #1329: повтор после отказа загрузки

- **Удаление неуспешных записей кеша охватывает index chunks, filters и fragments.** Новый `cachedLoad` при отклонении Promise удаляет запись по хешу и пробрасывает ошибку. Им обёрнуты `loaded_chunks`, `loaded_filters`, `loaded_fragments`; в `v1.5.2` эти записи сохранялись. Источники: [diff #1329](https://github.com/Pagefind/pagefind/pull/1329/files), [1.5.2](https://github.com/Pagefind/pagefind/blob/v1.5.2/pagefind_web_js/lib/coupled_search.ts#L359-L420), [1.6.0](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L373-L464).
- **Это возможность следующей попытки, без немедленного автоматического retry.** Повторный `search()` снова может загрузить нужный chunk/filter; повторный `result.data()` снова вызывает загрузку fragment. Цикла повторов, задержки или повторной постановки отказавшего запроса в очередь здесь нет. Проверка `response.ok` превращает HTTP-ошибки в отказ Promise; отклонение самого `fetch` также проходит через этот путь. Источники: [очередь fetch](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L120-L148), [cachedLoad](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L387-L418), [вызовы из search/data](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L725-L795).
- **Поведение ошибок неодинаково:** `loadChunk` и `loadFilterChunk` подавляют ошибку после удаления записи кеша, а `loadFragment` передаёт её вызывающему `data()`. Поэтому нельзя обещать, что любой отказ поисковых данных обязательно попадёт в UI-состояние ошибки. Источник: [обработчики загрузки](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L402-L464).
- В итоговом `v1.6.0` тот же механизм используется для кеша **групп fragments** (`loaded_fragment_groups`). Upstream-тест проверяет HTTP 404 группы, затем успешную загрузку другой записи этой группы и дальнейшее использование общего кеша; отдельный тест проверяет повтор index chunk после 404. Исходный #1329 добавлял только тест chunk. Источники: [загрузка группы](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L420-L450), [тесты v1.6.0](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/tests/fetch_failures.test.ts), [diff #1329](https://github.com/Pagefind/pagefind/pull/1329/files).
- **WASM, `pagefind-entry.json` и `.pf_meta` не получили этот механизм восстановления.** Их запросы используют общую проверку HTTP-статуса, но не `cachedLoad`. `loadMeta` ловит и журналирует ошибку; исключения инициализации сохраняются в `initError`, который затем проверяет `getPtr`. Переносить вывод о повторяемости fragments на инициализацию нельзя. Источники: [init и entry](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L252-L320), [meta/WASM](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L339-L371), [getPtr](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L540-L552).

**Вывод для проекта:** исправление непосредственно касается причины, по которой 29 октября убрали «Повторить»: [решение и воспроизведённый отказ fragments](/openspec/changes/archive/2026-10-29-suggest-reload-on-search-data-failure/design.md). После обновления можно пересмотреть это решение, сначала проверив настоящий сетевой отказ `/search/fragment/*` и восстановление на том же клиенте после снятия блокировки: отдельно до первой выдачи и при догрузке. Если используются группы, проверить и их. Upstream-код даёт основание для такого эксперимента, но не подтверждает восстановление всего нашего UI.

## #1318: конкретный дефект excerpt с U+FEFF

- JS раньше считал U+FEFF (BOM/zero-width no-break space) разделителем слов, что расходилось с позициями Rust-индексатора. PR заменяет разделитель на `/[^\S\uFEFF]+/g` в `build_excerpt` и `extract_words`: U+FEFF больше не создаёт дополнительную границу слова. Ветка с разделением по U+200B сохранена. Источники: [diff #1318](https://github.com/Pagefind/pagefind/pull/1318/files), [итоговый excerpt.ts](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/excerpt.ts).
- Регрессионный тест начинает содержимое с `\uFEFFDonec…` и проверяет правильный фрагмент с `<mark>elit</mark>`. Это узкое исправление смещения excerpt/подсветки при таком символе; из него не следует исправление всех проблем сниппетов. Для нашего корпуса эффект зависит от присутствия U+FEFF в индексируемом тексте. Источник: [тест #1318](https://github.com/Pagefind/pagefind/pull/1318/files).

## #1319: завышенный вклад составного слова в metadata

- В `v1.5.2` совпадения внутри metadata-поля группировались по найденной строке индексного слова. Несколько частей/форм составного слова, соответствующих одному термину запроса, могли увеличить сумму IDF несколько раз. Теперь ключ — `query_term_index`, поэтому каждый термин запроса учитывается один раз на поле. Это меняет расчёт `coverage` и metadata boost, который использует квадрат coverage. Источники: [diff #1319](https://github.com/Pagefind/pagefind/pull/1319/files), [сбор совпадений v1.6.0](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web/src/search.rs#L606-L618), [формула boost](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web/src/search.rs#L749-L766).
- Upstream-сценарий: запрос `filtering`, заголовки `Filtering` и `FilterMetadataService`; обычная страница должна быть выше составного имени. У второго заголовка `filtermetadataservic` и `filter` больше не считаются двумя совпадениями одного термина. Для нашего JS API это потенциальное изменение порядка результатов при составных названиях в индексируемых metadata, включая title. Пользу для конкретных русских запросов и записей участков нужно оценивать сравнением выдачи. Источник: [интеграционный тест](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind/integration_tests/metadata_search/compound-words-in-title-are-not-counted-twice.toolproof.yml).

## #1272: незавершённая запись файлов в service mode

- В обе ветки записи — с gzip и без сжатия — добавлено `file.flush().await` после `write_all`. По объяснению автора PR, завершение `write_all` могло означать только передачу байтов буферу Tokio; ответ `WriteFiles` приходил до фактического завершения записи, а остановка процесса оставляла обрезанный файл. В `v1.5.2` этого flush нет. Источники: [PR #1272 и его diff](https://github.com/Pagefind/pagefind/pull/1272), [write в 1.5.2](https://github.com/Pagefind/pagefind/blob/v1.5.2/pagefind/src/output/mod.rs), [write в 1.6.0](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind/src/output/mod.rs#L436-L470).
- **Исправление применимо к нашему пути сборки через Node API.** Upstream-обёртка запускает бинарник с `--service`; `writeFiles()` посылает `WriteFiles`, Rust отвечает после `write_files(...).await`, а `close()` обёртки завершает backend через `kill()`. Поэтому это аргумент в пользу надёжности сборки `createIndex` → добавление HTML/custom records → `writeFiles`. Наличие такого повреждения именно в нашем индексе не установлено. Источники: [запуск и close](https://github.com/Pagefind/pagefind/blob/v1.6.0/wrappers/node/lib/service.js#L17-L68), [Node writeFiles](https://github.com/Pagefind/pagefind/blob/v1.6.0/wrappers/node/lib/index.js#L223-L245), [ответ сервиса](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind/src/service/mod.rs#L209-L224).

## #1386: exact search при нескольких диакритических вариантах

- Раньше позиции нормализованного слова и его диакритических вариантов попадали в общий плоский список. Теперь они собраны **по термину запроса**, и проверка соседних позиций использует объединение вариантов каждого термина. Изменены пути проверки содержимого и metadata. Источники: [diff #1386](https://github.com/Pagefind/pagefind/pull/1386/files), [exact_term v1.6.0](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web/src/search.rs#L207-L371).
- Upstream-тест моделирует одну страницу с `café latte` и отдельным `cafe`. Проверяет совпадение `"café latte"` при обоих значениях `exactDiacritics` и отсутствие совпадения `"cafe latte"` при `exactDiacritics: true`. В этом тесте нет русских слов и проверки полного пути индексирования русской страницы. Источник: [регрессионный тест](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web/src/search.rs#L899-L962).
- **Для проекта область шире пользовательских кавычек.** По проверке основной сессии, [client.ts](/apps/www/src/lib/search/client.ts) запускает `searchExactToken` и для обычного однословного ввода. В upstream-алгоритме исправление не ограничено фразами из нескольких слов: тот же сбор вариантов выполняется для одного термина. Поэтому в приёмку стоит включить обычный однословный ввод по странице, где встречаются обе формы слова. Источник механизма: [группировка и проверка позиций](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web/src/search.rs#L218-L301).
- **Обещать новую поддержку ё/е или й/и по этому PR нельзя.** Нормализация через NFD и удаление комбинируемых знаков существовала уже в `1.5.2`; #1386 исправляет объединение позиций вариантов при exact search. Русские пары — кандидаты для проверки настоящего индекса, включая нежелательные совпадения й/и и действие `exactDiacritics`, а не доказанный результат обновления. Источники: [JS-нормализация 1.5.2](https://github.com/Pagefind/pagefind/blob/v1.5.2/pagefind_web_js/lib/coupled_search.ts#L14-L17), [Rust-нормализация 1.5.2](https://github.com/Pagefind/pagefind/blob/v1.5.2/pagefind/src/fossick/splitting.rs#L116-L135), [нормализация 1.6.0](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind/src/fossick/splitting.rs#L307-L342), [границы diff #1386](https://github.com/Pagefind/pagefind/pull/1386/files).

## Остальные изменения

- Ускорены широкие запросы. Автор [PR #1334](https://github.com/Pagefind/pagefind/pull/1334) сообщает об ускорении коротких и частичных запросов на корпусе в 10 000 страниц; это его измерение, не прогноз для нашего сайта. Есть также исправление размеров чанков при большом количестве вариантов слова и работа над воспроизводимостью индекса: [релиз](https://github.com/Pagefind/pagefind/releases/tag/v1.6.0).
- Новая сегментация ICU4X в extended build относится к китайскому, японскому и тайскому. Оснований обещать улучшение русской морфологии по этому пункту нет. Источник: [релиз](https://github.com/Pagefind/pagefind/releases/tag/v1.6.0).
- Новые атрибуты сортировки, ограничения подрезультатов и placeholder, а также исправления готового диалога относятся к Component UI. У нас свой [SearchDialog](/apps/www/src/components/search/SearchDialog.svelte), поэтому эти UI-изменения не дают непосредственной выгоды от обновления пакета.
- Отдельная продуктовая идея, **доступная и до 1.6.0**: фильтр по разделам. [BaseLayout.astro](/apps/www/src/layouts/BaseLayout.astro) уже публикует `data-pagefind-filter="section[data-search-section-id]"`. Для интерфейса потребуются передача фильтра через клиент и решение о специальных записях участков, у которых такого фильтра сейчас нет. Источники: [фильтры Pagefind](https://pagefind.app/docs/filtering/), [build-search-index.ts](/apps/www/scripts/build-search-index.ts).

## Приоритет внедрения и проверки

1. Обновить точную версию и пересобрать индекс; сравнить поиск до/после на одном корпусе, включая короткие запросы, русские словоформы, полные и короткие коды участков и их алиасы.
