# Реорганизация тестов карт — #975

Задача: [#975](https://github.com/silentroach/kpshelkovo/issues/975). Меняется только организация и выполнение тестов, без изменений production-кода.

## Исходный замер

База: `a87de98e602cacdd3bc559913a3c61a9ee004043`. macOS arm64, Apple M3 Pro, 12 CPU, Node 24.20.0, Vitest 5.0.2. Два последовательных запуска по исходной команде issue, штатный параллелизм `apps/www`, 231 файл и 1900 тестов; оба прошли.

- PlaceMap: 15,86 и 15,71 с. Сумма времени сценариев с hooks: 15,86 и 15,71 с.
- SettlementMap: 5,07 и 5,07 с.
- Первый запуск: 17,18 с по стандартному reporter. От старта до последнего результата в JSON: 17,25 и 17,01 с; ниже сравнивается именно эта одинаково рассчитанная величина.
- Первый reporter: tests 47%, import 28%, transform 16%, environment 6%, setup 3%, worker 1%. Это доли агрегированных расходов параллельного набора, а не части wall time.
- Отдельный исходный запуск PlaceMap: 111 сценариев, 16,42 с выполнения и 17,12 с всего; reporter: tests 96%, transform 3%, environment 1%.
- Дополнительный отдельный исходный запуск с разовым reporter: 16,49 с тестов, 17,19 с всего; transform 424 мс, setup 71 мс, import 29 мс. Reporter использует `TestModule.diagnostic()` и публичный экспериментальный `experimental_getRunnerTask` из установленного `vitest/node`, формулы фаз совпадают с default reporter 5.0.2. Файл reporter хранится вне репозитория и не становится проектным инструментом.

Команда из `/apps/www` (путь отчёта выбирается вне репозитория):

```sh
git ls-files -z 'src/**/*.test.ts' 'tests/**/*.test.ts' | xargs -0 pnpm exec vitest run --reporter=default --reporter=json --outputFile=<report.json>
```

После появления новых незакоммиченных тестов список для замера должен также включать их и исключать удалённый исходный файл.

Git-pattern `tests/**/*.test.ts` в исходной команде не включает три файла непосредственно в `/apps/www/tests/`. Поэтому сопоставимые замеры используют ту же выборку, а полный `vitest run` проверяется отдельно. После разделения это соответственно 234 файла / 1900 сценариев и 237 файлов / 1914 сценариев; дополнительные 14 проверок уже существовали в базе.

## Границы PlaceMap

Выбраны четыре группы вместо семи предложенных в issue:

- Lifecycle: SDK, JSON, clusterer, native control, ошибки, fallback, поздние завершения и unmount — 22 сценария.
- Места: маркеры, часы, геометрия, подсветка URL, камера и доступные кластеры — 36 сценариев. Клавиатура и восстановление фокуса остаются рядом с раскрытием объектов.
- Участки: загрузка слоёв, контуры и подписи, выбор, прямые ссылки и гонки — 41 сценарий. Связную область не делим ещё на несколько файлов ради длины.
- Popup: сведения, кеширование и retry, устаревшие ответы, жесты, позиционирование и фокус — 12 сценариев.

Fixtures, SDK-mock и setup/cleanup остаются локальными для этих тестов. Все 111 сценариев переносятся без удаления; универсальный harness и конкурентный запуск внутри файла не нужны.

При успешном mount настоящий runtime и renderer последовательно ждут два layout-барьера: каждый включает два animation frame и 50 мс. Компонентные тесты должны управлять готовностью SDK и импортов, а сам layout-barrier принадлежит проверкам runtime. Настоящие animation frame для фокуса и popup остаются включёнными.

Короткий partial mock объявлен в каждом тестовом файле: Vitest поднимает его до импорта компонента. Объявление в импортируемом support-файле зависело бы от порядка импортов, который меняет formatter; дополнительная абстракция здесь не нужна. Support содержит только существующие fixtures, SDK-mock и явную регистрацию hooks.

Сброс всего модульного графа убран; `vi.doMock` кластеризатора по-прежнему регистрируется перед каждым сценарием, сохраняя незавершённый и отклонённый dynamic import. Две паузы по 180 мс заменены на `tick()` и `vi.dynamicImportSettled()` после разрешения или отказа deferred promise. Проверки отсутствия поздних эффектов выполняются после этого барьера.

Первый успешный адресный прогон: четыре DOM-файла, 111 прошедших сценариев, названия всех сценариев точно совпали с исходным JSON-отчётом. Независимое ревью сверило все 82 исходных блока, дающих эти 111 сценариев, и все 19 inline snapshots. Ни один сценарий не удалён и не добавлен.

## SettlementMap

Файл сохранён единым: 28 сценариев достаточно удобно держать вместе. Локальный partial mock runtime убирает layout-паузы при установленном тестовом SDK, но ждёт настоящее `ymaps3.ready`; если SDK отсутствует, вызывает настоящий loader. Импорт native control и его поздние resolve/reject остаются под управлением сценариев. Сам загрузчик по-прежнему проверяется отдельно без этого mock.

Адресная проверка: 28 сценариев SettlementMap и 3 runtime-теста прошли. Отдельный замер SettlementMap после правки: 1,68 с. Окончательное сравнение берётся из полного набора, а не смешивает отдельный запуск с параллельным исходным замером.

## Итоговые замеры

Два последовательных запуска той же выборки, без параллельных сборок и проверок типов:

- 234 файла, 1900 сценариев; оба запуска прошли. Полный список названий сценариев совпал с исходным набором.
- Время от старта до последнего результата в JSON: **13,06 и 12,34 с** вместо 17,25 и 17,01 с. Среднее уменьшилось примерно на **26%**.
- Сумма времени четырёх групп PlaceMap: **3,56 и 3,62 с** вместо 15,86 и 15,71 с; самое долгое подмножество — участки, **1,54 и 1,57 с**. Сумма времени параллельных файлов не сравнивается с wall time набора.
- SettlementMap в этих же запусках: **1,54 и 1,54 с** вместо 5,07 и 5,07 с.

Отдельный запуск четырёх PlaceMap-файлов с тем же разовым reporter: 111 сценариев прошли, **2,18 с всего** вместо 17,19 с. Сумма времени сценариев с hooks — 3,30 с, самая долгая группа — 1,42 с.

Цена четырёх окружений видна в сумме расходов: transform **1633 мс** вместо 424 мс, setup **324 мс** вместо 71 мс, import **311 мс** вместо 29 мс. Transform здесь означает ожидание resolve/transform сервером Vite, а не чистое CPU-время; setup/import вычитают это ожидание по формулам default reporter. Это накопленные расходы workers, не отдельные части wall time. Разбиение увеличило setup/import, но сокращение повторных layout-пауз существенно перевесило эту цену.

Дополнительно полный штатный `pnpm exec vitest run` прошёл: **237 файлов, 1914 сценариев**, 15,00 с по default reporter. Это расширенный набор относительно исходной команды issue, поэтому его длительность не используется для расчёта процента ускорения.
