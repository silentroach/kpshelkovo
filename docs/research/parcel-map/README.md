# Участки Шелково: исследовательский снимок

Материалы исследования от 22 сентября 2026 года для [карты решений «Участки Шелково: границы, номера и поиск»](https://github.com/silentroach/kpshelkovo/issues/804).

Общая рабочая ветка — `feat/parcel-map-search`. Исследование, все дочерние вопросы, будущий OpenSpec change и реализация ведутся в этой ветке до итогового PR.

Читать при продолжении исследования, проверке привязки генпланов или повторном получении источников. Текущие вопросы и решения находятся в дочерних issues карты. Согласованный объём, требования и задачи реализации будут оформлены в OpenSpec change по `spec-driven`; этот каталог хранит свидетельства эксперимента.

## Файлы

- `nspd-parcels.ndjson` — кадастровые объекты из выбранной области НСПД. Одна строка — один объект с исходной геометрией, кадастровым номером, внутренним ID НСПД, статусом и площадью в м², если она дана источником. Геометрия сохраняет `EPSG:3857`; это исследовательский формат, а не GeoJSON в WGS84 для публикации.
- `genplan-plots.ndjson` — номера застройщика, часть посёлка, исходное написание номера, кадастровая ссылка, площадь в сотках и положение метки в процентах от размеров изображения. Одна строка — одна запись. Поле `cadastralReference` сохраняет исходную строку, в том числе пояснение о прежнем номере.
- `capture.json` — дата, адреса источников, область запроса, сверка количеств, предварительные преобразования изображений и подтверждённые соответствия. Точные параметры эксперимента брать из этого файла.

NDJSON отсортирован по кадастровому номеру или полному коду. Такой снимок можно сравнивать построчно. Данные получены из публичных источников через браузер; сохранены только перечисленные поля. Пустые сведения о площади или кадастровом номере опущены. Проверка Zod перед сохранением подтвердила структуру, конечность координат, замыкание колец и уникальность идентификаторов внутри наборов; топологическая корректность и полнота территории ещё требуют проверки.

## Что подтвердил эксперимент

НСПД вернула `FeatureCollection` с настоящими `Polygon` и `MultiPolygon` по географической области. Запрос `fullObject` возвращает целые объекты, поэтому часть геометрии может выходить за прямоугольник запроса. Выборка также включает соседние территории, дороги и общие земли; её размер не равен числу жилых участков Шелково.

Все четыре генплана состоят из JPG размером 5000 × 3000 и отдельных HTML-меток. Контуры нарисованы на картинке. `window['houses_data']` содержит сведения об участках, а `css/positions.css` задаёт положения меток. В изученных страницах и их `main.js` готовая векторная геометрия участков не обнаружена.

В снимке НСПД 3214 объекта, в каталоге застройщика 1968 записей. Прямое равенство кадастровых номеров связывает 1586 записей с контурами. Раскладка по четырём частям находится в `capture.json`.

Два важных исключения:

- Владелец подтвердил, что прежние L43 и L44 в Ривере объединены. Нынешний контур получен из НСПД; обе предварительно перенесённые метки попали внутрь него. Это подтверждение географической связи, а поведение поиска по двум номерам ещё обсуждается.
- У V43 в Форесте источник прямо называет нынешний кадастровый номер и прежний в скобках. Нынешняя геометрия есть в снимке. Поэтому первоначальную оценку «323 записи без номера» следует читать как **322 пустые ссылки и одну текстовую ссылку на нынешний и прежний номера**.

Точные номера и основания этих двух соответствий сохранены в `capture.json`. Из 59 простых кадастровых номеров, отсутствующих в выбранной области, два относятся к подтверждённому объединению L43 и L44; причины отсутствия остальных 57 ещё предстоит выяснить. Площадь V43 в Форесте расходится в двух источниках и требует отдельной проверки. Список четырёх записей без HTML-метки тоже сохранён в `capture.json`.

## Как повторить получение источников

Это описание проверенного исследовательского пути. Окончательную процедуру обновления согласовать в [вопросе о повторной выгрузке](https://github.com/silentroach/kpshelkovo/issues/807), после проверки модели и сопоставлений.

### 1. Подключиться к браузеру с работающей НСПД

Использовать skill `agent-browser` и его инструкции для установленной версии. В первой изолированной браузерной сессии портал отвечал `403`. В Chrome владельца он открылся, и запросы из этой вкладки сработали.

Для проверенного Chrome 153 владелец включил удалённую отладку на `chrome://inspect/#remote-debugging` и разрешил подключение. Рабочий адрес CDP оказался `ws://127.0.0.1:9222/devtools/browser`: HTTP `/json/version` возвращал `404`, автоматическое обнаружение не сработало.

```bash
SESSION="$(agent-browser session id --scope worktree --prefix parcel-research)"
agent-browser --session "$SESSION" --cdp ws://127.0.0.1:9222/devtools/browser --pin-tab tab list --json
agent-browser --session "$SESSION" tab <tab-id-карты-НСПД>
```

Порт и вкладку проверить заново, а не переносить из прежней сессии. Достаточное подтверждение доступа — успешный ответ географического запроса с геометрией. Завершая работу, закрыть созданные исследовательские вкладки и отключить агентскую сессию, сохранив браузер владельца.

### 2. Запросить область

Для воспроизведения этого снимка использовать `queryRing4326` из `capture.json`. Он получен из выбранного владельцем кадра: центр и zoom из URL, размер основного viewport OpenLayers 785 × 700 CSS-пикселей. Масштаб вычислен как `2π × 6378137 / (256 × 2^zoom)` в проекции `EPSG:3857`, затем углы переведены в `EPSG:4326`. Сохранённое кольцо позволяет повторить запрос независимо от нынешнего размера окна.

Из контекста вкладки НСПД выполнить `POST` на `nspd.endpoint` с `Content-Type: application/json` и телом следующей формы. Здесь `capture` — содержимое `capture.json`:

```js
const body = {
  categories: [{ id: capture.nspd.categoryId }],
  geom: {
    type: 'FeatureCollection',
    features: [
      {
        type: 'Feature',
        properties: {},
        geometry: {
          type: 'Polygon',
          coordinates: [capture.nspd.queryRing4326],
          crs: { type: 'name', properties: { name: capture.nspd.queryCrs } }
        }
      }
    ]
  }
};
```

Это поисковый запрос, он не изменяет объекты НСПД. ID слоя и категории различаются; их значения сохранены в снимке и требуют сверки при изменении портала.

Проверить HTTP-статус, формат ответа, наличие геометрии и её CRS. Ошибку сервиса отличать от успешной пустой выборки. Для проверки полноты сравнить общую выборку с объединением меньших областей, учитывая дубли пересекающих границы объектов; отдельно проверить охват всех четырёх частей. В этом эксперименте такая проверка полноты ещё не выполнена.

Сохранять из объекта `id`, `geometry` и выбранные поля `properties.options`: `cad_num`, площадь `specified_area` с запасным `declared_area`, `status`. Если номер отсутствует в options, сверить `properties.label`. При отсутствии обеих площадей сохранить геометрию без площади. Проверить новый снимок Zod перед использованием.

### 3. Получить каталог генпланов

Адреса четырёх страниц, изображений и CSS перечислены в `capture.json`. Из встроенного присваивания `window['houses_data']` прочитать JSON как данные. Для записи сохранить исходный `id`, кадастровую строку и площадь; добавить префикс части к коду через дефис.

В исследованном источнике встречаются кириллические `А` и `К` в кодах. Для канонического кода они заменены на латинские `A` и `K`, а исходное написание оставлено в `sourceId`. Новые необычные написания проверять отдельно.

Найти HTML-метку по `data-id`, затем её позиционный класс и правило в `positions.css`. `left` и `top` сохраняются в процентах. Отсутствующая метка означает отсутствие этой точки привязки, а не автоматическое исключение записи из каталога. Проверить уникальность полных кодов и диапазон позиций.

Текущий снимок не фиксирует серый цвет меток. Перед ручным разбором остатка определить его значение по актуальным данным и renderer-у генплана; вопрос включён в [визуальную проверку привязки](https://github.com/silentroach/kpshelkovo/issues/808).

### 4. Сопоставить номера и проверить привязку

Сначала сопоставить простые кадастровые номера из каталога с номерами геометрий. Отдельно разобрать текстовые ссылки на прежний и нынешний номер. Подтверждённые соответствия из `capture.json` — контрольные примеры; при изменении геометрии или исходных номеров их требуется перепроверить.

Предварительная привязка каждой картинки рассчитана методом наименьших квадратов: координатам меток в процентах сопоставлены взвешенные по площади центры кадастровых полигонов. Для отверстий площадь вычитается, для `MultiPolygon` учитываются все части. Участвуют только прямые совпадения с имеющейся меткой.

Преобразование из `preliminaryAlignment.transforms[part]` применяется так:

```text
offset = markerPosition - imageOriginPercent
projectedPoint = projectedOrigin + matrix * offset
```

Результат — точка в `EPSG:3857`. Геометрия НСПД этим преобразованием не изменяется.

Проверка на использованных опорных точках дала 97–100% попаданий меток в соответствующий контур. Это оценка на обучающих данных, а не независимая точность. Следующий шаг — визуальный прототип, независимые контрольные участки и проверка краёв, особенно там, где мало опорных совпадений. Попадание неподтверждённой метки в полигон создаёт кандидата для проверки.

### 5. Сравнить с прежним снимком

При повторном исследовании сохранять происхождение нового снимка и сравнивать появившиеся, исчезнувшие и изменившиеся контуры, номера и метки. Изменение порядка вершин само по себе ещё не доказывает изменение границы. Подтверждённые человеком соответствия и заметки требуют отдельной проверки при объединении или разделении.

Результат — объяснённые изменения и список оставшихся неоднозначностей, затем решение о следующем OpenSpec change по правилам проекта.
