# Ранняя проверка печати редакционной карты (задача 1.1)

23 сентября 2026 года. Раннее исследование **завершено по пересмотренной задаче 1.1** после [решения владельца о границе приёмки](https://github.com/silentroach/kpshelkovo/issues/819#issuecomment-5798818614). На момент пробников основная интеграция карт ещё не начиналась. Системная печать и итоговая реализация не проверены.

## Условия

- Временную страницу `/kb/editorial-map-print-check/` собрали через `pnpm --filter @shelkovo/www build`. После проверки исходный маршрут удалён. Страница использовала настоящий `loadYandexMaps()` и SDK v3, `BaseLayout` с классом `site-print-content` и действующий `styles/print.css`. Три отдельные карты создавались сразу при загрузке; каждая содержала векторную подложку, линию, полигон, DOM-лейбл точки, SDK-атрибуцию и подпись со ссылкой на схему в Яндекс Картах. Первый блок был ниже экрана, ещё два следовали за ним. Это минимальный пробник сцены, а не проверка импорта контрольного GeoJSON или будущего Markdown-рендера.
- Для проверки локальной production-сборки использовали отдельные сессии Chrome через `agent-browser`. Ключ из проектного `.env` использовали при сборке и для диагностики HTTP-ответа SDK; его значение не записано в исходники или этот протокол. Запрос SDK с реферером `127.0.0.1` завершался ошибкой загрузки; тот же ключ с реферером `kpshelkovo.online` получил HTTP 200. Поэтому локальный сервер на `:14339` открывали через временное Chrome-правило `--host-resolver-rules=MAP kpshelkovo.online 127.0.0.1`; DNS и production-сайт не менялись.
- После предупреждения о параллельной сборке пробник **пересобрали**, заново открыли в отдельной холодной сессии и повторно проверили PDF на актуальном `dist/www`. До печати `scrollY = 0`, все три карты находились ниже экрана (`top` около 756, 1048 и 1339 px) и сообщили `tilesReady=true`. Был один запрос за скриптом SDK. Отдельно выполнили typecheck при временном маршруте: прошёл.

## Что наблюдали

- `agent-browser pdf` для `/kb/…` создал двухстраничный PDF. На обеих страницах визуально видны подложка, красная линия, жёлтый полигон, лейблы «Ворота 1–3», текст «© Яндекс» и «Условия использования», все три подписи-ссылки. Карты 1 и 2 попали на первую страницу, карта 3 на вторую; до печати к ним не прокручивали. Логотип «Яндекс Карты» в печатной сцене **пропал**, хотя на экранном представлении SDK он есть: SDK задаёт его как CSS `background-image`, а общее правило `print.css` принудительно сбрасывает фон у всех потомков `main`. Вместе с ним пропали белые подложки кнопок. Это конкретный предмет доработки печатного CSS в 5.4; результат этой доработки пробник не подтверждает.
- После ручного перетаскивания первой карты мышью второй PDF сохранил сдвинутый кадр первой карты; две другие остались на прежнем кадре. Пробник не проверял будущую политику `fit` при resize/печати и не доказывает её корректность.
- Экспорт `agent-browser pdf` **не подтверждает печать с выключенными фонами**. Для проверки создали в DOM отдельный фиксированный квадрат с CSS-фоном цвета magenta вне `main`; он появился в PDF. Значит, этот способ экспорта печатал CSS-фоны. Не следует принимать видимую в нём картографическую подложку за доказательство сценария «Background graphics: off».
- Настольный Safari фактически не проверен: установленный `agent-browser` ответил `Unknown engine 'safari'. Supported engines: chrome, lightpanda`. Системный Safari установлен, но в этой проверке не было доступного через указанный инструмент способа получить и оценить его print PDF. Замедленную сеть тоже не включали; свежая изолированная сессия подтвердила **холодный кеш**, но не поведение на низкой скорости. Настоящие iPhone/Android здесь не проверялись; их необходимо перечислить среди непроверенных сценариев в PR по задаче 6.3.

## Дополнительная проверка 23 сентября

- Чтобы не создавать публикуемый маршрут, подняли отдельный временный локальный HTTP-пробник за пределами `apps/www` и `dist/www`. Он читает действующий `apps/www/src/styles/print.css`, использует настоящий SDK v3 и три независимые векторные сцены с линией, полигоном, DOM-лейблом точки, штатной атрибуцией и подписью-ссылкой. Chrome направлялся на localhost только через собственное правило DNS; ключ SDK читался локально, в протокол и исходники не записывался. Это **не** повторная production-сборка и не будущий renderer Markdown; проверка production-сборки выше остаётся отдельным наблюдением.
- В новом изолированном профиле Chrome ограничили сеть через CDP до задержки **200 мс** и пропускной способности **200 000 байт/с**. Все три сцены сообщили о готовности плиток без прокрутки (`scrollY=0`, верх первой карты ≈835 px от верха экрана). Проверяли печать уже загрузившихся карт; это не доказывает, что браузер дождётся загрузки при печати до готовности. Печатный PDF получен отдельным вызовом Chrome `Page.printToPDF` с явным `printBackground:false`, **не** командой `agent-browser pdf`. Добавленный для контроля цветной CSS-фон вне сцены исчез из PDF, что подтверждает отключение обычных фонов в этом экспорте.
- В полученном PDF с действующим print CSS видны все три подложки, линии, полигоны, лейблы, подписи-ссылки, «© Яндекс» и «Условия использования». Логотип «Яндекс Карты» отсутствует. В вычисленных стилях печати его `background-image` равен `none`: общее `background: transparent !important` из `print.css` сбросило поставляемый SDK SVG-фон. Это воспроизводит потерю части атрибуции и при явно выключенных фонах.
- Только внутри временного пробника заменили селектор общего сброса на исключающий контейнер сцены и его потомков, добавили для сцены `print-color-adjust: exact`. В том же Chrome PDF при `printBackground:false` логотип **реально появился** на всех трёх картах вместе со штатным текстом атрибуции. SVG остался предоставленным SDK, а не подменённым текстом или отдельным изображением. Это проверенный узкий CSS-кандидат; сочетание двух правок проверено вместе, их отдельный вклад и результат в других браузерах не установлены. Основной `print.css` не менялся.
- Системные окна печати и сохранения в PDF **не проверены**: Chrome CDP с `printBackground:false` управляет движком печати, но не подтверждает результат пункта «Background graphics: off» в пользовательском диалоге. В Safari 27 попытка создать WebDriver-сеанс вернула `You must enable 'Allow remote automation' in the Developer section of Safari Settings`; GUI-автоматизация через System Events вернула `osascript is not allowed assistive access (-1728)`. Настройки доступа владельца не меняли. Для проверки того же пробника в Safari потребовался бы разрешённый для ключа SDK origin: запрос с `127.0.0.1` ранее отклонялся, а правило DNS временного Chrome на Safari не распространяется. Настольная системная печать Safari и Chrome остаётся непроверенной; её проверка не является условием готовности этого change.

## Вывод

Chrome показал, что существующая сцена SDK в принципе попадает в печать без прокрутки; ручной кадр не сбрасывается. Дополнительный CDP-пробник подтвердил отрисовку трёх карт после холодной загрузки на ограниченной сети и показал CSS-кандидата на сохранение логотипа при `printBackground:false`. **1.1 выполнена как раннее исследование**: действующий CSS по-прежнему теряет логотип, а системная печать Chrome с отключённой фоновой графикой и Safari, печать до готовности карт и будущая политика fit/ручного кадра на печатном resize не подтверждены. Реализация может продолжаться без предварительной системной приёмки; подтверждённые наблюдения и непроверенные сценарии печати нужно разграничить в PR. Если при реализации обнаружится существенная невозможность сохранить согласованное поведение, вернуться к владельцу за решением о подходе. Подменять карту ссылкой или добавлять Static API без согласования нельзя.
