# ADR-028: Markdown-first карта мест с типизированными маркерами

## Статус

Принят

## Дата

2026-08-19

## Контекст

Жителям нужна общая карта полезных и заметных объектов КП Шелково: площадок, въездов, прогулочных зон, сервисов, инфраструктуры и мест с отдельными карточками. Карта должна работать как часть статического Astro-сайта, а не как отдельная CMS или динамический геосервис.

У места есть несколько представлений одной сущности:

- точка на общей карте;
- серверная HTML-карточка по устойчивому URL;
- Markdown companion для терминальных клиентов и агентов;
- при необходимости ссылка на связанную карточку «Сарафана»;
- стандартный или узнаваемый объектный маркер.

Хранить такие места непосредственно в Svelte-компоненте неудобно: редакционные данные смешиваются с renderer-ом, новый объект требует правки TypeScript, а отдельную карточку и Markdown-поверхность приходится синхронизировать вручную.

Произвольный путь к изображению во frontmatter тоже создает слабый контракт. Сборка не гарантирует единый размер, прозрачность, доступность asset-а, экспорт пакета и поддержку состояния маркера. При этом для части мест стандартной точки достаточно, поэтому кастомное изображение не должно быть обязательным.

Карта занимает весь viewport. Главный header должен оставаться доступным поверх карты, но footer на карте создает лишний вертикальный скролл. Начальный viewport должен показывать реальные опубликованные точки, сохранять контекст поселка и корректно пересчитываться при изменении размера окна.

## Решение

### Источник данных

Хранить места в `apps/www/src/data/places/*.md`. Один файл равен одному месту, имя файла без `.md` задает канонический slug.

Frontmatter проходит через границу ADR-013:

- `RawPlaceSchema` валидирует внешний Markdown/YAML-формат;
- mapper переводит raw-поля в readonly domain model `Place`;
- UI, маршруты и Markdown-адаптеры работают с domain model, а не с raw DTO.

Обязательные данные места:

- название;
- категория из фиксированного enum;
- lifecycle-статус;
- краткое описание;
- точные координаты.

Точные координаты частных домов и чувствительной инфраструктуры не публикуются без отдельного редакционного решения.

Необязательные возможности:

- body Markdown для дополнительных сведений;
- понятный адрес;
- ссылка на Яндекс Карты; если её нет, ссылка строится из координат;
- `contact: category/slug` для связи с существующей карточкой «Сарафана»;
- структурированное время работы;
- тип кастомного маркера.

Если одно место пересекается с другим доменом, например с контактом «Сарафана», домен places остается источником адреса и координат. Пересекающийся редакционный текст пока синхронизируется явно.

### Маршруты и публичные поверхности

Публиковать:

- `/map/` — общую интерактивную карту;
- `/map/<slug>/` — серверную карточку места;
- `/map/index.md` и `/map/<slug>/index.md` — Markdown companions.

Общая карта поддерживает временный фокус по URL `/map/?h=<slug>`. После клиентской инициализации карта находит место только по его каноническому slug, центрирует его с zoom 16 и на 5 секунд отмечает маркер кольцом и стрелкой. Затем маркер возвращается в обычное состояние, а `h` удаляется через `history.replaceState` с сохранением остальных query-параметров, hash и текущего history state.

Неизвестный или пустой `h` удаляется без смены viewport. При `prefers-reduced-motion` переход камеры и движение стрелки отключаются, но статическое выделение сохраняется. Карточка места формирует ссылку на общую карту с его каноническим slug; breadcrumbs и canonical URL остаются без query-параметра.

Маршруты places участвуют в общем статическом build и публикационных механизмах сайта. Наличие ссылки в главном меню не является признаком публикации route.

Временное скрытие «Карты» из primary navigation:

- не удаляет HTML- или Markdown-маршруты;
- не добавляет `noindex`;
- не исключает страницы из sitemap;
- не меняет правила корпуса Pagefind из ADR-025;
- не ломает прямые и внутренние ссылки.

Так раздел можно выпустить сначала по прямым ссылкам, а пункт главного меню включить отдельным маленьким изменением после продуктовой проверки.

### Renderer карты

Использовать Яндекс Карты v3 через общий runtime приложения. Карта остается клиентским Svelte-компонентом внутри статической Astro-страницы; карточки мест и metadata рендерятся на build-time.

Каждый отдельный маркер является настоящей HTML-ссылкой на карточку места. Ссылка получает доступное имя, `title`, lifecycle- и opening-hours-состояние, работает с `Tab`, `Enter` и `Space`. На coarse pointer карта не перехватывает обычную прокрутку одним пальцем.

Иконки и подписи базового слоя Яндекс Карт можно скрывать, но дороги, здания, территории и текстовые labels остаются частью подложки. CSP-ограничения Яндекс Карт регулирует ADR-017.

### Семантический масштаб и кластеры

Размер графики маркера зависит от zoom: между уровнями 16 и 13,5 обычная графика плавно уменьшается с 48 до 30 CSS-пикселей, а компактный маркер строительства — с 32 до 20 CSS-пикселей. Контейнер ссылки остается не меньше 44 CSS-пикселей, поэтому визуальное уплотнение не уменьшает доступную область нажатия.

Когда экранные области соседних точек сближаются, официальный `YMapClusterer` объединяет их по сетке 48 пикселей. Вместо отдельных ссылок появляется доступная HTML-кнопка с количеством мест. Нажатие приближает карту до bounds группы, после чего кластер снова раскрывается в ссылки. Кнопка использует спокойный редакционный стиль общей дизайн-системы, поддерживает клавиатуру и отключает CSS-переходы и анимацию приближения при `prefers-reduced-motion`.

### Типизированные кастомные маркеры

Поле `marker` является необязательным enum. Если поля нет, renderer использует общий стандартный `ui-map-marker`.

Каждый новый тип кастомного маркера должен одновременно получить:

- значение в `PLACE_MARKERS`;
- source PNG и подготовленный runtime PNG в `packages/ui/src/markers`;
- явный export с фактическими `src`, `width` и `height`;
- запись в исчерпывающем renderer registry;
- пример в visual catalog и component test.

Не разрешать произвольные URL или файловые пути во frontmatter. Это сохраняет сборочную проверку enum, единый asset pipeline и контролируемый визуальный набор.

Source PNG хранится для повторной подготовки без потери качества. Runtime PNG получает прозрачный фон, очищенный низкоальфовый ореол, обрезанные безопасные поля и достаточную плотность для целевого CSS-размера. Текущая реализация показывает объект шириной до 48 CSS-пикселей и использует растр шириной 144 пикселя для экранов до 3x; эти числа можно настраивать без нового ADR.

Координата Яндекс Карт совмещается с геометрическим центром контейнера и PNG через `translate(-50%, -50%)`. Объектные иллюстрации не используют нижний край или условный «носик» как anchor. Светлый контур и темная тень отделяют изображение от деталей подложки; grayscale закрытого места не должен удалять эти эффекты.

Тип маркера может появиться раньше первого места, которое его использует. Например, `construction` можно подготовить в общей серии заранее, не создавая фиктивную точку.

### Начальный viewport и layout

При двух и более местах вычислять bounds по фактическим координатам, добавлять контролируемый географический запас и округлять служебные границы до точности исходных координат. При одной точке использовать общий допустимый прямоугольник поселка как безопасный fallback.

Экранные margins могут быть асимметричными: header перекрывает верх карты, а полезная территория поселка не обязана быть симметрична относительно точек. Текущие margins сдвигают видимую область так, чтобы показать больше территории сверху и меньше нерелевантной территории снизу.

После resize и Astro-навигации повторный fit выполняется только после стабилизации layout. Это нужно, чтобы поворот телефона или изменение viewport не оставляли маркеры за границами карты.

Страница `/map/` использует overlay header, карту высотой `100svh` и не рендерит общий footer. Карточки `/map/<slug>/` сохраняют обычный layout с header и footer.

### Геометрия за пределами точек

`location.coordinates` задает основную точку места и будущую точку подписи. Линии и полигоны не кодируются произвольными полями frontmatter.

Если понадобятся маршруты, границы или площадные объекты, использовать GeoJSON features или соседний `[slug].geojson` и отдельный renderer через API карты. Это расширение не должно менять slug, карточку места или базовую point-модель.

## Рассмотренные альтернативы

### Хранить места в TypeScript-массиве компонента

Плюсы:

- минимум файлов для первой точки;
- типы доступны непосредственно renderer-у.

Минусы:

- редакционный контент смешивается с клиентским кодом;
- новая точка требует изменения компонента;
- HTML-карточки и Markdown companions получают параллельный источник данных.

Отклонено: место является контентной сущностью, а не настройкой renderer-а.

### Разрешить путь к PNG во frontmatter

Плюсы:

- новый вид маркера можно добавить одним полем;
- не нужен центральный enum.

Минусы:

- невозможно исчерпывающе проверить renderer registry;
- размеры, прозрачность и плотность растра становятся случайными;
- внутренние файловые пути протекают в редакционный контракт;
- visual catalog перестает покрывать весь набор.

Отклонено: небольшой явный enum дает более надежную сборочную границу.

### Использовать один стандартный pin для всех мест

Плюсы:

- меньше assets и CSS;
- привычная нижняя anchor-точка.

Минусы:

- разные объекты хуже различаются на общей карте;
- карта теряет локальный визуальный язык;
- детализированные иллюстрации приходится помещать внутрь маленького универсального pin.

Отклонено как единственный вариант. Стандартная точка остается fallback, а узнаваемые места могут выбрать типизированную объектную иллюстрацию.

### Привязать объектную картинку нижним краем

Плюсы:

- повторяет привычное поведение pin-маркера;
- объект визуально стоит над координатой.

Минусы:

- у изометрических объектов нет общего нижнего «носика»;
- разные пропорции дают разное смещение фактической точки;
- координата становится неочевидной при просмотре и масштабировании.

Отклонено: для этой серии координата находится в геометрическом центре картинки.

### Не публиковать route до появления пункта меню

Плюсы:

- пользователь не найдет незавершенный раздел через обычную навигацию.

Минусы:

- нельзя проверить production-route по прямой ссылке;
- ломаются устойчивые карточки и Markdown surfaces;
- rollout UI ошибочно связывается с sitemap, robots и поисковым контрактом.

Отклонено: primary navigation управляется отдельно от публикации route.

## Последствия

- Новое обычное место добавляется одним Markdown-файлом без правки TypeScript-реестра мест.
- Новый визуальный тип требует осознанного изменения enum, UI package, renderer-а и visual baseline.
- Кастомный маркер остается необязательным; неизвестное значение останавливает build вместо молчаливого отображения случайного asset-а.
- Карточка места доступна без выполнения JavaScript, но общая карта зависит от клиентского API Яндекс Карт.
- Карта сохраняет доступные HTML-ссылки и мобильную прокрутку, а не превращает точки в недоступные canvas-hotspots.
- Source PNG увеличивают размер репозитория, зато runtime assets можно безопасно пересобирать под новый размер и плотность.
- Начальный viewport автоматически адаптируется к росту набора мест; при сильных географических выбросах padding или группировку придется пересмотреть.
- Скрытие пункта «Карта» из главного меню не является удалением или деиндексацией раздела.
- Упоминания людей в body места публикуют backlinks на профиль через общий mention graph.
- Фильтры, подписи, GeoJSON-геометрия и отдельный публичный JSON feed остаются будущими изменениями.
