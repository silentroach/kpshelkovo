# ADR-025: Статический полнотекстовый поиск через Pagefind

## Статус

Принят. Действующий контракт поиска — [search](/openspec/specs/search/spec.md). Причины выбора корпуса статуса уточнены в [ADR-035](/docs/decisions/035-status-search-indexing.md), специальных записей участков — в [ADR-041](/docs/decisions/041-parcel-records-and-exact-search.md).

## Дата

2026-08-14

## Контекст

`kpshelkovo.online` — статический сайт: содержимое меняется вместе с опубликованной сборкой. Первоначальный вариант с Sphinx Search и Node gateway добавлял два постоянно работающих процесса, отдельный корпус, состояние индекса, мониторинг и обработку частичных отказов. Периодическая переиндексация могла рассинхронизировать страницы и выдачу.

Для текущего объёма серверный поисковик не нужен. Pagefind строит шардированный индекс после сборки HTML, поддерживает русский stemming и выполняет поиск через WebAssembly в браузере, загружая нужные части индекса по запросу.

## Решение

### Статический индекс вместе с сайтом

Использовать Pagefind без отдельного поискового API, daemon или cron переиндексации. Индекс входит в тот же build-артефакт, что и страницы: это упрощает согласованную публикацию и откат. Порядок сборки и остановка при ошибках заданы в [команде build](/apps/www/package.json) и [сборщике индекса](/apps/www/scripts/build-search-index.ts).

Для обычных документов источником служит явно выбранный пользовательский HTML. Так найденный текст соответствует содержимому после перехода. Включением страницы и её метаданными владеет шаблон раздела; отдельный центральный реестр поисковых DTO дублировал бы доменный контент. Специальные записи позиций генплана по ADR-041 дополняют HTML-корпус без тысяч отдельных страниц участков.

`/search/` — внутренний build asset, а не стабильный публичный API по [ADR-011](/docs/decisions/011-public-surface-registry.md). Обычный dev-режим может работать без готового индекса; полный сценарий проверяется на production-сборке.

### Клиентский поиск

Использовать JavaScript API Pagefind со своим интерфейсом: это сохраняет визуальный язык сайта и доступный диалог. Ленивая загрузка движка, индекса и поддержки подсветки переносит стоимость поиска на тех, кто им пользуется. Для больших документов heading anchors и sub-results дают переход к фрагменту без отдельного документа на каждый блок.

Релевантность остаётся основой выдачи: глобальная сортировка по дате вытесняла бы точный старый ответ свежим случайным совпадением. Настройки ранжирования принадлежат [клиенту](/apps/www/src/lib/search/client.ts), а их изменение требует проверки выдачи по [site-search](/.agents/skills/site-search/SKILL.md). Исторические веса и бюджеты пилота не являются постоянным контрактом.

Правила корпуса, видимого текста, основного excerpt и canonical URL, соответствующего ему якоря, передачи поискового контекста и ленивой подсветки целевой страницы, клавиатурной доступности и доказанных алиасов находятся в [search](/openspec/specs/search/spec.md). Смежные владельцы:

- [knowledge-base](/openspec/specs/knowledge-base/spec.md) — флаги KB и исключение страниц-разделов;
- [client-load-recovery](/openspec/specs/client-load-recovery/spec.md) — восстановление при отказе кода или запроса;
- [status-lifecycle](/openspec/specs/status-lifecycle/spec.md) — фазы статуса и время расчёта представлений.

### Доставка и ограничения

Same-origin файлы поиска используют обычную статическую доставку. Политика кеширования `/search/` задана в [nginx-конфигурации](/ops/nginx/kpshelkovo-online.conf): долгоживущие content-hashed chunks и обновляемые стабильные входы должны оставаться совместимыми с опубликованным индексом.

Pagefind требует компиляции WebAssembly и worker. Действующие разрешения и пределы исключений принадлежат [CSP.md](/ops/nginx/CSP.md) и [ADR-017](/docs/decisions/017-csp-inline-exceptions-for-astro-yandex-maps.md): широкий `unsafe-eval` нужен Яндекс Картам, самому поиску достаточно более узкого разрешения WebAssembly.

Запрос вычисляется на устройстве пользователя, поэтому ограничение его длины — часть UX, а не защита серверного API. Существующая Яндекс Метрика получает цели поиска с запросом и числом результатов; Вебвизор отключён. Термины для подсветки передаются в URL результата и могут попадать в access log и SPA-hit Метрики. Отдельный поисковый API или журнал запросов не создаётся.

## Рассмотренные альтернативы

- Sphinx с Node gateway и Manticore: сервер контролирует выдачу и не передаёт индекс пользователю, но требует daemon, адаптера, защиты endpoint и синхронизации индекса с deploy. При необходимости серверного поиска сначала оценивать Manticore.
- Typesense и Meilisearch: полезны для частых обновлений и typo tolerance, но сейчас их инфраструктура не покрывает подтверждённую потребность.
- SQLite FTS5 с Node-сервисом: компактный индекс, но остаётся API и собственная работа над русской морфологией, ranking и snippets.
- MiniSearch, Lunr или FlexSearch с JSON-индексом: сохраняют статическую архитектуру ценой собственного шардирования, ленивой загрузки, русской нормализации и excerpts. Pagefind уже решает эти задачи.
- Внешний SaaS: добавляет vendor, передачу запросов, лимиты и стоимость без необходимости для текущего публичного сайта.

## Последствия

- Сайт получает полнотекстовый поиск без новых постоянно работающих процессов; цена — дополнительный шаг сборки, сетевой трафик и вычисления в браузере.
- Качество корпуса зависит от явной разметки шаблонов. Машинные companions и исходные вложения не становятся отдельным поисковым корпусом автоматически.
- Поиск по закрытым данным, semantic/vector search, обязательная typo tolerance и публичный Search API требуют отдельного решения. Повод пересмотреть движок — измеренные ограничения трафика или задержки на целевых устройствах либо обновления контента независимо от deploy.
- Исторические замеры и RC-план сохранены в истории Git. Действующая приёмка — [site-search](/.agents/skills/site-search/SKILL.md), технические сценарии production-индекса — [search-quality.test.ts](/apps/www/tests/search-quality.test.ts).
