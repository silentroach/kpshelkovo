# ADR-025: Статический полнотекстовый поиск через Pagefind

## Статус

Принят

## Дата

2026-08-14

## Контекст

`kpshelkovo.online` собирается Astro в статический `dist/www` и выкладывается на VPS через `rsync`. Контент меняется только вместе с новым build-артефактом. На сайте уже есть новости, инциденты статуса, база знаний, встречи, профили людей, отзывы, полезные контакты, регламент и страницы поселков Compare.

Нужен быстрый поиск по этому публичному контенту. Первоначальный вариант архитектуры состоял из четырех частей:

- build создает отдельный поисковый корпус;
- Sphinx Search периодически индексирует корпус на сервере;
- небольшой Node-сервис валидирует запрос, обращается к Sphinx и нормализует ответ;
- фронтенд вызывает Node API.

Этот вариант технически работоспособен, но добавляет к статическому сайту два постоянно работающих процесса, приватный сетевой контракт, состояние индекса, переиндексацию, мониторинг и обработку частичных отказов. Периодический cron также может рассинхронизировать опубликованные страницы и выдачу, хотя данные сайта меняются только при деплое.

Для текущего объема серверный поисковик не является обязательным. Pagefind индексирует готовый статический HTML после основного build, кладет шардированный индекс рядом с сайтом и выполняет поиск в браузере через WebAssembly. Он поддерживает русскую морфологию по `lang="ru"`, метаданные, фильтры, веса, excerpts и загрузку только нужных частей индекса.

Пробный запуск Pagefind 1.5.2 на существующем `dist/www` без специальной разметки:

- обработал 223 HTML-файла и 8 736 слов;
- построил индекс за 0,279 секунды;
- создал 2,1 МиБ файлов на диске;
- ошибочно включил 404 и две служебные verification-страницы, потому что на сайте пока нет `data-pagefind-body`.

Это ориентир, а не production-бенчмарк. Размер всего каталога на диске не равен объему одного поискового запроса: Pagefind загружает индекс частями. По документации проекта поиск по сайту из 10 000 страниц укладывается менее чем в 300 КБ сетевого трафика вместе с библиотекой, а для большинства сайтов ожидается около 100 КБ.

## Решение

### Поисковый движок

Использовать Pagefind как первый поисковый движок сайта.

Pagefind запускается после `astro build` над `apps/www/dist/site` и до копирования результата в корневой `dist/www`. Каталог `/search/` входит в тот же неизменяемый build-артефакт, что и HTML. Каждый успешный деплой тем самым публикует согласованную версию страниц и индекса.

Не добавлять на первом этапе Sphinx, Manticore, поисковую базу, cron переиндексации или Node API. Запрос выполняется на устройстве пользователя. На VPS остаются только nginx и статические файлы.

Обычный `astro dev` не обязан строить или обновлять индекс. Полный локальный сценарий поиска проверяется через production build и preview. UI должен корректно переживать отсутствие `/search/` в dev-режиме и не ломать остальной сайт.

### Источник данных и границы корпуса

Источником истины для поиска является готовый пользовательский HTML, а не Markdown companion, JSON-ленты, `llms.txt` или новый параллельный набор DTO. Это сохраняет соответствие между найденным текстом и тем, что человек увидит после перехода.

Индексирование делается явным opt-in:

- в индекс попадает только содержимое элемента с `data-pagefind-body`;
- поисковые metadata, section filters и веса задаются через `data-pagefind-meta`, `data-pagefind-filter` и `data-pagefind-weight` рядом с шаблоном страницы;
- канонический URL и первый `h1` используются как основа результата;
- `lang="ru"` из `BaseLayout` включает русский stemmer;
- страницы с `noindex` или явным флагом исключения из внутрисайтового поиска, 404, служебные verification-файлы, архивы и списки, которые только повторяют дочерние материалы, не получают opt-in marker;
- Markdown, JSON, RSS, ICS, OpenAPI, схемы, `llms.txt` и другие не-HTML поверхности Pagefind не индексирует.

В первый корпус входят канонические содержательные страницы: отдельные новости, инциденты, статьи базы знаний без флагов `noindex` и `exclude-from-site-search`, встречи, профили людей, отзывы, карточки полезных контактов, содержательные страницы регламента и поселков Compare. Главная, страницы разделов, рейтинг и другие самостоятельные landing pages включаются только тогда, когда дают уникальный ответ, а не дублируют список ссылок.

Не вводить отдельный центральный реестр поисковых документов. Владельцем решения о включении и метаданных остается шаблон раздела. Общие типы и атрибуты можно вынести в app-level helper, но он не должен повторно собирать доменный контент.

Шаблон раздела может передать Pagefind необязательные `search_aliases` как отдельную metadata. Это служебные варианты пользовательского запроса, а не параллельный корпус или SEO-ключи. Поле по умолчанию отсутствует; алиас добавляется только после подтвержденного употребления или воспроизведенного провала поиска и не повторяет `title`, `summary`, body или теги. Алиасы не используются как title, description или excerpt результата. Они не видны в интерфейсе, но не являются секретными: metadata остается доступной в публичном HTML и поисковом индексе.

Сгенерированный `/search/` считается внутренним build asset, а не стабильным публичным API из ADR-011. Если появится отдельный канонический HTML-route поиска, его нужно рассмотреть для Public Surface Registry отдельно.

### Клиентский поиск

Использовать Pagefind JavaScript API, а не готовую тему как обязательный UI. Это позволяет сохранить визуальный язык сайта и общий доступный search dialog или страницу результатов.

Клиент:

- динамически импортирует `/search/pagefind.js` только при открытии или фокусе поиска;
- включает штатный `highlightParam` Pagefind, сохраняет его вместе с релевантным heading anchor в ссылке результата и лениво импортирует `/search/pagefind-highlight.js` только на целевой странице с таким параметром; буквальная форма запроса подсвечивается в индексируемом body, но совпадение только по stemming или metadata может остаться без визуальной подсветки;
- не добавляет Pagefind и индекс в начальную загрузку обычных страниц;
- ограничивает длину запроса на уровне UX и отменяет устаревшие асинхронные результаты;
- использует debounce/preload из Pagefind;
- показывает title, section, канонический URL и безопасный excerpt;
- сохраняет клавиатурную навигацию, видимый focus, корректные dialog semantics и объявление числа результатов;
- при ошибке загрузки сообщает, что поиск временно недоступен, не нарушая навигацию сайта.

Клиентское ограничение запроса не является security boundary: пользователь вычисляет поиск у себя и не может нагрузить поисковым запросом VPS сильнее обычной загрузки статических файлов. Сам Pagefind не отправляет запрос новому серверному API. В production существующая Яндекс Метрика получает цель поиска с запросом, а Вебвизор может записать взаимодействие с интерфейсом. После перехода Pagefind также передает нормализованные поисковые термины в повторяемом параметре `pagefind-highlight`: он нужен для подсветки, попадает в URL целевой страницы и поэтому может попасть в access log и SPA-hit Метрики. Отдельный поисковый API или журнал запросов не создается.

### Релевантность, актуальность и крупные документы

Релевантность Pagefind остается основой порядка результатов. Не сортировать глобальную поисковую выдачу по дате: Pagefind заменяет такой сортировкой relevance score, поэтому свежий материал со случайным совпадением может вытеснить старый точный ответ.

После загрузки текущей порции результатов клиент может применить ограниченную поправку к Pagefind score без дополнительных fragment-запросов:

- новости получают небольшой бонус только за первые четыре календарных месяца;
- вес инцидентов статуса плавно снижается по целым календарным месяцам с нижней границей, которая сохраняет историческую находимость;
- вес встреч снижается по полным годам;
- остальные разделы не получают возрастную поправку.

Поправка вычисляется в браузере по `publishedAt`, не меняет build-артефакт со временем и не инвалидирует HTTP-кеш поискового индекса. Клиент переставляет только уже материализованную порцию результатов: расширять candidate pool можно лишь после повторной проверки сетевого и latency-бюджетов.

Теги новостей хранятся как metadata с отдельным весом. Если запрос совпал только с тегом, интерфейс показывает естественный контекст с темами новости вместо случайного excerpt из начала body.

Несколько `data-pagefind-body` на одном HTML-route остаются одним поисковым документом. Для крупных справочных страниц, прежде всего регламента, гранулярность строится через стабильные heading anchors и Pagefind sub-results. Клиент упорядочивает подрезультаты по возвращенному Pagefind `balanced_score` и ведет на наиболее релевантный фрагмент страницы.

### Deploy, кеширование и CSP

Pagefind должен быть обычной частью `pnpm build`. Ошибка индексирования или отсутствие ожидаемого индекса останавливает deploy, а не публикует UI без данных.

Для `/search/` нужны production smoke checks:

- entrypoint, worker, metadata, index chunk и fragment возвращаются с `200`;
- `X-Content-Type-Options: nosniff` не мешает загрузке и компиляции WebAssembly;
- content-hashed chunks можно кешировать долго и как `immutable`;
- стабильные entrypoints и WebAssembly-файлы получают короткий TTL или revalidation, чтобы новая версия рантайма не расходилась с новым индексом;
- Pagefind сам сжимает файлы индекса, поэтому отдельный post-build `gzip` для них не является обязательным.

Текущая CSP уже содержит более широкое `script-src 'unsafe-eval'`, нужное Яндекс Картам, и `worker-src 'self' blob:`, поэтому архитектура не требует нового внешнего origin или расширения `connect-src`. Официальная документация Pagefind указывает `wasm-unsafe-eval` для WebAssembly и `worker-src 'self' blob:` для worker.

При реализации нужно обновить пояснение в `ops/nginx/CSP.md`: Pagefind становится вторым потребителем WebAssembly compilation, фактически разрешенной текущим `unsafe-eval`. Если Яндекс Карты позже перестанут требовать `unsafe-eval`, широкое исключение нужно заменить на более узкое `wasm-unsafe-eval`, а не сохранять ради Pagefind.

### Критерии выпуска пилота

До выпуска поиска в production пилот должен пройти измеримые проверки на production-like build:

- ожидаемые канонические страницы находятся, а 404, verification, `noindex` и повторяющие архивные страницы отсутствуют;
- формы одного русского слова находят один материал, в частности сценарии вроде `тариф`/`тарифы` и `вода`/`воды`;
- небольшой фиксированный набор реальных запросов возвращает релевантный URL в первых результатах без проверки хрупкого точного порядка всей выдачи;
- холодный типичный запрос загружает не более 300 КБ Pagefind-ресурсов, без изображений самих результатов;
- поиск после загрузки движка укладывается в p95 100 мс на согласованном среднем мобильном профиле;
- обычная страница без открытия поиска не загружает `/search/`;
- индекс не содержит произвольного скрытого текста: кроме явно объявленных `search_aliases`, поисковые слова происходят из пользовательского HTML и его отображаемых метаданных.

Если пилот не проходит бюджет, сначала корректируются corpus markers, веса и metadata. Серверный движок добавляется только после подтвержденного ограничения Pagefind, а не для преждевременной оптимизации.

## Область действия

Решение покрывает полнотекстовый поиск для людей по общедоступным HTML-страницам `kpshelkovo.online`.

Решение не создает:

- публичный Search API для агентов или внешних клиентов;
- поиск по исходным PDF и другим вложениям, которых нет в HTML;
- поиск по закрытым или персональным данным;
- семантический/vector search;
- отдельную поисковую аналитику;
- гарантию typo tolerance или автокоррекции.

Такие требования требуют отдельного решения и могут изменить выбор движка.

## Рассмотренные альтернативы

### Sphinx Search с Node gateway

Плюсы:

- зрелый быстрый C++-движок;
- plain indexes, ротация и русская морфология;
- сервер контролирует ranking, пагинацию и формат ответа;
- размер индекса не передается пользователю.

Минусы:

- нужны `searchd`, Node-процесс, systemd units, localhost ports, health checks и логи;
- нужен отдельный corpus format и безопасный query adapter;
- deploy должен атомарно согласовывать HTML, source corpus, индекс и metadata ответа;
- cron создает лишнюю задержку, а reindex на каждом deploy усложняет откат;
- публичный endpoint требует ограничения запросов, таймаутов и rate limiting.

Отклонено для первого этапа: для статического сайта эта эксплуатационная стоимость не дает подтвержденного преимущества.

### Manticore Search

Manticore является современным продолжением Sphinx. Он написан преимущественно на C++, поддерживает plain и real-time tables, stemming и lemmatization, HTTP JSON и MySQL protocol. По собственной документации пустой instance занимает около 40 МБ RSS.

Если сайту понадобится серверный поиск, сначала оценивать Manticore, а не возвращаться к исходному Sphinx. Он лучше соответствует современному API и продолжает развиваться. При этом даже Manticore оставляет daemon, индексируемое состояние, обновление пакетов, backup/rebuild и публичный gateway. Прямо проксировать общий Manticore HTTP API наружу нельзя; потребуется узкий read-only adapter и rate limiting.

Не выбран сейчас по той же причине: серверная инфраструктура пока не нужна.

### Typesense или Meilisearch

Оба варианта дают современный HTTP API, быстрый поиск и встроенную typo tolerance без Java/Elasticsearch. Typesense написан на C++, Meilisearch - на Rust.

Они удобнее Sphinx для интерактивного каталога с частыми обновлениями, но для текущего статического корпуса все равно требуют отдельного daemon, загрузки документов, API keys, контроля публичного API и синхронизации deploy. Их сильные стороны пока не покрывают подтвержденную потребность.

Отклонены для первого этапа. Их стоит повторно сравнить с Manticore, если typo tolerance станет обязательной.

### SQLite FTS5 и небольшой Node-сервис

Плюсы:

- один компактный файл индекса;
- минимум внешней инфраструктуры;
- транзакционная замена файла;
- знакомый SQL.

Минусы:

- все равно нужен постоянно работающий API;
- стандартный `unicode61` tokenizer разбирает кириллицу, но не дает полноценную русскую морфологию без расширений или собственной нормализации;
- ranking, snippets, prefix search и обновление корпуса придется проектировать и тестировать самостоятельно.

Отклонено: это меньше инфраструктуры, чем Sphinx, но больше собственного поискового кода, чем Pagefind.

### MiniSearch, Lunr или FlexSearch с собственным JSON-индексом

Плюсы:

- полностью статическая архитектура;
- полный контроль над форматом корпуса и UI;
- нет серверных процессов.

Минусы:

- нужно самостоятельно решать шардирование, ленивую загрузку, русскую нормализацию, excerpts, metadata и совместимость версий;
- монолитный JSON или JS-индекс быстрее растет и ухудшает холодную загрузку;
- появляется собственный поисковый pipeline без продуктовой необходимости.

Отклонено: Pagefind уже решает эти задачи для статического HTML.

### Внешний поисковый SaaS

Отклонен: для небольшого публичного сайта не нужны внешний vendor, отдельная передача запросов, лимиты и стоимость. Это можно пересмотреть только вместе с новыми требованиями к аналитике, SLA или общему поиску по нескольким сайтам.

## Последствия

- Сайт получает полнотекстовый поиск без Java, Elasticsearch, базы, Node gateway и новых постоянно работающих процессов.
- Индекс обновляется на каждом build и не может штатно отстать от контента на несколько cron-интервалов.
- Поиск выполняется в браузере пользователя без отдельного серверного API.
- Поисковые термины выбранного результата становятся частью URL для подсветки и видны системам, которые получают URL перехода; независимо от перехода существующая аналитика может получить запрос из интерфейса поиска.
- Цена поиска переносится с VPS на небольшой лениво загружаемый статический bundle и вычисление в браузере.
- Качество корпуса зависит от аккуратной `data-pagefind-*` разметки шаблонов. Новый тип содержательной страницы не попадает в поиск автоматически.
- `pnpm build` становится немного дольше и создает `/search/` внутри `dist/www`.
- Смена Pagefind на серверный движок остается возможной: UI-контракт title/URL/section/excerpt можно сохранить, но backend и deploy потребуют нового ADR.
- Сигналом к пересмотру являются измеренные проблемы, а не число страниц само по себе: превышение сетевого бюджета, недопустимая задержка на целевых устройствах, обязательная typo tolerance, независимые от deploy обновления, приватный corpus или потребность в публичном Search API.

## План реализации

1. Добавить Pagefind как закрепленную build dependency, конфигурацию и post-Astro шаг, который пишет в `apps/www/dist/site/search`.
2. Добавить явные corpus markers и metadata в выбранные канонические шаблоны; проверить exclusions и русский stemming на production build.
3. Реализовать лениво загружаемый доступный UI через Pagefind JavaScript API без влияния на начальный bundle страниц.
4. Добавить smoke/quality/performance checks, cache policy для `/search/` и синхронное пояснение CSP.
5. После production-like проверки выпустить поиск либо зафиксировать новым ADR причину перехода к серверному пилоту.

## Состояние реализации

На 15 августа 2026 года задачи 01-11 и последующая настройка корпуса реализованы в текущем незакоммиченном worktree. Локальный production build создает 221 страницу, а Pagefind 1.5.2 индексирует 152 русскоязычных документа; четыре малоинформативные страницы отдельных сервисов статуса исключены. Query matrix, morphology, exclusions, responsive layout, Chromium accessibility smoke и контролируемая nginx-доставка проверены.

Локальные критерии задачи 12 пройдены, но поиск еще не выпущен. Повторная RC-проверка подтвердила переходы по `Enter`, догрузку следующей порции без дублей и холодный запрос `тарифы` на 145 102 байта Pagefind-ресурсов при бюджете 300 КБ.

Query-scoped result cache снял локальный latency blocker. На профиле 390 x 844, DPR 2 и CPU slowdown 4x один явно измеренный uncached client call для прежнего тяжелого intent занял 304,2 мс и заполнил cache. Следующие 150 same-query initial-8 samples дали 1,6 мс p95 и для raw `search()`, и для полного клиента при бюджете 100 мс. Browser smoke также подтвердил, что смена запроса не переиспользует чужой excerpt: один документ получает разные корректные highlights и anchors для разных терминов.

Задача 12 остается незавершенной только из-за отложенных проверок dev-режима, реального deploy и public smoke, non-Chromium и screen reader. Эта заметка фиксирует состояние release candidate, а не production release и не изменение принятого архитектурного решения.
