# ADR-031: Единый жизненный цикл status-событий

## Статус

Принят, заменяет [ADR-010](/docs/decisions/010-home-status-maintenance-indicator.md).

## Дата

2026-08-26

## Контекст

Независимые расчёты в mapper, публичном DTO, серверных подписях, сводках и клиентских элементах расходились на будущих работах с указанным концом: API считал их завершёнными, а интерфейс — запланированными. Частичный клиентский пересчёт только плановых работ также пропускал будущие инциденты без конца и сохранял устаревший красный индикатор.

Статические календарь и журнал зависят от московской даты сборки: открытое событие затрагивает новые дни и месяцы даже без правки исходных данных.

## Решение и причины

- Один чистый [вычислитель жизненного цикла](/apps/www/src/lib/status/lifecycle.ts) получает окно и момент расчёта. Общий смысл фаз устраняет расхождения между API и интерфейсом; момент обновления остаётся свойством конкретного представления.
- Mapper сохраняет фазу снимка сборки в доменной модели. DTO и серверные подписи используют её, чтобы машинное состояние, `is_active` и текст не выводились независимо друг от друга.
- Для клиентского уточнения шапки и подписей сервисов достаточно встроенных инертных окон: вид события, начало и необязательный конец. Малый объём данных позволяет обойтись без отдельного запроса, передачи текста событий и фонового обновления вкладки.
- Ежедневная полная публикация заново строит календарь, счётчики и маршруты из снимка данных. Клиентское продление календаря потребовало бы повторить серверную агрегацию и всё равно не создало бы отсутствующий маршрут нового месяца.

## Рассмотренные альтернативы

- Исправить только DTO — оставило бы несколько независимых правил и риск нового расхождения на границе окна.
- Считать наличие конца подтверждением завершения — для будущих работ он описывает заявленное окно.
- Пересчитывать только плановые работы — не покрывает будущие инциденты, открытые окна и окончание аварии.
- Запрашивать данные или переключать индикатор таймером — добавляет сеть, обработку сна вкладки и временных границ ради сценария, которому достаточно уточнения при открытии и навигации.

## Последствия и владельцы

- Фазы, совместимость публичных значений и `is_active`, приоритет состояния, календарная проекция и свежесть публикации определены в [status-lifecycle](/openspec/specs/status-lifecycle/spec.md). Расписание и шаги публикации принадлежат [CI/CD](/.github/workflows/ci.yml).
- В [#434](https://github.com/silentroach/kpshelkovo/issues/434#issuecomment-5468330657) владелец выбрал установку маркера «сегодня» при подключении календаря к DOM; [PR #455](https://github.com/silentroach/kpshelkovo/pull/455) удалил минутный таймер. Это уточнило клиентскую границу решения: новая календарная проекция появляется при публикации.
- Общий вычислитель позволяет представлениям обновляться в собственные моменты. Ленивый таймлайн сохраняет отдельный жизненный цикл; в [#741](https://github.com/silentroach/kpshelkovo/issues/741#issuecomment-5757167840) владелец отклонил усложнение ради устранения повторного прохода при навигации после оценки его стоимости.
