# ADR-031: Единый жизненный цикл status-событий

## Статус

Принят

## Дата

2026-08-26

## Контекст

Состояние status-события вычислялось независимо в mapper, публичном DTO, подписях интерфейса, сводке сервиса, индикаторе шапки и клиентском таймлайне. Правила расходились на будущих плановых работах с `ended_at`: API считал наличие конца признаком завершения, а интерфейс показывал событие запланированным.

Статическая сборка создавала еще один риск. В HTML сохранялось состояние на момент сборки, а отдельные клиентские элементы пересчитывали только окна `maintenance`. После окончания окна индикатор шапки мог стать зеленым, пока карточка сервиса и событие оставались активными. Будущий `incident` без `ended_at` вообще не участвовал в клиентском пересчете.

## Решение

Использовать один чистый вычислитель жизненного цикла для всех status-поверхностей. Окно события полуоткрыто:

- `scheduled`, если `now < started`;
- `active`, если `started <= now` и `ended` не задан или `now < ended`;
- `resolved`, если `ended` задан и `now >= ended`.

Mapper вычисляет `phase` на переданном ему времени сборки. Доменная модель хранит `phase`, а не отдельный флаг активности. Публичный DTO, сводки и серверные подписи получают машинное значение, `is_active` и человекочитаемую подпись из этого phase.

Для HTML на клиент передаются минимальные окна всех событий, которые еще могут быть активными после сборки: `kind`, `start` и optional `end`. При загрузке страницы и после Astro-перехода шапка и карточки сервисов один раз пересчитывают состояние тем же вычислителем. Таймеры и дополнительные запросы не добавляются.

Публичные значения `active`, `resolved`, `scheduled`, поле `is_active` и существующая JSON Schema сохраняются.

## Рассмотренные альтернативы

### Исправить только публичный DTO

Это устранило бы сочетание `phase: resolved` и `phase_label: запланировано`, но оставило бы независимые правила в UI и сводках. Следующее граничное состояние снова потребовало бы нескольких согласованных правок.

### Считать `ended` подтверждением завершения

Для `maintenance` поле означает заявленный конец будущего окна, поэтому наличие `ended` само по себе не говорит, что событие уже завершилось.

### Оставить клиентский пересчет только для maintenance

Это не покрывает incident с будущим началом, incident без конца и переход красного статуса в зеленый после указанного конца. Частичный пересчет продолжал бы создавать противоречия.

## Последствия

- Границы начала и конца одинаковы в API, HTML, шапке, карточках сервисов и таймлайне.
- Будущие события остаются в полной публичной ленте и `incident_ids`, но не входят в `active` и активные списки сервисов.
- Открытая вкладка не меняет состояние по таймеру; пересчет происходит при загрузке и Astro-переходах, как и раньше.
- ADR-010 заменен этим решением: индикатор теперь учитывает окна всех status-событий, а не только плановых работ.
