# ADR-004: Lighthouse-профиль без аналитики

## Статус

Принят

## Дата

2026-05-15

## Контекст

Яндекс Метрика нужна для рабочей аналитики, но её сторонние cookie и `inspector-issues` снижают Lighthouse Best Practices. Если измерять только боевой сайт, принятые замечания интеграции мешают замечать регрессии собственного кода; отключение Best Practices целиком потеряло бы полезный сигнал.

## Решение

- Боевая сборка подключает Метрику по версионируемому build-time конфигу; профиль `production` проверяет фактически опубликованный сайт. Клиентский runtime не читает флаг.
- Плановый профиль `static` собирает отдельный артефакт с `LIGHTHOUSE_DISABLE_ANALYTICS=true`, отключая вставку Метрики только для аудита. Флаг учитывается в build cache как env-зависимость.
- Профиль `production` допускает более низкий порог Best Practices из-за принятой интеграции, `static` сохраняет более строгий ориентир. Все текущие assertions имеют уровень `warn`: это диагностические пороги, а не блокирующий gate по баллам.
- Сводка явно показывает профиль: `static` принудительно выключает аналитику, `production` проверяет опубликованную конфигурацию без вывода о состоянии счётчика из env runner-а. Найденные замечания Метрики поясняются как ограничение стороннего сервиса; статический профиль помогает отделить его влияние.

## Пересмотр 12 октября 2026 года

Первоначальное решение сохраняло Метрику во всех боевых сборках. По просьбе владельца добавлен build-time переключатель для временной паузы и обратного включения через сборку и deploy. Lighthouse override сохранён; разрешения CSP и параметры интеграции не меняются. Порядок управления — в [README](/README.md#яндекс-метрика).
