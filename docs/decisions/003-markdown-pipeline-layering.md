# ADR-003: Слоистый Markdown-рендер

## Статус

Принят

## Дата

2026-05-14; граница строковой типографики уточнена 2026-10-07.

## Контекст

Markdown на сайте объединяет универсальную обработку текста и доменные связи. GFM, безопасный HTML-вывод и типографика нужны независимо от раздела. Упоминания и обратные ссылки зависят от реестров сущностей, их URL, падежных форм и проверок при сборке.

Прямой вызов общего рендера для body markdown может дать внешне корректный HTML, но потерять упоминания и доменную валидацию. Перенос этих проверок в общий пакет, в свою очередь, связал бы его с данными и маршрутами конкретного приложения.

Строковая типографика нужна также коротким подписям, подсказкам статуса и сравнению редакций независимо от Markdown. Её клиентский вход должен обходиться без Markdown-парсеров и нативного Satteri, сохраняя общие с Markdown правила.

## Решение

- `@shelkovo/markdown` отвечает за универсальный Markdown-to-HTML pipeline и безопасный вывод, извлечение текста, генерацию Markdown и AST-адаптеры `rehypeTypograf`/`satteriTypograf`, включая коррекцию контекста дерева.
- `@shelkovo/typography` владеет строковыми API и единственной регистрацией общих правил Typograf. Его корневой вход пригоден для клиента и сервера, не зависит от Markdown, Satteri и приложения. Markdown-адаптеры используют это ядро и его общие определения; направление зависимости — `markdown → typography`.
- Приложение выбирает места применения типографики и владеет CSS сгенерированных обёрток по [ADR-034](/docs/decisions/034-native-css-architecture.md).
- Body markdown сайта проходит через одну обёртку приложения. Она объединяет доменную предобработку и вызов пакетного рендера; подготовка текста для mentions/backlinks использует тот же слой.
- Реестры сущностей, доменные ошибки и обратные ссылки остаются в приложении. Новые разделы расширяют общую обёртку, сохраняя единое поведение Markdown.

## Рассмотренные альтернативы

- **Поместить упоминания в общий пакет.** Это устранило бы риск забыть предобработку, но привязало бы пакет к реестрам и маршрутам сайта.
- **Выбирать renderer на каждой странице или завести независимые pipelines разделов.** Локальная свобода увеличивает риск тихих расхождений в упоминаниях, типографике и HTML-безопасности.
- **Закрыть весь пакетный API обёрткой приложения.** Это потребовало бы проксировать и низкоуровневые helpers, которые не рендерят body markdown и не обходят доменные проверки.
- **Оставить строковое ядро в Markdown-пакете с клиентским subpath.** Это изолировало бы клиентскую сборку, но сохранило бы неверного владельца строковой типографики. Два пакета отражают самостоятельные слои и сохраняют один набор правил.

## Последствия

Оба общих пакета остаются независимыми от данных сайта, а приложение имеет один вход для доменного Markdown. Строковые потребители напрямую используют `@shelkovo/typography`, AST-потребители — `@shelkovo/markdown`; типографические правила сохраняют единственного владельца. Обёртка требует явного использования в местах рендера, зато изменения общей обработки не приходится синхронизировать между разделами. Тонкие функции разделов над этой обёрткой совместимы с решением.
