# ADR-026: IndexNow после статического deploy

## Статус

Заменён ADR-027

## Дата

2026-08-16

## Контекст

`kpshelkovo.online` собирается Astro как статический сайт и публикуется на VPS через `rsync --checksum --delete`. Sitemap описывает полный набор канонических индексируемых страниц, но сам по себе не уведомляет поисковые системы сразу после изменения страницы.

IndexNow решает именно задачу уведомления об уже произошедшем добавлении, изменении или удалении URL. Протокол требует:

- стабильный ключ из 8–128 разрешённых символов, который не совпадает с корневым текстовым маршрутом сайта;
- доступный UTF-8 key-файл в корне того же host;
- не более 10 000 URL в одном POST;
- URL только подтверждённого host;
- отправку изменённых URL вместо повторной отправки всего сайта.

Полный список канонических индексируемых URL уже формируется при сборке sitemap, а точный список файлов, которые изменит текущий deploy, уже умеет определять `rsync`. Отдельный CMS hook или постоянно работающий сервис для статического сайта не нужен.

## Решение

Хранить стабильный `INDEXNOW_KEY` в repository secrets GitHub Actions, но не в git. После production build deploy-скрипт проверяет формат ключа и создаёт `dist/www/{key}.txt`. Файл попадает в тот же `rsync`-артефакт, что и сайт.

Во время `astro build` собирать прошедшие sitemap-фильтры URL в приватный JSON-манифест `apps/www/dist/indexnow-urls.json`. Манифест формируется из результатов того же `serialize`-прохода, что и sitemap, но лежит вне публичного `dist/site`: deploy использует готовый список напрямую и не читает сгенерированный XML обратно.

Перед фактической синхронизацией выполнять dry-run с теми же checksum, delete и filter options, что и у основного `rsync`. До успешного ответа IndexNow накапливать itemized changes в служебном файле deploy-пользователя на VPS вне web root. Каждый повторный deploy добавляет к нему новый diff, поэтому уже опубликованные URL не теряются при перезапуске job. Из накопленного списка выбирать только маршруты, представленные файлами `index.html`:

- добавленный или изменённый маршрут отправлять, только если его абсолютный URL присутствует в приватном URL-манифесте новой сборки;
- удалённый маршрут отправлять даже после исчезновения из нового манифеста, чтобы поисковая система быстрее увидела 404;
- не отправлять изменения assets, Markdown, JSON, RSS, key-файла, verification-файлов и HTML с `noindex`, отсутствующего в манифесте.

После `rsync` и production smoke-check сначала загрузить публичный key-файл с `https://kpshelkovo.online` и проверить точное содержимое. Только после этого отправлять изменённые URL на глобальный endpoint `https://api.indexnow.org/indexnow` пачками до 10 000 URL. Успехом считать ответы 200 и 202; только после такого ответа удалять накопленный манифест. Остальные ответы завершают deploy job ошибкой, не скрывая проблему уведомления.

Nginx обслуживает только корневые имена, подходящие под формат IndexNow key, как `text/plain` с `Cache-Control: no-store`. Это исключает устаревший ответ при ротации и не расширяет CSP: внешний POST выполняет GitHub runner, а не браузер.

## Рассмотренные альтернативы

### Отправлять весь sitemap после каждого deploy

Это проще, но нарушает назначение IndexNow, расходует crawl quota и повторно уведомляет о неизменившихся URL. Полный инвентарь сайта остаётся задачей sitemap.

### Вычислять изменения только по `lastmod`

У части статических страниц нет доменной даты обновления. Сравнение sitemap пропустило бы реальные изменения таких страниц. Checksum-diff готового HTML соответствует фактически опубликованному артефакту и не требует параллельного реестра дат.

### Вызывать IndexNow во время Astro build

Build ещё не опубликован: key-файл и новые страницы могут быть недоступны с production host. Вызов до успешного deploy создаёт гонку между уведомлением и публикацией.

### Коммитить key-файл в `public`

Это упростило бы сборку, но зафиксировало бы реальный ключ в истории git и усложнило ротацию. Генерация из repository secret оставляет ключ вне исходников, при этом после deploy он становится доступен поисковым системам по требованию протокола.

## Последствия

- Каждый успешный content deploy уведомляет IndexNow только о канонических HTML-маршрутах, которые действительно изменил или удалил `rsync`.
- Первый deploy после включения IndexNow не отправляет старые неизменившиеся страницы: они продолжают обнаруживаться через sitemap, как рекомендует протокол.
- Изменение общего layout может изменить много HTML-файлов и обоснованно создать большую отправку; helper автоматически разобьёт её по лимиту протокола.
- Без `INDEXNOW_KEY`, публичного key-файла или успешного ответа IndexNow production job завершится ошибкой. Уже синхронизированный статический сайт при этом остаётся доступен, а накопленный манифест позволяет безопасно перезапустить job без потери URL.
- При ротации достаточно заменить repository secret. Следующий build опубликует новый файл, а `rsync --delete` удалит старый.
