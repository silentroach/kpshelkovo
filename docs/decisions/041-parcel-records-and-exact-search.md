# ADR-041: Участки отдельно от мест, полнотекстовый поиск в Pagefind

## Статус

Принят, уточнён 2026-09-25 и 2026-09-28; дополняет [ADR-013](013-raw-domain-public-data-boundary.md), [ADR-025](025-static-full-text-search-with-pagefind.md), [ADR-028](028-markdown-first-places-map.md) и [ADR-039](039-shared-yandex-maps-runtime-and-preview.md).

## Дата

2026-09-22

## Контекст

Житель ищет номер застройщика и границы нынешнего участка. Место по ADR-028 имеет карточку, маркер и редакционное описание; участок имеет кадастровую геометрию и может объединять несколько обозначений. Pagefind по ADR-025 ищет содержательные HTML-страницы, а отдельные карточки для тысяч участков не нужны. Точный фильтр по номерам участков требовал дополнительного запроса и заметно увеличивал холодный трафик.

## Решение

- Хранить позиции генплана в отдельной Markdown-коллекции: одна редакционная запись с основным кодом и подтверждёнными алиасами может относиться к одному или нескольким самостоятельным нынешним кадастровым участкам. Каждый кадастровый номер, исходный контур и площадь остаются отдельными; карта показывает одну позицию и сохраняет межи. Цена и статус предложения относятся к позиции, не к каждой её кадастровой части. Снимки источников и основания соответствий остаются отдельно от записей; неопределённые связи не выводятся из близости меток. Raw-схемы, доменная модель и публичное представление карты следуют ADR-013.
- Добавить выключенный по умолчанию слой к существующей карте Яндекса, не расширяя сущность места, её маршруты и граф упоминаний. Подготовить геометрию из общего набора с единой поправкой координат, затем разделить на четыре проверенных JSON для интерфейса карты: `/map/data/parcels/{shf,shv,shp,shr}.json`. Загружать только нужные части по запросу; в геометрических JSON передавать необязательный исходный статус предложения застройщика для слабой заливки контуров и сероватой капсулы недоступного участка. Свободный и забронированный участки выглядят одинаково, проданный и участок без статуса остаются нейтральными. Цену, историю, признаки и редакционные заметки не включать в геометрию; поправка не меняет исходный кадастр.
- Для свободной или забронированной позиции собирать из той же редакционной записи отдельный JSON `/map/data/parcels/details/<основной-код>.json` с площадью при её наличии и полной сохранённой историей цен с датами наблюдений в исходном порядке. Загружать его только при открытии попапа выбранной позиции; показывать площадь и последнюю сохранённую полную цену, а не историю. У брони рядом с номером показывать тихий замок с доступным именем «Забронирован». Отсутствующие сведения обозначать явно, не вычисляя замену. Это вспомогательные данные карты, не общий feed или каталог участков.
- Добавлять действующие позиции непосредственно в Pagefind после индексирования HTML, по одной записи без геометрии на позицию. Сборщик читает все четыре JSON геометрии, проверяет каждый по публичной схеме и уникальность кодов и алиасов в объединённом наборе. Полный и короткий варианты основного кода и подтверждённых алиасов включать в поисковый текст записи; служебную подпись раздела не индексировать как слово каждой позиции. Для обозначений одного полнотекстового запроса достаточно: позиции возвращаются вместе со страницами в общем порядке без обязательного первенства точных совпадений. Результат ведёт по основному коду на `/map/?p=<полный-код>`, а карта разрешает прямую ссылку по JSON соответствующей части без поискового индекса. Поиск не загружает историю цен.
- Выбор позиции любого статуса сохранять без таймера и отражать основным кодом в `p` без нового шага истории браузера. Прямая ссылка восстанавливает выбор; выбор другой позиции заменяет код в `p`, а закрытие попапа, Escape на карте, клик по пустой карте, выбор места или выключение соответствующей части снимают выбор и удаляют `p`. Перемещение и масштабирование карты выбор не снимают.

## Почему так

Помещать участки в places означало бы создавать фиктивные карточки и менять смысл маркеров, видимости и backlinks. Отдельные HTML-страницы участков требовали бы создавать карточки ради поиска. Custom records Pagefind сохраняют поиск без геометрии и дополнительного словаря; короткие обозначения индексируются явно, потому что токенизация полного кода не обеспечивает их поиск. Отказ от отдельного точного фильтра сокращает холодную загрузку индекса. Четыре файла позволяют загружать геометрию нужной части, сохраняя общий редакционный источник карты и поиска; сведения и растущую историю цены не стоит загружать вместе с геометрией всей части. Отдельный JSON даёт сведения только выбранной позиции. Эти файлы служат интерфейсу карты, а не отдельным каталогом участков для агентов. Прежний `/map/data/parcels.json` удаляется без общего feed и перенаправления; агентской точкой входа остаётся Markdown-индекс карты.

## Последствия

- Поиск и карта получают представления одного редакционного набора через четыре проверенных файла геометрии; отсутствующий или повреждённый файл либо повторяющийся код или алиас в объединённом наборе останавливает сборку поискового индекса. Сведения для попапа публикуются отдельно по основному коду подходящих позиций и не расширяют эти файлы или поисковый индекс. Новый снимок проходит редакционную проверку до публикации. Размер и холодный трафик индекса нужно оценивать вместе с удалённым словарём, а не считать уменьшение числа файлов экономией байтов.
- Префиксы и цифровые фрагменты могут находить несколько участков по обычной релевантности Pagefind; они не расширяются отдельным правилом точного поиска. Подтверждённые алиасы остаются в доменной модели и поясняются при совпадении с запросом.
- Участок не получает HTML-карточку и не становится местом. Полная история цены свободной или забронированной позиции публикуется в её JSON, но в попапе видна только последняя сохранённая сумма; признаки и заметки остаются в редакционных данных.
- Окраска остаётся второстепенной подсказкой из сохранённого снимка: она не подтверждает собственность и актуальную доступность сделки. Отсутствие статуса нельзя принять за продажу; карта не даёт ответа по цвету без проверки первоисточника.
