# Обновление участков

Запускайте команды из корня workspace. Рабочие снимки лежат в `apps/www/src/data/parcel-sources/`, записи — в `apps/www/src/data/parcels/<часть>/<первая буква>/<короткий номер>.md` (например, `shr/l/l43.md`). Публикация происходит обычной сборкой сайта после ревью diff; скрипт сам ничего не публикует.

## Генпланы

- `pnpm parcels:update genplans` получает все четыре страницы `dgtime.ru`, извлекает JSON из единственного присваивания `window['houses_data']` и проверяет всю партию до записи. Он читает сохранённый кадастр, не запрашивая НСПД. При сетевой ошибке, незнакомом статусе или признаке исправьте причину и запустите команду заново; ошибка не означает исчезновение участков.
- `pnpm parcels:update genplans --snapshot apps/www/src/data/parcel-sources` повторяет обработку четырёх уже сохранённых файлов `genplans/{shr,shf,shp,shv}.json` с их исходным временем наблюдения. Можно указать другой каталог такой же структуры. Более старый снимок нельзя принимать поверх нового; для отката используйте Git.

## Кадастр

1. Откройте `https://nspd.gov.ru/map` в браузере с рабочим доступом. Возьмите `queryRing4326` и endpoint из принятого `apps/www/src/data/parcel-sources/nspd.json`, если границы области не изменились. Из контекста вкладки НСПД отправьте `POST` на endpoint с `Content-Type: application/json` и телом следующей формы (здесь `nspd` — содержимое принятого `nspd.json`):

   ```js
   const body = {
     categories: [{ id: 36368 }],
     geom: {
       type: 'FeatureCollection',
       features: [
         {
           type: 'Feature',
           properties: {},
           geometry: {
             type: 'Polygon',
             coordinates: [nspd.queryRing4326],
             crs: { type: 'name', properties: { name: nspd.queryCrs } }
           }
         }
       ]
     }
   };
   ```

   `36368` — ID категории при первой выгрузке; перед новой проверьте его по запросам портала. Параметр endpoint `typeIntersect=fullObject` возвращает целые объекты, в том числе за пределами запрошенного кольца. Отдельный доступ к НСПД может возвращать HTTP 403: это отказ, а не пустая выборка.

2. Проверьте HTTP 200, `FeatureCollection`, отсутствие ошибок и обрезания ответа, наличие целых `Polygon`/`MultiPolygon` с `EPSG:3857`, идентификаторов и кадастровых номеров. Проверьте охват всех четырёх частей: сравните общий ответ с объединением ответов по меньшим перекрывающимся областям без повторного счёта ID. Сравните число объектов и границы области с прошлым снимком. Если проверить полноту нельзя, не принимайте новый ответ как основание для удаления файлов.
3. В отдельном каталоге подготовьте `nspd.ndjson` (по одному исходному `Feature` на строку: `type`, `id`, `geometry` и `properties.cadastralNumber`, `area` при наличии, `status`) и `nspd.json` по форме текущего рабочего снимка. Сохраните URL источника и endpoint, фактическую дату получения `capturedOn`, время сохранения `savedAt`, CRS, `queryRing4326`, `viewportBounds3857`, проверенное количество `response.featureCount` и `response.coverageVerified: true`. Если изменили область — явно проверьте и покажите её изменение в diff. Не выдавайте время записи файла за время запроса. Исходную геометрию не сдвигайте и не округляйте.
4. Запустите `pnpm parcels:update nspd --snapshot <каталог>`. Режим использует последние принятые генпланы, не обращается к ним и не добавляет новую дату к старой цене. Повторите с тем же каталогом для проверки воспроизводимости.

Первый кадастровый снимок от 2026-09-22 имел `coverageVerified: false`; его сменил проверенный снимок от 2026-09-24. Для следующих обновлений проверяйте охват заново: прежняя проверка не подтверждает полноту нового ответа.

## Разбор несопоставленных обозначений по запросу

Эту процедуру запускают отдельно от обычного импорта. Правила действующих участков — в `openspec/specs/parcel-records/spec.md` и `openspec/specs/parcel-updates/spec.md`; проверенные редакционные связи хранятся в `apps/www/src/data/parcel-sources/matches.yaml`. Перед записью связи проверьте снимки, привязку, временное наложение, увеличенные скриншоты и контрольные точки. Исследовательские изображения, HTML и промежуточные расчёты не попадают в набор участка.

1. Прочитайте принятые генпланы, НСПД и `matches.yaml`. Получите текущий остаток и конфликты через `pnpm parcels:update genplans --snapshot apps/www/src/data/parcel-sources`: обновлятор использует существующее разрешение связей, повтор снимков не должен менять записи. Различайте отсутствие ссылки в генплане, номер вне принятого кадастрового снимка и изменившееся подтверждение. Запишите даты каждого источника и число случаев по четырём частям. Если живой генплан изменился, сначала примите целую партию обычным `pnpm parcels:update genplans`, проверьте diff и пересчитайте остаток.
2. Получите по страницам генпланов из принятых снимков JPG-подложки, HTML-метки `data-id`, их позиционные классы в `css/positions.css` и встроенный каталог `window['houses_data']`. Для каждого `id` проверьте `square_value` и исходный кадастровый номер каталога с помощью Zod, сопоставьте номер с принятым генпланным JSON; не сохраняйте персональные поля каталога. Запишите отдельно площадь в статичном HTML `<p class="square">` и площадь метки **после загрузки страницы**. `data-square` может быть пустым даже при известной площади. Если подписи расходятся с `square_value`, покажите оба свидетельства и их происхождение: для сравнения используйте проверенное значение каталога, которое обновляет метку, а при его отсутствии или ошибке выясните актуальную площадь у источника либо не используйте её как подтверждение. Например, у R63 статичный HTML показывает 9,73 сотки, каталог и обновлённая метка — 9,25; у R65 — 11 и 10,71 соответственно. Площадь контура НСПД читайте **только из принятого кадастрового снимка**, отдельно от генплана; не переносите исследовательскую площадь в рабочий генпланный JSON. В CSS могут быть кириллические буквы даже при латинском `data-id`: связывайте позицию с классом самой метки. Отсутствие HTML-метки фиксируйте как отсутствие координаты, а не как исчезновение обозначения. Прямые совпадения номера с одним контуром НСПД дают опорные пары; спорные и уже подтверждённые объединения не используйте как прямую опору.
3. Для каждой части отделите опорные пары от **независимых контрольных** до подбора привязки. Контроль должен покрывать края картинки и районы проверяемых обозначений. Подберите аффинное преобразование координат метки в процентах в `EPSG:3857`: `(x,y) = projectedOrigin + matrix × ([left%,top%] − imageOriginPercent)`. Центр полигона считайте по площади с учётом всех частей `MultiPolygon` и отверстий. Для численной устойчивости перед расчётом площадного центра вычитайте координату первой вершины из всех вершин кольца, затем возвращайте её к результату: прямой расчёт с координатами `EPSG:3857` в миллионах искажал некоторые прежние оценки ошибки контроля. Исходные геометрии НСПД и поправку отображения в Яндекс Картах не меняйте. Исторические параметры есть в Git (`3b74469d^:docs/research/parcel-map/capture.json`), но новую картинку и CSS проверяйте заново. Подготовьте временный автономный HTML: JPG естественного размера и SVG контуров с тем же `viewBox`, обратное преобразование геометрии EPSG:3857 в пиксели, все кольца и отверстия (`fill-rule: evenodd`). Откройте наложение, проверьте совпадение границ и сделайте читаемые увеличения районов каждого кандидата. Сверьте местные ошибки независимых контрольных точек в метрах `EPSG:3857`. Общий процент попаданий не подтверждает кандидата у соседнего контура.
4. Для каждого остатка используйте перенесённую метку только для **поиска кандидатов**: на увеличении проверьте все кольца, нарисованные межи, последовательность соседних обозначений, дороги, уже связанные коды, площади генплана и НСПД, возможность объединения или раздела. Небольшая невязка рисунка и контура либо разница площадей менее сотки не отвергает и не подтверждает связь автоматически: если независимый контроль района, межи и соседи однозначно выделяют один контур, объясните расхождение в основании; если остаётся соседний кандидат — ищите дополнительные свидетельства или оставьте обозначение нерешённым. Попадание в общие земли, необъяснённое большое противоречие площади либо близость метки к нескольким участкам не подтверждает отдельный участок. Номер вне локального снимка проверьте поиском на `https://nspd.gov.ru/map` и по расположению: отказ 403/429/502 и отсутствие в области выгрузки не означают, что номера нет в НСПД. Если требуется новый контур, сначала примите целую проверенную партию по разделу «Кадастр», а не один объект без проверки охвата.
5. Однозначную связь запишите в `matches.yaml` с **каждым** полным кодом, нынешним номером из НСПД, исходной строкой или `{ absent: true }`, датой, URL и датами источников, позициями, проверенными опорными и контрольными кодами с локальной ошибкой, параметрами привязки, границами, соседями, площадями и объяснением расхождений. Несколько обозначений одного контура объединяйте в одну запись, включая уже напрямую связанное обозначение; при новом номере явно выбирайте `primary_code` с учётом заметок и истории. Если одна позиция подтверждённо охватывает несколько **отдельных** кадастровых участков, запишите вместо `cadastral_number` список `cadastral_numbers` с каждым нынешним номером. Сверьте все межи, соседей и площади; суммы площадей и попадания метки недостаточно. При повторном импорте убедитесь, что присутствуют все составляющие: исчезновение одной или изменение исходной ссылки делает прежнее подтверждение неприменимым, состав и сохранённую историю не меняйте молча. `price_source_code` с `price_evidence` ставьте лишь при доказанной цене **целого**. Если доказательств недостаточно, перечислите коды, конкретное противоречие или недостающие сведения и вопрос владельцу; не записывайте предположение. Запустите `pnpm parcels:update genplans --snapshot apps/www/src/data/parcel-sources` для применения, затем повторите с теми же снимками. Сверьте обе выдачи, Markdown-записи, заметки/историю, исходные координаты НСПД и полный `git diff`: второй проход не должен менять файлы или историю. Итоговые количества и вопросы держите в PR, а основания каждой связи — в реестре.

Если источники изменились, прими их по действующей инструкции и пересчитай остаток.

```text
Сам получи HTML-метки, positions.css, JPG, встроенный houses_data и принятую геометрию НСПД. Проверь по id исходные номера и square_value каталога с Zod без персональных полей; сравни площадь из статичного HTML с отрисованной после загрузки подписью и каталогом (контрольные примеры: R63 — 9,73 против 9,25 сотки, R65 — 11 против 10,71). При расхождении сохрани обе подписи и происхождение значений, сопоставляй проверенный каталог с площадью из принятого снимка НСПД. Привяжи текущий генплан по прямым совпадениям с независимыми контрольными участками у краёв и в районах кандидатов; сделай и проверь временный HTML с наложением. Сделай читаемые увеличения небольших групп кодов и для каждого сверь нарисованные межи, дорогу, соседей, площади, уже связанные обозначения и объединения. Небольшое смещение подложек или разница менее сотки сами по себе не решают исход: однозначность дают местный контроль и совпадение окружения. Сохрани убедительно проверенные связи с источниками и конкретными основаниями в matches.yaml, неоднозначные обозначения перечисли с причиной и вопросом владельцу, не назначая связь по одной метке.

Примени подтверждения обычным импортом принятых снимков, повтори его для проверки неизменности файлов и истории, проверь записи, координаты и полный diff. В PR сообщи даты, число случаев по причинам и частям, установленные связи, контрольные участки, ошибки привязки и нерешённые вопросы. Работа по этому запросу сама по себе не разрешает публикацию или изменение согласованной модели; в explore mode ничего не записывай.
```

## Ревью результата

- Прочитайте stdout: даты и URL обоих источников, добавления, удаления, переименования, изменения геометрии и сведений, несопоставленные обозначения и конфликты. Сопоставьте `git diff` снимков, подтверждений и Markdown-записей. Несопоставленный номер не становится участком по близости к контуру. Если исходная кадастровая ссылка подтверждённой пары изменилась, выясните причину и обновите `matches.yaml` вместе с основанием только после проверки. Если нужен удалённый файл, восстановите его из Git до повтора: иначе не сохранятся его заметки и история цены.
- Для объединения с новым кадастровым номером укажите `primary_code` в `matches.yaml`, осознанно выбрав сохраняемую редакционную запись. Цену старой части не считайте ценой целого: `price_source_code` и `price_evidence` добавляйте только после подтверждения общей цены. При расхождении статусов скрипт сохраняет прежнее подтверждённое поле и показывает конфликт. Признаки обновляются отдельно. При разделе заметки и история прежнего целого остаются в Git, а новые записи не получают их автоматически.
- При изменении состава подтверждённой группы импорт сообщает конфликт идентичности. После нового пространственного подтверждения разберите прежнюю запись и её историю вручную, сохраните в Git, удалите устаревший файл и только затем примените новое подтверждение. Не переносите историю старой группы на новый состав автоматически.
- При ошибке получения/формата не должно быть изменений. При отказе записи отдельных файлов общая транзакция не предусмотрена: сначала проверьте частичный `git diff`, затем восстановите согласованный набор снимков и записей через Git и повторите команду. Не перезапускайте поверх несовместимой частично записанной партии. Повтор неизменённых входов должен показать нулевые добавления, удаления, переименования и изменения истории; нерешённые номера могут оставаться в отчёте.
