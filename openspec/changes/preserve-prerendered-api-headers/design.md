# Design

## Context

Мотивация и границы — в [proposal](/openspec/changes/preserve-prerendered-api-headers/proposal.md), публичное поведение — в [delta spec](/openspec/changes/preserve-prerendered-api-headers/specs/static-api-response-metadata/spec.md).

`apps/www` использует Astro 7.3.1 с `output: 'static'`. Обработчики задают заголовки на `Response`, а production nginx обслуживает файлы. Исследование нашло 94 endpoint-модуля, включая 26 параметризованных: Markdown, текстовые путеводители, JSON, каталоги API, RSS, ICS и vCard. Это снимок исходников, не количество URL и не ограничение генератора. Исходные 15 URL из issue входят в 20 JSON endpoints пяти API-семейств.

По решению владельца генерация охватывает все prerendered endpoints, а не allowlist разделов. HTML-представления и файлы из `public/` не входят в выборку. У Compare Schema и OpenAPI сейчас нет `Link`; эти два обработчика должны использовать существующий `links(root)` основной ленты.

[ADR-011](/docs/decisions/011-public-surface-registry.md) оставил nginx ручной реализацией с возможностью позже пересмотреть генерацию отдельных фрагментов. [ADR-009](/docs/decisions/009-markdown-accept-negotiation.md), [ADR-013](/docs/decisions/013-raw-domain-public-data-boundary.md), [ADR-033](/docs/decisions/033-integrated-tariff-comparison-section.md) и [ADR-036](/docs/decisions/036-llms-v2-guides.md) сохраняют согласование Markdown, границы данных, принадлежность Compare единому приложению и выбор наиболее конкретного путеводителя. Новый ADR закрепит генерацию только locations статических endpoints, не всего nginx или всего реестра поверхностей.

Владелец запросил отдельный PR только с планом. Этот документ не разрешает реализацию: следующая сессия читает change, состояние основной ветки и получает явное разрешение владельца.

## Goals / Non-Goals

**Goals:**

- Передавать фактические метаданные всех статических endpoints без повторного исполнения обработчиков или отдельного обхода сайта.
- Автоматически получать конкретные пути параметризованных маршрутов из сборки, а не заново исполнять `getStaticPaths`.
- Подключать один фрагмент точных locations и убрать заменённые правила, сохранив операционную политику nginx.

**Non-Goals:**

- Генерация HTML-locations, TLS, редиректов, ACME, proxy/media, Pagefind или правил файлов из `public/`.
- Новый описательный реестр media type и discovery-связей, middleware, собственный prerenderer или SSR.
- Изменение тел документов, их сериализации, URL, DTO, схем либо срока хранения старых `/static/` ресурсов.

## Decisions

### 1. Получать все endpoints через штатный staticHeaders API

Локальная интеграция в `/apps/www/src/integrations/` регистрирует минимальный static-only adapter: `entrypointResolution: 'auto'`, `buildOutput: 'static'`, `staticHeaders: true` и поддержку статического output. Runtime/server entrypoint не нужен.

В `astro:build:generated` Astro передаёт `routeToHeaders` — карту пути в `{ headers: Headers, route: IntegrationResolvedRoute }`. В установленном пакете проверены публичные типы и реализация: карта получает `response.headers` во время штатного prerender. Документация: [staticHeaders](https://docs.astro.build/en/reference/adapter-reference/#staticheaders).

Выборка определяется типом `endpoint` и признаком prerender в метаданных Astro, без списка разделов, расширений файлов или фиксированного числа маршрутов. HTML и редиректы не выбираются. Фрагмент использует конкретные pathname из карты, включая результаты `getStaticPaths`, отсортированные для воспроизводимости. На каждый выбранный pathname приходится один exact location; пустой или неполный обязательный результат не даёт успешный deploy.

Реестр публичных поверхностей помогает проверить ожидаемые контракты, но не определяет полноту выборки: не все endpoints зарегистрированы отдельной записью, а шаблоны маршрутов не перечисляют все URL. Основные 15 URL из issue проверяются отдельно как обязательная API-выборка. Остальное покрытие сверяется с картой endpoints самой сборки, а не с числом 94.

Альтернативы:

- Ручной nginx с тестами соответствия сохраняет повторение заголовков и правил для параметризованных файлов.
- Генерация из реестра потребовала бы восстановить фактические пути и специфичные заголовки, например имя vCard; ответы уже содержат их.
- Обёртка prerenderer или middleware сложнее штатного `staticHeaders` и не нужна.

### 2. Разделить заголовки представления и операционную политику

Из фактических ответов переносятся `Content-Type` со всеми параметрами, `Link`, `Content-Disposition`, `X-Robots-Tag` и `Vary`. Это набор метаданных текущих endpoints; дополнительные application-owned заголовки нельзя молча потерять — неподдерживаемый заголовок должен вызвать понятную ошибку сборки и потребовать явного решения о его публикации. Серверные и транспортные поля вроде `Date`, `Content-Length`, `Content-Encoding` и hop-by-hop headers не копируются: их формирует nginx для выбранного представления. Валидация перед выпуском — через Zod.

Источник объявленных заголовков — ответ обработчика. В частности, каталог сохраняет параметр `profile`, детальная смета — свои discovery-связи, ICS/vCard — своё имя скачивания, Markdown — директивы индексирования. MIME не выводится из расширения, обычный JSON не становится Schema из-за похожего имени файла.

Кеширование, security headers, настройки логов и дополнения, которых нет в ответе обработчика, остаются операционной политикой. Её компактная часть для генерируемых endpoints воспроизводит существующие правила nginx, без нового универсального реестра. Если обработчик объявляет поле, его значение не перекрывается ручной копией: для текущего Markdown без собственного `Link` политика добавляет существующий `describedby` на наиболее конкретный llms-путеводитель; выбор берётся из существующего app-helper/реестра. `Vary` объединяется без повторения токенов с нынешним `Accept` для прямых Markdown-ответов; `Accept-Encoding` по-прежнему добавляет nginx. Базовые security headers не конкурируют с application-owned метаданными.

Действующие классы доставки endpoints:

- Генерируемый Markdown: `no-cache`, `Vary: Accept`, действующий `X-Robots-Tag` и `describedby` на путеводитель.
- Compare `data/`, Map `data/` и RSS: `public,max-age=300,stale-while-revalidate=300`; у Compare/Map data отключены access/file-error logs.
- Status `data/`: `public,max-age=60,stale-while-revalidate=300`.
- API-контракты, остальные API-данные, каталоги, индексы навыков, llms/robots, events JSON/Schema и ICS: `public,max-age=3600,stale-while-revalidate=600`.
- Версионированный endpoint в `/static/`: `public,max-age=2592000,immutable`, прежние настройки логов.
- Endpoints без явного cache-control сейчас, например manifest и vCard: отсутствие явного cache-control сохраняется, новый TTL не назначается автоматически.

Эти правила различают тип/семейство ресурса, а не перечисляют все конкретные URL. Точное значение ответа `Content-Type` и application-owned заголовки остаются в обработчике; операционная часть не хранит их копий.

### 3. Выпускать один непубличный фрагмент и безопасно очистить основной nginx

Артефакт `/apps/www/dist/api-response-metadata.conf` лежит рядом с каталогом сайта, не внутри публичного `dist/site` или `/dist/www`. Turbo output `dist/**` сохраняет его вместе с результатом сборки. Главный `server` в `/ops/nginx/kpshelkovo-online.conf` включает `/etc/nginx/kps/api-response-metadata.conf`.

Каждый `location =`:

- Задаёт MIME через штатные `types`/`default_type` и charset-механизм nginx, сохраняя параметры вроде `profile` и `charset`; не использует `add_header Content-Type` и не создаёт повторный charset.
- Публикует согласованные заголовки представления и политики без конфликтующих дублей.
- Подключает существующий `/etc/nginx/kps/security.conf`, поскольку собственный `add_header` отменяет наследование стандартного nginx.
- Сохраняет прежнее кеширование, логи и наследуемую доставку сжатых представлений; файл отдаётся через `try_files $uri =404`.

Пути и значения экранируются как литералы nginx: кавычки, обратные слеши и `$` не становятся директивами или переменными; управляющие символы отклоняются. Конкретные Unicode-пути должны совпадать с нормализованным URI nginx, а percent-encoded запросы — попадать в тот же location. В этих проверках нельзя полагаться только на текстовый snapshot конфига.

Удаляются прежние exact locations, полностью заменённые генератором, и правила только для текущих endpoints. Смешанные regex/prefix сужаются только после сверки других обязанностей; одинаковые exact locations недопустимы даже при одинаковых заголовках.

Ручными остаются:

- HTML-locations, включая `@markdown`: negotiated Markdown имеет собственные `alternate`, `describedby` и `Vary`, отличные от прямого запроса `.md`.
- Правила Markdown-навыков и других статических файлов из `public/`, отсутствующих в карте заголовков.
- `/static/` fallback для сохраняемых старых поколений: текущий exact location не заменяет их срок хранения или обслуживание.
- Общие правила security, compression, скрытых файлов, ошибок, Pagefind, IndexNow ownership, ACME, перенаправлений и TLS.

### 4. Устанавливать конфигурацию согласованным комплектом

`/.github/workflows/ci.yml` передаёт построенный фрагмент отдельным `.new` вместе с конфигом сайта и `security.conf`. Отсутствие обязательного артефакта останавливает deploy до установки.

`/ops/nginx/deploy-nginx-site.sh` для главного сайта резервирует и устанавливает оба include вместе с site config; при ошибке `nginx -t` восстанавливает предыдущее содержимое либо отсутствие каждого файла и состояние enabled-site. Reload выполняется только после успешной проверки полного комплекта. Другие сайты продолжают прежний путь установки. Новые привилегированные entrypoints и разрешения sudo не нужны.

Текущий порядок «конфигурация → rsync сайта» сохраняется: публичные URL и тела не меняются. Наличие нового exact location ещё не означает, что файл уже доставлен; для впервые появляющихся URL остаётся существующее окно до rsync. При полном откате возвращаются конфиг без include, deploy script и исходники сборки; неиспользуемый файл конфигурации не участвует в ответах.

## Risks / Trade-offs

- Adapter может повлиять на output или CSP → static-only настройки, проверка структуры output и отсутствия переноса текущей nginx CSP в генерируемые application headers; сравнение клиентских JS/CSS по [инструкции анализа бандлов](/docs/development.md#анализ-клиентских-бандлов).
- Много конкретных путей увеличивает конфиг → deterministic exact locations без повторных загрузчиков; при приёмке измерить размер фрагмента и время `nginx -t`, а не вводить преждевременно regex-генератор.
- Новые MIME-параметры или Unicode могут неверно пройти nginx → проверка через реальный сервер, включая profile, charset, percent-encoded пути и сжатие.
- Очистка конфигурации может потерять nginx-only связи, negotiated Markdown или старые статические ресурсы → отдельные сценарии совместимости и сохранение fallback/`@markdown`.
- В текущей локальной среде nginx отсутствует, Docker daemon недоступен → runtime-проверка требует подходящего Linux/CI-окружения с nginx. Невыполненную проверку нельзя считать пройденной; production-конфиг валидируется в окружении deploy перед reload.

## Migration Plan

1. Опубликовать плановый PR с активным change; код, основные specs и production не менять. Issue содержит ссылку на change, согласованный расширенный объём и явную отметку «реализация отложена».
2. В отдельной сессии получить разрешение реализации и привязать его к коммиту плановых артефактов в issue. Сохранить исходное состояние документов, HTTP-политики по семействам и bundle-отчётов до изменения сборки.
3. Реализовать интеграцию для всех статических endpoints, два отсутствующих Compare `Link`, include/очистку nginx и согласованную установку/откат; выполнить задачи приёмки.
4. После приёмки реализации синхронизировать основные specs и архивировать change в ветке реализации. Открыть PR реализации с `Refs #479` и оставшейся production-проверкой.
5. После merge и deploy проверить `GET`/`HEAD` всех 15 URL из issue и представителей остальных семейств: каталоги с profile, Markdown, llms/robots, events JSON/Schema, RSS, ICS/vCard, Map JSON и версионированный static endpoint. Дополнительно подтвердить negotiated Markdown и доступность сохранённого предыдущего static-поколения. Результат записать в issue и закрыть его только при успешной проверке.
