# Proposal

## Why

В [#870](https://github.com/silentroach/kpshelkovo/issues/870) повторная проекция неизменённого кадастрового снимка дала лишний diff в последних разрядах координат участков. Та же избыточная точность возникает и в других подготовленных геоданных сайта. Владелец выбрал общий предел: не более восьми знаков после запятой у координат, которые сайт генерирует и отдаёт потребителям, при сохранении исходников без округления.

## What Changes

- Ввести общий предел в восемь десятичных знаков для числовых координат в градусах, подготовленных сайтом для HTML, Markdown companions, JSON, ссылок, структурированных данных и экспортов. Нормализовать результат после геометрических расчётов, не меняя исходные данные и внешние URL, заданные редактором.
- Округлять координаты участков при проекции НСПД в редакционные Markdown-записи; принятую геометрию EPSG:3857 в снимке НСПД не менять. Повторная обработка одного снимка не должна выдавать шум округления за изменение границы, а существенное изменение — исчезать.
- **BREAKING:** публичный Markdown companion для блока `map` больше не воспроизводит числовые координаты исходного GeoJSON побайтово: только эти значения нормализуются в опубликованной копии. Остальные исходные поля, текст и внешний URL сохраняют смысл и значения; редакционный Markdown остаётся без изменений.

## Capabilities

### New Capabilities

- `public-coordinate-precision`: общий контракт точности подготовленных числовых географических координат на публичных поверхностях сайта с сохранением исходников.

### Modified Capabilities

- `markdown-service-blocks`: уточнить сохранение исходного блока `map` в Markdown companion — исходные поля сохраняются, а публикуемые координаты нормализуются.

## Impact

- Затронуты подготовка кадастровых записей и карт, редакционного GeoJSON, представления мест, событий, контактов и сравнения поселков, а также соответствующие HTML/JSON/Markdown/JSON-LD/ICS/vCard и генерируемые ссылки с координатами. Явные редакционные и сторонние URL, произвольные упоминания координат в тексте и исходные файлы не переписываются.
- Первая нормализация затронет действующий набор Markdown-записей участков (сейчас 1620 файлов); её следует выполнять после учёта ещё открытого [PR #869](https://github.com/silentroach/kpshelkovo/pull/869), затем проверять повторный запуск и полный diff. Планирование и публикация этого PR не запускают генератор и не заменяют разрешение на реализацию.
- Нужны проверка схем после подготовки координат, точечные тесты выходов и ручное ревью одноразового diff. Проверка на production не требуется; человеческое ревью и merge остаются владельцу.
