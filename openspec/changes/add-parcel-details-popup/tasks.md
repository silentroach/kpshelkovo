# Tasks

Задачи относятся к будущей реализации в `feat/861-parcel-details-popup`. Текущий draft PR содержит только планирование. Перед началом следующая сессия читает change, issue, PR и фактическое состояние ветки и получает явное разрешение владельца на реализацию.

## 1. Сведения позиции из единого источника

- [ ] 1.1 Добавить Public DTO, отдельную Zod-схему и адаптер поверх `Parcel`, а также статический маршрут `map/data/parcels/details/[code].json.ts`. Генерировать только основные коды `available`/`reserved`; проверить целевыми тестами фильтрацию статусов, отсутствие дублей алиасов, исключение геометрии, заметок и признаков.
- [ ] 1.2 Сохранить в DTO полную историю в исходном порядке и необязательную доменную площадь. Проверить небольшими fixtures пустую историю, несколько наблюдений за один день, возврат цены к прежней сумме, составную позицию с известной суммой площадей и с отсутствующей площадью одной части; конечный DTO проверять Zod до сериализации.

## 2. Постоянный выбор и ссылка

- [ ] 2.1 Заменить таймер слоя постоянным выбором и уведомлениями для `PlaceMap`; связать снятие выбора с пустым кликом карты, Escape, другим объектом и выключением части. В тестах `PlaceMap` подтвердить сохранение выделения дольше пяти секунд для всех статусов, повторный выбор той же позиции, совместное выделение составной позиции и восстановление её статусного оформления после снятия выбора.
- [ ] 2.2 Расширить `parcel-url.ts` и интеграцию карты: записывать основной код через `replaceState`, удалять `p` при снятии выбора, сохранять остальные параметры, hash и `history.state`. Проверить обычный выбор, алиас и иной регистр, прямой переход, повторное открытие, перезагрузку с выбором и после закрытия, отсутствие лишних шагов истории и reduced motion.
- [ ] 2.3 Согласовать постоянный выбор с ожидающей геометрией и навигацией. Проверить, что неизвестный код удаляется, ошибка части сохраняет намерение повтора, выключение части или новый явный выбор отменяют старый переход, а поздний ответ не возвращает прежние камеру, выбор и URL.

## 3. Попап и отложенная загрузка

- [ ] 3.1 Добавить компактный попап для `available`/`reserved` с номером, частью, площадью и последней суммой истории; у брони добавить неброский замок с `title` и доступным именем. Проверить выбор контуром и номером, автоматическое открытие по `p`, отсутствие попапа у остальных статусов, дробные сотки, последнюю, а не максимальную цену, и явное отсутствие неизвестных значений. Видимый текст отредактировать по `humanizer-ru`.
- [ ] 3.2 Добавить запрос одного JSON, переиспользование успешных ответов и выполняющихся запросов, локальную загрузку, ошибку и кнопку повтора. Проверить отказ HTTP и разбора, восстановление, повторный выбор без лишней загрузки и поздние ответы после закрытия, замены позиции, выключения части и уничтожения карты; геометрия и `p` при ошибке сведений сохраняются.
- [ ] 3.3 Привязать попап к отображаемой позиции с обновлением при движении камеры и ограничением доступной областью карты. Проверить на широком, узком и низком экране, что drag, zoom, resize, уход опорной точки за край и исчезновение номера сохраняют попап, а закрытие, шапка, слои и штатные элементы Яндекса остаются доступны. Завершённый клик отличать от жеста перемещения.
- [ ] 3.4 Реализовать клавиатурный вход, видимый фокус, доступные оповещения и возврат фокуса к номеру либо карте. Проверить Enter/Space, Escape и крестик, приоритет Escape панели слоёв и поискового диалога, отсутствие ловушки Tab и перехвата фокуса поздним ответом. Для Svelte использовать `svelte-code-writer` и официальный MCP, повторить анализ после исправлений.

## 4. Документация и стоимость загрузки

- [ ] 4.1 Уточнить ADR-041 и раздел участков в дизайн-гайде: отдельные JSON с полной историей для свободных/забронированных, постоянный выбор, цена в попапе и тихая отметка брони. Сверить описание карты в Markdown/discovery, исправить только противоречащие этому поведению места; результат проверить чтением документов против delta spec, не добавляя каталог участков или feed.
- [ ] 4.2 Сравнить клиентские бандлы до/после по `docs/development.md` и сохранить актуальные YAML-отчёты. Подтвердить, что схема и build-time код сведений не попали в клиент, а включение слоя и поиск не загружают JSON историй; зафиксировать размеры отдельно от числа запросов и тел данных.

## 5. Приёмка реализации

- [ ] 5.1 Выполнить `pnpm openspec:validate`, сверить все требования и сценарии change с результатом; успешная структурная проверка не заменяет проверки поведения.
- [ ] 5.2 Выполнить целевые тесты parcels/`PlaceMap`, `pnpm lint`, `pnpm typecheck`, `pnpm test` и production-сборку `pnpm build`. Учесть уже выполненную эквивалентную сборку при анализе бандлов; сохранить фактические результаты без повторных прогонов при отсутствии новых изменений или проблем.
- [ ] 5.3 Провести браузерную приёмку по delta spec: указатель и клавиатура, свободный и забронированный участки, выбор без попапа, прямой URL и алиас, переход из общего поиска, перезагрузка, закрытие, смена выбора, жесты, узкий/низкий экран и повторный вход через клиентскую навигацию. Проверить реальные события SDK и доступность замка и закрытия; автоматический mock-тест этого не доказывает.
- [ ] 5.4 Разово проверить собранные JSON и сетевые запросы: файлы только нужных статусов, один файл составной позиции, вся история, компактная сериализация, прежний состав геометрических данных и поиска. Подтвердить обычную статическую выдачу и штатное удаление вышедших из продажи файлов через существующий `rsync --delete`; не превращать эту проверку артефактов в постоянный smoke-обход сайта.
- [ ] 5.5 Вызвать `reviewer` из основной сессии для всего актуального diff к `master`, включая staged, unstaged и новые файлы; передать issue, согласованный change, применимые specs, точный SHA базы, рабочую директорию и результаты проверок. Исправить подтверждённые замечания, обосновать отклонённые и повторить ревью после правок. Если reviewer недоступен, выполнить основной проход и отдельный `ponytail-review` самостоятельно, явно указав отсутствие независимого ревью.

После выполнения задач пройти штатные sync/archive workflows, повторить структурную валидацию и итоговое ревью с учётом основных specs и архива, затем обновить этот же PR результатами приёмки. На этапе планирования sync/archive и закрытие #861 не выполняются.
