# Design

## Context

Мотивация и согласованный объём описаны в [proposal.md](proposal.md), задача — [#861](https://github.com/silentroach/kpshelkovo/issues/861). Этот этап готовит документы; разрешение реализации нужно получить в следующей сессии после чтения артефактов и состояния ветки.

Сейчас `createParcelLayer` в `apps/www/src/components/places/parcel-layer.ts` объединяет выбор контура, кнопки номера и фокус по URL в `select()`. Слой сам снимает выделение через пять секунд, а `PlaceMap.svelte` по его callback удаляет `p`. Сведения для попапа в геометрических JSON отсутствуют.

`loadParcelsData()` уже возвращает доменные записи `Parcel`. Mapper вычисляет `areaM2` позиции, складывая площади всех кадастровых составляющих только при наличии каждой из них. `priceHistory` содержит упорядоченные наблюдения `{ on, price }`: полную цену предложения и московскую календарную дату наблюдения. Одинаковая цена не обновляет дату; несколько наблюдений за один день допустимы.

Применимые решения:

- [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md): отдельный Public DTO поверх домена, явный адаптер и собственная схема.
- [ADR-041](../../../docs/decisions/041-parcel-records-and-exact-search.md): участки отдельно от мест, четыре файла геометрии и общий поиск через Pagefind. Пункт о непубликации цены нужно уточнить при реализации.
- [ADR-039](../../../docs/decisions/039-shared-yandex-maps-runtime-and-preview.md): общий runtime Яндекс Карт, доменная логика остаётся в карте участка.
- [ADR-034](../../../docs/decisions/034-native-css-architecture.md): app-owned стили и токены.
- [ADR-011](../../../docs/decisions/011-public-surface-registry.md): явная классификация новой поверхности. Файлы сведений остаются вспомогательными данными UI, как четыре файла геометрии по ADR-041.

## Goals / Non-Goals

**Goals:**

- Использовать один редакционный источник для геометрии, поиска и сведений; не хранить ручной JSON рядом с Markdown.
- Разделить выбор позиции, получение её сведений и перемещение камеры: ошибка сведений не выключает рабочий слой.
- Сохранить лёгкую загрузку слоя и управляемый жизненный цикл попапа при асинхронных ответах и клиентской навигации.

**Non-Goals:**

- График, список или иное отображение истории цен. Полная история в JSON уже входит в этот change по явному решению владельца.
- Отдельная HTML-карточка участка, агентский каталог, фильтры по цене, новые поисковые поля, редакционные заметки и признаки в попапе.
- Обновление кадастровых данных, истории наблюдений, правил обновлятора или цен из внешнего источника при открытии карты.
- Универсальная библиотека попапов, изменение попапа сравнения поселков или поведения выбора мест.

## Decisions

### 1. Статический JSON на основную позицию

Новый маршрут: `/map/data/parcels/details/<основной-код>.json`; исходный маршрут Astro — `apps/www/src/pages/map/data/parcels/details/[code].json.ts`. Создавать файлы только для `available` и `reserved`, включая записи без площади или цены. Алиасы разрешаются по уже загруженной геометрии и не создают дополнительные файлы или перенаправления. Для позиции из нескольких кадастровых участков нужен один файл.

Public DTO:

- `code`: основной полный код;
- `part`: существующий идентификатор части;
- `status`: `available` или `reserved`;
- `areaM2`: необязательная доменная площадь всей позиции;
- `priceHistory`: вся сохранённая последовательность `{ on, price }`, включая пустую историю и исходный порядок наблюдений за один день.

Последняя цена — последний элемент `priceHistory`, а не максимум суммы, не отдельное продублированное поле и не сортировка по дате в браузере. `on` сохраняет смысл даты наблюдения по `parcel-records`; даты не показываются в попапе. Геометрия, алиасы, кадастровые номера, признаки, заметки и снимки источников в этот DTO не входят.

Адаптер получает доменную запись, явно собирает DTO и проверяет конечный результат собственной Zod-схемой перед компактной сериализацией. Схема и build-time адаптер не импортируются в клиентский код. Браузер получает проверенный артефакт своей сборки и обрабатывает ошибки доставки и разбора без повторной схемной валидации.

#### Сравнение с общим ленивым файлом и геометрическими файлами

Измерение 28 сентября 2026 года на редакционном корпусе базы `e9a66a2f`, без сборки и записи файлов: YAML frontmatter проверен существующей `RawParcelSchema`, в памяти собраны перечисленные выше поля, сериализация — `JSON.stringify`, gzip level 9 и Brotli quality 11. Значения описывают только тела JSON, без HTTP-заголовков, задержек и клиентского JS.

- Подходят 424 позиции: 403 свободных и 21 забронированная; сейчас у каждой одно наблюдение цены.
- Один общий массив: 50 745 байт raw, 3 214 gzip, 2 416 Brotli.
- Отдельный файл занимает 116–120 байт raw. Пример `SHF-W50`: 119 raw, 127 gzip, 96 Brotli.
- Сумма всех отдельных файлов: 50 320 raw, 53 228 gzip, 40 494 Brotli. Сжатие множества маленьких файлов менее эффективно.
- Для первых 1, 5 и 20 позиций в порядке файлового обхода: соответственно 1/5/20 запросов и 94/473/1 909 байт Brotli. Общий файл во всех трёх случаях — один запрос и 2 416 байт Brotli. Это иллюстрация затрат, не прогноз реальной последовательности просмотра.

Общий файл был бы простым и небольшим для нынешнего корпуса, а при просмотре многих позиций давал бы меньше запросов и лучшее сжатие. Выбран отдельный JSON по согласованному приоритету: точечный просмотр и полная история только выбранной позиции, с независимым ростом историй. Этот выбор не объявляется безусловно быстрее общего файла.

Добавление сведений в четыре геометрических файла отклонено: открытие слоя заставляло бы загружать истории всех его позиций. Ручные JSON отклонены из-за второго источника истины. Новый backend не нужен: используется существующая статическая сборка Astro.

### 2. Один выбор для слоя, попапа и URL

Расширить существующий контракт `parcel-layer` уведомлением о выбранной позиции и способом снять выбор. Убрать пятисекундный таймер у всех статусов. Смена позиции должна быть одним действием, без промежуточного callback, способного стереть URL нового выбора.

`PlaceMap` связывает выбранную позицию с попапом и URL. Отдельные `selected` для клика, клавиатуры и прямой ссылки не нужны. Попап и запрос сведений появляются только для двух разрешённых статусов; у остальных сохраняются постоянное выделение и URL.

Снятие выбора: крестик, Escape в контексте карты, обычное нажатие на пустую карту, выбор другого объекта, выключение выбранной части или уничтожение карты. Взаимодействие с попапом, панелью слоёв и штатными контролами само по себе не снимает выбор. Закрытие панели слоёв по Escape имеет приоритет, когда фокус в ней; следующий Escape может снять выбор участка. Поиск обрабатывает Escape в собственном диалоге.

Нажатие снаружи отслеживать как завершённый клик карты, а не любой `pointerdown`: начало перетаскивания не должно закрывать попап. Повторный выбор той же позиции, drag, zoom и resize не снимают выбор. Выбор другого объекта прекращает прежний запрос на показ; активация маркера места сохраняет его штатный переход в карточку.

### 3. URL хранит выбор

Расширить `apps/www/src/lib/parcels/parcel-url.ts` парным преобразованием: установить основной код или удалить `p`. Использовать `history.replaceState`, сохраняя другие query-параметры, hash и `history.state`. При прямом переходе алиас и иной регистр канонизируются в основной код после успешного разрешения.

Обычный выбор не двигает камеру. Прямая ссылка и переход из поиска сохраняют текущий фокус на `labelCoordinates` с масштабом первого появления номеров; reduced motion отключает анимацию. Существующий приоритет `p` над подсветкой места `h` сохраняется.

Пока геометрия не получена, сохраняются существующие правила неизвестного кода, ошибки части и повторного включения. После успешного выбора `p` остаётся до снятия выбора, в том числе при ошибке JSON сведений. Явный выбор другой позиции отменяет ожидающий URL-переход: поздняя геометрия не должна перехватить камеру и выбор. Перезагрузка URL с `p` снова открывает нужную часть и выбирает позицию; после снятия выбора перезагрузка открывает обычную карту.

### 4. Отложенная загрузка и защита от позднего ответа

При выборе подходящей позиции сразу показывать оболочку с известными номером и частью, небольшой загрузочный текст внутри попапа и доступный крестик. При успехе показывать сведения; при ошибке — короткое сообщение и кнопку «Повторить». Это локальное ожидание сведений, а не перекрывающий лоудер карты или геометрии слоя.

Переиспользовать принципы имеющейся загрузки частей: успешные результаты и выполняющиеся запросы по основному коду в пределах экземпляра карты, без постоянного хранилища. Повторный выбор не создаёт параллельного запроса того же JSON; ошибка не кэшируется как успех. Ответ применять только к всё ещё выбранной позиции и живому экземпляру карты. Закрытие, замена выбора или уход со страницы не позволяют ответу вернуть попап, выделение или URL. Дополнительный общий fetch-framework не нужен.

### 5. Компактная немодальная поверхность

Один попап для desktop и телефона. Состав: основной короткий номер с полным кодом в доступном имени, название части Шелково, площадь, цена и крестик. У `reserved` рядом с номером — небольшой замок с `title="Забронирован"` и таким же доступным именем; у `available` дополнительной метки нет. Использовать существующую иконографику и токены.

Площадь форматировать из `areaM2 / 100` по русской локали, максимум с двумя дробными знаками, без принудительных нулей. Цену показывать полной суммой в рублях с разделителями разрядов и знаком ₽. Для отсутствующих значений — короткие сообщения «Нет данных о площади» и «Нет данных о цене». Перед реализацией видимые формулировки проходят обычную редактуру `humanizer-ru`; даты, источники, оговорки и видимая история не добавляются.

Поверхность привязать к существующей отображаемой `labelCoordinates`, уже содержащей поправку. Её позиция должна следовать перемещению камеры, а не запоминаться только при открытии. Ограничивать положение и размеры доступной областью карты с учётом шапки, слоёв и штатных действий Яндекса. При уходе опорной точки за край сохранять попап у ближайшего допустимого края, не возвращая камеру самовольно. На малой высоте допустима внутренняя прокрутка содержимого с доступным закрытием. Отдельный мобильный sheet не нужен.

Ближайший образец — попап в `SettlementMap.svelte`: оттуда пригодны оформление и различение pointer/keyboard. Копировать его позиционирование целиком нельзя: оно вычисляется только при открытии и не покрывает сохранение попапа при движении карты. Ограничить решение компонентами карты участков, без переделки сравнения.

Кнопка номера остаётся нативной и доступной по Enter/Space. При клавиатурном открытии переводить фокус в попап, при закрытии крестиком или Escape возвращать на существующую видимую кнопку номера; если она удалена после pan/zoom — на доступный контейнер карты без смены камеры. Указатель и автоматическое открытие по URL не перехватывают текущий фокус. Загрузка и ошибка объявляются доступно, фокус видим, немодальный попап не запирает Tab. Позднее появление данных не перемещает фокус повторно.

## Risks / Trade-offs

- Много маленьких JSON увеличивают количество запросов при последовательном просмотре → кэшировать успешные ответы в текущей карте; сравнивать трафик честно, отдельно от веса JS. Числа нынешнего корпуса не становятся постоянным бюджетом.
- Новая версия сайта может удалить JSON позиции после продажи, пока старая вкладка ещё видит её свободной → показать обычную ошибку загрузки сведений с повтором, сохранив карту; не трактовать HTTP-ошибку как пустую цену или подтверждённую продажу.
- Пятисекундная очистка связана с URL и тестами → заменить весь жизненный цикл, а не отключать только один таймер. Проверить выбор без попапа, смену позиции и ожидание геометрии.
- SDK может передать событие контура и фоновой карты для одного жеста → проверить реальный hit-testing, всплытие, touch и drag; клик по выбранной позиции и попапу не должен тут же снимать выбор.
- Номера удаляются при zoom ниже порога или уходе за bounds → попап не зависит от существования DOM-кнопки номера; возврат фокуса имеет устойчивый fallback.
- Полная история сейчас состоит из одного наблюдения на подходящую позицию → тестовые fixtures должны покрыть несколько наблюдений, совпавшие даты, возврат к прежней сумме, пустую историю и составную доступную позицию.

## Migration Plan

1. В следующей сессии прочитать change, issue, draft PR и рабочую ветку; подтвердить разрешение реализации. Выполнить задачи в этой же ветке.
2. Выпустить новый маршрут и его потребителя одной статической сборкой. Текущий `.github/workflows/ci.yml` использует `rsync --delete`; исключения сохраняют `/search/` и `/static/`, но не `/map/data/`. Поэтому файлы позиций, вышедших из `available`/`reserved`, удаляются штатным deploy. При приёмке проверить набор артефактов и обычную выдачу JSON; отдельный механизм удаления или новый deploy-поток не нужен.
3. Уточнить ADR-041 и дизайн-гайд: цены публикуются отдельно для попапа, выбор больше не временный. Проверить описание карты в Markdown/discovery; добавить сведения о поведении только там, где существующее описание ему противоречит, не создавая новый feed.
4. После реализации и трёх частей приёмки синхронизировать `parcel-map`, архивировать change и обновить тот же PR. До этого draft PR использует `Refs #861`; завершённый PR сможет использовать `Closes #861`.
5. Откат — вернуть change целиком вместе с кодом, документацией и статическими артефактами предыдущей сборки. Редакционные записи и накопленная история цены не мигрируются.
