# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md). Основание действующего контракта — [ADR-030](../../../docs/decisions/030-normalized-estimate-detail-sources.md) и [PR #278](https://github.com/silentroach/kpshelkovo/pull/278). [PR #642](https://github.com/silentroach/kpshelkovo/pull/642) добавил публичные схемы с сохранением JSON.

Сверка 21 сентября 2026 года:

- `detail-json.ts` выделяет уникальные публичные источники, присваивает короткие ID при обходе данных и проверяет готовый ответ публичной Zod-схемой.
- `detail-public-schema.ts` закрепляет версию 2 и разрешимость ссылок из фактов и `needs_check`; `discovery.ts` публикует JSON Schema, OpenAPI и ссылки на них.
- Тесты `detail-json.test.ts`, `tests/detail-public-schema.test.ts` и `discovery.test.ts` прошли: 21 тест. Они проверяют повторяемость, реестр, ссылки, версию, отклонение невалидных ответов и публичное обнаружение контрактов.
- Основные specs не описывают детальную смету. Публичное OpenAPI-описание упоминает нормализованный реестр, но не объясняет область действия ID.

## Goals / Non-Goals

**Goals:** отделить обязательства потребителя от алгоритма и исторических измерений; сохранить причины выбора представления и доступ к его формальному описанию.

**Non-Goals:** менять формат или версию JSON, делать ID постоянными между обновлениями, расширять эту spec на другие связи сметы или переписывать схемы и сериализатор.

## Decisions

- **Перенести контракт, а не копию схемы.** Новая `estimate-detail-sources` хранит четыре группы обязательств. Они защищают выбор декодера, переход от факта к источнику, корректное чтение обновлённого ответа и повторяемость генерации. Списки полей, регулярные выражения ID и порядок обхода остаются в публичной схеме и реализации; иначе появился бы второй справочник вместо короткого контракта.
- **Ограничить повторяемость неизменным упорядоченным набором.** Это соответствует ADR, сериализатору и тесту. Обещание стабильности при перестановке фактов потребовало бы другого алгоритма и противоречило принятому отказу от content hash.
- **Оставить причины в ADR-030.** Кратко сохранить стоимость повторов после распаковки, преимущество коротких ID перед хешами и измеренный результат нормализации. Подробный benchmark и поиск потребителей v1 доступны в PR #278; отсутствие найденных потребителей объясняет только тот переход, а не будущую политику совместимости. Отдельный публичный адаптер сохраняет границу из [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md).
- **Использовать существующее публичное описание.** Уточнить только `description` операции detail OpenAPI: ссылки разрешаются через `sources` того же ответа, в том числе внутри `needs_check`, а ID нельзя переносить между обновлениями. ADR ссылается на основную spec, публичную JSON Schema и OpenAPI; индекс ADR — на spec. Новый публичный документ или endpoint для этого не нужен.

## Risks / Trade-offs

- Потерять трассируемость при сокращении → сохранить PDF, страницу, фрагмент и имеющееся публичное представление цитаты; не требовать одновременно plain-цитату и структурированные позиции.
- Принять пробелы проверок других связей за разрешённое поведение → явно ограничить spec источниками; открытая #291 остаётся отдельной задачей.
- Закрепить две нормативные копии → ADR содержит объяснение выбора и ссылки; OpenAPI даёт краткую инструкцию чтения, а не дублирует весь набор требований.

## Migration Plan

После согласования сократить ADR и уточнить описание, проверить ссылки и соответствие каждому сценарию, затем синхронизировать основную spec и архивировать change в той же ветке. Данные и конфигурация не мигрируют; откат возвращает документационный diff.

Обязательная production-приёмка не нужна: достаточно OpenSpec-валидации, существующих контрактных тестов, typecheck приложения и ревью полного diff. Публикация ветки и PR выполняется только при наличии разрешения владельца; PR закрывает #789 и ссылается на #776 через `Refs`.
