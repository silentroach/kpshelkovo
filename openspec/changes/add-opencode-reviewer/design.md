# Design

## Context

Мотивация и согласованные границы — в [proposal.md](proposal.md), контракт — в [delta `agent-tooling`](specs/agent-tooling/spec.md).

- `.opencode/agents/` пока пуст; `.opencode/opencode.jsonc` содержит настройки MCP, но не reviewer. В среде исследования установлен OpenCode V2 `2.0.16`.
- `AGENTS.md` уже требует полный актуальный diff, три части приёмки и `ponytail-review`; отдельного проверяющего и общего правила выбора базы нет.
- `openspec/config.yaml` доставляет правила задач через `rules.tasks`, а инструкции исполнителю — через `operations.apply.guidance`. Изменение этих полей не требует править сгенерированные skills.
- `scripts/openspec.mjs` обновляет только `openspec-*` skills и `opsx-*` commands. Собственный agent-файл хранится в Git и не требует изменения генератора.
- `scripts/agent-tooling.test.mjs` проверяет генерацию и skills; runtime permissions и качество ревью эти тесты не проверяют. Workflow `Agent tooling` уже охватывает планируемые пути.
- Основание решения — [ADR-038](../../../docs/decisions/038-openspec-development-workflow.md): штатная интеграция, проектные дополнения в собственных файлах и config, ревью внутри общего процесса. Нового архитектурного механизма нет.

## Goals / Non-Goals

**Goals:**

- Получить воспроизводимый вызов reviewer с независимым контекстом и проверяемой передачей всего изменения.
- Разделить технический запрет редактора и поведенческие ограничения остальных инструментов.
- Использовать существующие OpenSpec guidance и проверки, а качество самого ревью подтвердить небольшими реальными прогонами.

**Non-Goals:**

- Песочница ОС, изолированное исполнение тестов, универсальный фильтр shell или отдельный review runner.
- Новая обязательная стадия для короткого пути, автоматические хуки на ответы и одобрение PR агентом.
- Постоянный LLM benchmark в CI, собственная схема OpenSpec или изменения внешнего `ponytail-review`.

## Decisions

### 1. Один проектный subagent с двумя проходами

Создать `.opencode/agents/reviewer.md` с `mode: subagent`, `model: openai/gpt-6-sol` и понятным `description`. Владелец выбрал для reviewer отдельную модель вместо наследования модели основной сессии. Независимость контекста обеспечивает штатный вызов subagent.

Основной проход использует задачу, требования, код, тесты и профильные правила. Второй загружает `ponytail-review`; его формат и итог относятся только к упрощениям. В общем отчёте сначала идут результаты основного прохода, вопросы и непроверенное, затем отдельный блок упрощений. Фраза skill `Lean already. Ship.` не является одобрением PR.

Один агент выбран вместо двух независимых агентов: issue требует два вида проверки, но не повторное чтение всего контекста. Штатный вызов subagent достаточен, поэтому отдельная slash-команда не нужна.

### 2. Широкие инструменты и честная граница запрета

В native V2 frontmatter добавить только нужное ограничение `permissions`: `action: edit`, `resource: "*"`, `effect: deny`. В V2 действие `edit` покрывает edit/write/patch; поля V1 `permission`, `bash`, `tools` не использовать.

Не добавлять разрешающее правило `*`: остальные инструменты остаются под действующими разрешениями среды. Reviewer может читать внешнюю документацию, использовать профильные MCP, браузер, skills и shell для исследования. Инструкция запрещает через любой из этих каналов менять файлы проекта, индекс и refs, делать коммиты, публиковать файлы, комментарии или PR, а также поручать такие действия другому агенту. При работе в браузере применяются профильные правила и закрытие открытых сессий.

Тесты, сборку и проверки, которые исполняют проектный код или могут обновлять артефакты, запускает автор. Reviewer читает их результаты и просит конкретную недостающую проверку, когда без неё нельзя подтвердить гипотезу. Неизменяющие операции профильных инструментов доступны reviewer.

Это согласованное уточнение исходного issue: узкий shell allowlist и default-deny всех внешних инструментов отклонены владельцем в пользу широкого доступа. Технически проверяется запрет редактора; соблюдение остальных ограничений проверяется на прогонах. Свободный shell не становится read-only от наличия `deny edit`.

### 3. Явный контекст вызова и самостоятельный сбор diff

Основной агент передаёт reviewer:

- краткую задачу и существенные решения из issue;
- пути согласованного change, применимых основных specs и доступные подтверждения согласования;
- целевую ветку, точный SHA базы сравнения и рабочую директорию;
- команды, результаты и ограничения уже выполненных проверок;
- при повторном вызове — предыдущие находки, принятые решения и сделанные исправления.

Автор определяет базу как merge-base ветки изменения с целевой веткой и передаёт зафиксированный SHA. Reviewer проверяет существование commit и его отношение к HEAD; при отсутствии или противоречии данных возвращает вопрос основной сессии, а не выбирает другую базу молча. Автовыбор через GitHub и встроенный fallback на `origin/master` не нужны: ответственность за target остаётся у автора.

Reviewer сам читает Git и файлы. Ориентиры для инструкции:

- `git --no-optional-locks status --short --untracked-files=all` для состава рабочей копии;
- `git diff <base-sha> HEAD`, `git diff --cached` и `git diff` для коммитов, индекса и рабочей копии;
- `git ls-files --others --exclude-standard` и чтение содержимого новых файлов;
- итоговый tracked diff относительно базы и связанные вызывающие места — для проверки совместного поведения.

Diff читать с `--no-ext-diff` и `--no-textconv`, чтобы просмотр не запускал пользовательские преобразователи. Игнорируемые сборочные файлы не становятся новыми исходниками для ревью. Файл, затронутый несколькими слоями, оценивается по итоговому результату: исправленный следующим слоем дефект не выдаётся как сохраняющаяся ошибка.

В начале и конце проверки сверять HEAD и состояние изменения. Если параллельная работа изменила рассматриваемый diff, сообщить об этом автору и обновить охват; собственного механизма блокировок или снимков не добавлять. Для удалённой строки указывать путь и строку в базовой версии с явной пометкой; для текущего и нового файла — строку рабочей копии.

### 4. Отчёт, повторная проверка и fallback

В отчёте перечислить базу и охват, затем подтверждённые находки по важности. Для каждой нужны место, воспроизводимое условие, последствие, свидетельство из кода или проверок и короткая рекомендация. Не использовать количество замечаний как критерий качества: отсутствие находок допустимо. Предположения и непройденные проверки указывать отдельно.

Автор разбирает каждую находку: исправляет подтверждённую проблему, обосновывает отклонение или возвращает владельцу вопрос, меняющий согласованное поведение. После изменения diff повторный вызов reviewer проверяет правки и их влияние; неизменившийся материал не требует нового полного прохода без причины.

Если reviewer не обнаружен, запуск запрещён средой или вызов не может завершиться, автор выполняет оба прохода самостоятельно и пишет причину fallback в итогах приёмки/PR. Fallback не скрывает неполную базу, непрочитанные файлы или непроверенные сценарии. Он также не заменяет runtime-проверку установки нового reviewer при приёмке самого #840.

### 5. Доставка через OpenSpec config и документацию

В `rules.tasks` добавить указание планировать вызов reviewer как часть существующего ревью актуального diff. В `operations.apply.guidance` указать контекст вызова, разбор находок, повтор после правок и fallback. Подробный протокол и пример обращения к основной сессии разместить в `docs/development.md`, а не дублировать prompt по нескольким файлам.

В примере показать обычную просьбу использовать `reviewer` и передать change, target и base SHA. Документация объясняет перезапуск OpenCode после установки агента и различие между широким доступом к инструментам и запретом менять проект. Общая норма `AGENTS.md` уже покрывает собственную проверку перед PR; добавление туда обязательного reviewer распространило бы решение за согласованные границы OpenSpec.

Результат ревью должен соответствовать итоговому diff перед PR: если sync/archive изменили проверенный результат, автор передаёт эти изменения на повторную проверку по тому же правилу.

### 6. Приёмка реальным запуском

Основной агент готовит временный Git-репозиторий для пробных примеров вне рабочей копии проекта и удаляет его после проверки. Это одноразовая fixture, а не дополнительная рабочая ветка реализации. В ней используются тот же профиль reviewer и нужные инструкции/skills. Результаты и фактическую версию OpenCode записать в итогах приёмки.

- Проверить discovery и обычный вызов reviewer в основной рабочей копии после перезапуска или обновления контекста среды.
- В fixture подтвердить эффективный запрет edit/write/patch средствами runtime и безопасной попыткой редактора. Нужен результат блокировки инструментом, а не только текстовый отказ модели.
- Подготовить небольшой пример с несколькими коммитами, staged, unstaged и новым файлом; включить ошибку вне последнего коммита, подтверждаемый дефект в каждом незакоммиченном слое и одно обоснованное упрощение. Сопоставить отчёт с заранее известными последствиями и путями.
- Дать пример с уже исправленным последующим слоем дефектом и небольшой чистый пример: убедиться, что reviewer оценивает итог и не требует находки ради формата.
- Проверить сообщение о недоступной базе, повтор после исправления и явный fallback при недоступном reviewer. Для fallback достаточно разового прогона основного агента с недоступным профилем в тестовой среде, без изменения рабочих настроек.
- Сравнить содержимое отслеживаемых и новых файлов, индекс, HEAD и refs до/после. Одного `git status` недостаточно: содержимое уже изменённого файла может поменяться без изменения списка статусов. Проверить журнал действий на отсутствие коммитов и публикации.

Для самого репозитория выполнить `pnpm openspec:validate`, `pnpm skills:check`, `pnpm test:agent-tooling` и проверку форматирования затронутых файлов. Проверить выдачу инструкций tasks/apply у OpenSpec, чтобы новая guidance действительно доставлялась. Нового постоянного теста на точный текст prompt и общего LLM-harness не требуется.

## Risks / Trade-offs

- Широкие инструменты сохраняют косвенные способы записи → явно обозначить поведенческую границу и подтвердить её соблюдение в пробных прогонах; не обещать sandbox.
- Самопроверка при недоступности агента слабее независимого взгляда → записывать причину fallback и фактический охват, сохраняя человеческое ревью.
- Качество LLM-ревью не гарантируется формой prompt → проверить известные дефекты и чистый пример; факты и неопределённость разделять в каждом отчёте.
- Старый контекст сессии или объединённая конфигурация могут скрывать новый профиль либо менять effective permissions → проверять discovery и реальную блокировку на используемой версии V2, а не только YAML.

## Migration Plan

После отдельного разрешения на реализацию добавить профиль, guidance и документацию в одном change. Проверить реальную загрузку в OpenCode и пройти приёмку; затем синхронизировать specs и архивировать change по проектному workflow. Результаты проверок входят в PR с `Closes #840`; production-приёмки нет.

Откат возвращает agent-файл, guidance, документацию и синхронизированные требования как одно изменение. Глобальная конфигурация пользователя не участвует в установке и откате.
