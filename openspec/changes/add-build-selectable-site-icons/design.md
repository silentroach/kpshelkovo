# Design

## Context

Причина и границы изменения описаны в [proposal](/openspec/changes/add-build-selectable-site-icons/proposal.md). Владелец принял [примерку](/openspec/changes/add-build-selectable-site-icons/preview/README.md), затем попросил сохранить два набора с классическим вариантом по умолчанию.

Сейчас геометрия служебных значков хранится в Astro-компонентах `/packages/ui/src/icons`; Search продублирован для Svelte. Семь WebP-маркеров имеют два соответствия типов изображениям: внутри `PlaceMap.svelte` и в `marker-images.ts`. Превью места получает серверный `<template>`, который общий runtime карты клонирует без гидратации Astro. Девять эмоджи категорий лежат в текстовом formatter-е «Сарафана». Значок PDF обслуживает и Astro-компонент, и HTML редакционных материалов через `file-icons.ts`.

Применимые решения:

- [ADR-028](/docs/decisions/028-markdown-first-places-map.md): типизированный маркер и центрирование. Растровая подготовка продолжает относиться к классическому набору.
- [ADR-034](/docs/decisions/034-native-css-architecture.md): темы и semantic colors принадлежат приложению; пакетные компоненты владеют своим локальным оформлением.
- [ADR-039](/docs/decisions/039-shared-yandex-maps-runtime-and-preview.md): общий SDK и серверный шаблон компактного превью.
- [ADR-042](/docs/decisions/042-feature-owned-map-frame-css.md): допустимый способ явно подключаемого общего CSS внутри картографической feature.

## Goals / Non-Goals

**Goals:**

- Один явный выбор набора на этапе сборки и один источник каждого нового рисунка для Astro, Svelte и DOM карты.
- Сохранность классического вида и его исходников; отсутствие невыбранного набора в готовой сборке.
- Маленькие проверяемые адаптеры, статические локальные SVG и существующий runtime карт.

**Non-Goals:**

- Настройка иконок пользователем сайта, A/B-эксперимент, CDN иконок, новый sprite-сервис или универсальная библиотека тем.
- Перестройка карт, кластеризации, карточек, формы кнопок, палитры, шрифтов и анимаций.
- Перевод фирменных знаков, логотипов частей посёлка, предметных пиктограмм сервисов и эмоджи тональности отзывов на новые символы.

## Decisions

### 1. Два набора с выбором при разрешении модулей

Предусмотреть `classic` и `outline`, настройка по умолчанию `classic`. Единственная точка выбора находится в build-only модуле `/packages/ui/iconography.config.ts`, экспортируемом для конфигураций хостов. Модуль содержит выбранный набор и абсолютный Vite alias для стабильного префикса `@shelkovo/ui/selected-icons/`. В UI-код он не импортируется. Environment override не вводится. Изменение настройки требует перезапуска dev-сервера или новой сборки.

Штатный `vite.resolve.alias` разрешает импорты в выбранную реализацию до формирования графа модулей. В каталогах совпадают необходимые entrypoints, но внутренние реализации могут различаться. Так сохранённые рядом исходники не превращаются в два набора зависимостей браузера. Общие фирменные значки доступны обоим режимам. На уровне сайта остаются стабильные семантические имена действий и типов маркеров; пути выбранного набора не попадают в контент и публичные данные.

Один alias подключают основной Astro config, общий конфиг app-стендов и оба Astro-стенда UI-пакета. Проверить наследование обеими Vitest-конфигурациями через существующий `getViteConfig()`. Не вводить отдельный выбор для тестов и не импортировать целиком основной Astro config в стенды. Относительные импорты текущих barrels также направить через выбранные entrypoints: подмена только внешних package-путей их не перехватит.

Расположение настройки в `/packages/ui` позволяет существующим `transit`-зависимостям учитывать её как вход workspace-пакета. Отдельно проверить восстановление конечного результата: текущий build-скрипт копирует `/apps/www/dist/site` в `/dist/www`, но Turbo кеширует только package-relative `dist/**`. На cache hit копирование пропускается. Если последовательность режимов подтверждает устаревший `/dist/www`, адресно включить конечный output сайта в его кешируемые артефакты по документации установленного Turbo. Остальные пакеты не должны становиться владельцами этого каталога. Глобальное отключение кеша и проверка только с `--force` не решают контракт переключения.

Условие, вычисляемое в браузере, не подходит: оно расходится с запросом владельца и оставляет два набора в доставке. Константа с последующим dead-code elimination также недостаточна как единственная защита: неиспользуемые импорты могут успеть выпустить графические assets. Нужна проверка настоящего результата сборки, а не только отсутствия рисунков в DOM.

### 2. Локальный отобранный набор SVG

Новые рисунки хранить рядом с классическими в `/packages/ui`, с описанным происхождением и лицензией. Базовый источник: Tabler Icons, ревизия `a4ce1404bc6d24d3c365afe7b258d6bf6f48d62d`; сетка 24 × 24, `fill="none"`, `stroke="currentColor"`, толщина 1.75, круглые окончания и соединения. Собственный шлагбаум брать из согласованного [SVG](/openspec/changes/add-build-selectable-site-icons/preview/checkpoint-boom.svg), отдельно от атрибуции Tabler.

Сохранять только используемые рисунки. В SVG нет внешних ресурсов, исполняемого кода или собственной палитры. Astro может выводить статический SVG штатным импортом; Svelte и imperative DOM используют тот же локальный файл как доверенную raw-разметку через тонкие адаптеры. Разметка из контента или сетевого ответа в этот путь не принимается. Svelte-компонент не монтируется отдельно на каждый маркер.

Две framework-библиотеки создали бы параллельные входы для одинаковых рисунков. Внешний SVG через `img` не наследует цвет страницы, поэтому для контурного набора выбран inline SVG. При этом классические WebP остаются обычными изображениями.

### 3. Границы переключаемого набора

Вариант выбирается для следующих потребителей:

- Семь маркеров мест и их представления на общей карте, в превью и списке «Рядом».
- Девять категорий «Сарафана», включая верхние ссылки и значки групп. Контурные соответствия: `fence` → `fence`, `construction` → `tools`, `furniture` → `armchair`, `waste-removal` → `truck`, `garden` → `plant-2`, `food` → `tools-kitchen-2`, `electricity` → `bolt`, `education` → `books`, `travel` → `plane`.
- Небрендовые system-иконки: AlertCircle, CheckCircle, Calendar, CalendarPlus, ContactPlus, Email, FilePdf, Globe, Phone, Search, Star. Для PDF учитываются оба пути вывода, в том числе редакционный HTML.
- Собственные inline SVG действий: карта и контакты рядом с названием места, часы и ссылка места в событии, закрытие панелей, слои карты, переключение вида и сортировка сравнения, сброс калькулятора. Заменять рисунок, сохраняя область нажатия, доступное имя и назначение.

Domyland, Telegram, WhatsApp и коралловый MapPin с Яндекс-ассоциацией сохраняются в обоих наборах. Предметные пиктограммы сервисов, территориальные логотипы, знак слоя участков и эмоджи тональности отзывов остаются вне этого переключателя. Они несут самостоятельный предметный или фирменный смысл. Состояния рейтинга и заполнение звезды сохраняются независимо от выбранного контура.

### 4. Один реестр маркеров и согласованное оформление

Соответствия нового набора зафиксированы в [описании примерки](/openspec/changes/add-build-selectable-site-icons/preview/README.md). Изображение КПП не применяется к строительству; поднятое положение стрелы является рисунком типа места, а фактическая открытость по-прежнему определяется расписанием.

Убрать дублирование соответствий маркеров внутри `PlaceMap.svelte` и `marker-images.ts`: один app-owned реестр выбранного набора обслуживает общую карту, серверное превью и соседние ссылки. Отсутствие типа продолжает давать стандартную точку. SSR-превью сохраняет свой `<template>` и общий runtime.

Контурный маркер использует светлый круг, тонкую границу и мягкую тень, зелёный символ для обычного места, охристый для планирования и строительства. Начальная примерка: круг 36 px, символ 23 px; рабочий размер проверяется на масштабах карты и при увеличенном тексте. Круг и рисунок центрируются на прежней координате. Область ссылки остаётся не меньше 44 × 44 CSS-пикселей независимо от масштаба графики. Список соседей выводит те же символы в компактном виде без картографической подложки.

Классический набор сохраняет нынешние размеры, растровые фильтры и исходники. Контурный режим получает собственные правила подложки и цвета, не меняющие классический. Оформление закрытия сохраняет обесцвечивание и значок часов; планирование, строительство, URL-подсветка и клавиатурный фокус сохраняют предусмотренные признаки. Оттенок не подменяет состояние.

### 5. Документация и стоимость доставки

В дизайн-гайде описать оба режима и условность контурных правил: обычная сборка остаётся классической. В ADR-028 добавить уточнение о векторной альтернативе, сохранив причины и правила подготовки растров для `classic`. В README UI описать источники SVG и необходимые CSS-свойства, в документации разработки указать единственную настройку и перезапуск сборки.

Проверить `sideEffects` UI-пакета с учётом CSS и новых входов. Снять baseline и отчёты клиентских бандлов для обоих режимов. Канонические YAML в `/docs/bundle` оставить для окончательного `classic`; результат проверки `outline`, отсутствие неактивных файлов в свежем `/dist/www` и сравнение размеров записать в отчёт приёмки change. Существующее сохранение static generations на сервере относится к открытым клиентам прошлых deploy и не меняется. Временную build-настройку не превращать в общий механизм feature flags.

Подход проверен консультацией advisor: локальная SVG-подборка, тонкие адаптеры и штатный alias признаны соразмерными. Его замечания о раннем выпуске URL-assets, относительных imports, восстановлении `/dist/www`, перезапуске стендов и проверке обеих реализаций включены в этот план. Консультация не заменяет сборку и браузерную приёмку.

## Risks / Trade-offs

- Два набора могут разойтись по доступности → общие семантические параметры действий, адресные проверки в обоих режимах и визуальная сверка фокуса.
- Проверка типов может видеть только классический entrypoint → проверить совместимость входов обоих наборов, не полагаясь на успешный typecheck одной реализации.
- Новый выбор может оказаться только в SSR или только в клиенте → одинаковая конфигурация разрешения импортов у хостов, проверка прямого входа и клиентского перехода в обе стороны.
- Кеш может вернуть результат другого режима → выбор является входом сборки; проверить последовательность `classic → outline → classic` обычными командами с включённым кешем.
- SVG-обёртка может сломать размеры: `.ui-icon-action > svg` рассчитывает на прямого ребёнка → сохранить структуру либо адресно обновить соответствующий селектор и проверить календарное и контактное действия.
- При SVG больше не работают растровые фильтры состояния → отдельно подтвердить часы, планирование, строительство и подсветку на общей карте и в превью.
- Контуры могут потеряться на тайлах → сохранить светлую подложку, проверить тёмный и светлый фон, малый масштаб и реальный контраст по `site-color-roles`.
- Поддержка двух вариантов требует двух проверок → держать развилку в выборе ресурсов и минимальных правилах вида; после будущего решения об одном наборе её можно удалить отдельным изменением.
- Playwright может переиспользовать сервер предыдущего режима → перезапускать стенд при смене настройки и хранить результаты режимов раздельно.

## Migration Plan

1. Опубликовать draft PR с артефактами и примеркой для чтения владельцем. На этом этапе в PR только `Refs #1051` и `Refs #1045`, change остаётся активным, задачи реализации не отмечаются выполненными. До отдельного разрешения владельца код приложения не менять.
2. После разрешения зафиксировать исходное состояние `9709d9d36b841292c5e71ddf962edd1f29f65bb5` и baseline доставки с учётом фактической базы ветки на момент реализации.
3. Добавить контурные ресурсы, выбранные входы и адаптеры, сохранив классические рисунки и настройку `classic`.
4. Проверить оба режима, визуальный каталог и настоящую карту; вернуть настройку `classic` и соответствующие YAML-отчёты.
5. Обновить документацию, пройти полное ревью, синхронизировать spec и архивировать change в рабочей ветке. Готовый к merge PR закрывает #1051 в согласованном объёме двух наборов.
6. Обычный deploy использует `classic`. Включение `outline` по умолчанию и удаление классических ресурсов выполняются только по следующему решению владельца. Откат реализации возвращает однонаборное исходное состояние.
