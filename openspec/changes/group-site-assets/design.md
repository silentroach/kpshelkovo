## Context

Мотивация, ограничения и исходная гипотеза упаковки — в [proposal.md](proposal.md). Установлены Astro 7.3.1, Vite 8.2.2 и Rolldown 1.2.5. Владелец делегировал выбор окончательной группировки по результатам экспериментов.

- `apps/www/astro.config.ts` задаёт `assetsInlineLimit: 0` для внешнего исполняемого JS. Astro применяет этот же порог к CSS, поэтому мелкие стили остаются отдельными файлами.
- [ADR-034](../../../docs/decisions/034-native-css-architecture.md) закрепляет app-owned foundation и scoped стили компонентов. Это владение сохраняется.
- [ADR-017](../../../docs/decisions/017-csp-inline-exceptions-for-astro-yandex-maps.md) закрепляет внешний исполняемый код проекта. Порог встраивания, CSP, хешированные URL и существующая серверная политика кеширования сохраняются.
- Astro передаёт `rolldownOptions.output` в prerender, SSR и client, а также поддерживает отдельные настройки `vite.environments.client`.
- Поиск и Compare имеют отдельные сборки `write: false` с `codeSplitting: false`: самодостаточность нужна для повторной загрузки после ошибки. Эти сборки не наследуют новую vendor-группу.
- `lighthouserc.cjs` уже проверяет шесть маршрутов, но делает только два прогона и использует предупреждение Performance ниже 85. Это исходный инструмент, а не критерий успеха изменения. [ADR-004](../../../docs/decisions/004-lighthouse-analytics-profile.md) задаёт статический профиль без аналитики; развитие постоянных CI-бюджетов относится к #392.

### Результаты исследования

- На production `/news/`: 8 CSS, 58 895 байт до сжатия и 10 445 байт Brotli. На статье `/news/2026/09/august-report/`: 6 CSS; собственный пакет статьи занимает 19 215 байт, или 3 197 байт Brotli.
- У главной собственная разметка и стили новостей; `NewsCard` там не используется.
- В пробной Vite-сборке в памяти из CSS существующей локальной сборки и модели шести новостных страниц две явные группы дали `common` 54 928 / 8 823 байта и `news` 28 639 / 4 230 байт до сжатия / Brotli. Это проверка возможности группировки, не итог полной сборки Astro и не замер ускорения. Локальные CSS-хеши части общих компонентов отличаются от production.
- В отдельной модели `entriesAwareMergeThreshold: 4096` не сократил CSS-файлы. На автоматический порог склейки CSS решение не опирается.
- В JS-пробе с обычной зависимостью и динамически импортируемой зависимостью одна vendor-группа объединила их в начальную загрузку. `entriesAware: true` сохранил разные vendor-чанки и динамическую границу. Это подтверждает механизм, но не заменяет проверку реального клиентского графа.
- Исторические замеры и источники находятся в [#629](https://github.com/silentroach/kpshelkovo/issues/629). Они показывают направление регрессии, но между прежними SHA менялись контент и временные окна статуса; причинность текущей упаковки проверяется на одинаковых данных и времени.
- Прежняя ручная раскладка route styles из [#408](https://github.com/silentroach/kpshelkovo/pull/408) была отменена в [#417](https://github.com/silentroach/kpshelkovo/pull/417). Новый эксперимент ограничен конфигурацией штатного сборщика и не воспроизводит ту систему импортов и загрузки CSS.

## Goals / Non-Goals

**Goals:**

- Улучшить Lighthouse Performance и фактические метрики загрузки с учётом разброса измерений, холодного и тёплого кеша.
- Начать с определения пакета CSS по устойчивой директории владельца и сохранять только оправданную измерениями детализацию.
- Использовать штатные группы, минификацию, хеширование, CSS extraction и ссылки Astro.
- Отделить vendor только в клиентской сборке и сохранить существующие моменты загрузки интерактивности.

**Non-Goals:**

- Новый сборочный плагин, обход графа собственным алгоритмом, склейка готовых файлов или переписывание HTML после сборки.
- Перенос стилей из компонентов, переработка CSS-архитектуры, новый runtime-loader или единый JS всего сайта.
- Вынос библиотек из самодостаточных retryable-графов и переделка поиска или Compare.
- Погоня за 100 баллами за счёт inline, изменения контента, отключения рабочих возможностей или постоянного усложнения CI.

## Decisions

### Выбор схемы через ограниченный эксперимент

Сравнить исходную конфигурацию с простым кандидатом «общий CSS + CSS корневого раздела». Первоначальный кандидат объединяет весь `/815`, как выбрал владелец. Более позднее поручение выбрать упаковку по экспериментам позволяет выделить крупные подгруппы, если это даёт воспроизводимый выигрыш; один файл на раздел больше не является жёстким контрактом.

Влияние vendor измерить отдельно: сначала CSS-кандидат при штатном JS, затем тот же CSS с vendor-группой. Если простой вариант проигрывает из-за лишнего CSS или загрузки зависимостей, проверить один более выборочный вариант по найденной причине. Перебор десятков комбинаций и собственный анализатор графа не нужны. Зафиксировать победителя, сравнение с baseline и причины отказа от остальных вариантов в этом документе и сводке PR.

### CSS: стартовая группировка по владельцу

Для первого кандидата использовать `build.rolldownOptions.output.codeSplitting.groups`, отбирая CSS штатным `isCSSRequest` из Vite. Функция имени группы различает только владельца исходника:

- `src/pages/<root>/…` → пакет `<root>`; для `/815` берётся первый сегмент, без разделения Compare и регламента.
- `src/components/news`, `status`, `reviews` → одноимённые разделы.
- `src/components/contacts` → `sarafan`, `src/components/places` → `map`, `src/compare` → `815`.
- `src/pages/index.astro` и `src/pages/404.astro` → локальные пакеты главной и 404.
- Foundation из `src/styles`, layout, компоненты `site` и оболочки `search`, общая иконка территории и UI из `packages/ui` → `common`.

Обрабатываются в том числе виртуальные CSS-модули Astro/Svelte с query-суффиксом. Новая вложенная страница существующего раздела не требует записи в конфиге. Конкретные выходные имена и хеши формирует Astro; бессодержательные CSS-файлы не создаются. Эти правила описывают стартовый кандидат, а не заранее выбранную финальную упаковку.

Название директории отражает существующее владение. Неизвестный section-owned CSS нельзя автоматически прятать в глобальном пакете: при обнаружении такого исходника во время приёмки уточнить владельца в тех же коротких правилах. Собственный реестр маршрутов или анализ транзитивных импортов не вводится.

Альтернативы: `cssCodeSplit: false` загрузил бы стили всех разделов везде; ручные списки компонентов потребовали бы постоянного сопровождения. Встраивание мелкого CSS исключено прямым условием владельца.

### CSS и JavaScript остаются внешними

Сохранить `assetsInlineLimit: 0`. Ни CSS, ни обработанный исполняемый JS не переносить в HTML ради улучшения балла. Существующие служебные стили переходов и bootstrap-вставки Astro остаются, как отдельно подтвердил владелец. JSON-LD — данные, а не исполняемый JS. Перед экспериментами зафиксировать существующие категории inline-вставок; упаковка ресурсов не должна расширять их ради оптимизации.

### JavaScript: vendor с сохранением потребителей

В JS-кандидате в `vite.environments.client.build.rolldownOptions.output` дополнить CSS-группировку vendor-группой для JS из `node_modules`, исключая CSS. Включить `entriesAware: true`, чтобы Rolldown разделял зависимости по входам и динамическим потребителям. Проектные workspace-пакеты остаются кодом проекта.

Не задавать принудительный порог склейки vendor: он может снова добавить зависимости на чужие входы. Допустимы несколько vendor-чанков с хешами. Число файлов само по себе не является критерием выигрыша JS; проверяются реальное отделение библиотек, повторное использование и отсутствие ранней загрузки тяжёлого кода.

Самодостаточные артефакты `SearchDialog` и `SettlementsExplorerClient` остаются внешними отложенными ресурсами с собственными зависимостями. Их исключение из обычной vendor-группировки намеренное и сохраняет retry-контракт.

### Измерения и критерий выбора

- Для предварительного отбора достаточно трёх одинаковых cold mobile-прогонов ключевых маршрутов. Для baseline и финалиста выполнить по пять прогонов на каждом маршруте из текущего Lighthouse-набора и на `/map/`; остальные разделы включить в проверку ресурсов и браузерную приёмку, а при признаках регрессии — также в Lighthouse.
- Фиксировать Chrome и Lighthouse, viewport, CPU/network throttling, способ throttling, сервер, HTTP-протокол, сжатие, данные, время, timezone и состояние аналитики. Сборки сравниваются на одной ревизии с разной упаковкой, с одинаковыми контентом и LCP-кандидатом. Реальные данные и production-часы ради теста не меняются.
- Использовать существующий Lighthouse CI и временные параметры, например `--collect.numberOfRuns=5`; постоянный CI не перестраивать. Статические тестовые сборки используют `LIGHTHOUSE_DISABLE_ANALYTICS=true` по ADR-004. Выводы о сетевой цене дробления сверить с HTTP/2 и сжатием, как на production; встроенный `staticDistDir` сам по себе этого соответствия не доказывает.
- По каждому маршруту показать медиану и диапазон Performance, FCP, LCP, TBT и CLS, объём CSS/JS/HTML по сети, число stylesheet-запросов и момент завершения блокирующих стилей. Медианы считать по всем отчётам для каждой метрики, а не брать все значения из одного representative run. Сохранить исходные LHR-отчёты вне Git.
- Цель — воспроизводимый рост Performance прежде всего на `/news/` и `/status/`, подкреплённый улучшением FCP/LCP. При потолке или округлении балла допустим прежний score с подтверждённым ускорением реальных метрик. Уменьшение запросов или разница в пределах разброса сами по себе не доказывают успех.
- На остальных контрольных маршрутах не принимать подтверждённые ухудшения FCP/LCP, TBT/CLS или Performance. Подозрительные различия перепроверить одинаковой серией; не принимать случайный удачный прогон за победу. Если выигрыш не подтверждается, сохранить более простой вариант и сообщить, что цель ускорения пока не достигнута.
- Отдельно проверить тёплую повторную загрузку и переходы внутри и между разделами: повторное использование CSS/vendor, дополнительные байты, момент доступности интерфейса и отсутствие FOUC. Кеш не отключать в этих проверках. Склейка ради cold score не должна создавать подтверждённую регрессию повторных переходов.

### Ограничение сложности

Начать с небольшого изменения `astro.config.ts`: одна именующая CSS-группа и одна клиентская vendor-группа. При близких результатах предпочесть более простой вариант. Если для корректной работы потребуются новый плагин, собственный загрузчик, обход графа или длинный список исключений, остановить реализацию и вернуться к владельцу с результатами. Изменения групп в рамках согласованного эксперимента не требуют отдельного согласования; выход за ограничения требует.

## Risks / Trade-offs

- Рост CSS первого посещения страницы → сопоставить сетевой объём и Lighthouse всех контрольных маршрутов. Для `/815` проверить цену объединения Compare и регламента; при проигрыше сравнить обоснованную более выборочную схему.
- Смена порядка CSS и взаимодействие client/prerender extraction → проверить scoped селекторы, cascade layers, внешний вид и повторные клиентские переходы. Успех определяется метриками и корректностью, а не ровно двумя файлами.
- Vendor-группировка меняет порядок или момент исполнения → проверить начальные и динамические зависимости, консоль, поиск, Compare, карты и калькулятор. Успешный эксперимент на модели не доказывает корректность приложения.
- Новостной пример не представляет весь сайт → снять сопоставимый baseline полной сборки перед изменением; измерения списка новостей не распространять на другие разделы.

## Migration Plan

Сначала опубликовать обновлённые артефакты в рабочей ветке, актуализировать #629 и открыть draft PR с планом. Владелец разрешил эту публикацию, но реализация обновлённого change ещё не согласована. Не выдавать коммит планирования за разрешение реализации.

После отдельного разрешения провести A/B, выбрать конфигурацию, выполнить проверки и ревью полного diff; реализация войдёт в тот же PR. Обязательная production-приёмка для завершения change не нужна: достаточно production-сборки, сопоставимых измерений и браузера; затем синхронизировать specs и архивировать change. Проверку опубликованного результата можно выполнить после обычного merge и deploy.

Откат — возврат конфигурации и документации изменения вместе. Данные и серверная конфигурация миграции не требуют. На этапе планирования PR использует `Refs #629`; закрытие задачи возможно после реализации и подтверждения критериев.
