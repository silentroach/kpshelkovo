## Purpose

Улучшать фактическую скорость загрузки и Lighthouse Performance через простую кешируемую упаковку внешних CSS/JS, сохраняя оформление, повторные переходы и отложенную интерактивность сайта.

## ADDED Requirements

### Requirement: CSS разделов переиспользуется между страницами

Сайт SHALL поставлять общие и разделовые стили кешируемыми хешированными ресурсами для корневых разделов `news`, `status`, `kb`, `map`, `sarafan`, `reviews`, `people`, `meetings` и `815`. Повторно используемые пакеты SHALL иметь одинаковые URL в пределах одной сборки. Число и границы пакетов SHALL определяться сравнением производительности, а не обязательным правилом «ровно два файла». CSS, принадлежащий только постороннему корневому разделу, SHALL NOT включаться в начальные стили страницы.

#### Scenario: Переход внутри раздела новостей

- **WHEN** пользователь переходит между лентой, архивом, страницей тега и статьёй новостей
- **THEN** страницы переиспользуют общие для них CSS-пакеты по одинаковым URL, если соответствующие стили нужны странице
- **THEN** группировка сокращает избыточные запросы мелких стилей без обязательного объединения всех стилей раздела в один файл

#### Scenario: Переход в другой корневой раздел

- **WHEN** пользователь переходит из новостей в статус сервисов, карту или другой корневой раздел
- **THEN** общий CSS переиспользуется, а оформление раздела получает собственный пакет
- **THEN** новая страница не подключает пакет новостей, если не использует новостные компоненты

#### Scenario: Упаковка внутри раздела 815

- **WHEN** пользователь открывает сравнение тарифов, карточку поселка или регламент под `/815/`
- **THEN** используемые пакеты остаются в границе корневого раздела `815`; их объединение или детализация подтверждены измерениями
- **THEN** страницы других корневых разделов не загружают эти пакеты

#### Scenario: Главная и страницы без собственного CSS

- **WHEN** пользователь открывает главную, 404 или страницу без локальных стилей
- **THEN** локальные стили главной и 404 не становятся частью CSS постороннего раздела
- **THEN** сборка не создаёт пустой CSS-пакет только для соблюдения количества файлов

### Requirement: Оптимизируемые CSS и JavaScript остаются внешними

Оптимизируемые CSS и обработанный исполняемый JavaScript SHALL поставляться внешними ресурсами. Увеличение inline CSS/JS ради улучшения Lighthouse SHALL NOT использоваться. Уже существующие служебные вставки фреймворка, необходимые для переходов и запуска компонентов, сохраняются; структурированные данные не считаются исполняемым JavaScript.

#### Scenario: Проверка HTML после оптимизации

- **WHEN** сравнивается HTML исходной и выбранной сборки
- **THEN** оптимизируемые stylesheet и обработанные скрипты не перенесены в inline-блоки
- **THEN** существующие служебные вставки отдельно учтены и не используются как способ встроить оптимизируемые ресурсы

### Requirement: Улучшение производительности подтверждается сравнением

Принятая конфигурация SHALL показать воспроизводимое улучшение Lighthouse Performance на `/news/` и/или `/status/`, подкреплённое улучшением FCP или LCP и отсутствием подтверждённых регрессий на контрольных маршрутах. При потолке или округлении score прежний балл допустим, если реальные FCP/LCP воспроизводимо улучшаются. Уменьшение числа файлов или изменение в пределах разброса SHALL NOT считаться самостоятельным доказательством успеха.

#### Scenario: Сопоставимый финальный A/B-замер

- **WHEN** выбирается окончательная конфигурация
- **THEN** baseline и кандидат сравниваются минимум в пяти cold mobile-прогонах каждый, с одинаковыми версиями инструментов, условиями сети/CPU, сервером, контентом, временем и состоянием аналитики
- **THEN** по каждому контрольному маршруту доступны медиана и диапазон Performance, FCP, LCP, TBT и CLS, а также число ресурсов и объём передачи CSS/JS/HTML
- **THEN** выбор подкреплён реальными метриками без подтверждённого ухудшения FCP/LCP, TBT/CLS и Performance остальных контрольных маршрутов

#### Scenario: Балл почти достиг потолка или различие неубедительно

- **WHEN** балл не меняется из-за потолка или округления либо разница сопоставима с разбросом прогонов
- **THEN** приёмка опирается на воспроизводимые изменения реальных метрик, а не на один удачный отчёт
- **THEN** при отсутствии доказанного выигрыша задача не объявляется решённой только из-за другого числа файлов

#### Scenario: Повторные посещения и переходы

- **WHEN** пользователь повторно открывает страницу с тёплым кешем или переходит внутри и между разделами
- **THEN** повторно используемые CSS и vendor-ресурсы доступны из кеша согласно действующей политике
- **THEN** выбранная упаковка не вызывает подтверждённого ухудшения доступности интерфейса или дополнительных скачков оформления ради более высокого cold score

### Requirement: Vendor JS отделён с сохранением отложенной загрузки

В обычном клиентском графе сайта сторонние JavaScript-библиотеки SHALL поставляться отдельно от проектного кода в хешированных vendor-ресурсах с учётом их потребителей. Группировка SHALL сохранять динамические границы загрузки; несколько vendor-пакетов допустимы. Самодостаточные отложенные ресурсы с поддержкой повторной загрузки SHALL сохранять этот контракт.

#### Scenario: Статическая страница без запуска интерактивности

- **WHEN** пользователь открывает новости и не запускает поиск или другие отложенные возможности
- **THEN** vendor-группировка не добавляет в начальную загрузку библиотеки, нужные только этим возможностям или другим разделам
- **THEN** библиотеки обычного клиентского графа отделены от проектного кода и доступны по кешируемым хешированным URL

#### Scenario: Запуск и повторная загрузка интерактивности

- **WHEN** пользователь запускает поиск, Compare или другую ранее отложенную возможность
- **THEN** её зависимости загружаются в предусмотренный момент и интерфейс работает
- **THEN** предусмотренная повторная попытка после ошибки загрузки сохраняется, в том числе для самодостаточных ресурсов

### Requirement: Группировка сохраняет оформление и доставку

Группировка ресурсов SHALL сохранять scoped оформление, порядок каскада, работоспособность клиентской навигации и существующую политику внешнего исполняемого кода. Ссылки на ресурсы SHALL разрешаться после прямой загрузки и клиентского перехода.

#### Scenario: Прямая загрузка и возврат между разделами

- **WHEN** пользователь напрямую открывает страницу, переходит в другой раздел и возвращается назад
- **THEN** нужные CSS и JS доступны, интерфейс сохраняет оформление на мобильном и настольном экранах
- **THEN** группировка не вызывает ошибок исполнения, потерянных ресурсов или новых нарушений CSP
