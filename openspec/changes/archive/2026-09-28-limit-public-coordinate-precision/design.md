# Design

## Context

Мотивация — в [proposal.md](proposal.md), действующий контракт — в delta specs `public-coordinate-precision` и `markdown-service-blocks`. [ADR-013](../../../../docs/decisions/013-raw-domain-public-data-boundary.md) отделяет входные данные от публичных адаптеров; [ADR-041](../../../../docs/decisions/041-parcel-records-and-exact-search.md) хранит исходный кадастр отдельно от геометрии позиций и сдвига карты; [ADR-008](../../../../docs/decisions/008-markdown-ast-generation.md) требует генерировать публичный Markdown через AST.

Сейчас `projectNspdGeometry` сохраняет результат преобразования EPSG:3857 без ограничения разрядов; `reconcileParcels` сравнивает геометрию через `JSON.stringify`. Принятый снимок содержит 3328 колец и 32067 вершин: округление до восьми знаков в градусах не схлопывает их сегменты и не нарушает валидацию 1620 действующих записей, максимальное смещение вершины на этом снимке — около 0,64 мм. Семь знаков уже схлопывают один сегмент снимка. Это проверка текущих данных, не гарантия корректности будущего снимка.

Остальные выходы неоднородны: слой участков повторно рассчитывает поправку и подпись, редакционный GeoJSON расширяет приблизительные контуры, а места/события/контакты/сравнение публикуют точки в HTML, JSON-LD, Markdown, ссылках и экспортах. `appendEditorialMapCaptions` сохраняет исходный `map`-блок в companion дословно, что противоречит новому пределу для опубликованных координат.

## Goals / Non-Goals

**Goals:**

- Ограничивать разряды на границе записи созданных сайтом координат и на границах публичных представлений, не ухудшая расчёты и не вводя отдельный формат хранения внешних снимков.
- Сохранять структуру геометрии и явно обнаруживать невалидный результат после округления.
- Зафиксировать единое правило в долговечном контракте и кратких рабочих инструкциях для следующих редакционных и генераторных задач.

**Non-Goals:**

- Не утверждать геодезическую достоверность на миллиметровом уровне: число разрядов — верхний предел записи, а не обещание точности измерений.
- Не округлять исходные координаты НСПД в EPSG:3857, исходные файлы GeoJSON и Markdown, чужие/явно заданные редактором URL, числа вне числовых географических координат или координаты произвольно цитируемые в тексте.
- Не менять модель идентичности участков, их площади, цену, поиск или настройку поправки карты.

## Decisions

### Нормализовать после вычисления, адресно на выходах

Один небольшой helper в приложении `apps/www/src/lib/geometry` округляет число в градусах до восьми десятичных знаков и возвращает число, не строку с искусственными нулями. Использовать его только для координатных полей, а не как рекурсивный JSON-replacer: последний затронет цены, ID, площади и прочие числа. Внутренние расчёты, исходная геометрия и явно заданные URL остаются прежними; каждый публичный адаптер или генератор применяет правило после своего последнего преобразования.

Альтернатива — округлить все входные координаты в raw-схемах или доменной модели. Она проще по числу мест вызова, но теряет исходные значения до вычислений, меняет результаты расстояний и оставляет проблему повторных дробных разрядов после расширения и смещения. Округлять исключительно при сериализации тоже недостаточно: генератор участков сравнивает геометрию до записи, а другие форматы сериализуются по-разному.

### Подключить правило к фактическим границам

- В генераторе участков округлять обе компоненты каждой вершины `Polygon`/`MultiPolygon` сразу после перевода из НСПД и до сравнения с сохранённой записью. После последующей поправки отображения и вычисления точки подписи округлять вновь в публичном адаптере слоя.
- В общем преобразовании редакционных карт готовить округлённую копию геометрии после возможного расширения, затем проверять конечное представление; ту же логику использовать для HTML-карт, геометрии места в JSON и превью. Основные точки мест округлять на их публичных выходах.
- Для событий, контактов и поселков округлять координаты перед записью каждой формы выдачи: HTML-данные карты, JSON/Markdown, JSON-LD, ICS/vCard и ссылки, которые сам сайт собирает из точки. Не переопределять сохранённые внешние ссылки.
- У `map` в Markdown companion сохранять исходную форму объектов и свойства, но подготовить отдельную копию блока с округлением только массивов `geometry.coordinates`, **без применения** `outline_expansion_meters`. При уже соответствующих пределу значениях оставлять блок без переработки; при изменении координат форматирование внутри JSON может измениться, но значения остальных полей и метаданные блока сохраняются. Редакционное тело и файл источника не меняются.

Точка внедрения выбирается по действующему владельцу данных, а не через новый универсальный сериализатор HTML/Markdown/JSON. Контрольный перечень публичных выходов и их тестов ведётся в задачах изменения.

### Проверять геометрию после округления

Существующие Zod-схемы полигона и конечных представлений применять к нормализованному результату, пока известен источник объекта. Не удалять автоматически совпавшие вершины или исчезнувшие отверстия после округления: такой случай требует заметной ошибки с путём/контекстом. Исходный снимок остаётся доступен для анализа и исправления причины, а не изменяется под прошедшую проверку.

## Risks / Trade-offs

- Массовое одноразовое изменение Markdown участков → применять из сохранённых снимков после разрешения состояния PR #869, проверить отсутствие иных содержательных правок и побайтовый результат повторного запуска; большой diff проверять автоматически по координатным полям плюс выборочно вручную.
- Точка ровно у порога округления может различаться при крайне малой межплатформенной погрешности → проверить на реальном снимке и двух доступных runtime, не выдавать установленную причину расхождения за доказанную; если остаточный шум обнаружится, разобрать конкретный вход прежде чем менять предел или переписывать проекцию.
- Нормализация может повредить чрезвычайно маленький контур или отверстие → валидировать финальную геометрию и останавливать сборку с контекстом источника вместо молчаливого исправления.
- Публичный companion перестаёт быть побайтовой копией GeoJSON → исходник остаётся в редакционном Markdown; публичная копия сохраняет структуру и значения всех иных полей, а изменение контракта отмечено в spec и проверяется отдельно.

## Migration Plan

1. После разрешения владельца на реализацию восстановить состояние ветки и учесть результат PR #869, не перезаписывая его исходники или чужой diff.
2. Ввести точечную нормализацию и проверки выходов; обновить документацию об источниках и публичной границе. Повторить генерацию участков из принятого сохранённого снимка без сетевого обращения к НСПД и проверить большой diff, затем повторить без новых изменений.
3. Проверить HTML, публичные JSON/Markdown, экспорты и ссылки на типовых и вычисленных координатах; пройти все три части приёмки по `AGENTS.md`, sync/archive и обновить текущий PR из той же ветки. Плановый PR остаётся draft до реализации. При необходимости отката вернуть весь реализационный diff через Git без изменения исходных снимков.
