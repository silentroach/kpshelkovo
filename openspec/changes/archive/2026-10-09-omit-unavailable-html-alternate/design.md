# Design

## Context

Мотивация — в [proposal](/openspec/changes/archive/2026-10-09-omit-unavailable-html-alternate/proposal.md). `/meetings/` явно настроен как Markdown-only negotiated вход: при подходящем Accept он передаёт `$md` в общий `@markdown`, иначе возвращает 404. `@markdown` безусловно добавляет HTML alternate. Отдельные встречи имеют обе опубликованные версии.

Действующий контракт — [public-markdown-delivery](/openspec/specs/public-markdown-delivery/spec.md). Ручная конфигурация доставки и границы реестра следуют [ADR-011](/docs/decisions/011-public-surface-registry.md); Markdown-first архив — [ADR-014](/docs/decisions/014-meetings-transcript-first-archive.md). HTML-хаб не нужен для этой правки.

Advisor подтвердил небольшой подход без нового механизма определения маршрутов. Существующий workflow устанавливает конфиг и выполняет `nginx -t`; deploy-поток не меняется.

## Goals / Non-Goals

- Убирать только отсутствующее HTML alternate, не остальные заголовки `@markdown`.
- Не менять `$request_uri`, query, MIME, Accept negotiation, robots, кеш, `Vary` или прямые `.md`.
- Не вводить генератор nginx, файловые проверки на каждом запросе и HTML-хаб.

## Decisions

- В серверной области определить переменную полного HTML `Link` со значением текущего alternate по умолчанию.
- В Markdown-only `location = /meetings/` перед переходом через 418 установить её в пустую строку.
- В `@markdown` передавать переменную в существующий `add_header Link`. Пустое полное значение не добавляет заголовок; остальные поля `Link` сохраняются. Не добавлять `add_header` внутри нового `if` и не менять наследование security headers.
- Наличие представления описывает действующая публичная конфигурация маршрута. Случайный файл `index.html` не равнозначен опубликованному HTML: текущий location всё равно отвечает 404. Поэтому проверка `-f` хуже явного параметра маршрута.
- Генерация из реестра существенно дороже и меняет принятую границу ADR-011; исключена. Новый ADR для параметра существующего обработчика не нужен.
- До PR проверить настоящий nginx на временном локальном стенде. Не писать универсальный parser/validator или CI smoke-обход ради одного случая.

## Risks / Trade-offs

- Значение потеряется при переходе в named location → реальная GET/HEAD-проверка подтверждает передачу параметра, а не только текст конфигурации.
- Настройки пар могут потерять обратную ссылку или URI → контроль существующей встречи, `/status/history/` с общим Markdown и query-параметров.
- Проверка заголовков может проигнорировать сжатие → сохранить обе оси `Vary` при запросах с Accept-Encoding.
- Позднее появится HTML-хаб → его публикация должна одновременно удалить Markdown-only override; не закреплять вечный 404 в specs.

## Migration Plan

- Локально проверить конфиг и реальные GET/HEAD; выполнить структурную валидацию и независимое ревью всего diff. Открыть готовый PR с `Refs #942`, оставив change активным.
- После человеческого merge/deploy выполнить production GET/HEAD: Markdown-only negotiated вход не объявляет HTML, прямой Markdown доступен, опубликованная пара сохраняет alternate. Зафиксировать время и SHA проверенного deploy.
- После production-приёмки завершить соответствующую задачу, sync/archive и документальное ревью в отдельном завершающем изменении, затем закрыть issue. Не выполнять merge/deploy от имени владельца.
- Откат — возврат PR целиком и штатный deploy конфигурации.
