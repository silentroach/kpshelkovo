# Design

## Context

Мотивация и объём — в [proposal](/openspec/changes/archive/2026-10-06-adopt-taste-and-svelte-skills/proposal.md). Текущий `pnpm skills:check` подтверждает 19 внешних и 4 собственных skills. [Установщик](/scripts/skills.mjs) уже изолирует HOME, проверяет полный состав и хеши перед копированием; [тесты](/scripts/agent-tooling.test.mjs) покрывают нарушения установки и независимость генерации от профиля.

Решение следует [ADR-038](/docs/decisions/038-openspec-development-workflow.md): исходный upstream, закреплённые источники, проектные дополнения в правилах. [ADR-034](/docs/decisions/034-native-css-architecture.md) определяет CSS-владение, токены и светлую тему. Новый ADR для расширения набора не нужен.

## Goals / Non-Goals

**Goals:** воспроизводимо доставить полные skills и сделать выбор подходящих рекомендаций явным в существующих инструкциях.

**Non-Goals:** изменение установщика, npm-зависимостей приложения и исходников внешних skills; новый процесс планирования или отдельная библиотека дизайн-блоков.

## Decisions

### Закрепить исследованные источники

- `design-taste-frontend`: `Leonxlnx/taste-skill#ce26fc25c0e5e8cab638f883de62d9a86ee5e45b`, `skills/taste-skill/SKILL.md`.
- `animate`: `emilkowalski/skills#e8a175de22ae1e49370fc144c1f3bb9aeedf988d`, `skills/animate/SKILL.md`, включая `RECIPES.md`.
- `svelte-core-bestpractices`: `sveltejs/ai-tools#6b5d0dab3c9c083387247ab20dc684573481076b`, включая `references/`. В upstream несколько копий; `skillPath` и `computedHash` взять из фактической установки и сверить с выбранным каталогом.

Получить записи через локально закреплённый `skills` CLI в отдельном временном проекте с изолированными HOME/XDG-каталогами по [инструкции](/docs/development.md#внешние-skills). Перенести только три записи в существующий lock; восстановить набор штатной командой. Это сохраняет проверенные решения #943; обновление до текущих HEAD потребовало бы повторного исследования других версий.

### Условия подключения — в корневом AGENTS.md

- `design-taste-frontend` — при выборе визуального направления, создании или пересмотре композиции страниц. Начать с задачи читателя, реального материала и осмотра текущего интерфейса. Для плотных таблиц и рабочих экранов использовать лишь подходящие общие приёмы иерархии и композиции: upstream исключает их из своей основной области.
- `animate` — при создании или изменении конкретного движения; сначала определить его назначение и частоту использования. `apple-design` — для физики жестов, инерции и прерываемых взаимодействий по его предметной области.
- `svelte-core-bestpractices` вместе с `svelte-code-writer` — при создании, изменении или анализе Svelte-компонентов и модулей; первый задаёт инженерные приёмы, второй — работу с документацией и autofixer.

Разместить условия один раз в разделе skills; общую рамку — в разделе дизайна. Подробные инженерные оговорки Astro/Svelte оставить локальным правилам приложения.

### Проектный brief для Taste

Закрепить приоритет задачи читателя, доступности, полноты фактов и редакционных правил над маркетинговыми ограничениями upstream. Сохранять необходимые строки таблиц, источники, даты, цитаты и смысл текста; русские тире и диапазоны обрабатывать действующим типографом и редакционными правилами, включая `humanizer-ru`. Числа из источника не заменять ради визуального разнообразия.

Текущий [дизайн-гайд](/docs/design/design-code-shelkovo.md) — отправная точка. Агент вправе предложить более удачные шрифты, палитру, плотность и композицию, обосновав пользу для конкретной задачи. Согласованные изменения записывать в этот же гайд одновременно с UI; для шрифтов соблюдать Font Budget. Числовые dials, обязательные изображения и dual-mode из Taste сами по себе не расширяют задачу. Изображения подбирать по смыслу материала и публиковать по проектным правилам.

Эта рамка использует собственную оговорку Taste о контекстности правил. Внешние файлы остаются исходными, визуальные решения принадлежат гайду, компоненты — существующим app/package-каталогам, объём и согласование — OpenSpec. Раздел block library описывает upstream-справочник и не становится новым проектным хранилищем.

### Реализация движения — в apps/www/AGENTS.md

Выбирать самое простое подходящее средство: CSS/WAAPI, затем штатные возможности Svelte, затем библиотеку под подтверждённую потребность. Стек задают проектные инструкции; React/Tailwind/Motion-примеры служат иллюстрациями идеи, а применимость API проверяется по установленной версии и официальной документации. Статическому Astro-контенту для CSS-эффекта достаточно CSS.

Этап выбора UI-примитива из `animate` выполнять через существующие доступные компоненты и подходящий нативный HTML; при необходимости выбирать совместимую со Svelte библиотеку. Вызов отсутствующего `pick-ui-library` не является зависимостью задачи. Атрибуты Base UI из рецептов использовать только при наличии такого контракта у выбранного компонента.

Для движения проверять reduced motion, быстрые повторные переключения, фокус, клавиатуру и сенсорный ввод. Источник ввода сам по себе не определяет допустимость анимации: частота, назначение и пользовательские предпочтения важнее общего запрета upstream на keyboard-triggered действия. Для переходов Svelte проверять их реальное прерывание и reduced-motion поведение, а не переносить на них ограничения обычных CSS keyframes. Выбор API и точных параметров относится к конкретной UI-задаче.

## Risks / Trade-offs

- Длинный экспериментальный Taste содержит категоричные правила → задать узкие условия загрузки и явный проектный brief; при ревью проверить приведённые выше конфликты. Доказательство визуальной пользы даст отдельный пилот.
- Несколько копий Svelte skill в upstream → сверить выбранный установщиком путь, supporting files и хеш, затем воспроизвести результат в чистой временной копии проекта.
- Тесты tooling проверяют доставку, а не суждения агента → вручную сверить инструкции на трёх случаях: оформление русской статьи с цитатой и датами, плотная тарифная таблица, анимированное раскрытие в Svelte. Ожидаемые решения описаны выше; создавать UI для этой проверки не требуется.

## Migration Plan

После согласования обновить lock и инструкции, установить набор и проверить восстановление в чистой временной копии с тем же lock и изолированным HOME. Выполнить проверки из proposal и ревью по [проектному workflow](/docs/development.md#ревью-изменения-в-opencode). Перезапуск OpenCode обновит доступный набор skills.

Откат возвращает lock и инструкции вместе; удалить только три добавленных внешних каталога и восстановить прежний набор по проектному bootstrap. Собственные и глобальные skills сохраняются.
