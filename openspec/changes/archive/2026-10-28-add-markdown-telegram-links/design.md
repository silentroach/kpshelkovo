# Design

## Context

Мотивация, согласованный объём и разрешение реализации от 28 октября 2026 года — в [proposal](/openspec/changes/archive/2026-10-28-add-markdown-telegram-links/proposal.md). Реализация выполнена локально в рабочей копии `master`; публикацию владелец выполняет самостоятельно.

- [Обёртка приложения](/apps/www/src/lib/markdown/render.ts) уже даёт общий вход для редакционного HTML. Она принимает mdast-transform, затем применяет строковые преобразования блоков сравнения и PDF-ссылок.
- [LinkWithIcon](/packages/ui/src/LinkWithIcon.astro) распознаёт Telegram через `isTelegramUrl` и использует [Telegram.astro](/packages/ui/src/icons/system/Telegram.astro). Этот Astro-компонент не вызывается при Markdown-рендере. Сам `LinkWithIcon` задаёт открытие в новой вкладке и отдельное доступное имя, поэтому заменять им авторские ссылки целиком нельзя.
- Действующий glyph — один SVG path. У PDF уже есть [общий источник геометрии](/packages/ui/src/icons/system/file-icons.ts), используемый Astro-компонентом и строковым рендером.
- В корпусе есть простые `[@username](https://t.me/username)` в KB, новостях и местах; описательные ссылки на чаты, инвайты и сообщения; подписи с вложенным `strong`; подписи в виде URL. По URL username нельзя отличить человека от канала, бота или публичного чата.
- [Companion KB](/apps/www/src/lib/kb/markdown.ts) собирается отдельно из подготовленного Markdown. `preprocessSiteMarkdown` также используется загрузчиками и графом упоминаний, поэтому HTML-оформление не должно попадать в эту предобработку.
- Консультация advisor `ses_e7c33a3f1ffebgUHN4lq4dp4r2` сравнивала локальный рецепт одной памятки с общим поведением. После консультации владелец явно выбрал общее поведение. Рекомендация о change учтена; локальная вставка `img` потребовала бы обходить block/reset и prose-оформление изображений.

Применимые решения: [ADR-003](/docs/decisions/003-markdown-pipeline-layering.md) оставляет расширения сайта в app-wrapper; [ADR-008](/docs/decisions/008-markdown-ast-generation.md) разделяет HTML-рендер и Markdown-генерацию; [ADR-034](/docs/decisions/034-native-css-architecture.md) закрепляет стили generated content за приложением. Новый ADR для применения этих границ не нужен.

## Goals / Non-Goals

**Goals:**

- Выполнить оформление на сервере в существующем разборе Markdown, сохранив доступ к структуре подписи и адресам ссылок по определению.
- Использовать один источник glyph для Astro-контактов и Markdown; держать оформление сгенерированного содержимого у приложения.
- Сделать нормализацию консервативной и проверить её вместе с реальными потребителями wrapper и companion.

**Non-Goals:**

- Новый синтаксис Markdown, реестр соцсетей, generic link renderer или замена существующего PDF-механизма.
- Раскрытие нессылочного `@username` в Telegram, определение типа аккаунта, сетевые проверки существования контакта.
- Редактура исходных материалов, изменение ссылок, политики открытия вкладок и генераторов companion.

## Decisions

### 1. HTML-only преобразование существующего AST

Добавить узкий transform в `apps/www/src/lib/markdown/telegram-links.ts` и подключить его только из `renderMarkdownWithMetadata` через существующий `options.transform` пакетного renderer. Для ссылок по определению использовать уже экспортированный `resolveMarkdownResourceReferences`; пройти по полученным ссылочным узлам, сохраняя остальную структуру документа.

Значок добавлять отдельным сгенерированным узлом перед единым inline-span со всеми исходными детьми ссылки. Существующие `data.hName`, `hProperties`, `hChildren` позволяют выразить SVG и обёртку без raw HTML и без замены авторских inline-узлов. Этот механизм уже используется в [редакционных картах](/apps/www/src/lib/markdown/editorial-maps-html.ts); поведение подтверждено документацией `mdast-util-to-hast` и установленной версией 13.2.1. Сгенерированный пустой текстовый узел с SVG-данными не добавляет текст к заголовку. Class-маркер значка позволяет не вставлять второй значок и обёртку при повторном вызове transform.

Ревью `ses_e7c15647dffeAab7IdhyP3aSv0` выявило потерю видимого `figcaption` у отдельно стоящего image-link после добавления SVG. В `packages/markdown/src/image-figures.ts` распознавание единственного изображения проходит через inline-обёртки `a`/`span` и пропускает только декоративные `svg[aria-hidden=true]`. Видимый текст и несколько изображений сохраняют обычный абзац. Пакет не знает Telegram, его CSS-классы или app-transform; исправление сохраняет существующий контракт подписи изображения в итоговой структуре `svg + span(img)`.

Встраивать transform в полный документ после подготовки упоминаний и назначения авторских ID. Не пересчитывать якоря из сокращённого ника и не менять `localIds`. Кодовые узлы не обходить как Markdown. Преобразование работает и для Markdown-фрагментов вроде подписей фотографий, поскольку они вызывают тот же wrapper.

Рассмотренные варианты:

- Строковый postprocessor по образцу `file-links.ts` короток для одной вставки перед текстом, но нормализация подписи требует различать простой текст, вложенную разметку и экранирование. AST уже доступен и снимает эту неоднозначность.
- Повторный разбор готового HTML потребовал бы ещё одного полного обхода сериализованного документа. Он здесь не нужен.
- Передача поведения в `@shelkovo/markdown` привязала бы универсальный renderer к оформлению сайта. Существующий app-level transform сохраняет границы пакетов.

### 2. Разделить распознавание сервиса и нормализацию ника

Для значка использовать `isTelegramUrl` без дублирующего списка доменов. Это сохраняет единую классификацию с `LinkWithIcon`: HTTP(S) для `t.me` и `telegram.me`, включая `www.`, а также `tg:`. Сообщения, темы, приглашения и deep links получают тот же значок.

Начальный `@` убирать только при одновременном выполнении условий:

- Адрес — HTTP(S) Telegram URL без query и fragment, с единственным сегментом из латинских букв, цифр и `_`; разрешён завершающий `/`. Это распознавание простой формы username-ссылки, а не проверка существования или типа аккаунта.
- Подпись — ровно один текстовый mdast-узел, полностью равный `@` плюс username адреса при сравнении без учёта регистра.
- Меняется только первый символ подписи; её регистр, URL и `title` остаются исходными.

Подписи `чат праздника`, `Telegram`, `t.me/username`, другой ник, пробелы вокруг ника и вложенное форматирование сохраняются. Для `tg:`, сообщений, инвайтов и URL с параметрами подпись вообще не нормализуется. Совпадение строки ника с URL предохраняет от удаления значимого авторского `@` в описательной подписи.

### 3. Переиспользовать glyph, сохранив обычную ссылку

Вынести path из `Telegram.astro` в небольшой чистый модуль UI по существующему примеру PDF. Astro-компонент и app-transform импортируют эту геометрию; UI-пакет не получает зависимость от Markdown. Проверить export и `sideEffects` в `packages/ui/package.json`: чистый модуль совместим с действующим списком CSS-побочных эффектов.

SVG имеет `aria-hidden="true"` и не получает фокус. Ссылка сохраняет обычное доступное имя из своих детей, без нового общего `aria-label="Telegram"`, без навязанного `target` или `rel`. После снятия `@` доступное имя совпадает с видимым ником.

В app-owned слое generated content задать узкие hooks ссылки и иконки. Размер 14 px, промежуток 4 px, фирменный `--color-telegram` и оптическое выравнивание повторяют существующий значок контактов; текст сохраняет начертание, цвет и подчёркивание своего контекста. По адресной рекомендации advisor `ses_e7c33a3f1ffebgUHN4lq4dp4r2` внешний inline-anchor получает `white-space: nowrap`, а единый span со всеми детьми подписи — `white-space: normal`: значок удерживается у начала подписи, длинные фразы переносятся. Текст не режется на слова, пробелы и скрытые символы не добавляются. Hook должен работать как в `.ui-prose`, так и в Markdown-подписях фотографий. В штатной печати KB и новостей значок скрывается вместе с другими декоративными значками; текст и ссылка сохраняются.

### 4. Companion остаётся авторским Markdown

Нормализация и SVG существуют только в дереве конкретного HTML-рендера. Загрузчики, `preprocessSiteMarkdown`, исходники и companion-адаптеры не получают эти изменения. Регрессия проверяется через настоящий `buildKbPageMarkdown` на небольшой ссылке: авторская подпись, URL и `title` сохранены, SVG отсутствует. Пакетный `render` без обёртки сайта тоже сохраняет обычное поведение.

## Risks / Trade-offs

- Общий значок появится и у длинных ссылок-источников внутри прозы → сохранить inline-поток, проверить переносы, фокус и печать в production HTML; не превращать каждую ссылку в неразрывный `inline-flex`.
- Снятие `@` у форматированного ника потребовало бы более широкого переписывания дерева → в этом change форматированные подписи сохраняются; автор может написать ник без `@` непосредственно.
- HTML и companion визуально различаются начальным `@` → это намеренная граница представлений: адрес и идентичность контакта совпадают, companion сохраняет авторскую запись.
- Изменение общих стилей затрагивает несколько разделов → проверить все места вызова wrapper по их типам контейнеров, отдельно Markdown-подписи фотографий и контакты вне Markdown. Для типового поведения достаточно адресных тестов и разового осмотра сборки.
- Выделение path меняет импорты UI → проверить отсутствие побочных эффектов и сохранность Astro-иконки; при затрагивании клиентской цепочки выполнить проектный анализ бандлов. Серверный transform сам клиентского JS не добавляет.

## Migration Plan

Реализовать transform, общий glyph и стили, затем выполнить адресные проверки и обновить справочник Markdown и дизайн-гайд. Миграция редакционного корпуса не нужна. Обычная production-сборка применит правило ко всем потребителям wrapper; откат возвращает код и стили изменения без правки данных.

## Проверки при реализации

- Адресные DOM-проверки app renderer: прямые и reference-ссылки, автоссылки, сохранность фраз и вложенного выделения, нормализация совпадающего ника, сообщения/инвайты/deep links, похожий посторонний домен, отсутствие удвоенного значка и правильное доступное имя.
- Смешанный документ: Telegram, PDF, обычная ссылка, mention, code, заголовок и TOC; проверить сохранность адресов, текста, якорей и `localIds`.
- Настоящий companion KB и предобработка: сохранность авторской ссылки; низкоуровневый пакетный renderer без app-transform не получает значок.
- `pnpm --filter @shelkovo/www typecheck`, затронутые тесты Markdown/KB, `pnpm build`, адресный lint и форматирование.
- Разовый браузерный осмотр production-сборки после реализации: KB, новость, событие, статус, профиль, место, «Сарафан», отзыв, «У кого есть» и Markdown-подпись фотографии по реально встречающимся контейнерам; 320 px, увеличение текста, клавиатура, печать. Использовать согласованный свободный порт; `pnpm dev` и порты 4321/4336 в этой задаче не запускать.
- Структурная валидация OpenSpec и полное ревью актуального diff с адресным повтором после исправлений — по проектному workflow.
