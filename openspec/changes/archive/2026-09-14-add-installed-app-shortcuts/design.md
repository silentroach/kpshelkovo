## Context

Мотивация и согласованные границы описаны в [proposal.md](proposal.md), публичный контракт — в [specs/installed-web-app/spec.md](specs/installed-web-app/spec.md).

- `apps/www` собирается Astro в статические файлы; общий head находится в `src/layouts/BaseLayout.astro`. В нём уже есть имя приложения, короткое Apple-имя, иконки и `theme-color`, но нет manifest.
- `src/lib/browser-colors.ts` экспортирует `themeColor` (`#fcfcfb`). `src/lib/json-response.ts` предоставляет компактную JSON-сериализацию через `createJsonResponse`.
- В `public/` уже есть проверенные PNG 192×192 и 512×512. Заголовки безопасности разрешают same-origin manifest через `manifest-src 'self'` и локальные иконки через `img-src 'self'`.
- Корневой `location /` в `ops/nginx/kpshelkovo-online.conf` обслуживает существующий статический файл по его пути. JSON уже используется существующими endpoint, входит в типы для HTTP-сжатия nginx и список расширений для сжатия в `astro.config.ts`; общая MIME-таблица сервера находится вне репозитория.
- [ADR-033](https://github.com/silentroach/kpshelkovo/blob/master/docs/decisions/033-integrated-tariff-comparison-section.md) закрепляет единое приложение и бренд сайта. [ADR-038](https://github.com/silentroach/kpshelkovo/blob/master/docs/decisions/038-openspec-development-workflow.md) объясняет процесс пилота и передачу новой сессии. Новый ADR не нужен: технический выбор ограничен этим manifest и существующей архитектурой.

## Goals / Non-Goals

**Goals:**

- Добавить manifest штатным статическим endpoint без клиентского кода и дополнительной зависимости.
- Сохранить один источник цвета темы и один manifest для всего сайта, включая вложенные страницы.
- Оставить проверяемый объём для новой сессии: два файла реализации и разовая локальная проверка результата.

**Non-Goals:**

- Создавать общий реестр навигации, PWA-плагин или отдельный слой моделей ради константного manifest.
- Рисовать новые иконки, переделывать существующие под maskable или добавлять иконки каждому shortcut.
- Менять deploy-поток, CSP, поиск, публичные каталоги API или Markdown/llms-документы разделов: manifest не меняет их адреса и содержимое.

## Decisions

### 1. Статический endpoint `/manifest.json`

Создать `apps/www/src/pages/manifest.json.ts`: статический `GET` возвращает manifest через существующий `createJsonResponse` и импортирует `themeColor`. В `BaseLayout.astro` добавить одну ссылку `<link rel="manifest" href="/manifest.json" />` рядом с метаданными приложения. Корневые пути разрешаются на текущем origin, поэтому production и локальный preview используют один документ без отдельной конфигурации.

Расширение `.json` и MIME `application/json` поддерживаются браузерами для manifest. Это использует существующие сжатие и доставку JSON. Заголовки endpoint не следует считать настройкой production nginx: в статическом режиме Astro записывает тело ответа, а MIME при HTTP-раздаче определяет сервер.

Рассмотренные альтернативы:

- Статический файл в `public/`: потребовал бы второй копии цвета вместо импорта существующей константы.
- `.webmanifest`: допустим, но добавляет отдельный вопрос MIME и расширения для сжатия без пользы для выбранного контракта.
- PWA-интеграция: избыточна для одного файла с метаданными.

### 2. Параметры приложения и иконки

В endpoint задать параметры из спецификации: стабильные `id`, `start_url` и `scope` равны `/`, `display` равен `standalone`, язык `ru`, полное и короткое имена совпадают с существующими метаданными. Идентичность приложения не зависит от страницы установки и не меняется при будущем пересмотре shortcuts.

- Для `theme_color` и `background_color` использовать `themeColor`. Так фон запуска согласован с существующим светлым оформлением браузера.
- Основные `icons`: `/android-chrome-192x192.png` и `/android-chrome-512x512.png`, с точными `sizes`, `type: "image/png"` и `purpose: "any"`.
- Не объявлять эти изображения как maskable: рисунок и надпись выходят за гарантированную безопасную область.
- `shortcuts` содержат только `name` и `url`. Отдельные картинки необязательны, а одинаковая иконка у всех трёх пунктов не помогает различать их.
- Дополнительные описания, screenshots, категории и обработчик установки не нужны выбранным сценариям.

### 3. Поддержка платформ

Исследование на 2026-09-14 подтверждает Chrome Android 84+ и Safari macOS 17.4+; для web apps Safari нужен macOS Sonoma или новее. Chrome Android использует первые три пункта, поэтому порядок массива — приоритет меню. Safari показывает shortcuts в меню приложения и Dock. iOS их не поддерживает.

Service worker не нужен для этих переходов и современной ручной установки. `standalone` — предпочтение в manifest, а конкретный вид окна, возможность установки, число видимых пунктов и обновление уже установленного приложения зависят от браузера и ОС.

### 4. Приёмка

Владелец явно выбрал приёмку без обязательной установки на устройствах и без проверки после деплоя. Это решение относится к #724; оно не меняет общую политику проверок проекта.

Достаточные проверки перед готовностью PR реализации к merge:

- `pnpm openspec:validate` для структуры change и основных specs.
- `pnpm typecheck`, `pnpm test` и `pnpm build` для затронутого workspace.
- Разовая проверка собранного manifest через Zod: параметры приложения, ровно три согласованные пары имени и URL в правильном порядке, same-origin URL внутри scope, размеры и MIME иконок. Новый постоянный smoke-обход сайта и большой snapshot констант не нужны.
- Локальный preview production-сборки: HTTP 200 и JSON MIME manifest, загрузка обеих PNG с заявленными размерами, HTTP 200 с HTML для `/`, `/news/`, `/status/`, `/kb/`.
- Браузер без установки приложения: одна ссылка на manifest на этих четырёх страницах и на `/815/compare/` как вложенной странице другого раздела; после клиентского перехода между разделами ссылка остаётся корректной. Обычная навигация работает, запрос manifest не блокируется применяемой CSP. Разрешение same-origin manifest также сверяется с production `security.conf`, поскольку preview сам не воспроизводит nginx-заголовки.
- Ревью всего diff по требованиям, включая отсутствие добавленного install UI, service worker и лишних абстракций.

Проверка параметров запуска в manifest заменяет обязательную проверку реального запуска установленного приложения по решению владельца. В PR следует явно разделить выполненные локальные проверки и непроверенное системное меню; не утверждать, что установка на Android или Mac была проверена.

### 5. Передача новой сессии

Рабочая ветка — `feat/724-installed-app-shortcuts`. Владелец разрешил commit, push и PR и попросил сначала опубликовать документы в PR для чтения. На этом этапе PR остаётся draft с `Refs #724`; реализация требует отдельного разрешения после ревью артефактов.

После такого разрешения текущая сессия сохраняет итоговую версию согласованных документов в ветке и оставляет в issue короткую отметку разрешения со ссылками на соответствующий коммит и change. На этой точке работа передаётся новой сессии до изменения кода функциональности. Реализация добавляется в тот же PR.

Новая сессия читает issue, change, отметку разрешения и фактическое состояние ветки, затем продолжает по `tasks.md`. Результат восстановления контекста фиксируется в #724 для приёмки пилота #735. Успех передачи нельзя объявить по самопроверке текущей сессии.

## Risks / Trade-offs

- Системное меню и реальная установка не проверяются → локальная приёмка подтверждает только manifest, ресурсы и страницы; это согласованное ограничение результата.
- Браузер или launcher может показывать пункты и обновлять manifest по своим правилам → использовать стандартные поля и стабильный `id`, не обещать одинаковый интерфейс или мгновенное обновление.
- Готовые PNG могут получить поля при маскировании ОС → использовать корректный `purpose: "any"`; переработка графики не нужна для прямых переходов.

## Migration Plan

Миграция данных не требуется. После локальной приёмки синхронизировать `installed-web-app` с основными specs и архивировать change штатным workflow в той же ветке. PR включает код, основную spec и архив, использует `Closes #724` и ссылки на #734/#735; в #724 обновляется ссылка на архив и остаётся краткий результат настоящей передачи. Человеческое ревью и merge выполняет владелец.

Manifest и HTML-ссылка публикуются обычной статической сборкой вместе. Откат возвращает весь PR; браузеры могут сохранять ранее установленное приложение до собственного обновления метаданных или удаления пользователем.
