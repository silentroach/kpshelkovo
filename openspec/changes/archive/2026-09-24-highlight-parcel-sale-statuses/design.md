# Design

## Context

См. [proposal.md](proposal.md). По [ADR-028](../../../docs/decisions/028-markdown-first-places-map.md) участки включаются на общей карте мест; по [ADR-041](../../../docs/decisions/041-parcel-records-and-exact-search.md) их отдельный публичный JSON сейчас намеренно исключает статус продажи. [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md) требует явного адаптера публичных данных. Записи участков уже хранят `available`, `reserved`, `sold`, `unavailable` или не имеют статуса; клиентский слой сейчас создаёт один контур и одну подпись на участок, а временное выделение возвращает единый обычный стиль.

## Goals / Non-Goals

**Goals:** Использовать существующие редакционные статусы и слой без второго переключателя или отдельного запроса; сохранить читаемость номеров и различимость временного выбора на карте с подложкой.

**Non-Goals:** Подтверждать собственность, актуальную возможность покупки или дату изменения статуса; строить карточки, легенду, фильтры, историю цены и дополнительные сущности участков.

## Decisions

### 1. Передавать исходный необязательный статус в публичном представлении карты

Адаптер `/map/data/parcels.json` явно переносит `status` из редакционной модели; публичная схема допускает только четыре существующих значения и отсутствие поля. Клиент сопоставляет `available` и `reserved` одному виду, `unavailable` — второму, `sold` и отсутствие статуса — исходному нейтральному. Не вычислять статус из цены, контура или особенностей участка. Это одно дополнительное поле в уже отложенно загружаемом JSON, без нового endpoint и зависимости. Альтернатива — передавать только производный код визуальной группы; она экономит незначительный объём, но скрывает, какие исходные сведения публикуются, и создаёт второй словарь статусов.

### 2. Оформлять существующие контуры и короткие номера

Сохранить обычную геометрию, границы и масштаб показа номеров. Добавить к непроданным `available`/`reserved` одинаковую слабую заливку на основе существующих токенов; для `unavailable` использовать слабую серую заливку и нейтральные сероватые фон/рамку капсулы номера без ослабления контраста самого текста. Для `sold` и отсутствующего статуса сохранить исходный стиль без заливки и исходную капсулу. Выбор любого контура временно применяет существующий заметный стиль, а по окончании пяти секунд возвращает _его собственный_ обычный стиль. Не вводить новые токены, палитры и отдельные маркеры. Одних окрашенных капсул недостаточно: на общем масштабе номера скрыты, поэтому нужна именно заливка контуров.

### 3. Ограничить семантику визуальной подсказки

Не добавлять видимую легенду, статус на нажатии, ссылку на застройщика или дату обновления — по согласованному объёму это фоновое оформление, а не проверочный инструмент. Сохранить доступное имя кнопки номера и, если к нему добавляется статус для экранного диктора, не менять видимый текст и действие кнопки. Точное содержимое подписи не требует отдельного решения о поведении карты. `PRODUCT.md` и дизайн-гайд требуют, чтобы значимые статусы не передавались только цветом и неизвестность не подменялась отрицательным выводом. При реализации документировать узкое исключение для необязательной раскраски участков: отсутствие заливки не утверждает собственность; цвет нельзя описывать как надёжный ответ о продаже. Другие статусные интерфейсы сохраняют общие правила. Для сайта в целом сохраняется цель WCAG AA; риск этого конкретного способа подачи вторичных сведений отмечен ниже.

## Risks / Trade-offs

- Цвет без легенды и видимой подписи нельзя однозначно расшифровать, в том числе при особенностях цветовосприятия → оставить оформление спокойным и вторичным; не использовать его для действий, проверочных утверждений или текста «этот участок куплен». Это сознательное локальное исключение, а не подтверждение доступности цветовой информации для всех.
- Снимки генпланов обновляются по запросу → окраска показывает только сохранённые сведения, без обещания актуальности на момент просмотра; новых автоматических выводов о собственности и продаже не делать.
- Участок без статуса внешне совпадает с проданным → отсутствие заливки не считать доказательством продажи ни в коде, ни в документации.
- Цвет заливки поверх подложки и мест может оказаться чрезмерным → подобрать слабую прозрачность и проверить общий вид, приближение, взаимодействия и контраст номера на реальной карте до принятия.

## Migration Plan

Схема публичного JSON расширяется необязательным полем, редакционные файлы не меняются. Обновить ADR-041 и основной `parcel-map` после приёмки; в `Purpose` основной спецификации убрать старую формулировку «без кодирования статуса продажи». Откат — возврат вместе с изменением адаптера, стилей и описаний, без миграции записей.
