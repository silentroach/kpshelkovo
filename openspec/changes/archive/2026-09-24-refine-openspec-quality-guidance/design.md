# Design

## Context

Причина изменения описана в [proposal.md](proposal.md). В проекте установлен OpenSpec 1.13.1: он читает `rules` при подготовке артефактов и `operations.apply.guidance` при запросе инструкций для apply. Эти секции уже используются в `openspec/config.yaml`.

[ADR-038](../../../../docs/decisions/038-openspec-development-workflow.md) закрепляет штатную схему и хранение проектных дополнений в конфигурации. Требования `agent-tooling` сохраняются; рабочие формулировки хранятся в конфиге, поэтому delta specs для этого изменения не нужны.

## Goals / Non-Goals

**Goals:**

- Передавать каждое дополнение на нужном этапе через существующий механизм OpenSpec.
- Сохранить точный смысл правил после редактуры по `humanizer-ru`.

**Non-Goals:**

- Создавать новые этапы согласования, вводить обязательные subagents или TDD.
- Переносить в конфиг весь процесс Plus либо повторять действующие правила из `AGENTS.md`.

## Decisions

### Дополнить существующие списки

Правила подготовки артефактов добавляем в `rules`, указания для работы над задачами в `operations.apply.guidance`. Общий `context` оставляем для сведений и ограничений проекта. Новые правила читаются при запросе инструкций, поэтому регенерация skills не нужна.

Отдельный набор Plus потребовал бы согласовывать его процесс с проектным. Собственная схема и ручные правки generated skills усложнили бы обновления. Штатный конфиг поддерживает все выбранные дополнения.

### Формулировки для согласования

После редактуры по `humanizer-ru` добавляем следующие пункты к существующим спискам:

```yaml
rules:
  proposal:
    - >-
      Перед выбором решения выясни проблему, нужный результат и границы задачи.
      Используй уже полученные ответы; спрашивай только о том, от чего зависят
      объём или поведение.
  specs:
    - >-
      Перед завершением specs сверь их с решениями, согласованными в обсуждении.
      Сохрани важные ограничения и различия в поведении. Условия, нужные только
      для выполнения этой задачи, запиши в design или tasks по правилам отбора
      требований.
  design:
    - >-
      При важном техническом выборе сравни подходящие варианты, включая то,
      что уже есть в проекте. Объясни, почему выбран этот вариант и на какие
      компромиссы идём. Не добавляй альтернативы ради количества.
  tasks:
    - >-
      По возможности группируй работу по проверяемому результату: в одну группу
      входят все нужные для него технические слои. Учитывай зависимости между
      группами. Выделяй подготовку, документацию и общую приёмку в отдельные
      задачи, когда это нужно.
    - >-
      Проверь, что задачи охватывают согласованный объём: для каждого важного
      требования есть работа и способ проверки. Каждая задача должна следовать
      из требований, дизайна или правил проекта.
operations:
  apply:
    guidance:
      - >-
        Прежде чем отметить задачу выполненной, проверь результат указанным
        в ней способом. Сборка и проверка типов сами по себе не доказывают,
        что нужное поведение работает.
      - >-
        Не отключай и не ослабляй проверки ради успешного прогона. Если проверка
        расходится с согласованными требованиями, выясни причину. Изменение
        требований согласуй с владельцем.
```

## Risks / Trade-offs

- Инструкции не гарантируют, что агент выполнит каждое правило. CLI-проверка подтверждает их доставку; качество работы оцениваем по артефактам и результатам приёмки.
- Требование группировать работу по результату может оказаться неудобным для инфраструктуры и документации. В формулировке оставлены «по возможности» и отдельные задачи подготовки, документации и общей приёмки.

## Migration Plan

После согласования добавить пункты в конфиг и проверить выдачу инструкций. Новые правила действуют со следующего запроса к CLI. Откат удаляет добавленные пункты.
