## Context

Причина изменения описана в [proposal.md](proposal.md), наблюдаемое поведение — в [спецификации](specs/place-opening-hours/spec.md).

Сейчас расписание есть у трёх мест: Буржуйки, КПП Вилладжа и Green Dreams. Их `description` полностью повторяют `periods`; содержательных пояснений внутри этих полей нет. HTML и Markdown читают текст, а статус карточки и маркеров карты — интервалы. JSON карты уже экспортирует и `description`, и `periods`; клиент переносит описание в доменную форму, но статус от него не зависит.

Схема уже поддерживает несколько интервалов в день и часы в пределах одного дня. Пересечения и соприкосновения пока допускаются. `getPlaceClosingTime()` выбирает первый подходящий интервал, поэтому пересечение может дать неверное время «открыто до».

Подход опирается на действующие решения:

- [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md): отдельные raw-схема, readonly domain model и Public DTO.
- [ADR-028](../../../docs/decisions/028-markdown-first-places-map.md): карточки готовятся при сборке; общая карта работает на клиенте.
- [ADR-008](../../../docs/decisions/008-markdown-ast-generation.md): Markdown собирается через AST.
- [Дизайн-гайд](../../../docs/design/design-code-shelkovo.md): компактные плоские блоки, читаемые подписи и числовая типографика.

## Goals / Non-Goals

**Goals:**

- Переиспользовать одну функцию представления недели в HTML и Markdown; исходные интервалы остаются источником данных для статуса.
- Отклонять неоднозначные исходные данные до публикации и согласованно провести необязательность пояснения через все границы.
- Дать владельцу наглядные примеры расписания для проверки этой спецификации.

**Non-Goals:**

- Новый календарный движок, ночные часы, `24:00`, праздники, сезонность и часовые пояса отдельных мест.
- Новые статусы вроде «скоро закроется», расписание услуг внутри места или вывод часов в JSON-LD.
- Универсальное встраивание расписаний places в контакты: для Буржуйки достаточно существующей mention-ссылки.

## Decisions

### 1. Компактные строки в календарном порядке

Форматирование в `apps/www/src/lib/places/opening-hours.ts` строит представление семи дней из `periods`, сортирует интервалы каждого дня по началу и группирует только последовательные дни с равными списками интервалов. Порядок дней и периодов в редакционном файле не определяет порядок вывода. Воскресенье не объединяется с понедельником через границу недели.

HTML- и Markdown-адаптеры получают одинаковые подписи дней и часов. Функция не меняет исходные периоды и не объединяет временные интервалы. Группировка дней нужна только для чтения; клиентскому расчёту статуса достаточно исходных проверенных `periods`.

Рассмотрены семь отдельных строк, объединение несоседних дней и раскрываемая неделя. Выбраны компактные открытые строки: по ним легко найти день, а одинаковый график не занимает семь строк.

#### Пример: Буржуйка

**Часы работы**

- пн: 10:00–19:00
- вт: выходной
- ср–пт: 10:00–19:00
- сб–вс: 10:00–20:00

#### Пример: Green Dreams

**Часы работы**

- пн–чт: 09:00–22:00
- пт–сб: 09:00–23:00
- вс: 09:00–22:00

#### Пример: КПП Вилладжа

**Часы работы**

- Ежедневно: 07:00–23:00

#### Условный пример с перерывом и пояснением

**Часы работы**

- пн–пт: 09:00–13:00, 14:00–18:00
- сб–вс: выходной

Вход со двора.

### 2. Расписание готовится при сборке, статус — в браузере

Весь `opening_hours` необязателен. При его отсутствии HTML- и Markdown-карточки пропускают блок часов и статус работы, а общая карта — сведения о них в подписях. Заглушка «неизвестно» или другое сообщение об отсутствии расписания не выводится.

Если расписание задано, `PlaceOpeningHours.astro` выводит семантический список строк внутри существующего блока сведений о месте. На телефоне и компьютере видна вся неделя. Дни и часы образуют две общие колонки: ширина первой определяется самой длинной подписью дней, часы всех строк начинаются на одной линии. Двоеточия в HTML не выводятся; Markdown сохраняет их. Несколько интервалов переносятся внутри правой колонки, отдельный диапазон времени не разрывается. На мобильном экране расписание и пояснение сдвинуты на 12px вправо относительно заголовка, без дополнительного правого отступа; на широком экране заголовок остаётся слева от расписания. Для времени используется существующая числовая типографика.

Строки нерабочих дней целиком используют существующий `--color-text-muted`, рабочие строки — основной цвет текста. Это лёгкое отличие для обычного выходного с сохранением читаемого контраста и подписи «выходной». У Буржуйки приглушается строка вторника; рабочие суббота и воскресенье имеют обычный цвет. В Markdown смысл передаёт та же текстовая подпись.

Пояснение выводится отдельным текстом под списком только при наличии значения и проходит через существующий типограф. Вместо плашки статус показывает закрашенный круг диаметром 8px справа непосредственно от «Время работы»: зелёный, когда место открыто, красный, когда закрыто. Обычный HTML-атрибут `title` содержит «Открыто до HH:MM», где время — конец текущего интервала, или «Сейчас закрыто»; отдельная мобильная подсказка не нужна. Визуально скрытая доступная подпись с `aria-live` передаёт статус скринридерам. Статус вычисляется клиентом по `Europe/Moscow` и обновляется раз в минуту. Без JavaScript индикатор скрыт, полное расписание доступно; статический HTML не выдаёт момент сборки за текущее время.

`lib/places/markdown.ts` использует те же строки как список через `md`, затем добавляет абзац пояснения при его наличии. Это сохраняет одинаковый смысл HTML и Markdown без второго форматировщика или ручной сборки документа.

### 3. Конфликты исправляет редактор

В Zod-схеме `lib/places/raw-schema.ts` проверка расписания рассматривает периоды отдельно для каждого общего дня недели. После сортировки по началу следующий интервал обязан начинаться строго позже окончания предыдущего. Равенство границ, частичное пересечение, вложенный интервал и полный дубль отклоняются. Одинаковые часы в разных днях не конфликтуют.

Сообщение проверки указывает день и конфликтующие интервалы; контекст загрузчика добавляет файл или slug места. Для соприкосновения сообщение предлагает записать непрерывные часы одним периодом. Самостоятельного исправления данных при загрузке нет.

Альтернатива — автоматически сливать интервалы для показа и статуса. Владелец выбрал запрет: редактор должен явно задать непрерывное время работы. На валидном расписании текущий поиск интервала однозначен; границы `[opensAt, closesAt)` сохраняют настоящий перерыв.

### 4. Необязательное пояснение на каждой границе

В raw-схеме `description` становится optional; непустая строка проверяется только при наличии. Необязательность отражается в `types.ts`, `mapper.ts`, `map-public-dto.ts`, `map-public.ts`, `map-types.ts` и клиентском адаптере `PlaceMap.svelte` там, где передаётся расписание.

Публичный `/map/data/places.json` продолжает отдавать `periods` с `days`, `opens_at`, `closes_at`. `description` содержит только пояснение, а при его отсутствии ключ не сериализуется. Сгенерированное расписание в это поле не подставляется.

Рассмотрена совместимость через обязательное автоматически составленное описание в JSON. Владелец выбрал единый смысл поля во входных и публичных данных. Это осознанное изменение публичного контракта, поэтому тест Public DTO должен проверять оба случая: с пояснением и без него.

Discovery-описания карты пересматриваются вместе с контрактом: отдельной опубликованной JSON Schema для places сейчас нет, а существующие описания ресурсов не обещают обязательный `description`. Новая схема или версия API для этого изменения не вводится.

### 5. Миграция редакционных данных

Удалить дублирующие `description` из `burzhuyka.md`, `village-checkpoint.md` и `green-dreams.md`, сохранив их интервалы. В body Green Dreams отдельно остаются часы завтраков: они относятся к услуге, а не к доступности ресторана.

В `apps/www/src/data/contacts/food/burzhuyka.md` заменить два предложения с часами подписанной mention-ссылкой `[Часы работы — в карточке места](@burzhuyka)`. Механизм упоминаний уже поддерживает места в contacts и создаёт ссылку на `/map/burzhuyka/` в HTML и Markdown.

В `apps/www/src/data/places/AGENTS.md` обновить правило редактирования часов: интервалы определяют график, описание содержит только дополнительное пояснение, непрерывные часы задаются одним интервалом.

### 6. Отдельный компонент и визуальная регрессия

Расписание остаётся отдельным компонентом `PlaceOpeningHours.astro`, а форматирование недели — модулем `lib/places/opening-hours.ts`. Для проверки компонента используется существующая инфраструктура локальных Astro fixtures и Playwright по образцу `NewsEventCard`: настоящие компонент и стили, PNG-эталоны и отдельные команды сравнения и обновления.

Пять вариантов проверяются на широком и узком экране: ежедневный график, выходной посреди недели, разные часы в конце недели, перерыв с пояснением и отсутствие расписания. Время фиксируется до открытия страницы, чтобы динамический статус был воспроизводимым. Пустой вариант снимается вместе с соседним фактом карточки. Эталоны просматриваются перед сохранением; после генерации выполняется отдельный прогон сравнения. Как остальные screenshot suites проекта, эти тесты запускаются локально.

## Risks / Trade-offs

- Внешний клиент может ожидать обязательный `description` → изменение явно отмечено как breaking; `periods` сохраняет существующие имена полей, а потребители пояснения должны учитывать его отсутствие.
- Совпадение только первого интервала дня может ошибочно объединить разные расписания → сравнивается полный отсортированный список; тест включает дни с одинаковым утром и разным временем после перерыва.
- Длинный список интервалов может плохо читаться на телефоне → разовая браузерная проверка узкого экрана и естественного переноса строк.
- Статус может разойтись с расписанием на границе перерыва или московского дня → тестируются начало, конец, перерыв и другой часовой пояс устройства на фиксированных моментах времени.

## Migration Plan

1. Опубликовать этот change для просмотра спецификации владельцем. Публикация планирующего PR не означает разрешение реализации.
2. После явного разрешения обновить в рабочей ветке схему, типы, представления, данные и инструкцию; выполнить задачи из [tasks.md](tasks.md).
3. До выпуска проверить сценарии, typecheck, тесты, сборку и карточки в браузере. Приёмка проходит до публикации; обязательная production-проверка не требуется.
4. После готовности реализации синхронизировать основной spec и архивировать change штатным workflow. До этого артефакты остаются активным планом; issue #751 остаётся открытым.
5. При необходимости отката реализации вернуть согласованный комплект кода, схемы, данных и инструкции: возврат одной обязательности `description` без самих описаний сломает загрузку мест.
