## Context

Мотивация и границы задачи описаны в [proposal.md](proposal.md). Единственный production-caller `buildArticleEventIcs` — `apps/www/src/pages/news/[year]/[month]/[entry]/[event].ics.ts`; UI и публичный JSON используют уже сформированный `icsUrl`.

Исходные даты проходят Zod-схемы и московский парсинг до генерации календаря. `NewsEvent` хранит абсолютные `Date`, а справочник `Place` предоставляет название, необязательный адрес и обязательные координаты. Модуль `calendar.ts` одновременно выбирает эти данные и реализует escaping, folding и оболочку ICS.

Действующие основания:

- [ADR-013](../../../../docs/decisions/013-raw-domain-public-data-boundary.md): преобразование доменной модели в публичный формат остаётся отдельным адаптером; внутренние типы — handwritten readonly.
- [ADR-011](../../../../docs/decisions/011-public-surface-registry.md): ICS — существующая публичная поверхность со стабильными маршрутами и типом данных.
- [news-event-places](../../../specs/news-event-places/spec.md): источник данных места, уточнение встречи, географические свойства и ссылка на новость уже определены.

Это локальное разделение существующего модуля по установленным границам; отдельный ADR не требуется.

## Goals / Non-Goals

**Goals:**

- Один независимый сериализатор с небольшим типизированным входом и один новостной адаптер.
- Проверки формата на уровне пакета и предметных правил на уровне приложения.
- Те же файлы служат проверяемыми снапшотами и материалом для ручного импорта.

**Non-Goals:**

- Универсальная модель iCalendar: parser, recurrence, timezone database, alarms, plugin API или произвольные свойства.
- Дополнительные потребители пакета, публикация в npm и отдельный build-step пакета.
- Изменение формулы UID, добавление `SEQUENCE` или обещание автоматического обновления ранее импортированной записи.

## Decisions

### 1. Выделить собственный `@shelkovo/ical`

Создать private workspace-пакет в `packages/ical` по образцу небольших существующих пакетов с экспортом TypeScript из `src`. Перенести действующие алгоритмы escaping, UTC и UTF-8 folding с согласованными исправлениями. Ожидаемый сериализатор — порядка сотни строк без типов и тестов; это оценка объёма, не ограничение реализации.

Сравнение проведено по документации и исходникам опубликованных версий:

- [`ical-generator@11.1.1`](https://github.com/sebbo2002/ical-generator/tree/v11.1.1) — ближайший внешний вариант: MIT, TS/ESM, без обязательных runtime-зависимостей, встроенная Apple location, RFC 6868 и UTF-8 folding. Отсутствующий конечный CRLF, другой разделитель адреса и дополнительный `X-ADDRESS` допустимы для адаптера. Однако [GEO пропадает при нулевой координате](https://github.com/sebbo2002/ical-generator/blob/v11.1.1/src/event.ts#L1783-L1791), а [URL проходит TEXT escaping](https://github.com/sebbo2002/ical-generator/blob/v11.1.1/src/event.ts#L1949-L1952). Для всех допустимых данных понадобилась бы ручная вставка свойств в готовый календарь. Этот компромисс не выбран.
- [`ics@3.12.0`](https://github.com/adamgibbons/ics/tree/v3.12.0) — нет нужного расширения Apple location, folding считает Unicode-символы вместо UTF-8-байт; прямые зависимости `nanoid`, `runes2`, `yup`.
- [`ical.js@2.2.1`](https://github.com/kewisch/ical.js/tree/v2.2.1) — поддерживает типизированные свойства и параметры без runtime-зависимостей, но требует более подробного адаптера, настройки folding и нормализации переводов строк. Его универсальная модель не нужна для текущего экспорта одного события.

Собственный код остаётся ответственностью проекта. Выбор сделан ради малого и прямого решения без обходов библиотечного сериализатора, а не на основании универсального превосходства нашей реализации.

### 2. Передавать в пакет готовые календарные значения

Один публичный renderer получает UID, PRODID, timestamp, начало, окончание, заголовок, описание, URL и необязательное место с названием, адресом и координатами. Типы находятся отдельно от кода; параметры и вложенные данные readonly. Пакет не импортирует модели, aliases, окружение или loaders приложения.

Вход — доверенные типизированные данные после существующей app-валидации. Не дублировать raw-схемы в пакете; невалидная дата продолжает приводить к ошибке, а не к подстановке текущего времени. Пакет не выбирает UID, даты или содержание по умолчанию и не мутирует вход.

`apps/www/src/lib/news/calendar.ts` сохраняет фасад `buildArticleEventIcs`, `hasArticleEvents`, `articleEventIcsFilename` и следующие правила:

- UID: `${safeToken("news-event-" + article.id + "-" + event.slug)}@${new URL(article.canonical).host}` с текущим `safeToken`; filename — `${safeToken(event.slug)}.ics`.
- PRODID: `-//<host canonical>//News Events//RU`; timestamp — `article.publishedAt`.
- Окончание — `event.endsAt` или начало плюс 7 200 000 ms. Этот fallback остаётся только в ICS и не дописывается в доменную модель, JSON или JSON-LD.
- Описание — `event.description ?? article.summary`, затем непустой `locationDetails` через пустую строку; URL — `article.canonical`.
- Актуальное место переводится в календарные данные; отсутствие места означает отсутствие `LOCATION`, `GEO` и Apple location.

Сериализатор сохраняет `VERSION:2.0`, `CALSCALE:GREGORIAN`, `METHOD:PUBLISH`; координаты идут в порядке latitude/longitude. `LOCATION` остаётся названием с доступным адресом через запятую, Apple location — с `VALUE=URI`, `X-APPLE-RADIUS=100` и названием в `X-TITLE`. Случайные UID, текущее время и дополнительные поля не нужны. Даты выводятся в UTC с точностью до секунды, как в действующей реализации.

### 3. Исправить только найденные дефекты формата

- TEXT escaping сохранить отдельно от parameter encoding; URI не экранировать как TEXT.
- Для параметров применять [RFC 6868](https://www.rfc-editor.org/rfc/rfc6868): `^` → `^^`, двойная кавычка → `^'`, нормализованный перевод строки → `^n`. Backslash в параметре сохраняется без удвоения; внешний quoting остаётся допустимым. CRLF и одиночный CR сначала нормализуются в LF.
- Координаты в `GEO` и `geo:` URI записывать десятичным представлением без экспоненты и без произвольного округления. Явно сохранить ноль и отрицательные значения. Проверить случай `0.0000001`, для которого обычное преобразование числа выдаёт `1e-7`.
- Переносы выполнять после encoding, считая UTF-8-байты всей физической строки и пробел продолжения; не разрывать Unicode-символ. Сохранять завершающий CRLF.

Правила формата основаны на [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545). Новые способы кодирования могут изменить строковое представление; сохранение смысла данных важнее побайтового совпадения с ошибочным encoding.

#### Уточнение после ручного импорта: обратная косая черта перед переносом

Владелец проверил семь коротких примеров в Apple Calendar. Сочетание обратной косой черты и следующего сразу за ней переноса отображается служебным текстом и в месте, и в описании. Замена `\n` на допустимое по RFC `\N` и удаление Apple location не помогли. Пример с одним пробелом между косой чертой и переносом отобразился правильно; обычный перенос без косой черты также работает.

Владелец явно согласовал обход в сессии 17 сентября 2026 года. Перед escaping заголовка, описания и данных места нормализовать CRLF/CR в LF, затем заменить только соседство обратной косой черты и LF на косую черту, один ASCII-пробел и LF. Применить то же правило к названию в `X-TITLE`, чтобы два представления места совпадали. Уже имеющийся пробел и буквальные символы `\n`/`\N` сохранять. UID, PRODID и URI обход не затрагивает; входные данные не мутируются. Это согласованное исключение из точного сохранения текста, а не дополнительное правило RFC.

Регрессия проверяет все три исходных окончания строк, видимые TEXT-поля и параметр места. Открываемый `escaped-text.ics` включает сочетание в месте и описании. После проверок change возвращается в архив в той же ветке PR #758; временные диагностические файлы удаляются.

### 4. Использовать открываемые файловые снапшоты

В `packages/ical/src/index.test.ts` генерировать четыре небольших календаря и проверять сырой результат через `await expect(ics).toMatchFileSnapshot(...)`. Эталоны хранить в `packages/ical/src/fixtures/`:

- `with-place.ics`: место с адресом, координатами, описанием и уточнением встречи в готовом тексте.
- `without-place.ics`: событие без географических свойств.
- `place-without-address.ics`: место с названием и координатами без адреса.
- `escaped-text.ics`: длинные кириллица и emoji, специальные символы текста и параметров, переход через полночь.

У примеров фиксированные даты и разные стабильные UID. Пакет получает окончание и описание явно; app-fallback проверяется в тестах адаптера. Эти `.ics` — единственный полный snapshot-baseline, без второй копии в inline snapshots или отдельного генератора файлов.

Команды из корня workspace после появления пакета:

```bash
pnpm --filter @shelkovo/ical exec vitest run src/index.test.ts --update=none
pnpm --filter @shelkovo/ical exec vitest run src/index.test.ts -u
```

Первый запуск сравнивает результат с сохранёнными файлами и падает при несовпадении или отсутствии эталона. Вторая команда намеренно создаёт или обновляет эталоны; её diff требует ревью. Обычный локальный Vitest может создавать отсутствующие snapshots, поэтому проверку наличия эталонов выполнять с `--update=none`.

Vitest может нормализовать окончания строк при сравнении. Отдельные точечные assertions поэтому проверяют CRLF, конечный CRLF, лимит 75 байт, сохранность кириллицы/emoji, parameter encoding, нулевые и маленькие координаты. Сохранить CRLF эталонов при checkout; если нужна настройка Git, ограничить её этими `.ics`-файлами.

В приложении оставить короткие проверки UID/filename/URL, описания, `DTSTAMP`, явного окончания не через два часа, fallback и актуальных данных места. При сравнении старого и нового вывода допускается другой порядок строк; повторяющиеся полные app-snapshots заменить предметными проверками. Не писать универсальный ICS-parser ради тестов.

### 5. Передать владельцу те же файлы для ручного импорта

В README пакета указать команды, четыре файла и ожидаемые результаты: время и длительность, описание, ссылка на новость, название/адрес и распознавание места. Владелец импортирует файлы в Apple Calendar до merge реализации. Агент может подготовить PR после автоматических проверок, явно отметив оставшуюся ручную приёмку. Production-проверка не является условием завершения change.

## Risks / Trade-offs

- Ошибки RFC остаются нашей ответственностью → узкий API, отдельные проверки encoding/folding и открываемые эталоны.
- Snapshot-обновление может закрепить регрессию → обновлять явно, просматривать diff и проверять важные инварианты независимо от snapshot.
- Одинаковые UID тестовых файлов могут вызвать повторное использование импортированной записи → разные UID между примерами; повторную ручную проверку проводить в отдельном тестовом календаре.
- Структурно правильный Apple extension не гарантирует отображение карты клиентом → ручной импорт владельцем до merge.

## Migration Plan

1. Открыть PR с артефактами для ревью владельцем. Реализация начинается только после отдельного явного разрешения по проверенной версии change; продолжить в рабочей ветке задачи.
2. Зафиксировать текущие URL, filename, UID и календарные значения реальных событий как baseline для разового сравнения, затем подключить пакет через существующий фасад. Миграция контента и маршрутов не нужна.
3. Выполнить package/app-тесты, typecheck, сборку и разовое сравнение существующих экспортов по смыслу. Проверить весь diff и OpenSpec.
4. После самостоятельной проверки синхронизировать новую основную spec и архивировать change штатным workflow в ветке реализации. В PR передать результаты проверок и файлы для оставшегося ручного импорта до merge.
5. При необходимости откатить пакет, подключение, тесты и сопровождающие документы вместе; URL и UID не требуют отдельной миграции.
