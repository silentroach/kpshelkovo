# Design

## Context

Границы и причина — в [proposal.md](proposal.md), изменение контракта — в [delta spec поиска](specs/search/spec.md). [ADR-025](../../../../docs/decisions/025-static-full-text-search-with-pagefind.md) закрепляет общую релевантную выдачу Pagefind, [ADR-041](../../../../docs/decisions/041-parcel-records-and-exact-search.md) на момент подготовки описывал отдельный точный фильтр участков. Уже опубликованный [change `index-parcels-with-pagefind`](../2026-09-23-index-parcels-with-pagefind/design.md) оставляем историческим свидетельством предыдущего решения.

Сейчас `build-search-index.ts` добавляет 1 588 custom records с `content` только из полного основного кода, служебной `meta.sectionLabel: 'Участки'` и `filters.parcelCode` для полных и коротких кодов. Клиент параллельно вызывает текстовый Pagefind и `pagefind.search(null, { filters: { parcelCode } })`, затем вручную закрепляет найденные участки перед страницами. На текущей локальной production-сборке обычный Pagefind находит полный код, но не находит короткие `L43`/`A10`; запрос «участки» без фильтра даёт совпадение всех записей по служебной metadata. Холодный поиск номера до изменения описан в PR #810: 19 ресурсов Pagefind и 388 503 байта расчётного сетевого тела для выбранного алиаса.

## Goals / Non-Goals

**Goals:**

- По запросу кода или короткого номера получать общую выдачу одним полнотекстовым вызовом Pagefind без filter-only запроса и отдельной сборки двух списков.
- Сохранять нормальные тематические результаты и понятную строку участка с переходом на карту, не превращая подпись раздела в поисковое слово каждой записи.
- Сравнить релевантность и холодные байты на локальной production-сборке до/после, не обещая выигрыш без замера.

**Non-Goals:**

- Пересматривать подтверждённые соответствия бывших обозначений, модель `aliases`, прямые ссылки карты либо геометрический feed.
- Переписывать обычную коррекцию однословных текстовых запросов сайта, которая уже использует дополнительный поиск по цитате; правило «один вызов» относится к запросам с обозначением участка, а не ко всем запросам сайта.
- Вводить отдельный поисковый словарь, страницы каждого участка или новый движок.

## Decisions

### 1. Индексировать короткие обозначения как поисковые слова

По одной записи на нынешний участок по-прежнему строится из проверенного `/map/data/parcels.json`. В `content` добавляются полный и отдельный короткий вариант основного кода и каждого подтверждённого алиаса. Сохранить минимальную metadata, необходимую для отображения основного кода, части и пояснения алиаса, но убрать `sectionLabel: 'Участки'` из индексируемых значений; интерфейс знает эту подпись по `sectionId: 'parcels'`. Убрать фильтры `parcelCode` и `section`, если больше нет их потребителей. Публичная запись не получает геометрию и коммерческие поля.

**Почему:** Pagefind не разбивает текущий полный код так, чтобы короткий номер гарантированно находился; отдельное слово решает это без второго механизма поиска. Нулевой вес `sectionLabel` не препятствует совпадению по его тексту: без удаления metadata общий запрос «участки» начинает находить все служебные записи.

### 2. Получать участки и страницы из одного полнотекстового ответа

Для запросов в формате полного или короткого обозначения, включая префикс уже существующего номера, клиент делает один `pagefind.search(query)` и нормализует возвращённые ссылки обоих типов из одной порции. Участок определяется по `sectionId`, получает постоянную подпись раздела, основной код и часть из metadata, а URL берётся из исходного `raw_url`, чтобы Pagefind-подсветка не изменила `?p=`. Пояснение об алиасе показывается только когда запрос совпал с ним как с полным или коротким обозначением. Общий `total`, лимит и догрузка опираются на единый список Pagefind; существующие защита от устаревших ответов и retry остаются.

Для остальных текстовых запросов сохранить действующую проверку префиксного и цитатного совпадения, но снять исключающий фильтр `section: parcels`: записи участвуют в том же корпусе. В частности, цифровой фрагмент не становится обозначением участка лишь потому, что он встретился в коде. Ни одна ветка не делает дополнительный filter-only поиск и не переносит все участки в начало. Отдельная логика нормализации результата участка остаётся только потому, что запись без HTML отличается от результата обычной страницы.

**Почему:** один список устраняет загрузку всех частей индекса ради `search(null, ...)` и ручное соединение выдач. Альтернатива — оставить фильтр и добавить короткие слова в `content` — сохраняет две ветки поиска и специальный приоритет вопреки выбранному поведению. Полностью убрать существующий цитатный fallback для произвольных текстовых запросов означало бы отдельное изменение релевантности страниц.

### 3. Изменить действующее описание точного поиска

После проверки результата обновить ADR-041: участок остаётся отдельным доменным объектом и Pagefind custom record, но поиск номеров больше не использует точный фильтр и не гарантирует первое место перед обычными страницами. Delta spec `search` при завершении синхронизируется с основным контрактом; `parcel-map` и `parcel-records` не меняются. Проверка на уже развёрнутом production **не требуется**: до публикации достаточно локальной production-сборки, сравнения выдачи и байтов и браузерной проверки переходов.

## Risks / Trade-offs

- **Частичные и числовые совпадения могут давать участки и менять порядок обычных страниц** → до/после проверить номерные префиксы, цифры, общие темы и догрузку; принять только полезную выдачу, а не только исчезновение второго вызова.
- **Короткие номера не попадут в корпус из-за токенизации Pagefind** → проверить реальный индекс для одинаковых коротких номеров разных частей и алиаса, а не только unit-мок.
- **Один запрос всё ещё может загрузить много ресурсов или вытеснить полезные результаты** → сравнить холодные ресурсы, расчётные сетевые байты и фрагменты с замером PR #810 и контрольными текстовыми запросами; при неудаче вернуться к обсуждению до завершения реализации.
- **Pagefind добавляет `h` к URL записи** → использовать `raw_url`, сохранить проверку канонического адреса и переход из диалога без лишних параметров.

## Migration Plan

Сначала зафиксировать текущую выдачу и холодные запросы по согласованному набору, затем изменить сборку и клиент в текущей ветке. Проверить `build`, `search:prepare`, поисковые тесты, браузер и байты после изменения; актуализировать ADR-041 и PR #810. После разрешения и полной приёмки синхронизировать `search` и архивировать change в том же PR. Откат — возврат всего изменения сборки индекса, клиента и документов; прежний архив не редактируется.
