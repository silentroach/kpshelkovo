# Design

## Context

Мотивация и границы — в [proposal](/openspec/changes/archive/2026-09-30-optimize-map-marker-images/proposal.md), исходная задача — [#887](https://github.com/silentroach/kpshelkovo/issues/887). Design нужен из-за выбора растровых разрешений, общей доставки ресурсов и сетевой приёмки нескольких потребителей.

- [Реестр](/packages/ui/src/markers/index.ts) импортирует семь подготовленных PNG через `?url`. Их ширина — 144 px; высота зависит от рисунка. Редакционные `*-source.png` не импортируются.
- [Обзорная карта](/apps/www/src/components/places/PlaceMap.svelte) создаёт обычные DOM `img` и передаёт контейнер в `YMapMarker`. Нативный `srcset` доступен, API Яндекса не ограничивает выбор одним URL.
- [Превью](/apps/www/src/components/places/PlacePreview.astro), [ближайшие места](/apps/www/src/pages/map/[slug]/index.astro) и [визуальный каталог](/packages/ui/tests/icons-visual/src/pages/index.astro) тоже используют HTML `img`. Превью хранится в шаблоне до создания карты; этот жизненный цикл сохраняется.
- При корневом шрифте 16 px превью имеет ширину 48 CSS px, список — 32 CSS px. На обзорной карте обычный рисунок имеет базовую ширину 32 CSS px, яблоко — 28, строительство — около 21,333. Zoom-множитель лежит в диапазоне 0,625–1,3, hover/focus добавляет множитель 1,16. Максимум обычной графики — 48,256 CSS px; CSS-трансформации не учитываются автоматически при выборе источника.
- Статические импорты выходят в хешированные файлы `static`; `assetsInlineLimit: 0`. Существующее кеширование не меняется.
- [ADR-028](/docs/decisions/028-markdown-first-places-map.md) задаёт сохранение исходников, общий реестр, достаточную плотность, центрирование и оформление маркеров. Новый ADR не нужен; описание runtime PNG следует согласовать с новым форматом без переписывания исторического обоснования.

## Goals / Non-Goals

**Goals:**

- Сократить размер семи полноразмерных доставляемых изображений минимум на 25% относительно 200 173 байт.
- Дополнительно сократить холодную передачу на DPR 1/2 нативным выбором разрешения, сохранив качество на максимальном отображаемом размере.
- Переиспользовать один и тот же выбранный вариант между потребителями при одинаковых условиях, без собственных правил переключения на каждом zoom.

**Non-Goals:**

- Не создавать универсальную библиотеку обработки изображений, новый конвертер сборки или постоянный smoke-обход всех ресурсов сайта.
- Не обещать ускорение появления карты по одному сокращению байтов. Основной сетевой трафик карты относится к Яндексу.
- Не повышать исходное разрешение ради формальных 3×: текущие 144 px при максимуме 48,256 CSS px уже чуть ниже 3×. Требование — не ухудшать существующее качество.

## Decisions

### 1. Конвертировать подготовленные runtime-изображения, а не редакционные источники

Полноразмерный файл кодируется `cwebp -lossless -exact -m 6` без ресайза. Для вариантов используется уменьшение ImageMagick с фильтром Lanczos, затем те же параметры WebP. Размер по высоте округляется растровым инструментом с сохранением исходного соотношения сторон настолько точно, насколько допускают целые пиксели. Не растягивать варианты в квадрат.

Подготовка выполняется редакционно вне runtime, доступные инструменты можно получить через `nix-shell`; зависимости приложения не добавляются. В итогах сохранить команды, версии инструментов, размеры файлов и результат сравнения декодированных RGBA. Автоматический build-конвертер не нужен для семи стабильных ресурсов.

### 2. Небольшой набор 72 / 120 / 144 px с общим размером выбора

Каждый marker record сохраняет `src`, `width`, `height` полноразмерного файла и предоставляет статический `srcset` с дескрипторами ширины. Единый `sizes` — `3.0625rem`: 49 CSS px при корневом шрифте 16 px, с небольшим запасом относительно максимума 48,256. Значение не меняет отображаемую ширину `img`; действующие стили остаются прежними.

Применить одинаковый `sizes` ко всем потребителям, включая меньшие яблоко и строительный маркер. Это уступает индивидуальному подбору в экономии, зато упрощает код и повышает вероятность одинакового выбора ресурсов между картой, превью и списком. На увеличенном корневом шрифте браузер сможет выбрать более крупный имеющийся вариант; верхний предел качества остаётся тем же, что у исходного растра.

При создании DOM-изображения задать `sizes` и `srcset` до запасного `src`, чтобы не инициировать лишнюю загрузку. `src` указывает на полноразмерный WebP, а не PNG. Никакого наблюдателя размеров, обработчика DPR, обновлений на zoom или собственного кеша.

Обновить оба app registry: mapping обзорной карты и [mapping превью/списка](/apps/www/src/components/places/marker-images.ts). Не вводить новый общий renderer и не объединять реестры отдельным рефакторингом. Проверить `sideEffects` пакета: URL-импорты не добавляют обязательной runtime-инициализации, существующие CSS-эффекты сохраняются.

Прямые PNG-subpath exports в private workspace-пакете не имеют найденных потребителей. При переходе заменить их согласованными WebP-экспортами, не оставляя ссылок на удалённые файлы; не вводить PNG-алиасы к WebP. Перед удалением повторно проверить фактические импорты ветки.

### 3. Решение основано на двух временных экспериментах

На локальном стенде 29 сентября 2026 года семь рисунков отображались обычными `img`, с реальными базовыми ширинами и максимальным CSS-множителем 1,508. Каждый изолированный DPR-прогон начинался в новой browser session; измерялись `currentSrc` и `PerformanceResourceTiming.encodedBodySize`. Это не production-сборка приложения и не измерение времени появления карты.

- Исходные PNG: 200 173 байта. Полноразмерный WebP: 140 758 байт, экономия 59 415 байт / 29,7%. Декодированные 8-bit RGBA совпали у всех семи файлов, включая прозрачные пиксели.
- Суммы файлов по ширине: 48 px — 32 006; 49 px — 33 496; 72 px — 60 702; 96 px — 91 264; 98 px — 94 484; 120 px — 126 780; 144 px — 140 758 байт.
- Набор 48 / 96 / 144 перескакивал на следующий вариант из-за максимума 48,256 CSS px. Набор 49 / 98 / 144 устранил этот порог, но на снимках максимального увеличения была заметна мягкость на DPR 1 и сомнительны тонкие детали на DPR 2.
- Набор 72 / 120 / 144 на просмотренных снимках DPR 1/2/3 не показал прежней явной мягкости. Это предварительная визуальная оценка, не завершённая приёмка качества.
- При индивидуальных максимальных `sizes` обзорной карты последний набор передал 60 702 / 115 726 / 138 168 байт на DPR 1/2/3. Эти числа включают более мелкий выбор для строительства и не описывают окончательно выбранный единый `sizes`.
- При размере выбора 48 CSS px в отдельном прогоне превью браузер загрузил 60 702 / 126 780 / 140 758 байт. Такие же суммы ожидаются при общем `sizes` 49 CSS px: дополнительная экономия к полноразмерному WebP — 56,9% / 9,9% / 0%. Общий `sizes` в `rem` ещё требует проверки на production-сборке.
- В адаптивных прогонах каждый рисунок загружался одним файлом; переключения минимального и максимального CSS-масштаба не добавляли запросов. Межстраничное переиспользование кеша и реальный жизненный цикл карт этим стендом не проверены.

Временные изображения, скрипты и снимки не являются обязательными входами следующей сессии: воспроизводимые параметры и измерения сохранены здесь. Не добавлять временный стенд в приложение.

### 4. Остановиться на полноразмерном WebP, если адаптивность не проходит приёмку

Полноразмерный lossless WebP — проверенный запасной путь: один URL на рисунок и достаточная экономия без ресайза. Он предпочтительнее бесконечного подбора ширин, фильтров, отдельных вариантов для каждого маркера или изменения рисунков.

Вернуться к нему, если на реальных поверхностях заметно ухудшение качества на максимальном размере либо суммарные загрузки при zoom/навигации съедают экономию относительно полноразмерного WebP в сопоставимом сценарии. Удалить неиспользуемые варианты и поля выбора, записать причину и реальные цифры в результат. Такой возврат входит в обсуждённый объём; расширение набора или изменение поведения требует нового согласования.

## Risks / Trade-offs

- Потеря тонких деталей после уменьшения → проверить все семь рисунков на DPR 1/2/3, zoom, hover/focus, закрытом состоянии, превью и списке. Не принимать предварительную оценку стенда за результат приложения.
- Увеличенный шрифт и браузерный zoom меняют фактическую плотность → использовать `rem`, проверить увеличенный корневой шрифт и масштаб страницы; качество не должно уступать полноразмерному baseline при одинаковых условиях.
- Браузеры свободны в выборе `srcset`, учитывают кеш и плотность → не закреплять точный `currentSrc` как постоянный тестовый контракт для каждого DPR; проверить фактическую сеть, отсутствие двойной доставки и переходы между потребителями.
- Экономия на DPR 2 умеренная, на DPR 3 отсутствует → не приписывать адаптивности общий выигрыш смены формата; отдельно показать полный WebP-baseline и выбранные варианты.
- Три разрешения увеличивают сумму файлов в сборке, хотя браузер не обязан загружать все → считать переданные изображения отдельно от общей суммы emitted assets и JS/CSS-отчётов.
- Каталог сейчас показывает лишь три маркера на DPR 2 → проверить весь набор, используя существующий каталог и адресные браузерные проверки, без новой универсальной инфраструктуры.

## Migration Plan

### Итог реализации

30 сентября 2026 года выбран предусмотренный разделом 4 полноразмерный fallback. Адаптивный набор прошёл сетевую проверку, но на реальной карте при root24 / DPR1 / максимальном hover рисунок Foodtruck потерял тонкие детали относительно полноразмерного baseline. Подробности — в [визуальной приёмке](/openspec/changes/archive/2026-09-30-optimize-map-marker-images/quality-validation.md).

Итоговый реестр использует только семь полноразмерных lossless WebP: `src`, исходные `width` и `height`. Варианты 72/120 px, helper и поля `srcset`/`sizes` удалены. Геометрия, стили и жизненный цикл потребителей сохранены. Передача изображений — 140 758 байт вместо 200 173, экономия 59 415 байт / 29,7%; дополнительная экономия адаптивности не заявляется. Решения выше описывают согласованный эксперимент, а не итоговый набор ресурсов.

1. План публикуется в draft PR на ветке `perf/887-optimize-map-marker-images`. Реализация отсутствует; явное разрешение на подготовленные артефакты пока не зафиксировано.
2. Следующая сессия читает change, issue и состояние ветки, подтверждает разрешение и оставляет в issue отметку со ссылкой на коммит согласованных артефактов. Реализует задачи в той же ветке и PR.
3. До изменения импортов сохранить исходные отчёты через `pnpm bundle:analyze`; после изменения повторить анализ по [инструкции](/docs/development.md#анализ-клиентских-бандлов).
4. Проверить production-сборку, короткие регрессионные тесты и браузерную сеть. Сравнить холодное открытие, zoom in/out и последовательные переходы карта → карточка → карта с полноразмерным WebP-baseline на DPR 1/2/3. Для кеш-проверки использовать существующие правила доставки, а не делать вывод из временного Python HTTP-сервера.
5. После выполнения задач провести полное ревью, архивировать change штатным workflow (sync не нужен при `skip_specs`) и обновить этот PR до готового к человеческому ревью. Только тогда заменить `Refs #887` на `Closes #887`; не открывать отдельный PR реализации.
6. Если после публикации обнаружена регрессия, откатывать реализацию целиком; хешированные ресурсы не требуют перезаписи объектов или миграции данных.
