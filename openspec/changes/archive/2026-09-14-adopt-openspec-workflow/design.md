## Context

Мотивация и границы этапов описаны в [proposal.md](proposal.md). Осмотрена чистая рабочая копия на `master`; для #736 создана ветка `chore/736-openspec-workflow` в этой же копии по просьбе владельца.

Проверено до подготовки подхода:

- Установлен локальный `@fission-ai/openspec@1.13.0`; `init --tools opencode` создал штатную структуру и интеграцию. Основных specs ещё нет.
- `init` принимает `--profile`, но список workflows берёт из global config. `update` не имеет project-level флага профиля. Global config поддерживает `XDG_CONFIG_HOME`, `profile`, `workflows`, `delivery`.
- Генератор содержит обычные примеры команд OpenSpec; настройки префикса терминального вызова в исследованном CLI нет. `openspec/config.yaml` поддерживает `context`, `rules` и `operations`.
- Установленный `skills@1.5.24` поддерживает `ref` в `skills-lock.json`, в том числе полный Git SHA. Текущий lock содержит пути и хеши, но не ревизии.
- В отдельном временном каталоге `skills experimental_install` восстановил `grilling` по `3cca18b368ae95cdbdebbff572ccafa662551015`; хеш совпал с проектным `4dd886b0…`. По коду установщика `computedHash` при восстановлении не проверяется, некоторые ошибки только печатаются. Значит, exit code самого установщика недостаточен.
- В Git хранятся четыре собственных skills; внешний набор ignored. `code-review` ссылается на отсутствующий `docs/agents/issue-tracker.md` и удаляемый setup-flow. `domain-modeling` и несколько сохранённых методов предлагают `CONTEXT.md` вместо `GLOSSARY.md` и `docs/adr/` вместо `docs/decisions/`.
- В `.superpowers/sdd/` лежат завершённые материалы прежней разработки раздела отзывов. У `tailwind-design-system` остался пустой `references/`, у `.opencode/skills/news-maker` — пустой каталог.
- В ADR-025 есть старый план и состояние release candidate; это историческая запись с конкретными непроверенными на тот момент пунктами, а не доказательство их текущего выполнения.

## Goals / Non-Goals

**Goals:**

- Использовать штатные CLI и возможности их конфигурации; helper-скрипт отвечает только за воспроизводимость и обнаружение ошибок.
- Отделить исполняемую проектную политику от исторического обоснования ADR и от upstream-инструкций.
- Сохранить внешний набор в исходном upstream-виде, а проектные дополнения — в правилах и собственных skills.

**Non-Goals:**

- Собственная схема OpenSpec, сторонний store, подключение дополнительных агентских инструментов.
- Переписывание всех предметных требований приложения в specs и рефакторинг самого приложения.
- Функциональная реализация #724 и окончательная приёмка #734/#735.
- Изменение глобальных skills и их lock-файлов: владелец отдельно подтвердил эту границу. Согласованный внешний набор берётся из проектного lock-файла после уборки.

## Decisions

### 1. Один раздел политики в AGENTS.md

Добавить раздел «Жизненный цикл изменений» с правилами из `development-workflow`. README и собственный `project-issues` ссылаются на него. В конфигурации OpenSpec оставить краткий контекст проекта, язык, ссылки на правила и указания для артефактов/операций, не копируя политику целиком.

`project-issues` сохраняет GitHub-специфику, ссылки issue/change/PR, собственную проверку перед PR и человеческий merge. По уточнению владельца текущая рабочая копия используется по умолчанию; отдельный worktree нужен только по явной просьбе об этом или о решении нескольких тикетов параллельно. В последнем случае каждый тикет получает отдельные worktree и ветку. Явные ограничения сессии на commit, push и PR сохраняют силу.

По уточнениям владельца в ревью все 16 skills, для которых готовились patches, удаляются из проектного набора. Ревью всего diff, владельцы требований, ведение существующих glossary/ADR и упрощение собственной реализации определяются непосредственно в `AGENTS.md`. Из методов обсуждения сохраняется `grilling`; обязанности удалённых методов не требуют их отдельной установки.

Причины выбора записаны в [ADR-038](../../../../docs/decisions/038-openspec-development-workflow.md). Старые отчёты и ADR оценивать по содержанию: устаревшие планы убрать из действующей навигации, а исторические результаты и незавершённую приёмку явно датировать, не объявляя их выполненными задним числом.

### 2. Воспроизводимая штатная генерация

Закрепить `@fission-ai/openspec` на `1.13.0`. В проекте зафиксировать `profile: custom`, `delivery: both` и точный список штатных workflows: `propose`, `explore`, `apply`, `update`, `sync`, `archive`, `verify`. Это профиль доставки, а схема остаётся штатной `spec-driven`. Явный список сохраняет состав даже при расширении upstream-профиля `core`.

Helper генерации создаёт временный `XDG_CONFIG_HOME` с этими настройками и вызывает `pnpm exec openspec init --tools opencode --profile custom` / `pnpm exec openspec update --force` из корня workspace. Временный каталог удаляется после вызова, личная конфигурация не меняется. Восстановление и проверка используют тот же путь генерации.

Файлы `.opencode/skills/openspec-*/SKILL.md` и `.opencode/commands/opsx-*.md` сохраняются в Git в штатном виде и исключаются из форматирования. В `AGENTS.md` закрепить правило исполнения: любой пример терминальной команды OpenSpec, включая upstream-инструкции и CLI-подсказки, исполняется через `pnpm exec openspec` из корня workspace. Штатные примеры не редактируются вручную и не становятся отдельным fork генератора. Правило списков вместо таблиц также задаётся на уровне проекта.

Проверка генерирует ожидаемые файлы во временном проекте, сопоставляет их с рабочей копией и сообщает о недостающих, лишних или отличающихся файлах. Она не исправляет Git diff молча.

### 3. Исходные skills по Git SHA

Закрепить `skills@1.5.24` и полные `ref` ревизии внешних источников в существующем `skills-lock.json`. Хеши сохранить как контроль содержимого upstream, не заменяя ими ревизии. Удалить девять управляющих skills из постановки и дополнительно согласованные методы из lock и локальной установки.

Документированный bootstrap сначала выполняет frozen-установку зависимостей, затем восстанавливает внешний набор штатным `skills` CLI и проверяет состав и хеши. Для всех валидаций структур использовать Zod. Собственные skills остаются в `.agents/skills/`; каждый внешний skill имеет одну активную копию там же и совпадает с закреплённым upstream.

По решению владельца механизм patches исключён целиком. Проверка установленного набора напрямую сверяет хеши; временные копии для снятия patches не нужны. Общие правила проекта сохраняются в `AGENTS.md`, OpenSpec config и собственных skills. Несовместимые методы исключаются из набора по согласованию.

После ревью оставшегося набора владелец исключил ещё 12 вспомогательных skills: обёртку `grill-me`, учебные и прототипные процессы, вспомогательные команды Ponytail, отдельные методы исследования, передачи контекста и оформления документов. Итоговый набор — 16 внешних skills; обязанности по работе с задачами и знаниями остаются в проектной политике.

Личные глобальные skills не изменяются. Установку согласованного проектного набора проверять в окружении без их участия. Обязательную ссылку из корневого `AGENTS.md` на `agent-browser` обеспечить проектной установкой из `vercel-labs/agent-browser` с закреплённой ревизией; источник подтверждён. Это не требует переносить или править личную глобальную копию. Остальные личные skills в проектный набор автоматически не включать.

Во время реализации `xixu-me/skills` вернул 404. Владелец явно разрешил удалить проектный `github-actions-docs`; он исключается из установки и lock. Для humanizer закреплена прежняя v3.24.0, чтобы не менять редакционный метод при настройке процесса; скомпилированный Python `__pycache__` не относится к исходному содержимому skills. Skill Turborepo впоследствии удалён вместе с остальными патченными методами.

### 4. CI, обновление и откат

Добавить отдельную проверку агентского tooling в CI для `openspec/`, сгенерированной интеграции, её настроек/скриптов, зависимостей/lock-файлов и проектных правил. Она выполняет штатную строгую валидацию активных изменений и основных specs, проверку завершённости архивов и согласованности генерации. Проверку воспроизводимости skills запускать при изменении их lock-файла и bootstrap. Поведение отрицательных проверок проверить на временных fixtures без обхода сайта.

В Dependabot исключить OpenSpec из общей dev-группы, чтобы он получал отдельный PR. Совместимые обновления выполняются коротким путём по инструкции в README или связанном техническом документе. Изменение политики требует change. Откат возвращает пакет, lock-файл, параметры и интеграцию вместе.

### 5. Приёмка этого этапа

Проверить установку в чистой временной копии файлов предполагаемого изменения без ignored-остатков и глобальных skills, затем повторить её. Отдельно проверить генерацию при отличающемся глобальном профиле, drift после изменения generated-файла и отказ при неполной установке skills. Для CI использовать подходящую локальную проверку workflow и те же команды, которые будут запускаться в Actions.

Результаты сверить с двумя specs и всем актуальным diff. Записать команды, результаты и конкретные остатки в отчёт этого change и краткий комментарий #736; ссылаться на #734 через `Refs`, а закрытие #736 подготовить через `Closes` только после выполнения её критериев. До разрешённых commit/push ссылки на ещё несуществующие коммит и PR не подставлять.

## Risks / Trade-offs

- Установщик skills пока экспериментальный и не всегда сигнализирует ошибку exit code → проверять полученный состав и исходные хеши, а не только успешность процесса.
- Переустановка внешних skills требует доступа к закреплённым Git-ревизиям → при недоступности завершаться явной ошибкой; обновления ревизий проверять отдельным diff.
- Upstream-инструкции могут конфликтовать с правилами проекта при обновлении → смотреть release notes и сгенерированный diff, проверять совместимость до принятия обновления.
- Обязательный `agent-browser` сейчас доступен из личной установки → восстановить его проектную зависимость по закреплённому upstream, не считая глобальную копию доказательством чистого bootstrap.
- Уборка ignored-файлов не видна в PR → сохранить инвентаризацию до удаления и результат в отчёте и issue.
- Полная функциональная проверка передачи контекста ещё впереди → оставить её пилоту #724 и приёмке #735, не подменять проверкой существования файлов.

## Migration Plan

1. Подготовить и согласовать этот change. Bootstrap для подготовки уже добавил CLI и штатную интеграцию; основная реализация ожидает разрешения владельца.
2. Реализовать воспроизводимость и проектные правила; удалить прежние активные процессы, согласованные несовместимые методы и проверенные остатки.
3. Подключить CI, Dependabot и инструкцию эксплуатации; выполнить приёмку этого этапа.
4. После успешных проверок синхронизировать основные specs, архивировать change и подготовить PR с результатами; публикацию выполнять в пределах разрешений сессии.
5. При откате вернуть всё изменение целиком. Локальные удалённые Superpowers-артефакты не являются зависимостью восстановления нового процесса.
