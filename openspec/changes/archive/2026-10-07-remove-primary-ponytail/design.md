# Design

## Context

Мотивация и границы — в [proposal](/openspec/changes/archive/2026-10-07-remove-primary-ponytail/proposal.md). Основной `ponytail` подключается через правило `/AGENTS.md` и широкий `description` установленного skill. [OpenCode V2](https://opencode.ai/v2/docs/skills) обнаруживает `/.agents/skills/` и показывает модели описания доступных skills.

`/scripts/skills.mjs` восстанавливает внешний набор по `/skills-lock.json` и до установки отклоняет неизвестные каталоги. `/.opencode/agents/reviewer.md` уже задаёт два прохода; внешний `ponytail-review` предлагает также `shrink` и итог по числу удалённых строк. [ADR-038](/docs/decisions/038-openspec-development-workflow.md) закрепляет исходные upstream-skills без проектных patches.

## Goals / Non-Goals

**Goals:** согласовать проектные правила, состав установки и инструкции reviewer; обеспечить переход существующего checkout и проверку свежего контекста.

**Non-Goals:** изменение установщика, новые зависимости, правки upstream-skills, глобальных настроек или соседних worktree, пересмотр `ponytail-audit`, постоянный LLM benchmark в CI.

## Decisions

### Удаление skill из состава установки

Удаляем запись `ponytail` в lock-файле и его проектную копию, снимаем обязательное подключение в `/AGENTS.md`. Одного удаления правила недостаточно: описание установленного skill остаётся доступным модели. Правка `description` или скрытие skill через permission не нужны при согласованном полном удалении и добавили бы отдельное правило сопровождения.

Переход использует существующий bootstrap. При приёмке удаляем только проверенную проектную копию `/.agents/skills/ponytail` перед восстановлением обновлённого набора. Установщик продолжает отклонять неизвестные каталоги: автоматическая уборка лишних skills выходит за задачу и могла бы удалить локальную работу.

### Приоритеты и приёмка упрощений

Reviewer свободно предлагает упрощения через штатный `ponytail-review`; основной агент самостоятельно оценивает их пользу и решает, какие принять. Формат skill не становится критерием принятия правки. Затронутые проверки и адресное ревью после принятых правок выполняются по действующему процессу.

### Проверки по изменённому результату

- Повторный `pnpm agents:setup` после уборки подтверждает воспроизводимость состава; `pnpm skills:check` — совпадение внешних skills с lock-файлом. Сверяем diff lock-файла: удалена только запись основного `ponytail`.
- `pnpm test:agent-tooling` и `pnpm openspec:validate` проверяют существующую интеграцию и структуру требований. Новые тесты на точный текст инструкций не нужны.
- В свежей сессии OpenCode с рабочим каталогом этого worktree проверяем доступный каталог skills и источники: проектный `ponytail` отсутствует, `ponytail-review` доступен. Проверяем новый контекст правил и фактический порядок двух проходов reviewer; фиксируем наблюдения и ссылки на сессии в итогах приёмки.
- В сценариях оценки упрощений различаем полезное удаление дублирования и сокращение, которое скрывает необходимую граничную проверку либо ухудшает понятность. Отчёт должен объяснять пользу первого и причину отказа от второго. Это адресная ручная приёмка, без нового тестового механизма.

## Risks / Trade-offs

- Загруженный основной skill остаётся в истории текущей сессии → проверяем результат в свежем контексте после восстановления окружения.
- Личная глобальная копия может быть обнаружена OpenCode независимо от проекта → при обнаружении фиксируем её источник; проверка проектной установки и уборка остаются локальными.
- `ponytail-review` сохраняет upstream-уклон в количество строк → основной агент самостоятельно оценивает пользу каждого предложения до принятия правки.

## Migration Plan

1. После разрешения реализации сохранить согласованные артефакты в ветке и оставить отметку в #972 по проектному процессу.
2. Изменить lock-файл и правила, сверить содержимое локального `ponytail` с закреплённым хешем и удалить эту проектную копию. Если обнаружатся локальные изменения, сначала разобрать их.
3. Восстановить окружение через `pnpm agents:setup`, выполнить проверки и приёмку свежего контекста, сохранить результаты в отчёте приёмки.
4. После ревью синхронизировать specs, архивировать change и открыть PR. Откат возвращает весь PR и восстанавливает набор через bootstrap с перезапуском OpenCode.
