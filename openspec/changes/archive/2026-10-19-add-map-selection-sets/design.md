# Design

## Context

Мотивация и границы — в [proposal](/openspec/changes/archive/2026-10-19-add-map-selection-sets/proposal.md). План подготовлен для [#1121](https://github.com/silentroach/kpshelkovo/issues/1121) по обсуждению 2026-10-19, исходная версия кода — `c51487ffb97e6b6f5fc2aa549d13761801904ce3`.

### Что уже есть

Ниже исходные точки изменения относительно SHA базы. К моменту расширения плоская версия уже реализована локально, её проверки и первоначальные снимки сохранены в [отчёте приёмки](/docs/research/map-selection-sets/acceptance.md). Владелец принял фиолетовый `#7c3aed` с заливкой 22%. Эти результаты не подтверждают вложенные наборы и новый Markdown-формат. Предварительный перенос плоских требований в основные specs остаётся локальным; окончательную синхронизацию выполнить после расширенной приёмки.

- [PlaceMap.svelte](/apps/www/src/components/places/PlaceMap.svelte) владеет камерой, загрузкой четырёх частей, одиночным `p`, временным `h`, местами и их кластерами. По умолчанию части участков выключены; переключателей категорий мест нет.
- [parcel-layer.ts](/apps/www/src/components/places/parcel-layer.ts) хранит один выбранный объект. Сейчас `clearSelection` возвращает статусное оформление, а `disable` удаляет объекты части. Это точки изменения для независимой принадлежности набору.
- [load.ts](/apps/www/src/lib/parcels/load.ts) уже разрешает основные коды и алиасы в одну позицию. [map-public.ts](/apps/www/src/lib/parcels/map-public.ts) собирает все кадастровые части в геометрию с сохранёнными межами, применяет общую поправку и округляет координаты публичного слоя. Использовать именно эти подготовленные координаты для обводки.
- [polygon-label.ts](/packages/geo/src/polygon-label.ts) использует `polyclip-ts` для точки подписи, но не предоставляет общую обводку. Библиотека уже закреплена в `@shelkovo/geo`, в текущем клиентском отчёте её нет.
- Места общей карты ограничены `show_on_map: true`. Дополнительная геометрия сейчас раскрывается по hover/focus/`h`; маркер ведёт на карточку. `h` заканчивается через пять секунд, `p` сохраняется до действия пользователя.
- При начальном открытии непустой `p` подавляет `h`. URL-helpers сохраняют чужие query, hash и history state через `replaceState`; кадр и весь список включённых частей не сериализуются.

### Архитектурные основания

- [ADR-013](/docs/decisions/013-raw-domain-public-data-boundary.md): раздельные raw-схема, доменная модель, mapper и адаптер подготовленного JSON.
- [ADR-039](/docs/decisions/039-shared-yandex-maps-runtime-and-preview.md): renderer и состояния общей карты принадлежат приложению; общему runtime не передаются наборы и parcel-логика.
- [ADR-011](/docs/decisions/011-public-surface-registry.md): различать самостоятельные публичные ресурсы и вспомогательные артефакты карты.
- [Дизайн-гайд](/docs/design/design-code-shelkovo.md) и [публичная точность координат](/openspec/specs/public-coordinate-precision/spec.md) остаются действующими ограничениями. Новый долговечный архитектурный выбор отдельного ADR не требует: меняется локальная возможность существующей карты.

## Goals / Non-Goals

**Goals:**

- Разделить состав набора, текущую видимость частей и одиночный выбор, переиспользовав существующую загрузку геометрии.
- Добавить точную обводку без новой копии исходных координат и без геометрической зависимости в обычном открытии карты.
- Оставить редактору небольшой JSON, который можно разделить или исправить без изменения UI.
- Переиспользовать состав набора в самостоятельных ссылках, сборных подборках и Markdown-картах без копирования кодов или координат между источниками.
- Сохранить синхронный Markdown pipeline и прежние GeoJSON-блоки; подготовку зависимостей выполнять на существующих асинхронных границах сборки.

**Non-Goals:**

- Универсальный менеджер слоёв, отдельный геосервис, браузерный редактор, произвольные внешние JSON и сбор данных КТП.
- Восстановление исторических межей генплана, подгонка обводки к скриншотам, соединение через дороги и зазоры, расширение области ради толстой линии.
- Новая модель одиночного выбора или сохранение всего viewport в URL.
- Дерево наборов в интерфейсе, наследование оформления дочерних наборов и перенос коммерческого интерфейса участков во встроенную схему.

## Decisions

### 1. Небольшие определения наборов и проверка ссылок при сборке

Предлагаемые технические имена: источники `apps/www/src/data/map-selection-sets/*.json`, app-owned обработка `apps/www/src/lib/map-selection-sets/`, выдача `/map/data/selection-sets/<id>.json`, параметр `/map/?set=<id>`. Имя файла без расширения — стабильный ID. Это технические defaults плана; публичным адресом для читателя служит ссылка на карту.

Авторский JSON содержит `parcels` с полными кодами позиций, `places` со slug, `sets` с ID других файлов и необязательный `outline` с default `false`. Отсутствующий список равнозначен пустому. Прямые участники и ссылки могут находиться в одном файле; непустым должен быть состав после разрешения ссылок, поэтому родитель без собственных `parcels`/`places` допустим. Имя и поля проверяются строгой Zod-схемой. Название, описание и произвольное оформление набору не нужны; metadata и собственные features относятся к Markdown-вставке, не к JSON-набору.

Build-loader сначала читает и проверяет все источники, затем разрешает граф `sets` без фиксированного ограничения глубины. Обход хранит текущую цепочку для обнаружения циклов и кеш завершённых результатов; повторное использование общего дочернего набора несколькими ветками допустимо. Самоссылка, цикл и неизвестная ссылка останавливают сборку с источником и цепочкой ID; частичный состав не публикуется. Отдельный файловый loader или глобальная предварительная инициализация не нужны: используются существующие datasets и Promise-кеши.

Разрешение кодов без учёта регистра, замена алиасов основными кодами и удаление повторов применяются ко всему объединённому составу. Повтор одной позиции через алиас, прямой список или несколько вложенных ветвей включает её один раз и целиком. Неизвестный код и место вне общей карты останавливают сборку с источником и проблемным значением. Пустые дочерние наборы не становятся допустимыми из-за непустого родителя.

Состав дочерних наборов объединяется, а их `outline` не наследуется. Публичный adapter каждого открываемого файла использует его собственный флаг, по умолчанию `false`. Браузер не получает дерево ссылок, не делает запросов дочерних определений и не показывает структуру файлов в UI.

Отдельный public adapter выдаёт компактный JSON с `id`, canonical `parcels`, `places`, `outline`. Он проверяется до сериализации; браузер не импортирует Zod. Координаты, bounds, копии карточек и история цен в этот JSON не входят. Части определяются по canonical-кодам, геометрия получается существующими загрузчиками.

JSON определения — вспомогательный runtime-артефакт `/map/` по исключению ADR-011: отдельный каталог, лента, OpenAPI и индекс наборов не нужны. Ссылку с `set` и редакционный формат описать в существующей документации карт. Проверить фактическую выдачу нового пути; внешние origin и изменение deploy-потока не требуются.

Альтернативы: HTML-payload всех наборов увеличивает обычную карту; внешняя загрузка усложняет контракт; производная геометрия в определении дублирует данные без необходимости.

### 2. Три состояния вместо подмены одиночного выбора

Состояния различаются по ответственности:

- Активный набор: ID, canonical membership и настройка обводки.
- Включённые части: существующее состояние видимости и кеш запросов.
- Одиночный выбор: существующие `p`, попап и условия снятия.

В parcel renderer единая функция оформления выбирает `одиночный выбор → участник набора → обычный статус`. Она используется и при создании контура, и при снятии `p`, и при повторном включении части. Отдельная копия интерактивных parcel-features не нужна.

Отдельное доступное действие снятия набора показывается и при ожидании/ошибке его загрузки. Оно удаляет только `set` и состояние набора; камера, включённые части и самостоятельный `p` сохраняются. Кнопку встроить в управление существующей картой без информационной панели набора. Отдельного переключателя обводки для читателя нет.

Подсветка отличается от статусной заливки и одиночного выбора усиленным контуром/ореолом и читаемой лёгкой заливкой. Владелец принял фиолетовый `#7c3aed` с заливкой 22%; размеры границ и кольца записаны в действующем дизайн-гайде. Одиночный выбор сохраняет своё синее оформление. Не копировать неоновый цвет и толщину исходных скриншотов как контракт.

### 3. Объединение видимых контуров в браузере по запросу

Принята рекомендация advisor: чистый helper объединения в `@shelkovo/geo`, app-owned lazy-модуль обводки в renderer-е карты. Модуль запрашивается только для набора с `outline: true` и участками. Внутри него использовать статический named import helper-а, чтобы остальные экспорты пакета исключались сборкой; проверить `sideEffects` и фактический bundle.

Вход union — геометрии участников из фактически включённых и готовых частей, с уже применённой поправкой отображения. Пересчитывать при применении/снятии набора, появлении или выключении части. Pan, zoom и одиночный выбор не запускают union.

Результат рисуется отдельной неинтерактивной геометрией без заливки, с сохранением всех внешних и внутренних колец. Она усиливает общую границу, но не заменяет parcel-features, не скрывает внутренние межи и не перехватывает клики. Выключение части пересчитывает union оставшихся видимых участников, включая восстановление границы с выключенным соседом. Геометрия мест исключена из расчёта.

Без буферизации, snapping, hull и допуска «почти соседние». Исходные координаты и площадь не меняются; генерируемые публичные координаты следуют действующей точности. Пустой видимый состав снимает обводку, сохраняя membership.

Рассмотренные варианты:

- Один union при сборке не позволяет корректно выключить только часть участников и восстановить открывшуюся границу.
- Union отдельно на каждую часть оставляет лишний шов, если участки разных частей имеют общую сторону.
- Предвычисление всех сочетаний возможно: до 15 непустых вариантов для четырёх частей. Но добавляет формат вариантов и производные данные; подтверждённой проблемы runtime, оправдывающей это, пока нет.

Цена: замер установленного minified UMD `polyclip-ts` дал 42 517 байт, 15 099 gzip и 13 728 Brotli. Это ориентир зависимости, не измерение будущего Vite-чанка. В реализации измерить фактический lazy-чанк и время union первого набора на мобильном профиле; обычная карта и набор без обводки не должны запрашивать его. Кеш комбинаций и Web Worker заранее не нужны.

### 4. Места остаются местами

Участие места в наборе — дополнительное независимое условие показа всей его геометрии. Завершение `h`, уход hover и blur не скрывают её, пока набор активен. Маркер сохраняет ссылку на карточку; это не новый постоянный одиночный выбор места.

Технический default для гарантированной одновременной подсветки: места набора показывать отдельными основными маркерами, временно исключив их из обычной кластеризации. Остальные места кластеризуются как сейчас; после снятия набора участники возвращаются в обычный поток. Не рисовать вторую копию того же маркера. Это покрывает требование не терять подсветку в обычном кластере.

Набор допускает только опубликованные на общей карте места. `show_on_map` не меняется автоматически, скрытые карточки не раскрываются ссылкой на набор.

### 5. Одно начальное вписывание и существующий приоритет URL

Запрашивать определение только при непустом корректном `set`. После его получения включить нужные части через существующие механизмы; для places использовать имеющиеся данные общей карты. При повторных включениях переиспользовать успешные данные и выполняющиеся запросы.

Приоритет начального перехода: непустой `p`, иначе непустой `h`, иначе набор. При наличии отдельной цели подсветка набора применяется независимо, но отдельное вписывание набора не ставится в очередь даже после удаления неизвестного `p`/`h`. Так сохраняется простой существующий приоритет без цепочки запасных переходов.

Для ссылки только на набор однократно вычислить bounds после готовности всех необходимых данных: все координаты parcel-геометрий, основных точек мест и их дополнительных геометрий. Переиспользовать обход координат редакционной карты: нынешний `getPlaceBounds` учитывает только основные точки. Сохранить разумный предел масштаба для одной точки и reduced motion.

Читательское движение камеры, новый одиночный выбор, выключение части или снятие набора отменяют ожидающее вписывание. Повторное включение слоя и resize не возвращают исходный кадр набора. Проверить существующий путь `refreshMapLayout → fitPlaces`, чтобы он не перезаписывал новый приоритет. Поздний ответ или импорт обводки должен проверять актуальность набора и экземпляра карты.

Неизвестный набор, ошибка запроса/разбора определения или расчёта обводки дают короткое доступное сообщение и возможность снять набор; технический текст/stack пользователю не выводится. Ошибки частей используют штатные оповещение и повтор переключателем. Полный набор не вписывается по частичным данным. Исчезновение ошибки и повтор не должны возвращать отменённое пользователем намерение.

### 6. Первый редакционный набор

Общий файл сохраняет принятое имя `2026-10-ae-electro.json` и ссылку `/map/?set=2026-10-ae-electro`. Его состав задают три ссылки, а не повторный список участков. Три самостоятельных дочерних файла соответствуют исходным картинкам, а не двум частям посёлка:

- `2026-10-ae-electro-shp-f.json`: изображение 1, пять позиций Парка F89/F90/F94/F95/F96.
- `2026-10-ae-electro-shv.json`: изображение 2, 33 позиции Вилладжа.
- `2026-10-ae-electro-shp-ab.json`: изображение 3, 29 canonical-позиций Парка A/B.

В каждом дочернем файле и общем файле явно включить `outline: true`, чтобы каждая самостоятельная ссылка показывала выбранную обводку. Название само по себе не добавляет сведений о причине выделения.

```json
{
  "sets": ["2026-10-ae-electro-shp-f", "2026-10-ae-electro-shv", "2026-10-ae-electro-shp-ab"],
  "outline": true
}
```

Источник состава — три изображения владельца из обсуждения #1121. Основной агент прочитал номера внутри жёлтых линий и сверил их с реестром на исходном SHA. Изображения не служат геометрическим источником, их точный контур повторять не нужно. Сами вложения в репозитории не сохранены; список ниже позволяет продолжить без доступа к прежней сессии.

- Изображение 1: Парк, 5 обозначений → 5 canonical-позиций.
- Изображение 2: Вилладж, 33 обозначения → 33 canonical-позиции. Префикс здесь `SHV`, включая все F- и G-коды.
- Изображение 3: Парк, 30 обозначений → 29 canonical-позиций. `SHP-B43` разрешается в `SHP-B42`.
- Итого: 68 прочитанных обозначений → 67 позиций. Все найдены. Единственное дополнительное обозначение внутри выбранной canonical-позиции — `SHP-B44`: текущая `SHP-B42` объединяет B42/B43/B44. Владелец явно согласовал включение целиком, хотя B44 вне линии на картинке.

```json
  "places": [],
  "outline": true
}
```

### 7. Короткое определение Markdown-карты

Сохранить прежний полный `FeatureCollection` и добавить короткую форму только для ограждённых Markdown-блоков `map`. Формат соседних `.geojson` мест не расширять. Короткая форма допускает `sets`, `parcels`, `places`, собственные GeoJSON `features`, прежние metadata и `outline`; все списки можно сочетать или опускать. Итог после раскрытия ссылок должен содержать хотя бы один объект. Флаг обводки задаёт сама вставка, по умолчанию `false`; настройки упомянутых наборов не наследуются.

````markdown
```map https://kpshelkovo.online/map/?set=2026-10-ae-electro-shp-f
{
  "sets": ["2026-10-ae-electro-shp-f"],
  "parcels": ["SHP-C34"],
  "metadata": { "name": "Выделенные участки" },
  "outline": true
}
```
````

Ссылка подписи остаётся явным абсолютным HTTP(S)-URL после `map`, со всеми прежними проверками и правилами подписи. Не генерировать новый именованный набор или URL для произвольной смеси объектов. Отсутствие URL допустимо; `metadata.name` не становится обязательным. Ссылки `sets`/`places` являются структурными данными карты, не Markdown-упоминаниями и не новым источником backlinks.

### 8. Build resolver без перестройки Markdown pipeline

Принята рекомендация advisor после исследования зависимостей: отделить синхронный разбор формы от разрешения ссылок. `extractEditorialMaps` продолжает раннюю проверку JSON, собственных features, metadata и URL без загрузчиков. На существующих асинхронных границах подготовки HTML и companions новостей/KB загрузить готовый resolver и передать его через options синхронным AST-преобразованиям. Ошибки ссылок должны останавливать сборку до публикации с именем материала и номером вставки; ранняя проверка коллекции не обязана сама загружать геоданные.

Markdown-модули не импортируют загрузчики реестров: иначе возникает обратная зависимость `render → resolver → places/load → places/mapper → render`. Resolver использует базовый `loadPlacesData()`, не вариант с backlinks, чтобы не ждать граф упоминаний, который сам зависит от новостей. Не переводить весь рендер на async, не читать коллекции вторым синхронным filesystem-loader и не хранить подготовленные карты во всех доменных записях ради передачи между слоями.

При подготовке участков один раз получить полный публичный массив той же сборки и затем выбрать нужные позиции. Нельзя вызывать `buildParcelMapPayload` отдельно на каждой подборке: поправка отображения зависит от широтного охвата входного массива и тогда может разойтись с общей картой. Места брать с основной точкой и всей подготовленной дополнительной геометрией, только при `show_on_map: true`. Разделение raw → domain → public и итоговая Zod-проверка HTML-payload сохраняются.

Во встроенной схеме нет переключателей частей, поэтому union её участков рассчитывается при сборке. Использовать тот же чистый helper, сохраняя отверстия, отдельные области и межи; места и собственные редакционные полигоны в union не входят. В браузер вставки передавать готовую геометрию, без обхода ссылок на наборы, загрузки их JSON и геометрической зависимости ради union.

### 9. Renderer схемы и публичный Markdown

Встроенная карта показывает всех участников и собственные features сразу, начиная с кадра всей схемы. Места включают основной неинтерактивный маркер и всю дополнительную геометрию; штатные правила камеры после ручного движения, подписи, ошибок и ссылок сохраняются. Вставка не получает панель частей, отдельный выбор участка, попапы, статусы продажи, цены или площади.

Номера позиций показывать с порога zoom 17, как на общей карте, без интерактивных кнопок. Переиспользовать правило короткого номера и составных обозначений, но не подключать весь `parcel-layer` с коммерческими сведениями и выбором. Основное оформление ссылочных объектов соответствует принятому фиолетовому выделению; собственные GeoJSON features сохраняют авторское оформление. Для подписи места использовать его название, без дополнительных коммерческих данных.

Короткий редакционный блок остаётся неизменным в исходнике. Его публичный companion содержит обычный самодостаточный GeoJSON `FeatureCollection`: раскрытые участки, основные точки и дополнительную геометрию мест, собственные features и при запросе готовую общую обводку. Ссылки на исходные `sets`/`parcels`/`places` не заменяют координаты и не требуют обхода внутренних файлов потребителем. Номера участков представить обычными точечными features с текстовыми подписями; порог масштаба относится к HTML renderer, не к расширению GeoJSON-формата. Метаданные, явный URL и одна подпись сохраняются.

Импортируемую геометрию использовать уже подготовленной, без повторной поправки или расширения. Собственные features короткого блока сохраняют авторские значения и исходные границы в companion по прежним правилам; HTML применяет их обычную подготовку. Старые полные GeoJSON-блоки сохраняют нынешний контракт companion, включая числовые строки оформления и исходные границы до расширения. Во всех публичных координатах соблюдать precision 8. Публичный Markdown создавать существующим AST API, без нового генератора строк.

### 10. Исследованные примеры геометрии

Разовые результаты исследования текущих данных, не постоянные требования к этим кодам:

- `SHP-F89/F90/F94/F95/F96` имеют точно совпадающие стороны и дают один полигон без отверстий. У F89/F90 два общих отрезка суммарно около 47,56 м; дальнейшие пары имеют по одному отрезку.
- `SHP-C34/C35/C36` также объединяются в один полигон.
- `SHP-A1` и `SHP-A3` касаются только вершиной и дают два полигона; добавление A2 делает всю тройку связной.
- Между `SHP-B20` и `SHP-B24` в исходных данных есть зазор около 2 м вдоль примерно 18 м границы. Его назначение неизвестно; union должен сохранить две области. Это не ошибка округления или поправки карты.
- Проверка 267 позиций Парка обнаружила 399 пар с точным общим полным отрезком и 109 с общей вершиной без такого отрезка; площадных перекрытий не обнаружено. Результат не заменяет проверки всех четырёх частей и не гарантирует отсутствие иной топологии в будущих данных.

## Risks / Trade-offs

- Runtime-union добавляет клиентский вес и вычисление → lazy-загрузка только при обводке, измерение полного первого набора и мобильного профиля. При подтверждённой проблеме вернуться к advisor и владельцу до существенного обхода.
- Снятие `p` или таймер `h` могут стереть оформление набора → один приоритет оформления и независимое условие раскрытия places, адресные регрессии.
- Кеш части не равен её видимости → обводка строится только по включённым участникам, с проверкой межчастной общей стороны.
- Неявный повторный fit или поздний ответ может перехватить камеру → одно отменяемое начальное намерение и тесты смены состояния до ответа.
- Скриншоты и нынешний кадастр различаются → применять согласованные canonical-позиции целиком; B42/B43/B44 уже согласована. Остальные новые конфликты состава возвращать владельцу.
- Старые ссылки показывают актуальный JSON → для другой истории редактор создаёт новое имя, а исправление того же набора делает в прежнем файле.
- Вложенность может дать цикл или многократное раскрытие общей ветки → текущая цепочка для диагностики и кеш завершённых наборов, без публикации частичного результата.
- Подготовка ссылочных карт может замкнуть loaders через Markdown и backlinks → инъекция готового resolver-а на async-границе и только базовые datasets.
- Повторная подготовка координат даст смещение либо расширение второй раз → выбирать из полного подготовленного массива общей карты, разделять импортированную и авторскую геометрию.
- Раскрытый companion больше короткого исходника → это согласованная цена самодостаточного GeoJSON; прежние блоки не переписывать без необходимости.
