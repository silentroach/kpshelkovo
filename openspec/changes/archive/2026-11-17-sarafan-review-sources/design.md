# Design

## Context

Мотивация и объём описаны в [proposal](/openspec/changes/archive/2026-11-17-sarafan-review-sources/proposal.md), поведение в [delta spec](/openspec/changes/archive/2026-11-17-sarafan-review-sources/specs/contacts-catalog/spec.md).

Raw-схема уже принимает произвольный HTTPS-источник, но отзыв содержит только оценку, выжимку, дату и URL. `/apps/www/src/components/contacts/ContactReviews.astro` выводит иконку Telegram и дату под выжимкой; вся запись связана с исходным сообщением. Метастрока сейчас имеет размер `0.75rem`, вес 600 и цвет `text-muted`. Расчёт звезды не различает источники. Markdown-карточка передаёт отзывы во frontmatter через отдельный адаптер.

Решение продолжает [ADR-018](/docs/decisions/018-markdown-first-useful-contacts.md), границы [ADR-013](/docs/decisions/013-raw-domain-public-data-boundary.md) и scoped CSS по [ADR-034](/docs/decisions/034-native-css-architecture.md). Нового архитектурного решения не требуется.

## Goals / Non-Goals

**Goals:**

- Передавать короткую редакционную подпись от исходных данных до HTML и Markdown.
- Использовать существующую метастроку и переход по отзыву.
- Сохранить совместимость опубликованных полей, URL и якорей.

**Non-Goals:**

- Реестр посёлков или чатов, автоматическое получение Telegram-метаданных, изменение расчётной формулы звезды.
- Определение места жительства автора, места заказа или зоны работы мастера по адресу чата.

## Decisions

### 1. Необязательная редакционная подпись у отзыва

В raw-данных добавить `reviews[].source_label`, в явном readonly-домене `ContactReview` поле `sourceLabel`. Mapper передаёт значение без извлечения названия из URL. Поле содержит полную короткую подпись, например `чат Гринвуда`, чтобы рендеру не требовалось склонять название.

Редактор заполняет подпись для соседнего чата и сверяет её с исходником. У местного отзыва поле опускается. Отсутствие поля не порождает подставное название «Шелково». Формат и правила подготовки закрепляются в `/apps/www/src/data/contacts/AGENTS.md`; обычную валидацию непустого текста выполняет Zod.

Альтернативы: нынешняя ссылка без подписи не выполняет согласованную задачу; реестр чатов и автоматическое распознавание URL создают отдельную структуру ради короткого редакционного значения. Связь с реестром сравнения тарифов смешала бы независимые области.

### 2. Подпись в существующей метастроке

Порядок: существующая иконка площадки, дата, затем `· чат Гринвуда`. Разделитель выводится только вместе с подписью. Для всей строки установить вес 400, сохранить компактный размер `0.75rem` и существующий `text-muted`. Ненавязчивость достигается обычным начертанием; дополнительно осветлять цвет или уменьшать размер не нужно. Действующее оформление hover и фокуса сохраняется.

Строка допускает переносы, в том числе внутри длинного названия. Разделитель остаётся рядом с началом подписи. Текст источника входит в доступное имя существующей ссылки отзыва; дополнительная вложенная ссылка и остановка Tab не появляются. Изменение локально для компонента, соответствующее правило фиксируется в разделе «Отзывы в Сарафане» [дизайн-гайда](/docs/design/design-code-shelkovo.md#отзывы-в-сарафане).

Отдельная строка «Источник», цветной бейдж и всплывающая подсказка вместо видимого текста хуже отвечают пожеланию владельца о компактной пометке.

### 3. Согласованное публичное представление

Адаптер `/apps/www/src/lib/contacts/markdown.ts` публикует необязательное `reviews[].sourceLabel`. Новое поле использует camelCase; действующие `published_at` и остальные legacy-поля не переименовываются. Без значения сериализация опускает новое поле. `url` хранит исходную ссылку целиком, поэтому добавление подписи не меняет якорь отзыва.

Подпись остаётся метаданными вне индексируемой выжимки. Существующие Pagefind-заголовки и границы индексирования сохраняются. Маршруты, discovery и HTTP-выдача соответствуют действующим [public-content-discovery](/openspec/specs/public-content-discovery/spec.md) и [public-markdown-delivery](/openspec/specs/public-markdown-delivery/spec.md); новые публичные точки входа не нужны.

### 4. Редакционные формулировки и первый материал

Вводный текст HTML и Markdown каталога должен учитывать отзывы из Шелково и соседних посёлков. Уточнить связанные описания общей и категорийных страниц, а также определение «Сарафана» в `/GLOSSARY.md`. Существующая ссылка на таблицу Гринвуда остаётся самостоятельным полезным материалом. `ContactPoint.areaServed` описывает зону обслуживания, поэтому происхождение нового отзыва не является основанием менять это поле.

Первый материал относится к `/apps/www/src/data/contacts/construction/ilya.md` по указанию владельца:

- Исходный URL: <https://t.me/MainChatGreenwood/36671/130111>.
- Чат в публичном виджете Telegram: `Greenwood - Соседи`; подпись: `чат Гринвуда`.
- Дата проверена 17 ноября 2026 года: `datetime="2026-11-12T09:00:49+00:00"`, календарная дата по Москве `2026-11-12`.
- Текст источника: «Привет. Здесь рекомендовали этого специалиста. Я обращалась. Мне помог. Сделал все отлично. Живет в Шелково .»
- Выжимка передаёт факт обращения и положительную оценку результата. Автор и ник не публикуются; действуют [правила отзывов](/apps/www/src/data/contacts/AGENTS.md). Оценка `positive`.

### 5. Единый учёт опыта

`hasManyPositiveContactReviews` уже использует только оценку и календарную дату. Источник не добавляется в расчёт. Редакционная дедупликация одного заказа охватывает пересылки между чатами; разные подтверждённые заказы по-прежнему допустимы.

## Risks / Trade-offs

- Редактор может забыть подпись или назвать один чат по-разному → закрепить правило заполнения, сверять соседний источник при редакторском ревью. Полный URL остаётся проверяемым источником.
- Маленькая второстепенная строка может стать плохо читаемой или выйти за ширину → использовать штатный контрастный цвет и проверить длинную подпись на телефоне и при увеличении текста.
- Новый публичный атрибут может потеряться в адаптере → проверять сохранение подписи и исходного URL в разобранном frontmatter, а также отсутствие подставного значения у местного отзыва.

## Migration Plan

Добавить совместимое необязательное поле, его отображение и публичный адаптер, затем первый отзыв и редакционные уточнения. Действующие записи принимаются без массовой миграции. Выпустить код, данные и документацию одним изменением; при откате вернуть их вместе, чтобы строгая старая схема не встретила новое поле.
