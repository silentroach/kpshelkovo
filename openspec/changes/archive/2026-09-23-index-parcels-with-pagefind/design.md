# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md). Действующий контракт поиска — [search](../../specs/search/spec.md), прямой ссылки — [parcel-map](../../specs/parcel-map/spec.md). [ADR-025](../../../docs/decisions/025-static-full-text-search-with-pagefind.md) закрепляет Pagefind для HTML-поиска, [ADR-041](../../../docs/decisions/041-parcel-records-and-exact-search.md) — отдельные участки и точные номера; этот change меняет способ исполнения второго решения, сохраняя различие участков и мест. Границы Raw → domain → Public — в [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md).

Сейчас `astro build` пишет `/map/data/parcels.json` (компактный массив с `code`, необязательными `aliases`, `part` и геометрией), затем CLI `pagefind` индексирует HTML. Отдельный `/map/data/parcel-search.json` строится из той же коллекции; `site-client.ts` ищет в нём номера, а `PlaceMap.svelte` дополнительно читает его перед геометрией при `?p=`. В текущем локальном артефакте словарь занимает около 70 КБ без сжатия и 1,9 КБ Brotli; удаление файла само по себе не доказывает экономию трафика. Установленный Pagefind 1.5.2 предоставляет Node API `addDirectory` / `addCustomRecord` / `writeFiles` и точный фильтр в браузерном `search(null, { filters })`.

## Goals / Non-Goals

**Goals:**

- Единственный поисковый движок в браузере — уже используемый Pagefind; участки индексируются в нём без создания HTML-карточек.
- Один публичный JSON участков нужен только карте; поиск не загружает ни JSON, ни геометрию.
- Сохранить сценарии `search` и `parcel-map`, включая обычный текстовый поиск, номерные алиасы, несуществующие коды, retry и догрузку.

**Non-Goals:**

- Менять редакционные записи, контуры, публичную схему `/map/data/parcels.json`, ранжирование обычных страниц либо вводить новый сервис поиска.
- Обещать выигрыш в сетевых байтах без измерения Pagefind-индекса.

## Decisions

### 1. Расширить существующую сборку Pagefind записями участков

После `astro build` один app-owned build script создаёт индекс Node API с действующим `rootSelector: '[data-pagefind-root]'`, индексирует `dist/site` через `addDirectory`, читает готовый `/map/data/parcels.json` и добавляет по одной записи `addCustomRecord` на нынешний участок. Скрипт проверяет ошибки каждого шага и пишет файлы в прежний `/search/`; обе команды `build` и `search:prepare` вызывают один способ построения индекса с разными путями вывода. Сохранить существующие компрессию, URL ресурсов и обнаружение dev-snapshot. Конфигурация CLI `pagefind.yml` после перевода не должна оставаться второй, неиспользуемой копией root selector.

У записи — URL `/map/?p=<основной-код>`, язык `ru`, минимальный `content`, metadata для основного кода, части, алиасов и секции, и набор значений точного фильтра `parcelCode`: полный и короткий основной код, полные и короткие алиасы. Коды берутся из уже проверенного статического представления, но сборка не переносит в индекс геометрию и коммерческие поля. Нужную для вывода алиаса metadata читать только у совпавших результатов. Вход из файла проверяется действующей публичной Zod-схемой: билд не публикует частично индексированные или противоречивые записи. Короткий номер может соответствовать нескольким записям разных частей, полный код — одной. При ошибке индексации сборка завершается до публикации.

**Почему:** Pagefind Node API добавляет не-HTML записи в тот же статический индекс, тогда как CLI индексирует только HTML. Чтение уже построенного представления карты не требует второго парсера Markdown и повторного импорта `astro:content` из Node. Отдельный HTML на каждый код и отдельный поисковый JSON устранили бы требуемое единое владение поиском.

### 2. Точное совпадение выполняет Pagefind-фильтр

Клиент нормализует лишь пробелы по краям и регистр и распознаёт целый полный код либо целый короткий номер. Для него выполняется `pagefind.search(null, { filters: { parcelCode: code } })`; результат преобразуется в действующий `SearchResult`: основной код, часть, пояснение совпавшего алиаса и URL `?p=`. Проверить, что `p` сохраняется при нормализации адреса и что никакие чужие query-параметры не проходят. Несколько совпадений сортируются по основному коду, один участок выдаётся один раз. Далее идут текстовые результаты Pagefind с действующим общим лимитом, счётчиком и догрузкой.

Обычный текстовый запрос сохраняет нынешний путь поиска. Для текстовой ветки исключить служебные записи участков с помощью штатного Pagefind-фильтра по секции; это требуется даже при минимальном `content`, чтобы metadata или будущие изменения индекса не породили случайных результатов. Номерный запрос тоже сохраняет текстовую выдачу после точных совпадений. Сохранить проверки актуальности асинхронного запроса, ошибку данных с локальным повтором и `devUnavailable` без отдельного fallback-словаря. Существующий интерфейс диалога остаётся; композицию `site-client.ts` убрать, объединив запросы к одному Pagefind runtime, вместо добавления нового поискового слоя.

**Почему:** обычный токенный поиск Pagefind допускает нормализацию и префиксы и не является доказательством точного номера. Фильтр даёт точное равенство, а исключение служебной секции сохраняет привычный полнотекстовый корпус.

### 3. Прямая ссылка разрешается по геометрическому представлению

При допустимом полном `?p=` `PlaceMap` сразу загружает `/map/data/parcels.json`, проверяет `code` и `aliases` без учёта регистра и только после найденного совпадения включает слой и фокусирует контур по основному коду. Неизвестный код удаляется без включения слоя; в этом случае геометрический JSON уже получен и кешируется в документе. Сетевая ошибка сохраняет параметр и предлагает повтор, как сейчас. Ручное включение слоя по-прежнему запрашивает только геометрический JSON и может переиспользовать уже загруженные данные. Короткий номер в прямом `p` не разрешается.

**Почему:** файл карты уже содержит все обозначения и всё равно нужен для фокуса. Поисковый индекс нужен только поиску; загрузка его на карте вместо геометрии создала бы лишнюю зависимость и не устранила бы параллельный справочник.

### 4. Убрать устаревшее представление и зафиксировать измерения

Удалить статический маршрут `/map/data/parcel-search.json`, поисковый adapter, схемы и типы словаря, URL-helper и связанные тестовые сценарии после перевода потребителей. `ADR-041` обновить, сохранив историческую причину отделения участков от мест, но заменив решение о двух JSON на запись участков в Pagefind и один геометрический feed. Основные specs не переписывать: их наблюдаемые требования остаются прежними.

Перед удалением сохранить исходные наблюдения по затронутым запросам и сетевым байтам на актуальной локальной production-сборке. После — сравнить выдачу `SHR-L43`, `SHR-L44`, `L43`, одинакового короткого номера разных частей, неполного номера, только цифр и соседних текстовых запросов; измерить холодный Pagefind-трафик и общий размер индекса на тех же условиях. Оставить результаты в PR, не создавать постоянную матрицу реального контента.

## Risks / Trade-offs

- **Новый индекс окажется тяжелее удалённого словаря** → измерить байты загруженных ресурсов Pagefind и время запроса до/после, сообщить фактическую цену решения; не скрывать её за размером JSON на диске.
- **Служебные записи вытеснят обычные страницы** → исключать секцию участков из текстового поиска штатным фильтром; на production-индексе проверить соседние запросы, счётчик и догрузку.
- **URL custom record потеряет `?p=` при клиентской нормализации** → явно проверить форму `/map/?p=<основной-код>` и переход из диалога, не менять правила подсветки текстовых страниц.
- **Недействительный `?p=` теперь загружает геометрию** → принять эту цену ради отсутствия отдельного словаря; слой остаётся выключенным и карта не приближается. При сбое загрузки не выдавать «не найдено».
- **Краткий переход между версиями статических ресурсов при деплое** → выпускать HTML, индекс и карту единым build-артефактом, как сейчас; при необходимости откатить весь PR, а не один ресурс.

## Migration Plan

Сначала воспроизвести исходную выдачу и байты локальной production-сборки, затем обновить сборку и клиентов, удалить словарь и связанные контракты, выполнить production-сборку и сравнение. Обновление `ADR-041`, проверка актуального diff, `pnpm openspec:validate` и архивирование change входят в тот же PR #810. Обязательной проверки на уже развёрнутом production для завершения изменения нет; до перевода PR в ready проверяются локальная production-сборка, индекс и браузерные переходы. Откат — возврат всего изменения, включая скрипт сборки, клиентов, индекс и статический маршрут.
