# Design

## Context

Мотивация — в [proposal.md](proposal.md). Astro 7 собирает клиентские и серверные модули отдельно через Vite 8/Rolldown; `astro-compressor` уже создаёт `.br` и `.gz`. Корневая сборка проходит через Turbo, а app-сборка копирует результат в `dist/www`. Отчёт нужен о клиентском коде именно готового сайта, без включения анализа в обычный build.

Применим [ADR-004](../../../docs/decisions/004-lighthouse-analytics-profile.md): измерение собственного кода не следует выдавать за оценку всей страницы с внешними ресурсами. Решений об архитектуре карт и редакционных данных этот change не меняет.

## Goals / Non-Goals

**Goals:**

- Получать воспроизводимый список модулей клиентских чанков и размеры готовых JS/CSS-файлов.
- Сравнивать YAML-снимки обычным Git diff, а структуру чанков изучать в локальной HTML-диаграмме.

**Non-Goals:**

- Автоматически устанавливать бюджеты, хранить историю измерений или определять допустимость изменения размера.
- Оптимизировать клиентские зависимости, менять поведение страниц или анализировать внешние SDK как часть собственного бандла.

## Decisions

### Один анализатор и два вида локального отчёта

`rollup-plugin-visualizer` подключается только к клиентскому Vite environment при `BUNDLE_ANALYZE=1`. Его штатные форматы `list` и `treemap` дают `docs/bundle/client.yaml` и `.cache/bundle/client.html`; `projectRoot` приводит пути модулей к виду, пригодному для Git diff. Выбор одного плагина вместо отдельного BundleStats или собственной системы сравнения оставляет отчёт простым: изменения YAML сравнивает Git, а решение об оптимизации принимает человек.

`docs/bundle/assets.yaml` перечисляет готовые JS/CSS в `dist/www/static` и размеры их файлов, `.br` и `.gz`. Скрипт использует уже установленный YAML-сериализатор и результат штатного сжатия, не разбирает CSS и не вычисляет собственные метрики модулей. `rendered` в отчёте Visualizer помогает разобраться в составе чанка; размеры отдельных модулей нельзя суммировать как сетевой вес файла.

`pnpm bundle:analyze` вызывает app build напрямую, обходя кеш корневой Turbo-задачи и используя существующий search/compression pipeline. Обычный `pnpm build` отчёты не перезаписывает; локальный HTML лежит вне публикуемого `dist/www`, YAML хранится в Git. Хеши файлов не стабилизируются вручную: при сравнении нужно смотреть на модули и точки входа, а не считать новую строку с другим хешем новой зависимостью.

## Risks / Trade-offs

- Хеши чанков меняются без изменения зависимостей → читать diff по составу модулей и размерам, а не по одному имени файла.
- Анализ плагином зависит от корректной атрибуции Rolldown → проверять ненулевые размеры крупных известных модулей и отсутствие серверных/абсолютных путей в отчёте.
- Отчёты показывают собственные файлы, а не полный Network или Lighthouse → не выдавать их за измерение скорости страницы.

## Migration Plan

Анализатор и исходные снимки уже добавлены и проверены в ветке. Убрать экспериментальные оптимизации из итогового diff, документировать команду, выполнить сборку и сравнить отчёты с зафиксированным baseline, затем пройти штатные проверки и ревью. Откат инструмента возвращает вместе скрипты, настройку, зависимость и YAML; данные сайта миграции не требуют.
