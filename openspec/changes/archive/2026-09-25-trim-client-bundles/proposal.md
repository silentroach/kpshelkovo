# Proposal

## Why

На страницах встречается код, который им не нужен, но по обычной сборке трудно понять, какой модуль попал в клиентский бандл и сколько весят готовые файлы. Нужен воспроизводимый локальный отчёт, чтобы разбирать такие случаи и заводить отдельные задачи по фактическим результатам.

## What Changes

- Добавить opt-in команду `pnpm bundle:analyze` для анализа production-сборки: состав клиентского JavaScript, размеры готовых JS/CSS и локальную HTML-диаграмму.
- Хранить YAML-снимки в Git как ориентир для следующих задач; описать запуск и сравнение отчётов в инструкции разработки и коротком правиле для агента.
- Все оптимизации часов работы, карт, поиска и условной загрузки ресурсов вынести за пределы этого change. Анализатор сам по себе не меняет ресурсы публикуемого сайта.

## Capabilities

### New Capabilities

Нет: это инструмент разработки, а не новый контракт для посетителей сайта.

### Modified Capabilities

Нет: поведение страниц и публичных данных не меняется.

## Impact

- Сборка и документация: `apps/www/astro.config.ts`, интеграция анализатора и скрипт отчёта, package scripts, lock-файл, `docs/bundle/`, `docs/development.md`, `AGENTS.md`, игнорирование локального HTML.
- Задача: [#838](https://github.com/silentroach/kpshelkovo/issues/838), рабочая ветка `perf/trim-client-bundles`. Исходные наблюдения и выполненные в ветке эксперименты остаются в истории Git и обсуждении, но не входят в итоговый diff.
- Границы: без оптимизаций клиентского кода, CI-бюджетов и блокировки роста, собственного анализатора, ручной раскладки чанков, изменений публичных контрактов и production-приёмки. Перед PR достаточно локальной сборки, проверки отчётов и ревью diff.
