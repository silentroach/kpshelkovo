# Design

## Context

- Мотивация и границы: [proposal.md](proposal.md), issue #741.
- `bindStatusTimelineLazyHydration` подписывает `bindOrHydrate` на два события Astro. `hydrateStatusTimelines` каждый раз пересчитывает все найденные таймлайны; установка обработчиков идемпотентна, пересборка сегментов — нет.
- `handleIntent` и `hydrateLoadedTimelines` независимо ожидают один import, а затем каждый вызывает гидратацию текущего документа. Поэтому одной правки подписок недостаточно для перехода во время загрузки.
- Production-проверка: `/status/` → `/status/electricity/` → назад дала один пересчёт при первом взаимодействии и по два на каждый переход при одном скачивании DOM-модуля. На главной было 8 таймлайнов и 13 маркеров; между уведомлениями Astro прошло около 5–6 мс. Это наблюдение порядка вызовов, а не профиль стоимости CPU.
- [ADR-002](../../../../docs/decisions/002-client-transitions-prefetch-cache.md) закрепляет ClientRouter и устойчивую инициализацию при переходах. [ADR-031](../../../../docs/decisions/031-status-incident-lifecycle.md) задаёт общие временные границы фаз и отсутствие таймерного обновления.

## Goals / Non-Goals

**Goals:**

- Одна точка обновления при навигации и одна ожидающая операция гидратации на время загрузки модуля.
- Сохранение времени фактического пересчёта и работы первого взаимодействия.

**Non-Goals:**

- Кеширование геометрии, новые таймеры и переписывание вычислителя фаз.
- Изменение геометрии маркеров из PR #159 или общей навигации сайта.

## Decisions

- Использовать только `astro:page-load` для пересчёта при навигации. Прямой первоначальный вызов привязки сохраняется, как и обработка первого взаимодействия. По документации Astro `page-load` приходит и при прямом открытии, и при клиентских переходах вперёд/назад после готовности блокирующих стилей и скриптов.
- На `astro:after-swap` только включать лёгкий захват намерения для новых маркеров, без загрузки модуля и пересчёта. До `page-load` сохранять последнее взаимодействие, затем повторять его после общей гидратации, если маркер ещё подключён и намерение не отменено. Замена DOM сбрасывает намерение удалённого маркера. Это уточнение согласовано по ревью PR #770: задержка актуализации допустима, потеря взаимодействия — нет.
- Направить загрузку по взаимодействию и обновление при навигации через общую ожидающую операцию «загрузить и гидратировать». Пока операция не завершена, новые запросы используют тот же promise. После завершения блокировка снимается; следующий переход может пересчитать таймлайны заново. Кеш успешного import остаётся отдельным от временного объединения работы.
- DOM и время брать непосредственно перед гидратацией, после ожидания модуля. При нескольких переходах в ожидании загрузки обрабатывается текущий документ. Если таймлайнов на нём уже нет, гидратация не требуется.
- Сохранять намерение до самого replay, включая ожидание модуля после `page-load` и при первом прямом открытии. Отменять наведение по `pointerout`, фокус по `focusout` именно для исходного маркера; переходы к его потомкам через `relatedTarget` не считать уходом. Завершение старой операции не должно повторять отменённое намерение или стирать более новое. Выход указателя или фокуса не отменяет открытие по касанию. Это уточнение согласовано по повторному ревью PR #770.
- При пересчёте не скрывать видимый маркер перед вычислением его состояния: это снимает фокус в браузере и отменяет актуальное намерение. Скрывать только маркеры с некорректными данными или вне текущего диапазона; геометрические расчёты сохраняются.
- Первое актуальное взаимодействие повторять после общей гидратации только для подключённого маркера. При ошибке сбросить состояние загрузки и ожидающей операции, восстановить обработчики намерения на странице с таймлайнами; автоматический бесконечный retry не добавлять.
- Не вводить кеш по URL или постоянную отметку «уже гидратировано»: возврат на тот же адрес должен обновить время. Загрузка, начатая взаимодействием до замены DOM и завершившаяся до окончания навигации, и последующий `page-load` могут потребовать отдельных актуализаций: между ними время могло измениться. Объединяются именно одновременно ожидающие запросы, а пересчёт по навигационному событию остаётся только на одной стадии.
- Число полных проходов и объединение promise — проверяемые технические условия этого исправления, а не ограничения будущих реализаций публичного контракта. Основная spec сохраняет актуальность состояния, восстановление после ошибки и работу первого взаимодействия, в том числе во время перехода.
- Нового ADR не требуется: это локальный выбор точки инициализации в рамках ADR-002 и ADR-031.

## Risks / Trade-offs

- Серверная фаза может быть видна до `page-load`, особенно при медленных блокирующих скриптах → явно принять задержку до завершения перехода; проверять итоговую фазу на временной границе. Гарантию раннего обновления до показа страницы этот вариант не даёт.
- Неосторожное объединение запросов может подавить последующий переход или повторную попытку → тесты с управляемым promise, успешным завершением, ошибкой и новым взаимодействием.
- Загрузка может завершиться на другой странице → проверка текущего DOM и подключённости исходного маркера.
- Тесты lazy-пути сейчас находятся в `timeline.dom.test.ts`, который затронут PR #159 → новые регрессионные тесты хранить в `tests/timeline.lazy.test.ts`, существующий интеграционный тест фаз сохранить.

## Migration Plan

- Проверить регрессии в happy-dom и реальную клиентскую навигацию на локальной production-сборке. Для воспроизведения задержки модуля и границ времени использовать детерминированные тесты, а не ожидание реальных событий статуса.
- Измерить число проходов и ориентировочную стоимость гидратации на странице с несколькими таймлайнами до/после; не обещать ускорение страницы по одному замеру.
- Обязательная приёмка после deploy не требуется: достаточно собственной проверки сборки перед PR. Production baseline уже снят; ожидается обычное закрытие issue через PR после выполнения проверок.
- Синхронизировать spec и архивировать change в той же ветке после реализации и приёмки. Публикация стандартная; откат — возврат изменения загрузчика, тестов и документов одним revert PR.
