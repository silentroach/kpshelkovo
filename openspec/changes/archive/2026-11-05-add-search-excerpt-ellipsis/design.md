# Design

## Context

Объём и связь с [#1263](https://github.com/silentroach/kpshelkovo/issues/1263) заданы в [proposal](/openspec/changes/archive/2026-11-05-add-search-excerpt-ellipsis/proposal.md). Архитектура следует [ADR-025](/docs/decisions/025-static-full-text-search-with-pagefind.md), оформление принадлежит приложению по [ADR-034](/docs/decisions/034-native-css-architecture.md).

У [SearchDialog](/apps/www/src/components/search/SearchDialog.svelte) `resultRow` сравнивает основной и секционный excerpts после нормализации пробелов. Якорь выбирается только при единственной цели. [Клиент](/apps/www/src/lib/search/client.ts) передаёт HTML, экранированный Pagefind, а UI декодирует текст и отдельно выводит разрешённую подсветку `<mark>`.

Обычное `excerptEllipsis: '…'` нарушает равенство одинакового текста на границе секции: один excerpt получает обозначение обрезки, другой нет. Пример воспроизведён в [исследовании](/docs/research/pagefind-1.6.0-upstream.md). Консультация `advisor` подтвердила подход со служебным маркером и проверила его на исходном `build_excerpt` версии 1.6.0, включая авторские многоточия и буквальный текст маркера.

## Goals / Non-Goals

**Goals:**

- Разделить исходный excerpt и достоверные сведения о его обрезке на границе клиента.
- Оставить действующее сравнение текста, единственность цели и canonical fallback.
- Получить отдельное сравнение обновления движка и нового оформления на одном корпусе.

**Non-Goals:**

- Собственный генератор предложений, вычисление окна слов или изменение primary excerpt ради якоря.
- Перенастройка релевантности, массовое добавление алиасов, Component UI и `maxFragments`.

## Decisions

### 1. Обновление входит только в этот change

После разрешения снять baseline 1.5.2, обновить точную зависимость и lock-файл до 1.6.0, затем проверить индекс с прежними options. Разделить результат этого этапа и подключения многоточий в проверках, даже если всё войдёт в один PR. Два остальных change используют этот результат и не повторяют обновление пакета.

Включение зависит от совместимости действующего Node API `createIndex/addDirectory/addCustomRecord/writeFiles` и JS API. Пересобрать весь индекс штатной командой приложения вместе с компрессией и dev-snapshot при его подготовке. Актуальные отчёты `docs/bundle/client.yaml` и `docs/bundle/assets.yaml` сохранить по [правилам анализа](/docs/development.md#анализ-клиентских-бандлов).

### 2. Статический маркер вместо обычного многоточия в options

Передать `excerptEllipsis: '<!--pagefind-excerpt-cut-->'`. На границе нормализации excerpt распознавать только этот точный сырой маркер в начале и конце строки, до HTML-декодирования. У основного результата сохранить undecorated `excerptHtml` и два readonly-признака обрезки; у подрезультатов убрать служебные маркеры для прежнего сравнения. Тип результата helper-а хранить в отдельном types-модуле.

Подтверждённый порядок upstream: [Pagefind экранирует исходный текст](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/coupled_search.ts#L468-L500), затем [build_excerpt добавляет строку опции](https://github.com/Pagefind/pagefind/blob/v1.6.0/pagefind_web_js/lib/excerpt.ts). Буквальный авторский текст `<!--pagefind-excerpt-cut-->` уже превращён в entities и не может совпасть с сырым маркером. Маркер не выводится как HTML и не попадает в видимый текст.

Это небольшой адаптер закреплённой версии. Не нужны случайные токены, DOMParser, модификация Pagefind, два поиска с разными options или восстановление границ по `content/locations`. Снятие крайних обычных `…`/`...` отвергнуто: оно повреждает авторский текст. Подмена основного excerpt секционным нарушает действующий контракт. Более простой отказ от эффекта возможен, если владелец не примет этот адаптер; тогда объём change нужно пересогласовать, а не писать собственный генератор.

### 3. Представление использует признаки основного excerpt

`resultRow` продолжает сравнивать undecorated excerpts. UI добавляет обычный текст `… ` и ` …` по признакам основного результата. Проверка повторяющегося заголовка работает с текстом без служебного оформления. Существующий безопасный decoder и разделители между соседними `<mark>` сохраняются.

Резервное description и `matchContext` не получают признаки обрезки по догадке. CSS line-clamp остаётся самостоятельным ограничением отображения. В [дизайн-гайде](/docs/design/design-code-shelkovo.md#результаты-поиска) заменить запрет любого добавленного многоточия правилом подтверждённой обрезки; композиция результата сохраняется.

### 4. Приёмка проверяет контракт, а не случайные ранги

Короткие fixtures подтверждают каждый край, авторские `…`/`...`, буквальный маркер, entities, подсветку, разные границы секции и страницы, неоднозначные цели и несовпадающие excerpts. Ручное сравнение использует настоящий production-индекс: `пропуск` из #1254, длинную расшифровку, `тариф`, `вода`, короткий запрос, слова с `е/ё`, полный/короткий код участка и подтверждённый алиас. Целевые материалы и дополнительные контроли выбираются по актуальному корпусу до правки. Сравнить выдачу, основной фрагмент, контекст, `hash`, `h` и реальный переход по [site-search](/.agents/skills/site-search/SKILL.md).

## Risks / Trade-offs

- Адаптер зависит от порядка экранирования upstream. Закреплённая версия, адресный regression fixture и реальная проверка escaped-текста подтверждают границу; при следующем обновлении её сверяют заново.
- Исправления metadata scoring и exact search могут изменить порядок выдачи. Сравнение этапа обновления проводится до изменения оформления; полезность оценивается вручную.
- Обозначение обрезки не превращает фрагмент в целое предложение. #1254 остаётся связанным обсуждением; этот PR сам по себе не закрывает более широкие ожидания.

## Migration Plan

1. Получить апрув трёх планов; сохранить согласованный коммит в рабочей ветке и отметить разрешение в #1263 по проектному процессу.
2. Выполнить обновление, проверки и адаптер в этом change. Затем выполнить явные секции и повтор поиска последовательно в той же ветке.
3. Провести общую приёмку и полный reviewer всего diff. Синхронизировать и архивировать все три change в этой ветке; после этого выполнить адресное ревью новых правок и открыть один PR с `Closes #1263` и `Refs #1254`.
4. Откат после публикации возвращает общий PR целиком, включая точную версию, lock-файл, реализацию и specs, с пересборкой согласованного индекса.
