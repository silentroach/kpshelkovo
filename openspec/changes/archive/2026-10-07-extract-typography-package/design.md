# Design

## Context

Причина изменения — в [proposal.md](/openspec/changes/archive/2026-10-07-extract-typography-package/proposal.md). Фактическая граница уже видна в коде: `/packages/markdown/src/typography-core.ts` зависит только от Typograf, а `/packages/markdown/src/typography.ts` подключает Satteri и адаптирует текстовые узлы обоих AST-путей. Строковые функции экспортируются из корня Markdown-пакета и отдельного клиентского subpath.

[ADR-003](/docs/decisions/003-markdown-pipeline-layering.md) сохраняет общий Markdown-pipeline и app-level обработку упоминаний. Его описание владельца типографических правил нужно уточнить при выделении ядра. По [ADR-034](/docs/decisions/034-native-css-architecture.md) CSS для создаваемой разметки принадлежит приложению.

## Goals / Non-Goals

**Goals:** самостоятельный клиентский и серверный вход строкового типографа; одна регистрация общих правил; однонаправленная зависимость Markdown от типографики; сохранение текущего вывода и действующих регрессионных проверок.

**Non-Goals:** новые правила или изменения алгоритмов типографики, перенос CSS, перенос AST-адаптеров в строковое ядро, расширение мест применения типографа, обновление версий внешних библиотек.

## Decisions

### Два пакета с одной границей зависимости

- Создать приватный workspace-пакет `/packages/typography` по существующим ESM/TypeScript-соглашениям. Его корневой вход предоставляет `formatText`, `formatTextHtml`, `formatDynamicHtml` и напрямую ведёт к переносимому строковому ядру.
- Typograf становится production-зависимостью нового пакета. В новом пакете отсутствуют зависимости и импорты Markdown, Satteri и приложения.
- `@shelkovo/markdown` получает зависимость `workspace:*` на типографику; его rehype/Satteri-адаптеры и коррекция контекста дерева остаются на месте.
- Три уже существующих набора `TYPOGRAPHY_BLOCK_TAGS`, `TYPOGRAPHY_SKIP_TAGS`, `TYPOGRAPHY_WRAPPER_CLASSES` экспортируются новым пакетом для адаптеров. Это общие определения ядра, а не копии списков в Markdown-пакете; отдельный конфигурационный слой или специальный `/internal`-вход не нужен.
- Регистрация правил остаётся в единственном модуле ядра. `sideEffects` обоих пакетов пересматривается по фактической инициализации и цепочкам экспортов; production-проверка подтверждает сохранение правил и отсутствие AST-парсера в строковом клиентском входе.

Сохранение нынешнего subpath уже обеспечивает изоляцию сборки, но не выбранное владельцем разделение ответственности. Переименование всего пакета в `typography` оставило бы под этим названием Markdown-генерацию и парсеры. Два пакета отражают существующие слои с минимальным переносом кода.

### Атомарная миграция приватных импортов

`apps/www` явно зависит от обоих пакетов. Все вызовы трёх строковых API, включая content diff и статус, переходят на `@shelkovo/typography`. Markdown-API и импорты `rehypeTypograf`/`satteriTypograf` сохраняют владельца.

Прежний subpath и строковые реэкспорты Markdown-пакета удаляются вместе с миграцией потребителей. Внешних опубликованных потребителей у приватных workspace-пакетов не заявлено; совместимые прокладки продлили бы неоднозначность импортов. Прямые обращения к исходникам соседнего пакета не используются.

### Проверки следуют за владельцем поведения

Строковые проверки из текущих `/packages/markdown/src/typography.test.ts` и `/packages/markdown/src/index.test.ts` переносятся в новый пакет с прежними ожиданиями. AST-проверки, включая сопоставление с HTML-входом, остаются в Markdown-пакете и используют настоящий `@shelkovo/typography`. Сохраняется покрытие экранирования, атрибутов и кода, диапазонов, контекста кавычек и повторной обработки. Существующие проверки приложения подтверждают интеграцию и текстовые границы.

Новая разовая клиентская проба импортирует `formatText` из корня `@shelkovo/typography` обычной production-сборкой, без исключения отсутствующих зависимостей. Проверяются состав модулей и выполнение собранных правил. Сравнение бандлов сайта проводится по [инструкции](/docs/development.md#анализ-клиентских-бандлов); это дополняет пробу, поскольку текущие подсказки получают уже подготовленный сервером текст.

README обоих пакетов, `/apps/www/AGENTS.md` и действующая граница в ADR-003 обновляются вместе с импортами. Архивы прежних changes и исторические отчёты сохраняют описание проверенного тогда состояния.

## Risks / Trade-offs

- Пропущенный старый импорт или workspace dependency → поиск оставшихся исполняемых импортов, обновление lock-файла, typecheck и production-сборка.
- Потеря регистрации правил при tree-shaking → проверка `sideEffects` и выполнение клиентской пробы с диапазоном даты и собственным правилом названия посёлка.
- Перенос тестов скрывает изменение результата → сохранить существующие ожидания и межпакетное сравнение HTML/AST; расхождение вывода расследовать, а не обновлять snapshots автоматически.
- Нативный Satteri перестаёт разрешаться при сборке → сохранить существующую серверную интеграцию в `/apps/www/astro.config.ts` и проверить полный production-проход Markdown; строковый пакет от неё не зависит.

## Migration Plan

1. После согласования артефактов зафиксировать разрешение в #963. Работа выполняется в текущей рабочей копии, ветка `refactor/963-extract-typography-package` основана на `5ef9b74e` из PR #961.
2. Перенести ядро и строковые тесты, изменить зависимости, экспорты, импорты и рабочую документацию в одном изменении. Затем выполнить проверки и независимое ревью всего diff.
3. Пока PR #961 открыт, связанный PR #963-задания сравнивается с `fix/958-unbreakable-date-ranges`; после merge родительского PR целевой становится `master`, с повторной сверкой базы и состава diff. В обоих случаях показывать только самостоятельный объём #963.
4. По завершении архивировать change штатным workflow; delta specs отсутствуют. Откат возвращает весь рефакторинг, включая manifests, lock-файл и импорты, одним возвратом PR.
