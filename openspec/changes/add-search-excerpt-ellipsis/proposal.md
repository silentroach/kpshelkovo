# Proposal

## Why

Поисковый фрагмент может начинаться посреди фразы без обозначения обрезки. Pagefind 1.6.0 умеет обозначать её сам; это позволяет улучшить читаемость без восстановления авторского предложения по догадке.

Общий тикет: [#1263](https://github.com/silentroach/kpshelkovo/issues/1263). Связанное обсуждение: [#1254](https://github.com/silentroach/kpshelkovo/issues/1254). Источники и воспроизведённый конфликт сравнения excerpts: [исследование](/docs/research/pagefind-1.6.0-upstream.md).

## What Changes

- Первым этапом обновить точную зависимость Pagefind с 1.5.2 до 1.6.0 и пересобрать индекс с проверкой поиска на прежних настройках.
- Показывать многоточие с той стороны основного excerpt, где движок подтверждает обрезку.
- Сохранить авторский текст, подсветку, отдельный контекст секции и выбор якоря того же фрагмента при различии служебных многоточий.
- Уточнить правило представления результатов в дизайн-гайде.

## Capabilities

### New Capabilities

Новых областей нет.

### Modified Capabilities

- `search`: достоверное обозначение обрезки с сохранением контекста, текста и цели перехода.

## Impact

Затронуты [зависимость приложения](/apps/www/package.json), `/pnpm-lock.yaml`, [поисковый клиент](/apps/www/src/lib/search/client.ts) и его типы, [SearchDialog](/apps/www/src/components/search/SearchDialog.svelte), связанные тесты, [дизайн-гайд](/docs/design/design-code-shelkovo.md) и отчёты клиентской сборки. Корпус и веса поиска остаются входными условиями сравнения; новая версия движка может изменить выдачу.

Ветка всех трёх change: `feat/pagefind-1.6-search`, итоговый PR один. Этот change владеет обновлением зависимости; [явные секции](/openspec/changes/add-explicit-search-sections/proposal.md) и [повтор поиска](/openspec/changes/restore-search-data-retry/proposal.md) выполняются после него. Код меняется только после апрува владельца. Приёмка планируется на локальной production-сборке до PR; отдельная production-приёмка не требуется.
