# Tasks

Реализация отложена до отдельного запроса владельца в следующей сессии. Продолжать в `perf/preformat-search-dates` и том же draft PR; публикация этого плана не разрешает выполнение пунктов ниже.

## 1. Сопоставимый baseline

- [ ] 1.1 До правки получить актуальные отчёты через `pnpm bundle:analyze`, сохранить исходный снимок для сравнения и записать SHA, состояние дерева, инструментов и корпуса. В существующем поисковом UI зафиксировать датированный и недатированный результат, трафик холодного открытия с первой порцией и затронутые запросы по [site-search](/.agents/skills/site-search/SKILL.md), включая слова месяца/года; baseline считается готовым, когда результаты и условия доступны для проверки после правки.

## 2. Передача готовой подписи

- [ ] 2.1 В серверном `BaseLayout` готовить и публиковать `publishedAtLabel` существующим `formatDate`, не меняя producers, raw `publishedAt` и sort. Расширить существующие проверки layout: точная подпись, исходная дата, високосный день, отсутствие обоих полей без даты; подтвердить, что подпись не зависит от таймзоны окружения.
- [ ] 2.2 Провести optional подпись через типы и адаптер результата в `SearchDialog`, сохранить исходный `datetime`, безопасный текстовый вывод и отсутствие пустого `<time>`, убрать клиентский `formatDate`, сохранив `count`/`pluralize`. Проверками адаптера и компонента подтвердить готовый текст, неизменный `datetime`, поведение без даты/при неполной metadata и отсутствие исполняемого HTML в подписи; проверить Svelte официальным autofixer.
- [ ] 2.3 Добавить только нулевой вес `publishedAtLabel`, сохранив остальные веса и возрастную поправку. Короткой проверкой реального Pagefind на fixture подтвердить, что подпись сама не создаёт совпадений и не меняет результат; при расхождении остановиться и согласовать решение, не расширяя задачу до изменения релевантности.

## 3. Интеграция и сетевой баланс

- [ ] 3.1 На актуальной production-сборке проверить полный путь HTML → Pagefind → UI для существующих датированных producers и результатов без даты. В браузере подтвердить одинаковую подпись в `Europe/Moscow` и `America/Los_Angeles`, первое/повторное открытие, догрузку и переход через ClientRouter; по затронутым запросам сравнить до/после состав, порядок, URL, excerpts и подрезультаты. Использовать существующие проверки, не создавать постоянный smoke-обход всех страниц.
- [ ] 3.2 Повторить `pnpm bundle:analyze`, сохранить актуальные YAML-отчёты и записать фактические изменения в design/PR. Сравнить все клиентские чанки, HTML metadata и все части индекса на одинаковых входах, а также уникальные запросы холодного открытия с первой порцией; подтвердить отсутствие Luxon во всём клиентском графе, положительный суммарный баланс и отсутствие дополнительных запросов ради даты или загрузки всех фрагментов заранее.

## 4. Завершающая приёмка

- [ ] 4.1 Выполнить `pnpm typecheck`, `pnpm test`, `pnpm --filter @shelkovo/www test:search-quality`, форматирование и `pnpm openspec:validate`; сохранить актуальные результаты и сверить их с границами change, [search](/openspec/specs/search/spec.md) и [client-load-recovery](/openspec/specs/client-load-recovery/spec.md). Сборки внутри анализа бандлов и поисковой проверки переиспользовать без лишнего отдельного `pnpm build` при неизменных входах.
- [ ] 4.2 Вызвать `reviewer` для первого полного прохода актуального diff с точным SHA базы и результатами проверок, разобрать замечания и после исправлений выполнить адресный повтор по [процедуре](/docs/development.md#ревью-изменения-в-opencode). При недоступности reviewer провести основной проход и отдельный `ponytail-review` самостоятельно и явно записать fallback. Завершить пункт только при отсутствии неразобранных замечаний; последующий архив и финальную публикацию того же PR выполнить по проектному workflow с повтором ревью изменившихся документов.
