# Design

## Context

Мотивация и границы — в [proposal](/openspec/changes/preformat-search-dates/proposal.md). Дизайн нужен для изменения нескольких слоёв и оценки баланса между клиентским кодом и индексом.

Текущий путь: `SearchDialog.svelte` вызывает `formatDate` из `@shelkovo/format`, который использует Luxon. Это единственный клиентский путь Luxon в сохранённом отчёте бандлов. `count` и `pluralize` не зависят от него и остаются в компоненте.

Поисковые страницы новостей, встреч и инцидентов передают в `BaseLayout` календарный `publishedAt` вида `YYYY-MM-DD`. Он выделен из московского ISO исходника без перевода в UTC. Встречи и новости используют его также для существующей возрастной поправки, а диалог — для `<time datetime>`. Мероприятия и записи участков не получают эту дату автоматически.

Действующие решения:

- [ADR-025](/docs/decisions/025-static-full-text-search-with-pagefind.md): индекс готовится из HTML, metadata принадлежит шаблонам, `/search/` — внутренний build-артефакт, результаты загружаются порциями.
- [ADR-035](/docs/decisions/035-status-search-indexing.md): сохраняются корпус и отсутствие возрастного понижения статуса.
- [ADR-002](/docs/decisions/002-client-transitions-prefetch-cache.md): сохраняются ClientRouter, обычные динамические импорты и восстановление после отказа кода.

Новый ADR и delta specs не нужны: меняется техническое место форматирования при сохранении пользовательского поведения.

## Goals / Non-Goals

**Goals:**

- Убрать Luxon из всех клиентских чанков, а не переместить его в другой файл или отложить до первого результата.
- Передавать готовую подпись вместе с уже загружаемыми данными результата без отдельного запроса и клиентского разбора даты.
- Подтвердить положительный сетевой баланс на сопоставимом корпусе, сохранив внешний вид и работу поиска.

**Non-Goals:**

- Замена общего `formatDate`, удаление серверного Luxon или воспроизведение его ISO-парсера на клиенте.
- Перевод календарной даты материала в таймзону посетителя, изменение возрастных бонусов, UTC-границ их расчёта или даты начала инцидента.
- Изменение схем редакционных материалов, новых дат у разделов без `publishedAt`, поискового корпуса, алиасов, Pagefind, deploy или CSP.
- Отдельная библиотека форматирования, универсальный слой кеширования либо постоянный performance-benchmark в CI.

## Decisions

### 1. Готовить подпись в общем серверном слое

В frontmatter [BaseLayout](/apps/www/src/layouts/BaseLayout.astro) готовить `publishedAtLabel` существующим серверным `formatDate`, только если передан `publishedAt`. Опубликовать строку через `data-search-published-at-label` и metadata `publishedAtLabel[data-search-published-at-label]`.

Не добавлять готовую строку в редакционные данные или каждый producer: это производное представление уже переданной календарной даты. Исходный `publishedAt`, существующий sort и raw `<time datetime>` не меняются. Подпись сохраняет день без ведущего нуля, русский месяц в родительном падеже, год, обычные пробелы и отсутствие суффикса «г.». Посетитель в Москве и США видит одну строку.

Альтернативы:

- Клиентский `Intl.DateTimeFormat` тоже убирает Luxon и немного экономит данные индекса, но оставляет отдельное клиентское правило форматирования и разбора. Выбран серверный вариант: он переиспользует действующее правило при малой добавке к индексу.
- Замена общего `formatDate` затрагивает HTML, Markdown и metadata других разделов без необходимости для #875.
- Динамический импорт Luxon переносит тяжёлую загрузку на показ результата, не устраняя её.

### 2. Передавать подпись как текст, отдельно от исходной даты

В [типах результата](/apps/www/src/lib/search/client.types.ts) добавить optional `publishedAtLabel`; [адаптер](/apps/www/src/lib/search/client.ts) принимает её через существующую нормализацию текста. В [SearchDialog](/apps/www/src/components/search/SearchDialog.svelte) выводить готовую строку обычной Svelte-интерполяцией, без HTML и вызова форматтера. Сохранить `publishedAt` в `datetime` и в текущем ранжировании.

Согласованная сборка должна давать пару «исходная дата + готовая подпись» для каждого датированного результата. Результат без даты остаётся без `<time>`. Для неполной metadata не создавать пустой `<time>` и не вводить клиентский fallback-форматтер; ссылка и остальные сведения результата остаются доступными. Полноту пары проверять на границе HTML → индекс → UI.

Изменение рассчитано на совместно собранные HTML, индекс и клиент. Отдельный протокол совместимости поколений внутреннего `/search/` не вводится.

### 3. Не давать подписи поискового влияния

У Pagefind metadata searchable по умолчанию. Для `publishedAtLabel` явно задать `metaWeights: 0`, как уже сделано для исходного `publishedAt`; остальные веса оставить прежними. Не вставлять подпись в скрытый body ради индексирования.

Нулевой вес сам по себе не заменяет проверку результата. На одинаковом корпусе сравнить состав и порядок выдачи, URL, excerpts и выбранные подрезультаты, включая запросы со словами даты. Подпись не должна создавать дополнительные совпадения или менять ранжирование. Если это не подтверждается, остановиться и согласовать решение внутри change, а не принимать новую релевантность побочным эффектом оптимизации.

### 4. Проверять полный граф загрузки и весь индекс

Исследование 30 сентября 2026 года дало следующие ориентиры:

- Опубликованный `lazy._0oewFB7.js`: 87 670 байт JS / 25 527 байт Brotli. Обособленный блок Luxon — около 70 422 байт JS; его условное удаление из текста и пересжатие дают разницу 19 249 байт Brotli. Это оценка без рабочей сборки после замены, не обещанная экономия или измерение задержки.
- Сохранённый локальный индекс Pagefind 1.5.2: 1 855 записей, из них 71 с датой. A/B выполнен через `addHTMLFile`, неизменные custom records участков и `getFiles` целиком в памяти, без записи индекса. Контрольные фрагменты суммарно занимали 666 777 байт, как в сохранённой сборке.
- Добавление подписи: +781 байт фрагментов, +198 байт index chunks, +4 байта metadata, +1 байт фильтров; суммарно +984 байта готовых сжатых данных. Количество файлов не изменилось. Ориентир для восьми датированных результатов — около +90 байт фрагментов, отдельно от служебных частей.
- Сохранённый индекс не был подтверждён как побайтная сборка HEAD: тогда production содержал 1 856 записей. Эти числа обосновывают подход, но не заменяют новый baseline в сессии реализации и не становятся фиксированным бюджетом или snapshot корпуса.

Перед правкой получить актуальный baseline по [анализу бандлов](/docs/development.md#анализ-клиентских-бандлов), зафиксировать SHA, состояние дерева, версию инструментов и корпус. После правки сравнить уникальные запрошенные JS-файлы и все части индекса, а не один переименованный чанк. Для индекса сравнивать одинаковые входные HTML и записи участков; при изменении временного окна корпуса обновить baseline, не приписывая разницу форматированию.

Приёмка требует отсутствия Luxon во всём клиентском графе и уменьшения суммарного трафика холодной активации поиска с первой порцией результатов с учётом добавки индекса. Отдельно проверить повторное открытие, догрузку и переход через ClientRouter. Не добавлять запрос ради даты и не загружать все фрагменты заранее. Наличие улучшения Lighthouse или конкретная экономия миллисекунд не являются критериями этой задачи.

## Risks / Trade-offs

- Дополнительная metadata меняет index chunks и может влиять на поиск → нулевой вес, проверка совпадений на малом fixture и ручное сравнение выдачи до/после по [site-search](/.agents/skills/site-search/SKILL.md).
- Неполная передача подписи скрывает дату → проверки server metadata, адаптера, `<time>` и собранного индекса для существующих producers, без общего обхода всего сайта в CI.
- Ошибка выделения календарного дня сдвигает дату около московской полуночи → не менять producers и не заменять их ISO-срез на UTC `toISOString`; проверить одинаковый текст в `Europe/Moscow` и `America/Los_Angeles`.
- Рост индекса расходует трафик при новых результатах → считать все сжатые части, холодную порцию и кешированные повторные открытия; исторические числа не считать гарантией текущего выигрыша.
- Изменение общего date-пакета расширяет риск → оставить пакет и серверных потребителей без правок, удалить только клиентское использование форматтера в поиске.

## Migration Plan

План публикуется в draft PR ветки `perf/preformat-search-dates` без реализации. Следующая сессия читает этот change, состояние ветки и issue, получает отдельное разрешение владельца и продолжает тот же PR по [tasks](/openspec/changes/preformat-search-dates/tasks.md).

После реализации HTML, индекс и клиент выходят одной обычной сборкой. Дополнительной миграции данных, внешнего API и production-приёмки нет. После проверок архивировать change и перевести тот же PR из draft в готовый к человеческому ревью; тогда использовать `Closes #875`. Для отката вернуть всё изменение вместе с обычной пересборкой, не смешивая новый клиент со старым индексом.
