# Tasks

Реализация начинается после отдельного разрешения владельца на подготовленные артефакты и отметки в issue со ссылкой на их коммит. Чекбоксы ниже относятся к реализации и её приёмке; подготовка этого плана их не завершает.

## 1. Ранние проверки выбранного подхода

- [ ] 1.1 Подготовить минимальный сквозной приёмочный пример карты с настоящим SDK на production-сборке и проверить штатную печать в Chrome и Safari: подложка, объекты, лейблы, атрибуция, подпись/ссылка, несколько вставок ниже экрана без прокрутки, ручной кадр, холодный кеш/замедленная сеть и выключенная печать фонов. Зафиксировать наблюдения; при необходимости существенной смены подхода вернуться к владельцу до основной интеграции.
- [ ] 1.2 До изменения поисковой разметки выбрать затронутые запросы и соседние формулировки, снять выдачу существующего UI по `site-search`: URL, порядок, snippets, highlights и переходы. Сохранить краткую исходную запись для сравнения с задачей 6.2; приёмочные материалы держать отдельно от публикуемого контента.

## 2. Общие геоданные и публичное представление

- [ ] 2.1 Реализовать общую raw Zod-схему, readonly domain types и mapper для `map-geodata`; проверить контрольные экспорты и производные примеры всех поддерживаемых геометрий, ID `0`/строковых ID, числовых строк оформления, сохранённых описаний, неизвестных свойств и неподдерживаемой геометрии. Отдельно проверить контекстные ошибки вместо молчаливого отбрасывания данных.
- [ ] 2.2 Перенести подготовку приблизительных контуров к общему преобразованию, сохранить независимость `precision` от оформления и явный пунктир. Проверить отдельные части MultiPolygon и сокращение вырезов при расширении; выполнить затронутые тесты полигональных helpers и потребителей участков без ослабления их валидации.
- [ ] 2.3 Подключить общий вход к sidecar-loader мест, заменить узкую доменную геометрию и адаптировать пруды с явным оформлением. Проверить `lib/places/tests/geometry.test.ts` и `load.test.ts`: привязку по slug, orphan-ошибку, отсутствие обязательной геометрии и сохранение основной точки/видимости места.
- [ ] 2.4 Обновить public DTO adapter и потребителя `/map/data/places.json` на подготовленный `geometry: FeatureCollection`; проверять выход отдельной публичной Zod-схемой. В `map-public.test.ts` подтвердить сохранение оформления/текстов, уже расширенные координаты, отсутствие `outline_expansion_meters`, неизменность остальных полей и исключение скрытых мест.

## 4. Markdown HTML и companions

Подтвердить, что GeoJSON не участвует в mentions/backlinks, а упоминания вокруг него продолжают работать.
- [ ] 4.2 Добавить минимальный нейтральный AST hook пакетного renderer-а и app-преобразование в безопасный контейнер со статической подписью. - [ ] 4.3 Подключить регистрацию custom element и стили через реальные шаблоны новостей/KB. Проверить собранный HTML и клиентскую загрузку: контейнер и подпись доступны до SDK, приложение создаёт карту из `set:html`, а одна регистрация элемента без его экземпляров не инициирует SDK.

## 5. Клиентская карта, поиск и печать

- [ ] 5.1 Реализовать eager custom element для Markdown через общий runtime и режим жестов места. DOM-тестами проверить несколько независимых карт с одной загрузкой SDK, disconnect/reconnect, уход до завершения async init, освобождение экземпляров/обработчиков, ошибку без retry, доступную подпись и ссылку.
- [ ] 5.2 Реализовать fit до ручного pan/zoom и сохранение center/zoom после него, включая печатный resize. Проверить, что программные обновления не устанавливают признак ручного кадра; сценарии resize/возврата со страницы и жестов подтвердить тестами и затем настоящим SDK в задаче 6.1.
- [ ] 5.3 Разметить название в подписи как штатную поисковую секцию, исключить SDK/GeoJSON и обеспечить переход к началу карты. Проверить на production-индексе несколько/одноимённые карты, совпадение в соседнем тексте, сохранение одного результата статьи и отсутствие слов из скрытых данных; сохранить прежние веса и алгоритм выбора `sub_results`.
- [ ] 5.4 Доработать print CSS по результату ранней проверки, сохранив сцену карты и подпись, выбранный кадр и обычную печать текста/изображений/событий. Проверить итоговую печатную страницу с картой и соседними блоками, включая разрывы страниц и выключенные фоны; полную системную приёмку выполнить в задаче 6.3.

## 6. Документация и сквозная приёмка

- [ ] 6.1 На production-сборке с настоящим API проверить контрольные схемы и пруды в трёх представлениях: геометрию/стили/лейблы, узкий экран, мышь/трекпад/сенсорные жесты, resize до/после ручного кадра, несколько карт, клиентскую навигацию, ошибку API и без JavaScript. Подтвердить клавиатурные действия и фокус, атрибуцию и независимое назначение штатной и редакционной ссылок; записать фактические результаты и сетевые запросы, при необходимости синхронно обновить CSP.
- [ ] 6.2 Повторить ручной поиск по набору 1.2 и случаям нескольких/одноимённых карт и соседнего текста; сравнить пользу, URL, snippets, highlights и фактическое положение карты после перехода. Проверить прямой и клиентский переход до готовности SDK; записать результат без требований фиксированных рангов.
- [ ] 6.3 Повторить итоговую системную печать по 1.1 и ADR-037: Chrome/Safari на компьютере, Safari на iPhone, Chrome на Android. Подтвердить полноту слоёв, подпись/ссылку, нетронутый и ручной кадры, несколько карт вне экрана, холодный кеш/замедление и выключенные фоны; перечислить фактически проверенные устройства, не подменяя их эмуляцией ширины.
- [ ] 6.4 Обновить ADR-028/039/037, редакционные инструкции мест и `map`, описание JSON и затронутые agent-facing/discovery-поверхности; при изменении пакетного API — README Markdown. Сверить документы с реализацией, удалить устаревшее обещание типизированного источника геометрии в ADR-028 и проверить ссылки/примеры; не представлять старые исследовательские экспорты как новые данные.
- [ ] 6.5 Выполнить `pnpm test`, `pnpm typecheck`, `pnpm build` и `pnpm --filter @shelkovo/www test:search-quality`; сверить результаты с требованиями и сценариями пяти delta specs и соседними контрактами видимости/публичной карточки/восстановления ошибок. Проверить общие preview-потребители событий и сравнения, если изменены их helpers или стили.
- [ ] 6.6 Выполнить `pnpm openspec:validate`, повторить отбор долгоживущих требований и отрецензировать весь актуальный diff, включая staged, unstaged и новые файлы. Подтвердить покрытие согласованных решений, отсутствие разовых миграционных условий в specs и исправить найденные ошибки/лишнюю сложность; зафиксировать фактические проверки и оставшуюся ручную приёмку для PR.

После выполнения задач — штатные sync/archive в этой ветке, повторный `pnpm openspec:validate` и человеческое ревью PR. Обязательной приёмки после выкладки нет; незавершённые обязательные браузерные проверки не считать выполненными по наличию артефактов или успешным unit-тестам.
