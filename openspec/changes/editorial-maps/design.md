# Design

- [Общий формат геоданных](https://github.com/silentroach/kpshelkovo/issues/813#issuecomment-5795973774): оформление, расширения и разрешённое несовместимое изменение JSON.
- [Контракт служебных блоков](https://github.com/silentroach/kpshelkovo/issues/814#issuecomment-5796854086): `map`, подпись, обычные строки, companions, действующие `change`/`[TOC]`.
- [Техническая интеграция и приёмка](https://github.com/silentroach/kpshelkovo/issues/817#issuecomment-5797328993): app-owned механизм, ранняя загрузка, печать и штатный выбор поисковой секции; заменяет прежнюю формулировку о лучшем совпадении только названия карты.

### Фактическая отправная точка

- `apps/www/src/lib/places/load.ts` связывает raw-файлы `.geojson` с местами по slug. `raw-geometry-schema.ts` допускает ровно один feature `area` с `kind: area`, `precision: approximate` и Polygon/MultiPolygon. `geometry.ts` расширяет контуры при сборке и формирует `PlaceGeometry.area`.
- `lib/places/map-public.ts` и `map-public-dto.ts` готовят `/map/data/places.json`; выборка фильтруется по `showOnMap`. Карточка места использует полный dataset. Основная точка, расписание, статус и маркер места существуют отдельно от области.
- `components/maps/map-preview.ts` умеет один основной маркер и область, откладывает загрузку до приближения к viewport и повторяет fit после resize. `map-preview.types.ts` связан с типами места. Это ещё не независимый renderer произвольной схемы.
- `lib/yandex-maps/runtime.ts` уже объединяет загрузку SDK и сохраняет его стили при клиентской навигации; `open-maps-control.ts` добавляет общую штатную кнопку. `lib/geometry` содержит нейтральную проверку полигонов и географические helpers, используемые также участками.
- `lib/markdown/render.ts` выполняет нормализацию body, упоминания, пакетный HTML-render, затем обработку `change` и файловых ссылок. `lib/news/load.ts` и `lib/kb/load.ts` знают источник при подготовке body. Генераторы `lib/news/markdown.ts` и `lib/kb/markdown.ts` используют AST, а не HTML.
- `packages/markdown/src/render.ts` обрабатывает документ целиком, строит TOC и ID заголовков, отбрасывает raw HTML. Текущий API принимает строковые preprocessors, но не app-owned AST-преобразования. `code.meta` не сохраняется как надёжный `data-meta` в итоговом HTML.
- `lib/search/client.ts` уже сортирует штатные `sub_results` по возвращённым оценкам; подпись-заголовок может использовать этот путь. `styles/print.css` сейчас принудительно задаёт прозрачный фон и тёмный цвет всем потомкам `main`, а также меняет размеры всех изображений: это нужно учитывать для сцены SDK.

## Goals / Non-Goals

**Goals:**

- Один проверяемый географический вход для двух источников и общая отрисовка объектов при разном управлении представлениями.
- Сохранение редакционного исходника для companions отдельно от подготовленных координат и оформления клиента.
- Встраивание в имеющиеся Markdown, навигацию, поиск и печать с короткими проверками конкретного поведения.

**Non-Goals:**

- Универсальный GIS-движок, универсальный renderer всех карт сайта, реестр плагинов и отдельный workspace-пакет.
- Перенос кластеров, слоёв участков и расписаний в редакционную карту; изменение полигональной валидации участков ради нового входа.
- Дополнительный Markdown-парсер в браузере, второй pipeline упоминаний, особое ранжирование карт или отдельный сервис печатных изображений.

## Decisions

### 1. Общий app-owned географический вход и явные границы данных

Разместить общий формат рядом с нейтральной геометрией в `apps/www/src/lib/geometry`: raw Zod-схема, явно написанные readonly domain types и mapper в отдельных модулях. Два адаптера отвечают только за извлечение code node либо чтение sidecar и контекст ошибки. Загрузка `.geojson` по slug и проверка orphan-файлов остаются в places.

Поддерживаемый набор свойств берётся из `map-geodata`; точная структура и диапазоны проверяются исполняемой схемой. Сохраняются ID `0`, строковые ID, корректные числовые строки оформления, известные `metadata` и строки объектов. `description` проверяется как строка, но его разметка не разбирается. Неизвестные содержательные поля и неподдерживаемая геометрия дают ошибку, а не молча отбрасываются. Номера и выбранные в Конструкторе иконки точек не входят в поддержку обычного маркера.

Внутренняя модель использует camelCase и явно различает геометрию, оформление и текст. Нейтральные проверки координат/колец переиспользуются без ослабления контракта полигонов. Существующее приближённое расширение контура переносится из places к общему преобразованию: отдельно для каждой части, с сокращением внутренних колец. Полный топологический buffer и автоматическое исправление геометрии не добавляются.

Raw-исходник Markdown остаётся внутри body; domain содержит подготовленную коллекцию для карты. Публичный adapter отдельно формирует `FeatureCollection` с исходными именами GeoJSON/экспортных свойств и нормализованными значениями. Это внешний формат, а не прямой dump camelCase-домена. Применённое `outline_expansion_meters` не попадает в подготовленную коллекцию; исходный блок companion его сохраняет.

Альтернатива с отдельными форматами для статей и мест отклонена: она заставляет поддерживать два разных толкования одного экспорта. Превращение схемы в `Place` добавило бы несуществующие сущности, ссылки и расписания.

### 2. Общая отрисовка объектов, отдельные представления

Рядом с `components/maps` выделить минимальные helpers преобразования поддерживаемой геометрии в SDK-объекты, применения оформления, создания обычных точек с текстовыми лейблами и вычисления bounds. Переиспользовать существующие географические helpers и `loadYandexMaps`; не переносить доменные возможности `PlaceMap` в общий renderer.

- Markdown-карта создаёт только собственную коллекцию и сразу показывает её целиком.
- Превью места добавляет коллекцию к основному маркеру, его внешней ссылке и opening-hours-состоянию; bounds учитывает все объекты. Resize сохраняет нынешний безусловный fit.
- Общая карта получает подготовленную коллекцию из JSON. Hover/focus/временная URL-подсветка управляют всей группой дополнительных объектов, включая точки и лейблы. Основные точки продолжают определять кластеры и начальный охват; их ссылки ведут в карточки.

Стили дополнительных объектов берутся из данных, включая явный `stroke-dasharray`, а не выводятся из `precision` или состояния hover. Состояние представления отвечает за видимость. Для прудов выбирается одно явное оформление; раздельные области и расширение сохраняются.

Шрифт и обычная форма точки используют существующие ресурсы сайта. Лейблы создаются текстовыми узлами, без `innerHTML`, попапов и автоматического раскладывания пересекающихся подписей. Видимые строки проходят общую типографику при подготовке отображения, не меняя сохранённый исходник. Новые шрифты и внешний UI-пакет ради лейблов не нужны.

### 3. Извлечение map из AST в едином Markdown pipeline

Добавить app-owned обработку `map` через `lib/markdown/render.ts` и его options. На подготовке body извлечь code nodes, прочитать `lang`, `meta`, тело и позицию, проверить URL/GeoJSON с контекстом материала и порядковым номером вставки. В диагностике использовать индекс объекта, ID и путь поля, когда они доступны; ID проверять на отсутствие, а не на truthiness.

До завершения общего mention-прохода GeoJSON остаётся защищённым содержимым `code`. Подпись строится затем из обычного текста и ссылки. Внешний URL проверяется как безопасный абсолютный веб-адрес; он не вычисляется из геометрии. Подготовленный body не получает generated-подписей, поэтому повторный вызов pipeline их не дублирует.

Для HTML нужен узкий нейтральный AST extension point пакетного renderer-а, использующий уже установленные unified/remark. Само знание о `map`, источниках, схемах и ошибках остаётся в приложении. Документ проходит один render целиком: обработка TOC, reference-ссылок и ID не делится на фрагменты вокруг карт. Входной HTML по-прежнему отбрасывается; доверенные контейнеры создаёт app-преобразование, а строки и сериализованные данные экранируются на границе HTML.

Выход — контейнер custom element, безопасно сериализованные подготовленные данные и статическая подпись/ссылка. Клиентская регистрация и стили подключаются реальным app bundle через шаблоны новостей и KB; тег, попавший в `set:html`, сам по себе не является Astro/Svelte-компонентом. Регистрация элемента сама по себе не инициирует SDK: загрузку начинает экземпляр карты.

Для companion добавить app-helper над AST существующего редакционного body: сохранить исходный code node с `meta` и значением, а следом построить подпись через `md.text`/`md.link`/`md.paragraph`. Не реконструировать экспорт из domain model, не разбирать generated-подпись как Markdown и не прогонять её повторно через mentions. Сериализатор может менять ограждение/форматирование Markdown, но не значения исходного JSON. KB сохраняет своё преобразование внутренних ссылок.

Обычные `change`, `diff`, неизвестные языки и `[TOC]` сохраняют действующее поведение, подтверждённое `lib/markdown/render.test.ts` и `packages/markdown/src/index.test.ts`. Новый extension point проверяется вместе с ними, а не заменяет их новым редакционным DSL.

### 4. Поисковая секция под картой и переход к её началу

Название внутри статической подписи размечается настоящим заголовком с ID, визуально оставаясь подписью под картой. Оно участвует в обычных `sub_results`; существующий поисковый клиент выбирает секцию по прежним правилам. Допускается выбор из-за следующего за подписью текста. `data-pagefind-anchor`, отдельные поисковые документы карт, дополнительные веса и caption-only алгоритм не применяются.

Клиентский контейнер, сериализованные данные, элементы SDK, лейблы и состояния загрузки исключаются через `data-pagefind-ignore`; подпись находится вне исключённой области. Обычный `pre/code` не считается автоматически исключённым из индекса.

ID карт выделяются с учётом всех ID страницы и повторных названий. Генерация не должна менять цели существующего TOC: generated-подпись не становится новым авторским разделом оглавления. Необходимые нейтральные hooks для ID остаются в Markdown-пакете, app-префикс и цели карт — в приложении. Порядковый ID допустим; постоянство якоря при перестановке содержания не обещается.

Переход к заголовку-подписи должен оставлять в поле зрения начало карты. Первый вариант — нативный `scroll-margin-block-start`, учитывающий зарезервированную высоту карты и sticky header; браузерная проверка охватывает первый вход, клиентский переход и resize. Если потребуется локальная коррекция прокрутки, она принадлежит контейнеру карты, не алгоритму ранжирования. Цель перехода существует до SDK и при его отказе.

### 5. Ранняя загрузка и ручной кадр

Markdown custom element начинает инициализацию при подключении, включая вставки ниже экрана. Он использует общий SDK, но отдельный экземпляр карты. Минимальная общая логика жизненного цикла и жестов переиспользуется из preview; Markdown не подключает его расписание, основной маркер или обязательные координаты места.

При disconnect уничтожаются экземпляр, наблюдатели и обработчики; асинхронные шаги сверяют актуальность подключения. Возвращение через клиентскую навигацию создаёт новый экземпляр. Дополнительный пул экземпляров, очередь загрузок и выгрузка при уходе за экран не нужны.

Разрешение жестов остаётся у SDK по существующему режиму карты места. Отличается политика кадра: до пользовательского pan/zoom resize делает fit, после — сохраняет текущие center/zoom. Признак ручного кадра ставится по пользовательскому действию карты, а не по любому событию обновления: программный fit, загрузка и resize не включают его. Ошибка оставляет статическую подпись и сообщение, без локального retry UI.

### 6. Печать существующей сцены SDK: ранний пробник и реализация CSS

Печать следует ADR-037: существующий DOM и CSS, без отдельного сервиса, файла или редакционного представления карты. Все карты загружаются заранее; `beforeprint` не используется для асинхронной загрузки, которую браузер не обязан ждать.

Ранний пробник с настоящим SDK на production-сборке и отдельный CDP-пробник задокументированы в [наблюдениях по печати](../../../docs/research/editorial-maps/print-acceptance.md); отметка о незавершённой 1.1 в этом протоколе относится к прежней задаче обязательной системной приёмки. Chrome PDF показал подложку, объекты, лейблы, текст атрибуции и подписи трёх карт ниже экрана; ручной кадр сохранился. Отдельный пробник на замедленной сети с `printBackground:false` воспроизвёл потерю логотипа из-за общего сброса фонов в `print.css` и проверил узкий CSS-кандидат, возвращающий логотип. Эти опыты не подтверждают системную печать, Safari, готовность сцены в момент вызова печати до загрузки и будущую политику кадра при print resize. Eager-инициализация сама по себе подтверждает только начало загрузки.

Уточнить `print.css` так, чтобы общие правила очистки страницы не обесцвечивали/не скрывали сцену SDK и не меняли произвольно размеры его изображений. Рамка карты получает печатный размер, подпись остаётся с ней; прежние правила текста, иллюстраций и скрытия фоновой карты события сохраняют назначение. Печатное изменение размеров подчиняется политике кадра Markdown: fit до ручного изменения, center/zoom после.

Обнаруженная при реализации существенная невозможность сохранить поведение печати возвращается владельцу как развилка подхода; это не даёт разрешения скрыть карту, подменить её ссылкой или автоматически добавить Static API. По [согласованной границе этого change](https://github.com/silentroach/kpshelkovo/issues/819#issuecomment-5798818614) браузерная и системная проверка печати, включая Chrome/Safari на компьютере и физические iPhone/Android, не являются условиями готовности PR. В PR отделить подтверждённые факты раннего исследования и проверок реализации от сценариев печати, которые остались непроверенными; выполнение требований печати не объявлять подтверждённым системной приёмкой.

### 7. Приёмка и документация

Контрольные данные — неизменённые `docs/research/editorial-maps/yandex-detour.geojson`, `yandex-polygons.geojson` и адаптированные геоданные прудов. Производные fixtures явно отделяются от реальных экспортов: строковый ID, пунктир, произвольные скрытые строки, конфликтующие заголовки, несколько карт и ошибочные данные.

Автоматические проверки покрывают границы данных, сохранение исходника, безопасный HTML, особенности AST, подготовленный public DTO, видимость объектов и жизненный цикл. Они не подменяют настоящий SDK, жесты и системную печать. Для полигональных helpers учитываются потребители участков; для общего preview — события и шапки сравнения.

До изменения индексирования снять ручную выдачу по затронутым и соседним запросам через существующий UI согласно `site-search`. Затем сравнить на production-индексе названия/несколько карт/одноимённые подписи/совпадения соседнего текста, контекст, highlights и переходы. Проверять пользу и отсутствие потерь обычных результатов, без фиксированных рангов. Публикация настоящей новости об объезде для проверки не нужна: можно использовать локальный приёмочный материал, не попадающий в выпуск.

Обновить ADR-028/039/037 в соответствующих разделах, описание формата мест, `apps/www/src/data/places/AGENTS.md`, публичный путеводитель `apps/www/public/.well-known/agent-skills/site-sections/SKILL.md` и связанные Markdown/discovery-поверхности. ADR-028 ошибочно называет типизированный источник геометрии: его нет в текущей схеме, поэтому убрать расхождение, не добавляя фиктивное поле. Разобрать также устаревшее утверждение об отсутствии публичного JSON и ограничении геометрии одним `area`. Пакетный README меняется только по фактическому нейтральному AST API.

Новые внешние origins не планируются. Приёмка проверяет реальные запросы SDK; если они требуют правки CSP, она выполняется синхронно с конфигами и документацией по проектным правилам. Отдельный новый ADR для повторения уже принятых границ не нужен.

## Risks / Trade-offs

- Системная печать сцены SDK не подтверждена → применить выводы раннего пробника при доработке CSS, перечислить непроверенные сценарии в PR; обнаруженную при реализации существенную развилку вернуть владельцу.
- Ранняя загрузка всех вставок увеличивает работу при открытии статьи → принятый компромисс ради печати без прокрутки; общий SDK загружается один раз.
- Заголовок подписи образует обычную поисковую секцию, включающую последующий текст → это согласованный результат; ручная проверка выявляет регрессии, но не вводит специальную релевантность.
- Новый AST hook затрагивает TOC, ID и mentions → рендер целого документа, сохранение code node и короткие смешанные примеры; никаких независимых фрагментов и повторного mention-прохода подписи.
- Полигональный helper используется участками → общий формат расширяется вокруг существующей полигональной схемы, а её контракт проверяется регрессиями потребителей.
- Публичный JSON меняется несовместимо → producer, consumer и описание публикуются одним артефактом; временного двойного формата нет.
- Лейблы могут пересекаться → редактор проверяет фактический вид; автоматическое скрытие и раскладывание не входят в объём.

## Migration Plan

1. После отдельного разрешения владельца сохранить ссылку на коммит согласованных артефактов в связанном issue; использовать завершённые раннее исследование печати и исходную выдачу поиска при реализации.
2. Подключить общий формат и отрисовку. Перевести пруды: убрать `kind: area`, сохранить MultiPolygon, `precision` и расширение, задать оформление и пунктир явно.
3. Заменить доменную узкую `PlaceGeometry.area` и public `geometry.area`; синхронно адаптировать общую карту, превью, сериализацию, документацию и точечные тесты. Остальные поля публичного JSON не переименовывать попутно.
4. Подключить Markdown HTML/companions, клиентские assets, поиск и печать; пройти задачи и три части приёмки в согласованных границах без обязательной браузерной/системной проверки печати. Требования `place-map-visibility`, `place-markdown-card` и `client-load-recovery` проверяются как соседние контракты без delta.
5. Повторить отбор долгоживущих требований, синхронизировать specs и архивировать change в той же ветке, выполнить `pnpm openspec:validate`, довести draft PR до человеческого ревью. Production-приёмка после выкладки не является условием завершения.

Откат возвращает код, исходник прудов, producer/consumer JSON и документы одним изменением, затем пересобирает статический сайт. Серверного состояния и миграции базы нет. Если после выпуска уже появились редакционные блоки `map`, перед откатом нужно учесть эти материалы: старый renderer не покажет их интерактивно.
