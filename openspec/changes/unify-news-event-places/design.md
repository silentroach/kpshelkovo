## Context

Мотивация и границы — в [proposal.md](proposal.md), задача — [#749](https://github.com/silentroach/kpshelkovo/issues/749).

- В `src/lib/places/raw-schema.ts` обязательны название, категория, статус, summary и координаты. Помимо мировых диапазонов координаты проверяются на `PLACE_MAP_BOUNDS`. Все 13 мест сейчас попадают в карту.
- `src/lib/news/raw-schema.ts` допускает независимые `location` и `coordinates`; `load.ts` переносит их в событие. В трёх статьях есть пять таких событий.
- Общая карта имеет несколько представлений: `map-public.ts`, `/map/` с количеством, fallback-ссылкой и JSON-LD ItemList, Markdown-список. Фильтрации только маркеров недостаточно.
- Карточки мест и Markdown backlinks публикуются отдельно. HTML-backlinks сейчас выключены. `news/mentions.ts` берёт связи из упоминаний статьи.
- `news/public-dto.ts`, `public-schema.ts`, `calendar.ts`, `seo.ts` и `view.ts` потребляют inline-место. Markdown статьи сейчас не выводит структурированные события, RSS публикует краткие сведения о новости.

Действующие решения:

- [ADR-028](../../../docs/decisions/028-markdown-first-places-map.md): Markdown-first places, карточки `/map/<slug>/`, координаты и поведение `?h=`. При реализации нужно уточнить независимость места от карты и сценарии начального viewport.
- [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md): границы raw, domain и public DTO.
- [ADR-012](../../../docs/decisions/012-entity-mention-graph.md): реестр сущностей и граф source refs. Структурная ссылка события добавляет источник связи, но не расширяет Markdown-синтаксис на произвольный frontmatter.
- [ADR-011](../../../docs/decisions/011-public-surface-registry.md) и [ADR-025](../../../docs/decisions/025-static-full-text-search-with-pagefind.md): публикация карточки и поиск не зависят от видимости маркера.

## Goals / Non-Goals

**Goals:**

- Разрешать ссылку события один раз при построении domain dataset и передавать готовые данные существующим потребителям.
- Разделить полный справочник мест и выборку общей карты, сохранив текущие маршруты и публичные форматы.
- Выполнить миграцию данных одновременно с изменением схем, без переходного двойного формата.

**Non-Goals:**

- Универсальный entity API, новая коллекция локаций или отдельный каталог скрытых мест.
- Версионирование места, геокодинг, автоматическое объединение точек, модель маршрутов или нескольких мест одного события.
- Новые фильтры, режимы кластеризации и интерфейс редактирования карты.

## Decisions

### 1. Явное включение в общую карту

В raw-схему места добавить `show_on_map?: boolean`, в domain model — `showOnMap: boolean`, нормализованный через сравнение с `true`. Полный dataset и `bySlug` сохраняют все места. Выборку видимых мест переиспользовать во всех представлениях общей карты; не фильтровать общий loader.

Фильтрация охватывает JSON `/map/data/places.json`, маркеры и контуры, расчёт viewport и кластеров, количество, fallback-ссылку, ItemList и `/map/index.md`. Карточки, sitemap, поисковая индексация и реестр упоминаний получают полный dataset. Не добавлять скрытым местам `noindex`.

Карточка скрытого места не предлагает «Показать на общей карте». `?h=` ищет только среди опубликованной выборки; скрытый slug идёт по существующему пути неизвестного slug: параметр удаляется без смены viewport, остальные query, hash и history state сохраняются.

Альтернатива — включать место по умолчанию — отклонена владельцем: новое место события не должно случайно появляться на общей карте.

### 2. Координаты без локального географического запрета

Убрать refine по границам посёлка, сохранив обязательные числовые координаты и диапазоны широты `[-90, 90]`, долготы `[-180, 180]`. Проверить все использования константы границ: она может оставаться fallback viewport для пустой карты, но не ограничителем данных или видимых точек.

Viewport строится по видимым местам. Единственную видимую точку нужно показывать и за пределами посёлка; пустая выборка использует существующий локальный fallback. Совпадающие координаты не участвуют в проверке уникальности сущностей: идентификатором остаётся slug.

Ограничение только для `show_on_map: true` тоже отклонено владельцем. Сам факт нахождения далеко от посёлка не запрещает показать место на карте.

### 3. Структурная ссылка события

Редакционный формат:

```yaml
events:
  - title: Встреча жителей
    starts_at: 06.06.2026 12:00
    place: green-dreams
    location_details: в беседке
```

- `place` — необязательный канонический slug сущности `places`, без `@`.
- `location_details` — необязательный непустой plain text, допустимый только вместе с `place`. Он уточняет место, а не переопределяет название, адрес или координаты.
- Старые `location` и `coordinates` в исходнике события должны давать явную ошибку валидации, а не молча отбрасываться схемой.
- Неизвестный place останавливает сборку с указанием статьи и события. Без `place` событие остаётся без места во всех выходных форматах.

Для разрешения использовать полный `bySlug` из базового `loadPlacesData`, не dataset с backlinks: news участвует в построении графа, поэтому graph-enriched загрузка здесь замкнула бы цикл. Domain event хранит ссылку на разрешённое место и уточнение; DTO и UI получают производные поля из этой ссылки. Не создавать независимый справочник координат или второй loader places.

Альтернатива — поддерживать inline и ссылочный формат параллельно — оставляет дублирование и потому отклонена. Исторических снимков нет: следующая сборка применяет исправления места ко всем связанным событиям. Физический переезд объекта оформляется другой локацией, если старые события должны оставаться привязаны к прежней.

### 4. Публичные представления

- `NewsEventCard.astro`: название места — внутренняя ссылка на карточку; уточнение — рядом. Внешняя ссылка использует map URL сущности, iframe — её координаты. Видимость на общей карте не влияет на эти элементы.
- Публичный JSON сохраняет `location: string`, `coordinates`, `map_url`, `ics_url`. `location` содержит каноническое название; адрес не подмешивается в название. Добавить optional `place_id`, `place_url`, `location_details`; `place_url` — абсолютный canonical URL карточки. При отсутствии места географические поля отсутствуют, а `ics_url` сохраняется. Обновить Zod public schema и документацию формата одновременно.
- `.ics`: прежние URL и UID, каноническое название и доступный адрес в `LOCATION`, координаты места в `GEO` и `X-APPLE-STRUCTURED-LOCATION`; уточнение добавляется в `DESCRIPTION` с сохранением существующего описания и ссылки на новость.
- Event JSON-LD: вложенный `Place` получает каноническое название, URL карточки, координаты и адрес при наличии. Название не используется как выдуманный адрес.
- Не добавлять новый блок событий в Markdown статьи или RSS. Проверить связанные discovery-документы и примеры публичного формата; Markdown карточки места сохраняет связи через существующий граф.

Совместимость означает сохранение формы прежних JSON-полей и идентичности календарных событий, а не буквальное сохранение старого текста `location`: значения теперь канонические. Добавочные поля дают потребителю явную связь с сущностью без смены типа строки на объект.

### 5. Связи через существующий граф

News-адаптер объединяет упоминания из редакционного Markdown и ссылки `events[].place` в refs статьи. Одна статья даёт одну обратную ссылку на одно место, даже если оно встречается в нескольких событиях и в body. Общий граф не получает зависимости от news или places datasets.

Не включать отдельный HTML-блок backlinks в рамках этой задачи; существующие потребители refs, включая Markdown карточки, получают новую связь автоматически.

### 6. Миграция пяти событий

Технические slug новых мест фиксируются здесь, чтобы данные и проверки использовали один список:

- `apple-garden.md`: существующий `apple-garden`; уточнение «возле спортивной площадки». Каноническая точка сада `55.063710, 37.724333` заменяет прежнюю точку события `55.063808, 37.725320` по решению владельца.
- `ok-meeting-june.md`: новый `green-dreams`, ресторан Green Dreams, категория `food`, точка `55.074958, 37.755599`; уточнение «в беседке».
- `victory-day-greenwood.md`, шествие: новый `greenwood-2-kpp`, КПП Гринвуд 2, категория `entrance`, та же точка `55.074958, 37.755599`; место обозначает старт, а не весь маршрут. Ресторан и КПП находятся в одном здании, но остаются разными сущностями.
- `victory-day-greenwood.md`, мероприятие у сада: новый `greenwood-orchard`, фруктовый сад в Гринвуде, категория `nature`, точка `55.077635, 37.755967`; уточнение «у фруктового сада». Это не яблоневый сад в Вилладже.
- `victory-day-greenwood.md`, возложение цветов: новый `shelkovo-memorial`, памятник в деревне Шелково, категория `infrastructure`, точка `55.065050, 37.720861`, адрес — улица Центральная, 46–48.

У новых мест статус `existing`, минимальные фактические summary из источников и отсутствующий `show_on_map`. Перед добавлением проверить отсутствие коллизий slug с людьми и местами. Не придумывать контакты, часы работы или дополнительные сведения. У 13 прежних мест явно поставить `show_on_map: true`; их slug и координаты не менять.

## Risks / Trade-offs

- Скрытие места ошибочно затронет публикацию карточки → фильтровать только поверхности общей карты; проверить карточку, поиск, sitemap и mention registry отдельно.
- Снятие границ оставит единственную удалённую точку вне viewport → проверить пустую, одиночную и множественную выборки, включая точку за прежними границами.
- Место исправится задним числом в старом календаре → это согласованная живая ссылка; сохранить UID и явно проверить обновление данных без смены идентичности события.
- Загрузка backlinks из news создаст цикл → разрешать места через базовый dataset и строить refs в адаптере источника.
- Схема молча проглотит старые поля → отдельная отрицательная проверка редакционного формата.
- Координаты ресторана совпадают с КПП → не дедуплицировать по координатам. Новая модель кластеров для совпадающих точек не нужна для миграции: оба места скрыты.

## Migration Plan

1. После отдельного разрешения реализации изменить схемы, domain mapping, потребителей и редакционные данные атомарно в одной ветке. Синхронизировать ADR-028 и уточнить в ADR-012 структурный источник refs; отдельный новый архитектурный механизм не вводится.
2. Обновить проектные редакционные инструкции событий и примеры формата с учётом установленного способа владения skills; не править сгенерированные upstream-файлы вручную.
3. Выполнить focused regression checks, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm openspec:validate`; проверить браузером карту, скрытое место и событие. Зафиксировать результаты и ревью всего diff.
4. Обязательная production-приёмка не требуется: контракт проверяется на сборке и локальном результате. Человеческое ревью и merge выполняет владелец.
5. После выполнения задач синхронизировать основные specs и архивировать change в ветке реализации. Планировочный PR использует `Refs #749`; закрытие issue возможно только PR с выполненной реализацией.
6. Откат реализации возвращает код и мигрированные данные вместе. Новых внешних хранилищ, объектов или необратимой миграции нет.
