# Design

## Context

Задача и согласованный объём описаны в [proposal](/openspec/changes/show-place-related-materials/proposal.md). Владелец согласовал план и разрешил реализацию в этой сессии 5 ноября 2026 года: «давай делать. пользуй субагентов».

Исследованное состояние:

- [Страница места](/apps/www/src/pages/map/[slug]/index.astro) уже получает `loadPlaceWithBacklinks`, но скрывает старую разметку через `showBacklinks = false`. Старый блок расположен перед картой в мобильном порядке и содержит выдержки, которые теперь не нужны в HTML.
- [Composition root графа](/apps/www/src/lib/site-mention-graph.ts) подключает новости, события, статус, отзывы, места, людей и контакты. KB отсутствует. Статусы без подробной страницы отсекаются до адаптера.
- [KB loader](/apps/www/src/lib/kb/load.ts) уже сохраняет подготовленный body и найденные mentions. Даты публикации KB нет. В просмотренном корпусе упоминаний мест через `@slug` пока нет, хотя имеются обычные ссылки на карту.
- [Status mapper](/apps/www/src/lib/status/mapper.ts) рассчитывает фазу при загрузке и создаёт подробную страницу только при непустом body. `sortLastChangeAt` может равняться будущему концу работ, поэтому не подходит как дата публикации в смешанной хронологии.
- [Markdown места](/apps/www/src/lib/places/markdown.ts) уже выводит полный граф с группами и выдержками. [Публичный адаптер людей](/apps/www/src/lib/people/public-dto.ts) явно перечисляет группы, но общие константы sections и доменные aliases требуют проверки при добавлении KB.

Действующие решения:

- [ADR-012](/docs/decisions/012-entity-mention-graph.md): источники готовят refs, общий граф не импортирует datasets; отдельные доменные представления используют один граф.
- [ADR-013](/docs/decisions/013-raw-domain-public-data-boundary.md): raw schema, домен и public DTO имеют отдельные границы.
- [ADR-034](/docs/decisions/034-native-css-architecture.md): app-owned tokens и scoped CSS страницы.
- [ADR-008](/docs/decisions/008-markdown-ast-generation.md): публичный Markdown собирается через AST.
- [status-lifecycle](/openspec/specs/status-lifecycle/spec.md): общий расчёт фаз и ежедневная публикация; [date-labels](/openspec/specs/date-labels/spec.md): формат дат.

## Goals / Non-Goals

**Goals:**

- Переиспользовать существующие нормализацию mentions, загрузчики, дедупликацию и календарные маршруты.
- Отделить полный набор связей от выборки для HTML, чтобы лимиты и случайный выбор не меняли граф и Markdown.
- Передавать признак затронутости из записи статуса, сохраняя обычные текстовые упоминания как навигационные связи.

**Non-Goals:**

- Новый универсальный графовый API, собственный поисковый алгоритм или вывод связей из координат и свободного текста.
- Поля `related_places` в KB, новое `summary` для статуса, автоматические пересказы и извлечение фрагмента вокруг упоминания.
- Клиентский пересчёт фаз, кнопки раскрытия списков, новый публичный формат людей или статуса.
- Пересмотр общего жизненного цикла плановых работ: истечение окна продолжает означать фазу `resolved`, а уточнение подписи относится к карточке места.

## Decisions

### 1. Явная связь принадлежит записи статуса

Добавить опциональный список `affected_places` в raw schema статуса и readonly `affectedPlaces` в его домен. Разрешать цели через identity-реестр с проверкой типа `place`; не загружать полные карточки мест из status loader, чтобы не создать цикл. Отсутствие поля означает пустой список. Корректность списка и повторов проверяет Zod, неизвестные цели отклоняются с контекстом записи.

Адаптер статуса объединяет цели из `affectedPlaces` и `mentions`. Дедупликация остаётся по материалу и цели. Признак затронутости определяется по доменной записи статуса при построении представления места; общему графу не требуется понимать фазы и последствия работ.

Поднимать любое упоминание наверх отклонено на реальном примере: в сообщении об ограничении КПП Ривера КПП Фореста и Вилладжа названы как альтернативные въезды. Явная привязка исключает такое смешение ролей.

### 2. Короткий статус получает адрес существующего календаря

Снять общее отсечение `hasPage` в composition root и передать выбор публичного назначения адаптеру статуса. Для записи с подробной страницей сохранить её URL. Для явно связанных мест записи без страницы использовать `statusCalendarDayUrl` с московской датой начала; Markdown-ссылку направить на companion этого календарного месяца.

Markdown календаря не обещает ISO-якорь дня: не переносить туда HTML-fragment автоматически. Период и состояние рядом со ссылкой сохраняют контекст. Несколько записей одного дня остаются разными источниками, даже если адрес календаря совпадает.

Создание пустых подробных страниц отклонено: действующая модель намеренно оставляет короткие записи в журнале. Для статуса с body ссылки на людей продолжают работать как до изменения.

### 3. KB подключается адаптером источника

Новый адаптер в `/apps/www/src/lib/kb/` получает готовые `KbPage`, выбирает mentions типа `place` и формирует refs с заголовком, URL страницы и её companion. Источник получает отдельный section KB; ключ материала определяется устойчивым маршрутом страницы. Датой файловой системы или Git история KB не дополняется.

Внутренний `sources`, обычные ссылки `/map/...` и `?h=...`, GeoJSON и похожие слова не становятся refs автоматически. Упоминания людей продолжают раскрываться в KB, но новые backlinks людям не публикуются: это задача про места.

При расширении общего enum проверить aliases и `PERSON_MENTION_SECTIONS`. Публичные группы, счётчики и schema людей должны остаться согласованными с их опубликованным контрактом; пустой ключ `kb` не должен попасть в people JSON из-за расширения общего типа. Поле `affected_places` также не сериализуется в status JSON автоматически.

### 4. HTML использует отдельное представление полного графа

Сохранить полные `PlaceBacklinks`. В app-owned представлении места соединить status refs по `sourceId` с уже загруженным `StatusDataset.byId` и подготовить три независимых списка:

- Приоритетные записи: явно затронутое место и фаза `active` или `scheduled`. Сначала активные аварии, затем активные плановые работы, затем будущие по началу. Внутри текущих групп новые начала идут первыми; равенства разрешаются русским заголовком и ID.
- KB: случайная выборка без повторений размером `min(3, N)` из уникальных KB refs. Выбор производится при формировании HTML, на копии списка. Для чтения выбранные ссылки можно расположить по русскому заголовку. Полный граф не перемешивается и не усекается.
- «Материалы по теме»: новости и все остальные status refs, включая косвенные упоминания. Исключить ID приоритетных записей до ограничения длины. Сортировать по публикации новости или началу статуса, затем по русскому заголовку, разделу и ID; взять три.

Последнее правило является техническим уточнением слова «последние»: дата начала статуса совпадает с видимым началом его периода. Будущий конец работ не поднимает источник как будто это свежая публикация. Общая сортировка полного графа и остальных доменов сохраняется.

Случайная подборка выбрана владельцем вместо предложенного алфавитного отбора. Новая сборка может повторить прежнюю тройку; принудительная ротация и история выборов не нужны. Повторные просмотры готового HTML получают один сохранённый набор, клиентского shuffle нет.

### 5. Состояние и краткие подписи принадлежат представлению места

Использовать фазу из общего status dataset. Не добавлять в браузер окна, таймеры и обработчики возвращения к вкладке для этих блоков. Снимок сообщения одинаков с JavaScript и без него; существующая динамика расписания самого места остаётся отдельным механизмом.

Текущие аварии получают danger-оформление, текущие плановые работы warning-оформление. Будущие имеют явную подпись «Запланировано» или «Ожидается» и видимый период; оформление не должно обозначать уже наступившую аварию. Все состояния названы текстом.

Текущие `maintenance` получают понятную подпись «Плановые работы». В нижней подборке у работ остаются вид и даты, без дополнительной подписи о завершении. В Markdown сохраняются вид и период работ, а состояние добавляется только инцидентам. Общие фазы и подписи журнала не меняются. Владелец отклонил формулировки о «заявленном периоде» как лишние и непонятные в этом интерфейсе.

Плашка содержит только состояние, заголовок-ссылку и период. Нижняя история содержит заголовок, раздел новости либо вид записи статуса, дату новости или период; состояние добавляется только инцидентам. KB содержит названия-ссылки. Новое редакционное `summary` и выдержки в HTML не нужны.

### 6. Композиция использует существующий редакционный дизайн

Построить один DOM-поток: название и действия; приоритетные сообщения; расписание и описание; карта с адресом; соседние места; KB; история. На широком экране CSS Grid образует два ряда. Сверху собственные сведения места слева и карта справа на уровне breadcrumbs. Снизу KB и история слева, соседние места справа, с общей верхней позицией после более высокой колонки основного ряда. При длинном body соседние места также начинаются после описания; этот компромисс согласован владельцем. На телефоне сохраняется прежний DOM-порядок. Длины текстов не измеряются, JavaScript и дублирующее содержимое для выравнивания не нужны.

Названия разделов: «База знаний», «Материалы по теме». Пустые блоки вместе с заголовком, отступом и разделителем отсутствуют. Лимиты означают короткую подборку без «Ещё» и пагинации. Существующие действия места и список «Рядом» сохраняют свою роль.

Плашки остаются плоскими, с мягким фоном и смысловым акцентом. Основное описание сохраняет `ui-copy` / `ui-prose` 17 px. После приоритетных плашек до описания суммарный отступ 40 px. На широком экране нижняя навигация получает согласованные интервалы и выравнивание заголовков между колонками; на узком KB и история отделены от географического блока тонкой границей и увеличенным отступом. Вспомогательные заголовки используют приглушённый `ui-section-label`, ссылки подборок Fira Sans 400, 16 px с узнаваемым спокойным подчёркиванием; ссылка плашки Fira Sans 600, 16 px. Это навигационные дополнения к описанию, а не самостоятельная новостная лента. Использовать существующие semantic colors и Font Budget, без новых шрифтов и анимации. Названия типографировать через `formatTextHtml`, периоды форматировать существующими helpers. Ссылки сохраняют штатное открытие в новой вкладке и видимый фокус, текст переносится целиком.

Основание: [дизайн-гайд](/docs/design/design-code-shelkovo.md), понятия [близости](https://ilyabirman.ru/reference/#proximity), [информативности](https://ilyabirman.ru/reference/#informativeness) и [ссылки](https://ilyabirman.ru/reference/#link) у Бирмана, [длина строки](https://practicaltypography.com/line-length.html) и [устойчивость при изменении текстовых интервалов](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html). Согласованные размеры, состояния и интервалы записать в существующий дизайн-гайд вместе с UI.

### 7. Markdown остаётся полной выдачей

Генератор использует исходные полные backlinks, сохраняет группы, даты, виды и имеющиеся выдержки, добавляет KB и явные status-связи. Для статуса доступен период и состояние из его домена. У человека, события, отзыва, контакта и другого места связь сохраняется даже при отсутствии этого раздела в HTML карточки.

Сохраняются frontmatter, авторский body, heading «Где упоминается» и явное пустое состояние Markdown. Это согласованное отличие от HTML, в котором пустые блоки отсутствуют. В публичном Markdown применяется существующий AST API; случайная подборка на генерацию Markdown не влияет.

## Risks / Trade-offs

- Состояние устаревает между сборками: владелец выбрал статический снимок. Ежедневная публикация остаётся штатным способом обновления; браузер не уточняет эти плашки.
- Случайный KB меняет HTML даже при неизменном корпусе: это выбранное поведение. Полный Markdown остаётся устойчивым; проверки отбора используют управляемый источник случайности и проверяют состав, уникальность и лимит.
- Изменение общей модели backlinks затрагивает people types и счётчики: сохранить самостоятельную публичную проекцию людей и проверить её существующие контрактные тесты.
- Много явно связанных работ удлиняют верх страницы: лимит к ним намеренно не применяется; проверка мобильной композиции включает несколько одновременных записей.
- Отсутствующие или чрезмерные редакционные связи снижают полезность: начальное наполнение опирается на конкретный смысл источников; альтернативные въезды и общие инструкции автоматически к месту не привязываются.

## Migration Plan

1. Добавить модель `affected_places`, source adapters, представление места и тесты на обобщённых данных, сохранив загрузку существующего корпуса.
2. В `/apps/www/src/data/status/incidents/2026/09/dam-river-reconstruction.md` явно связать КПП Ривера. Проверить другие уже упоминающие места записи статуса и добавить только подтверждённую затронутость; ссылки на объезд остаются обычными mentions.
3. Для начального KB использовать естественные упоминания существующих объектов в `/apps/www/src/data/kb/infrastructure.md`: перевести подходящие авторские подписи в общий mention-синтаксис, сверяя объект и сохраняя цитаты и источники. Не добавлять перечни мест в общие памятки ради backlinks. Исходные ссылки с фокусом карты не заменять механически: для каждой выбранной строки проверить, уместен ли переход на карточку места.
4. Подключить HTML и полную Markdown-выдачу, синхронно обновить дизайн-гайд и локальные инструкции. Поисковая оболочка сохраняет исключение новых связанных блоков из Pagefind; если придётся менять её контракт, применить отдельные правила `site-search`.
5. Пройти адресные тесты, typecheck, сборку, редакторскую и браузерную приёмку, независимое ревью diff. Среду браузера подготовить по `/docs/development.md`; запуск `pnpm dev` требует отдельного разрешения владельца. Анализ клиентских бандлов нужен только при фактическом изменении клиентских импортов или сборки.
6. После разрешённой реализации и приёмки синхронизировать и архивировать change в той же ветке, затем открыть PR с `Closes #187`. При публикации обновить issue ссылкой на артефакты и отметить уточнения относительно его первоначального текста.

Откат возвращает реализацию вместе с новыми полями данных, редакционными связями и документацией одним изменением. Существующий граф и полный Markdown остаются исходной точкой восстановления.
