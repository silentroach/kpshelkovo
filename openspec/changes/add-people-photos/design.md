# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md), контракт — в [people-photos](specs/people-photos/spec.md). Связанная задача: [#800](https://github.com/silentroach/kpshelkovo/issues/800).

Профиль проходит через `src/lib/people/raw-schema.ts`, явные типы `types.ts` и `mapper.ts`, затем используется HTML-страницей и отдельными публичными адаптерами. Сейчас фотографий в этой цепочке нет. HTML-каталога `/people/` нет: опубликованы отдельные страницы, Markdown-обзор и JSON-лента.

Страница `src/pages/people/[slug]/index.astro` показывает имя, должность, контакты и body в текстовой колонке. Карточка места использует правую колонку для карты, но её размер и порядок блоков на телефоне предназначены для географического контекста, а не для портрета.

Публичная JSON Schema людей запрещает неизвестные поля, а OpenAPI строится из неё. Добавить поле только во frontmatter или домен недостаточно. Структурированные данные `Person` собираются отдельно в `seo.ts`; передача портрета в социальные metadata через `BaseLayout` означала бы ещё и изменение превью ссылок.

Действующие решения:

- [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md) — разделение raw, домена и публичных DTO.
- [ADR-008](../../../docs/decisions/008-markdown-ast-generation.md) и [ADR-011](../../../docs/decisions/011-public-surface-registry.md) — генерация Markdown через AST и согласованность публичных представлений.
- [ADR-034](../../../docs/decisions/034-native-css-architecture.md) — локальные стили страницы и существующие app-owned tokens.
- [ADR-021](../../../docs/decisions/021-public-section-files-in-s3.md) — публичные media URL, раздел-владелец и недатированные изменяемые ключи по явному решению владельца. Портреты и их замену описывает [ADR-040](../../../docs/decisions/040-people-portraits-in-public-s3.md).
- [ADR-023](../../../docs/decisions/023-news-images-in-public-s3.md) — существующий способ подготовки качественной JPEG-копии, который используем и для портретов.

## Goals / Non-Goals

**Goals:**

- Добавить фотографию в существующую цепочку данных без отдельного загрузчика или реестра изображений.
- Показывать небольшой портрет целиком и сохранять доступ к сведениям независимо от загрузки изображения.
- Хранить источник одной структурой и переносить его в HTML, Markdown и JSON без ручного дублирования подписи в body.
- Доставлять портрет непосредственно с нашего media-origin, не связывая просмотр профиля с доступностью сайта компании.

**Non-Goals:**

- Общий медиакомпонент, клиентское состояние, lightbox, автоматическое кадрирование или обновление фотографий по расписанию.
- Обогащение графа упоминаний изображениями и рефакторинг существующих legacy-полей публичного JSON.
- Хранение бинарных изображений в Git или добавление отдельной сборочной обработки портретов.

## Decisions

### 1. Необязательный объект `photo` во frontmatter

Структура данных:

```yaml
photo:
  src: https://media.kpshelkovo.online/people/kschemelinin.jpeg
  width: 450
  height: 600
  source:
    label: ОК Комфорт
    url: https://ok-komfort.ru/company/
```

Это пример структуры, а не подтверждение публикации объекта. Имя файла совпадает со slug профиля.

- `photo` необязателен; если указан, содержит `src` и фактические размеры опубликованного файла. Размеры нужны для резервирования места без сетевого запроса при сборке.
- `source` необязателен; при наличии содержит оба поля `label` и `url`. Для шести фотографий этой задачи он заполняется одинаково. Организация человека не служит запасным источником атрибуции.
- Raw Zod-схема проверяет media URL проекта без query string и fragment, положительные целые размеры, непустой label и HTTP(S)-ссылку источника. Домен хранит явную readonly-структуру; mapper переносит её вместе с остальными данными профиля.
- Текстовую альтернативу строим из канонического `name`: отдельное редактируемое поле `alt` для обычного портрета не требуется.

Одного URL было бы недостаточно для резервирования места и указания источника. Поля верхнего уровня `photo_source`, `photo_width` и подобные разнесли бы одну сущность по всему frontmatter. Общую абстракцию медиа для других разделов не вводим.

### 2. Статическая HTML-разметка и локальная адаптивная вёрстка

- Использовать обычный `<img>` с `width`, `height` и `alt`, при наличии источника — `figure`/`figcaption` с обычной ссылкой. Фотография вверху страницы не требует отложенной загрузки или JavaScript.
- На широком экране портрет располагается у правого края общей области контента, верх изображения выровнен с хлебными крошками, как превью карты места. Имя, контакты и описание идут в левой колонке; описание следует сразу за контактами независимо от высоты портрета. Ширина портрета — `14rem` (224 px при базовом размере шрифта). Это уточнение владелец дал при просмотре промежуточных скриншотов.
- В узкой раскладке порядок DOM и чтения: имя/должность → портрет/источник → контакты/body. Изображение ограничено доступной шириной и сохраняет естественное соотношение сторон, без `object-fit: cover` и обрезки головы или плеч.
- Для профиля без фотографии не создаётся правая пустая колонка. Недоступный JPEG не блокирует текстовую часть страницы.
- Стили принадлежат странице людей и используют существующие токены. Правило расположения фиксируется в дизайн-гайде; общий layout с карточкой места ради двух случаев не выделяется.

Нативный `<img>` достаточно прост для источников около 450 × 600 px. Astro Image Service добавил бы сетевую зависимость сборки и производные файлы для небольшого портрета. Круглый аватар потребовал бы отдельного кадрирования, а колонка размером с карту чрезмерно увеличила бы фотографию.

### 3. Фото и источник в публичных представлениях

- `view.ts` добавляет в Markdown-карточку изображение после имени/должности и отдельный абзац со ссылкой источника, если он указан. Используется существующий AST API `@shelkovo/markdown`.
- `public-dto.ts` явно публикует необязательный `photo` со структурой `src`, `width`, `height`, `source?: { label, url }`. При отсутствии фотографии или источника соответствующего ключа нет в сериализованном JSON.
- `discovery.ts` описывает объект в JSON Schema и производном OpenAPI. Существующие имена `html_url`, `body_markdown` и остальные legacy-поля сохраняются; фотография не добавляется в `body_markdown`, `mentions` или backlinks.
- `seo.ts` получает URL портрета и добавляет его в `Person.image`. В `BaseLayout` портрет как социальное изображение не передаётся.
- Краткое описание нового поля добавляется в существующую документацию раздела для агентов. Новые endpoints и дублирование портретов в Markdown-обзоре людей не нужны.

Это позволяет внешнему потребителю получить портрет вместе с профилем, не разбирая HTML. Одного `Person.image` недостаточно: он не заменяет явный JSON-контракт и источник фотографии.

### 4. Подготовка и публикация в `people/`

Долговечное разрешение на публикацию публичных портретов оформляется новым ADR в существующей серии. Он дополняет ADR-021, задаёт сценарий фотографий людей и использует уже принятую подготовку JPEG. До загрузки синхронно обновляются ссылки в ADR-021 и индексе ADR, `ops/storage/public-media.md` и проектный skill `public-media-publisher`.

- Ключ: `people/<slug>.jpeg`. Владелец явно выбрал один актуальный портрет без истории: новая фотография заменяет содержимое по тому же адресу. Это уточнение принято при приёмке первоначальной реализации.
- Подготовка: применить ориентацию, сохранить полный кадр, не увеличивать исходник, ограничить длинную сторону 2560 px, sRGB, progressive JPEG quality 90, удалить метаданные. GPS и другие поля обратно не переносить. Найденные исходники меньше лимита и сохранят размеры.
- Проверить точный key и при наличии объекта сравнить SHA-256. Совпадение означает повторное использование; различие допускается для явно запрошенной замены портрета этого человека. Неожиданное содержимое требует выяснения конфликта. При замене синхронно обновить фактические размеры и источник в профиле.
- Публиковать через существующий S3-процесс с `Content-Type: image/jpeg` и `Cache-Control: public, max-age=300`, без `immutable`. После загрузки проверить HTTP 200, тип, размер, SHA-256, размеры изображения и отсутствие метаданных через `media.kpshelkovo.online`. Для замены учитывать существующий proxy cache nginx до 10 минут и клиентский короткий кеш; query string для обхода кеша не используется.
- Добавлять URL в профиль только после успешной проверки. Исходники и временные копии остаются вне репозитория.
- Проверить CSP сайта с учётом прямых `<img>` с media-origin; ссылка атрибуции не требует загрузки ресурса с сайта ОК Комфорт.

Датированные редакции усложняют адрес без пользы для актуального портрета. Ссылка на внешний JPEG оставила бы профиль зависимым от изменения сайта компании. Плоский JPEG-ключ использует уже подготовленные файлы и действующий короткий кеш media-origin.

- `nmakhrova` — Надежда Махрова, 449 × 600: [исходный JPEG](https://ok-komfort.ru/upload/iblock/4dc/rw54390eb9tl00u52bt2y5nkir3nad8i.jpg).

## Risks / Trade-offs

- Умеренное разрешение исходников → компактный размер отображения, без увеличения файлов и автоматической обрезки.
- Внешняя страница или файл могут измениться между исследованием и реализацией → повторно сверить подписи и JPEG перед загрузкой; при потере однозначной связи остановить публикацию соответствующего портрета.
- Повторное JPEG-кодирование даёт небольшую потерю качества → использовать принятый quality 90 и проверить итоговые лица и контуры визуально.
- Расхождение HTML и публичных данных → короткие проверки адаптеров на фотографию с источником, без источника и на отсутствие фотографии.
- Ошибка media-origin оставит недоступный портрет → текст и контакты остаются обычной статической разметкой; отдельный клиентский обработчик ошибок не требуется.
- Замена по прежнему URL видна не мгновенно → проверять результат с учётом TTL proxy cache и клиентского кеша, задавать короткий кеш и в S3.

## Migration Plan

1. Опубликовать этот change в draft PR для чтения владельцем. До отдельного разрешения не начинать реализацию и публикацию изображений. После разрешения продолжить ту же ветку и PR, отметив разрешение в issue ссылкой на коммит согласованных артефактов.
2. Закрепить правила портретов в ADR и рабочих инструкциях. Добавить поддержку необязательного поля, HTML и публичные представления.
3. Скачать и подготовить шесть изображений, опубликовать и проверить их по адресам `people/<slug>.jpeg` через media-origin, затем заполнить frontmatter соответствующих людей. Уже подготовленные JPEG первоначальной реализации используются без повторного кодирования. Удаление ранее опубликованных датированных объектов требует отдельного запроса по правилам хранилища.
4. Проверить требования автоматизированными проверками и в браузере на локальной сборке. Публикация media-объектов проверяется до включения ссылок; отдельная production-приёмка сайта после merge для завершения change не требуется.
5. После успешной приёмки и ревью синхронизировать основную spec, архивировать change и обновить этот PR результатами реализации. До завершения задачи PR использует `Refs #800`; готовая реализация — `Closes #800`.

Откат возвращает изменения кода и данных профилей. Уже опубликованные изображения автоматически не удаляются: их URL могли быть использованы отдельно от сайта. Откат Git не возвращает прежние байты заменённого портрета; для этого нужна отдельная публикация доступной исходной копии.
