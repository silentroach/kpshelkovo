# Tasks

Это задачи последующей реализации. Начать их можно после ревью и явного разрешения владельца на одобренную версию плана по [порядку передачи](/openspec/changes/unify-page-headings/design.md#migration-plan). В плановом PR все чекбоксы остаются открытыми.

## 1. Общие компоненты и их контракт

- [ ] 1.1 До изменения клиентских импортов снять исходные bundle-отчёты по [инструкции](/docs/development.md#анализ-клиентских-бандлов); сохранить сравнимую базу и указать её коммит.
- [ ] 1.2 Создать `PageHeading.astro` и отдельные типы по [design](/openspec/changes/unify-page-headings/design.md#1-два-компонента-приложения-и-композиция-через-слоты): исходный `title`, атрибуты H1 и subtitle, слоты, строковый поток и общий стиль. Адресными render-тестами проверить H1 без названий экшенов в его имени, `id`/атрибуты, безопасную типографику, отсутствие пустых частей и несколько абзацев со ссылкой; typecheck должен подтвердить интерфейс.
- [ ] 1.3 Создать `HeadingAction.astro` с типизированным компонентом иконки и нативной ссылкой/кнопкой; при необходимости перенести SVG места в существующий пакет иконок. Проверить доступное имя и декоративную иконку, `type="button"`, `href`/`download`/`target`/`rel`, ресурсный prefetch и проброс DOM-hooks короткими тестами поведения; сверить `sideEffects` пакета при изменении импортов/экспортов по [правилам workspace](/AGENTS.md#правила-workspace).
- [ ] 1.4 Обновить общий раздел Page Headers в дизайн-коде: H1, экшены, несколько абзацев subtitle, переносы, порядок метаданных, пример композиции и исключения главной/404. Сверить правило с обоими компонентами и [визуальным контрактом](/openspec/changes/unify-page-headings/design.md#4-один-визуальный-контракт); размеры не дублируются в scoped-правилах потребителей.

Удалить их локальные переопределения заголовка и пояснения вместе с копиями правил в дизайн-коде.

- [ ] 2.4 Перевести остальные шаблоны status, reviews, sarafan, people и meetings по карте переноса; пояснение собрания должно предшествовать дате и источникам. Проверить HTML и существующие тесты: полноэкранная карта не получает видимую шапку, инструменты сохраняют управление и связанные идентификаторы, локальные уменьшения H1 заменены общей ролью. Завершить удаление дублирующих правил этих заголовков из дизайн-кода.

- [ ] 3.1 Заменить статичный `Hero.svelte` Astro-композицией с `PageHeading`, subtitle и существующим KPI-блоком. Перенести значимые проверки H1, текста и ссылки из `Hero.svelte.test.ts` на Astro-композицию; удалить тест старой обёртки без дублирования уже покрытых сценариев. Проверить typecheck, итоговый HTML сравнения и доступность KPI; прежние специализированные параметры ссылки в subtitle и неиспользуемая Svelte-обёртка удалены.
- [ ] 3.2 Перестроить оболочку заголовка посёлка по [решению](/openspec/changes/unify-page-headings/design.md#5-границы-сравнения-и-карты): один видимый H1 и один набор `GlobeIcon`/`TelegramIcon`/`MapPinIcon` для обеих раскладок; район в subtitle, компания и значки ниже. Адресной проверкой HTML и обеих раскладок подтвердить единственный доступный H1, условия ссылок, прежний `mapUrl`, независимость от загрузки карты, сохранность настольных фактов, мобильного паспорта, tooltip ID и скрытого абзаца `searchDescription` с `data-pagefind-body` на уровне страницы вне `PageHeading`; удалить декоративные копии заголовка и заменённые стили.
- [ ] 3.3 Повторить `pnpm bundle:analyze`, сравнить состав и размеры с базой 1.1, сохранить актуальные YAML-отчёты. Объяснить изменения импортов; общая композиция не добавляет клиентский runtime, исходный Hero также не гидратировался.

## 4. Интеграционная приёмка

- [ ] 4.1 Сверить весь diff с картой переноса и требованиями `page-headings`: пропущенных главных заголовков нет, главная и 404 исключены, прежние локальные правила удалены. Выполнить `pnpm openspec:validate`, `pnpm lint`, `pnpm typecheck`, `pnpm test` и `pnpm build`; разбирать ошибки по их причине, без ослабления защитных проверок.
- [ ] 4.2 Выполнить браузерную приёмку общих вариантов: короткий и многострочный заголовок, длинное слово и диапазон дат, 0–3 экшена, отсутствие subtitle и несколько абзацев со ссылкой; ширины 320/390/768/1024/1440 px и увеличение текста до 200%. Проверить переносы от конца текста, отсутствие горизонтального переполнения, область нажатия, Tab/Enter/Space, видимый фокус и рабочие скачивания. Отдельно проверить обе раскладки посёлка, компоновку с портретом и печать news/KB; сохранить доказательства. Для настоящей карты подготовить разрешённый dev-стек по [инструкции](/docs/development.md#проверка-настоящих-карт); запуск `pnpm dev` требует явного разрешения владельца.
- [ ] 4.3 По skill `site-search` проверить сохранение корпуса, заголовков и исключения действий из индексирования там, где оно было задано; сопоставить выдачу затронутых страниц до/после при обнаруженном изменении релевантности. Сверить тексты и подписи с источниками: если текст изменён, выполнить `humanizer-ru` и [редакторское ревью](/docs/development.md#редакторское-ревью-текстов-сайта) с адресным повтором; иначе зафиксировать сохранность текста.
- [ ] 4.4 Вызвать `reviewer` на весь актуальный diff, включая новые файлы, с базовым SHA, change и результатами проверок. Исправить подтверждённые замечания и получить адресный повтор; при недоступности агента выполнить самопроверку по [протоколу](/docs/development.md#ревью-изменения-в-opencode), явно указав отсутствие независимого ревью. Закончить приёмку после покрытия требований актуальными проверками.

## Workflow follow-up

- После завершения реализации повторить отбор долговечных требований, синхронизировать delta spec и архивировать change штатными workflows в реализационной ветке.
- Проверить результат `pnpm openspec:validate` и провести адресное ревью изменений после sync/archive.
- Открыть реализационный PR с `Closes #1312`; плановый PR остаётся связан через `Refs #1312`. Обновить ссылку на change в issue на архивную после завершения.
