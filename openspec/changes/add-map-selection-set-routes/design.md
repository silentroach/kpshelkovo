# Design

## Context

Мотивация и границы — в [proposal](/openspec/changes/add-map-selection-set-routes/proposal.md). Текущий loader набора принимает только `parcels`, `places`, `sets`, `outline`; resolver канонизирует и сортирует ссылочный состав. `/map/?set=2026-halloween` показывает 18 участков без порядка обхода.

В проекте уже есть `RawEditorialGeometrySchema`, подготовка `mapEditorialGeometry`, публичный адаптер `toPublicEditorialGeometry` и `createEditorialMapObjects`. Последний уже импортирован общей картой для дополнительной геометрии мест. Точки показывают `iconContent` и `iconCaption` через `textContent`, но три схемы ограничивают внутренний номер одной цифрой.

Решение следует [ADR-013](/docs/decisions/013-raw-domain-public-data-boundary.md), [ADR-039](/docs/decisions/039-shared-yandex-maps-runtime-and-preview.md) и [ADR-041](/docs/decisions/041-parcel-records-and-exact-search.md): отдельные границы данных, общий runtime и renderer, без фиктивных карточек домов или маршрута. Новый ADR не требуется.

## Goals / Non-Goals

**Goals:**

- Дополнить текущий JSON набора готовой дорожной линией и читаемыми номерами визитов.
- Переиспользовать существующие геометрические схемы, подготовку, renderer и жизненный цикл карты.
- Сохранить согласованность общей карты, runtime JSON и Markdown-вставки с этим набором.

**Non-Goals:**

- Расчёт маршрутов при сборке или открытии страницы, GPS-навигация, поворотные команды и автоматическая перенумерация.
- Отдельные сущности маршрута, остановки и парковки, наследование маршрутов и граф связей точек с участками.
- Новые страницы, панели, легенды, переключатели маршрутов и самостоятельный редактор.

## Decisions

### 1. Собственные `features` в исходнике, подготовленная `geometry` в выдаче

В исходный JSON добавить необязательный `features` с объектами `Point` и `LineString`. Элементы используют существующий редакционный GeoJSON-контракт с ограничением типов, без отдельной копии всех правил свойств. Отсутствующий или пустой массив означает отсутствие собственной геометрии. Прежнее требование непустого ссылочного состава сохраняется: файл только с `features` не становится новым типом самостоятельной карты.

Loader проверяет данные Zod-схемой, затем готовит коллекцию через существующий mapper. Домен получает необязательную readonly-геометрию; публичный адаптер добавляет `geometry: FeatureCollection` только при её наличии. В старых наборах поле отсутствует, их публичное представление не меняется. Источник ошибки включает ID набора и объект/поле геометрии.

Такой вход совпадает с привычным `features` короткой Markdown-вставки. Полный `geometry: FeatureCollection` в исходнике потребовал бы лишней оболочки для каждого набора; отдельный соседний файл — дополнительных правил привязки и загрузки. Поля маршрутизатора и новая модель `stops` не нужны для показа готовой схемы.

### 2. Геометрия принадлежит открываемому определению

Ссылки `sets` по-прежнему раскрывают только участки и места. Собственная геометрия не наследуется: родитель задаёт свою схему, подобно собственной настройке `outline`. Это предотвращает наложение маршрутов дочерних наборов с повторяющимися номерами. Участники продолжают сортироваться, а порядок визитов хранится в явных `iconContent` точек.

Выключатели частей и слоёв управляют участниками, но не собственными линиями и точками. Для геометрии не вводятся ссылки feature → parcel, пространственное отсечение или частичное скрытие пути. Снятие набора удаляет всё его собственное оформление.

Эти два решения рекомендовал advisor после проверки кода. Цена расширения умеренная: меняются границы данных и интеграция, но новый renderer или контроллер маршрутов не нужен.

### 3. Интеграция в существующий жизненный цикл общей карты

В `PlaceMap.svelte` хранить небольшой отдельный список объектов собственной геометрии активного набора. Преобразовывать подготовленную публичную коллекцию существующим адаптером `fromPublicEditorialGeometry` и создавать объекты через `createEditorialMapObjects`.

- Создавать геометрию после проверки ответа набора и существующей проверки актуальности запроса.
- Включать её вершины в `getSelectionSetBounds`, сохраняя ожидание полного состава, приоритет `p`/`h`, отмену вписывания после действия пользователя и поведение resize.
- Удалять объекты при снятии набора и очистке карты. Поздний ответ после снятия или уничтожения не добавляет объекты.
- При ошибке создания или добавления убрать уже добавленные объекты этой коллекции и использовать штатное сообщение сбоя набора. Сохранить работоспособность обычной карты.
- Проверять расширенный публичный результат Zod-схемой при сборке, до сериализации. По [site-maps](/openspec/specs/site-maps/spec.md#requirement-подготовленные-данные-карт-проверяются-до-публикации) браузер использует собственный проверенный артефакт без повторной схемной проверки. Сохранить обработку ошибок HTTP, JSON-разбора и применения; не возвращать схемы и Zod в клиентский граф.

Самостоятельный класс слоя, универсальный контроллер и дополнительный запрос геометрии не требуются. Обычное открытие `/map/` по-прежнему не запрашивает определения наборов.

### 4. Двузначные метки в общем renderer

Расширить `iconContent` до строковых целых `0`–`99` без ведущих нулей в raw-, domain-data- и public-схемах. Сохранить ограничение только для точек, несовместимость с `captionOnly: true` и буквальный текстовый вывод.

Использовать существующий круглый маркер и семейство шрифта. Проверить числа 10–19 на реальной карте; при необходимости изменить только локальное размещение текста двузначного номера. Отдельные шрифты и собственный renderer маршрута не нужны. Любое согласованное изменение размеров фиксируется в действующем дизайн-гайде.

### 5. Markdown получает тот же набор объектов

`createEditorialMapSelectionResolver` дополняет результат собственной подготовленной геометрией каждого непосредственно указанного набора один раз. Общий дочерний набор не приносит собственную геометрию через родителя; прямое указание самого дочернего набора приносит её.

Авторские цвета, подписи и номера сохраняются. Импортированная геометрия не перекрашивается под участки и повторно не подготавливается. Существующие HTML- и companion-адаптеры получают её через общий результат resolver. Собственные features вставки продолжают добавляться отдельно; новые правила ссылок, подписей и backlinks не вводятся.

### 6. Наполнение `2026-halloween`

В тот же JSON добавить `places: ["forest-park"]` и собственные features. Нумерация обозначает каждый визит, включая дома внутри пеших блоков, а не стоянки автомобилей:

1. SHR-R29
2. SHR-R80
3. SHR-L43
4. SHR-L20
5. SHP-C79
6. SHP-C42
7. SHP-F50
8. SHR-E46
9. SHV-G84
10. SHV-G36
11. SHV-G38
12. SHV-E50
13. SHF-M71
14. SHF-M70
15. SHF-W58
16. SHF-M36
17. SHF-N24
18. SHF-V4
19. forest-park

Точки получают явные номера и короткие подписи с частью посёлка и кодом; финал подписан названием лесного парка. Первая точка — R29. Координаты домов остаются ориентирами участков, а не объявлением точных въездов. Для размещения меток использовать координаты, согласованные с подготовленным слоем участков; дорожную геометрию не сдвигать кадастровой поправкой.

Путь берётся из сегментов полного рассчитанного автомобильного маршрута. Сохранённый исследовательский `halloween-routing-evidence.json` в рабочем временном каталоге содержит старый маршрут с M48: его нельзя просто публиковать. Получить новый полный экспорт по приведённым 19 точкам или восстановить его из актуального сохранённого ответа, если такой появится. API-координаты `[lat, lng]` перевести в GeoJSON `[lng, lat]` и округлить до восьми знаков. Разрывы сегментов сохранять отдельными `LineString`, без прямых перемычек через участки. Не заменять дорожный путь линией между центрами домов.

Расчёт API выполняется один раз при подготовке данных с разрешённым localhost Referer. Ключ не попадает в исходники, артефакты, логи и коммиты. Страница и сборка получают только сохранённые координаты; нового внешнего runtime-запроса и изменения CSP не требуется.

Оставить полную автомобильную схему. Пешие варианты рядом с G84/G36/G38 и M71/M70 обсуждались организационно, но конкретные стоянки не установлены; смешанный пеший/автомобильный граф в этот change не входит.

## Risks / Trade-offs

- Близкие точки и маркер парка могут перекрываться → проверить обзор и приближение, особенно номера 9–11 и 19. Сохранить обычную ссылку маркера парка и отображение номера финиша; не вводить алгоритм разнесения подписей без подтверждённой необходимости.
- Самостоятельная геометрия остаётся после выключения частей → явно описать это в редакционной инструкции и проверить; действие «Снять набор» удаляет её целиком.
- Определение набора становится больше → геометрия загружается только по `set`, не попадает в общий payload мест и не добавляет маршрутный SDK. Размер итогового JSON зафиксировать в приёмке.
- Ограничение общих номеров затрагивает разные карты → адресно проверить общие схемы, renderer, превью места и Markdown companion, сохранив одноцифровые метки и `captionOnly`.
- Рассчитанные точки не являются проверенными калитками → не строить вымышленные проходы; фактическое совпадение линий с дорогами сверить в браузере.

## Migration Plan

1. После разрешения реализации сохранить согласованные артефакты в рабочей ветке и связать change с issue по проектному процессу.
2. Сначала расширить совместимые схемы и потребителей, затем добавить геометрию конкретного набора в той же ветке.
3. Выполнить проверки, независимое ревью и редакторское ревью новых подписей; после согласования запуска проверить настоящую карту через `pnpm dev` на `http://localhost:4321`.
4. Синхронизировать specs и архивировать change перед PR. Код, данные и документация поставляются вместе.
5. Откат возвращает весь PR. Старые наборы не требуют миграции; отдельно публиковать данные с новым полем на старом коде нельзя.
