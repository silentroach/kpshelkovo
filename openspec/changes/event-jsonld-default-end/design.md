# Design

## Context

Причина изменения описана в [proposal](/openspec/changes/event-jsonld-default-end/proposal.md). Сейчас `buildEventIcs` подставляет два часа только при точном начале; `buildEventJsonLd` выводит `through ?? endsIso`. Новостной JSON-LD уже использует общий генератор мероприятий.

[events-calendar](/openspec/specs/events-calendar/spec.md) и тесты прямо запрещают перенос условного окончания ICS в JSON-LD. Требуется изменить этот контракт, сохранив неизвестность в редакторской записи и остальных представлениях. [ADR-013](/docs/decisions/013-raw-domain-public-data-boundary.md) оставляет такие преобразования публичным адаптерам; новая граница данных или ADR не нужны.

## Goals / Non-Goals

**Goals:**

- Один расчёт окончания для двух адаптеров без изменения доменного снимка.
- Явное окончание сохраняет приоритет, включая длительности короче двух часов.

**Non-Goals:**

- Новые поля данных, подстановка окончания в raw-схеме или mapper-е, изменение поискового окна.
- Изменение `offers`, `image`, `performer` или места публикации Event.

## Decisions

1. Вынести расчёт точного или двухчасового окончания из ICS в небольшой общий helper внутри `/apps/www/src/lib/events/`. Использовать его в ICS и для fallback в JSON-LD. Дублирование константы проще только на первом шаге и допускает расхождение двух экспортов; импорт ICS-генератора в SEO создаёт лишнюю зависимость.
2. В JSON-LD сохранить существующие ветки `through` и `endsIso`; вызывать общий расчёт только при точном начале без окончания. Расчётный момент сериализовать как ISO 8601 с явной зоной, допустим UTC. Это сохраняет нынешнее представление заданных редактором дат и многодневных периодов.
3. Не заполнять `endsAt`/`endsIso` в mapper-е: иначе расчёт попадёт в UI, JSON-ленты и правила актуальности. Видимые подписи продолжают использовать редакторские данные. Состояния отмены и условного набора не влияют на выбор окончания.
4. В `/apps/www/src/data/events/2026/11/dam-opening-2026.md` добавить `ends_at: 13.11.2026 12:30` по указанию владельца от 13 ноября 2026 года. Сохранить уже добавленного в рабочей копии организатора «ОК Комфорт». Проверить этот точный интервал в новости, странице мероприятия и ICS.
5. Уточнить редакторские инструкции: неизвестное окончание по-прежнему не записывают в `ends_at`; ICS и JSON-LD рассчитывают резервный интервал при экспорте. Основной spec меняется через delta этого change.

## Risks / Trade-offs

- Расчётный `endDate` воспринимается потребителем как время окончания, хотя видимые сведения могут его не содержать. [Google](https://developers.google.com/search/docs/appearance/structured-data/event#date-time-best-guidelines) рекомендует точные сведения; отсутствие рекомендованного поля допустимо. Сохранение прежнего поведения остаётся альтернативой. По запросу владельца планируется подстановка, с приоритетом точного окончания и без обещания улучшения поисковой выдачи.
- Правка общего расчёта может затронуть ICS или переход через полночь. Проверить оба адаптера на одинаковом моменте окончания, заданном коротком интервале, переходе даты, неизвестных часах и многодневном периоде; сохранить существующие проверки ICS.

## Migration Plan

Развернуть обычной статической сборкой после проверок. Миграции форматов и URL не нужны. Откат поведения возвращает изменения helper-а, адаптеров и их контрактов; редакторское окончание открытия дамбы остаётся самостоятельным подтверждённым сведением.
