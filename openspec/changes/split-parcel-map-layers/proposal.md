# Proposal

## Why

Сейчас включение «Участков» на `/map/` загружает геометрию всех четырёх частей Шелково, даже если жителю нужна одна. [Задача #862](https://github.com/silentroach/kpshelkovo/issues/862) добавляет независимый выбор частей и загрузку только нужных данных, в том числе при переходе к участку по номеру.

## What Changes

- Превратить пункт «Участки» в группу: общий трёхсостоянийный чекбокс и четыре сразу видимые строки с существующими иконками и короткими названиями в порядке **Форест / Вилладж / Парк / Ривер**. Счётчик выбранных частей не показывать.
- Разрешить любую комбинацию частей. Общий чекбокс включает все части из пустого или частичного выбора и выключает все из полного выбора.
- Собирать четыре компактных статических JSON из существующих редакционных записей. Загружать выбранные части независимо и повторно использовать успешно полученные данные в пределах экземпляра карты. Обычное открытие карты и раскрытие панели не загружают участки.
- По `/map/?p=<код>` определять часть по префиксу, загружать только её JSON, разрешать основной код или алиас и выполнять существующие фокус и временное выделение участка.
- Убрать текст загрузки участков и отдельную кнопку «Повторить». Ошибка одной части не должна выключать остальные или считаться отсутствием запрошенного участка.
- **BREAKING:** удалить общий `/map/data/parcels.json` без совместимого feed и перенаправления. Удалить его описание и ссылки из Markdown-представления карты и каталога публичных данных. По решению владельца агентской точкой входа пока достаточно существующего Markdown-индекса; четыре JSON обслуживают интерфейс карты.
- Перевести сборщик поискового индекса на чтение четырёх файлов с общей проверкой кодов и алиасов. Состав и поведение поисковых записей сохраняются.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `parcel-map`: независимые части слоя, общий выбор, отложенная загрузка и повторное включение, адресный переход по префиксу, восстановление после ошибки без отдельной кнопки.
- `site-maps`: проверка конечных данных каждой части участков при сборке вместо привязки к одному общему JSON.

## Impact

- UI и жизненный цикл карты: `apps/www/src/components/places/PlaceMap.svelte`, `parcel-layer.ts`, типы слоя и поведенческие тесты; подключение существующих иконок из `packages/ui/src/icons/areas/` через `apps/www/src/pages/map/index.astro`.
- Доставка данных: маршруты в `apps/www/src/pages/map/data/`, адаптер, схема и URL-helpers в `apps/www/src/lib/parcels/`. Общая поправка координат применяется до разделения подготовленного набора.
- Публикация и поиск: `apps/www/src/lib/places/markdown.ts`, `public-surface.ts`, связанные проверки реестра и `apps/www/scripts/build-search-index.ts`. Требования `search` не меняются.
- Документация: уточнить действующее описание доставки данных в ADR-041 и ссылку на источник поисковых записей в skill `site-search`; сравнить и сохранить клиентские bundle-отчёты при реализации.
- Границы: обычный JSON, без JSONL и потоковой отрисовки; без ссылки на часть целиком, хранения выбора между открытиями, новых карточек участков, цен и попапов из #861. Доставка геометрии мест из #858 остаётся отдельной задачей.
- Порядок передачи: этот PR сначала содержит план для чтения владельцем. Реализация продолжится в той же ветке в отдельной сессии после явного разрешения на подготовленные артефакты. Публикация плана не является разрешением реализации; до неё основные specs не синхронизируются и change не архивируется.
- Отдельная production-приёмка не требуется. Плановый PR использует `Refs #862`; после реализации и полной приёмки тот же PR может использовать `Closes #862`.
