# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md), задача — [#862](https://github.com/silentroach/kpshelkovo/issues/862).

`PlaceMap.svelte` хранит один флаг включения, один кеш массива и один счётчик актуальности запроса. `parcel-layer.ts` добавляет готовый массив контуров, управляет видимыми номерами и одним пятиисекундным выделением. Прямая ссылка разрешается по этому массиву без обращения к Pagefind.

`buildParcelMapPayload` готовит отображаемые координаты и проверяет конечные данные Zod-схемой. Опорная широта поправки вычисляется по всему переданному набору. `build-search-index.ts` затем читает готовый общий файл, проверяет уникальность кодов и создаёт поисковые записи без геометрии. Markdown-индекс и реестр публичных поверхностей сейчас рекламируют этот общий JSON.

Применимые решения:

- [ADR-041](../../../docs/decisions/041-parcel-records-and-exact-search.md): участки отдельно от мест, общий редакционный источник карты и поиска, переход по основному коду. При реализации уточнить описание единственного JSON.
- [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md): отдельное подготовленное представление карты, без публикации полной доменной записи.
- [ADR-039](../../../docs/decisions/039-shared-yandex-maps-runtime-and-preview.md): общий runtime карт, независимая доменная логика общей карты и освобождение экземпляра при навигации.
- [ADR-011](../../../docs/decisions/011-public-surface-registry.md): согласованное описание агентских поверхностей. Новые JSON используются как вспомогательные данные UI, без добавления четырёх агентских feeds в каталог.
- [Дизайн-гайд](../../../docs/design/design-code-shelkovo.md): плоская панель, существующие шрифты и цвета, состояние различимо без распознавания цвета или иконки.

## Goals / Non-Goals

**Goals:**

- Сохранить подготовку координат и семантику поисковых записей при разделении доставки данных.
- Сделать переключение частей независимым от очередности ответов и сохранить одно выделение участка на всей карте.
- Переиспользовать существующую панель и рендерер вместо отдельного SDK-слоя с собственной камерой для каждой части.

**Non-Goals:**

- Универсальный менеджер слоёв, сетевой кеш между страницами, предзагрузка выключенных частей, порционная отрисовка и новые зависимости.
- Перенос редакционных записей или изменение кадастровых соответствий, поискового корпуса и ранжирования.
- Постоянное выделение части посёлка или самостоятельный URL для неё.

## Decisions

### 1. Вертикальная группа с обычными чекбоксами

Кнопка с доступным именем «Слои» открывает прежнюю всплывающую панель. В ней общий чекбокс «Участки» с существующей иконкой участка, затем четыре строки: **Форест, Вилладж, Парк, Ривер**. Строки видны сразу, без дополнительного раскрытия. В каждой строке чекбокс, существующая иконка части и короткое название; вся подпись нажимается. Счётчика и отдельных массовых кнопок нет.

Схема использует латиницу только для ASCII-макета; видимые названия остаются русскими:

```text
+------------------------------+
| [-] [plot] Uchastki           |
|                              |
|     [x] [icon] Forest         |
|     [ ] [icon] Village        |
|     [x] [icon] Park           |
|     [ ] [icon] River          |
+------------------------------+
```

Общий чекбокс вычисляется из выбранных частей: пустой при нуле, отмеченный при четырёх, `indeterminate` при промежуточном выборе. Нажатие из пустого или смешанного состояния включает все, из полного — выключает все. Отдельного сохранённого «последнего набора» нет. Владелец принял два нажатия для выключения всего из смешанного состояния.

Использовать нативные чекбоксы и подписи, видимый фокус и область нажатия от 44 px. Иконки декоративны рядом с текстом и сохраняют пропорции; их цвет не обозначает состояние выбора. Закрытие по внешнему нажатию и Escape с возвратом фокуса остаётся. Выбор пункта не закрывает панель. На узком экране панель помещается в карту; при малой высоте доступна прокрутка её содержимого.

Существующие иконки — Astro-компоненты в `packages/ui/src/icons/areas/`. Передать их из `apps/www/src/pages/map/index.astro` в Svelte-панель как статическую разметку через именованные слоты: это позволяет переиспользовать исходные SVG без новой библиотеки, отдельной обёртки и копий path-данных. Сетка 2 × 2 отклонена владельцем в пользу вертикального списка.

### 2. Четыре обычных JSON из одного подготовленного набора

Адреса данных UI:

- `/map/data/parcels/shf.json` — Форест.
- `/map/data/parcels/shv.json` — Вилладж.
- `/map/data/parcels/shp.json` — Парк.
- `/map/data/parcels/shr.json` — Ривер.

Собирать их одним статическим параметризованным маршрутом Astro. Сначала подготовить весь набор существующим адаптером с общей опорной широтой поправки, затем разделить по `part`. Проверить каждый конечный массив перед компактной сериализацией. Нельзя отдельно пересчитывать поправку на каждом подмножестве: это меняет координаты относительно общего набора. Форма записи, алиасы, статус продажи и подготовленная точка подписи сохраняются.

Проверка существующего локального `dist/www` во время обсуждения, без новой сборки:

- Общий набор: 1620 позиций, 662 872 байта, 129 326 байт gzip.
- Форест: 356 позиций, 141 079 байт, 27 235 байт gzip.
- Вилладж: 501 позиция, 191 644 байта, 34 597 байт gzip.
- Парк: 260 позиций, 112 769 байт, 23 458 байт gzip.
- Ривер: 503 позиции, 217 383 байта, 45 014 байт gzip.

Четыре сжатых файла суммарно занимают 130 304 байта: почти столько же, сколько общий, но требуют до четырёх запросов. Для одной части экономится примерно 65–82% геометрического трафика. Это измерение размера, а не доказательство ускорения всей карты.

JSONL рассмотрен и отклонён владельцем: gzip отличается всего на 1–4 байта на часть, а потоковый парсер и добавление контуров порциями усложняют слой. Ранний фокус зависит от позиции нужной строки в файле. Выбран обычный JSON с независимой готовностью частей.

### 3. Независимые запросы и единое выделение

В пределах экземпляра карты хранить выбранные части, успешно полученные данные и выполняющийся запрос отдельно для каждой части. Повторное включение использует данные или уже выполняющийся запрос; отказ не кешируется как успешный результат. Одновременное включение всех запускает запросы недостающих частей параллельно, каждая показывается по готовности.

Открытие панели ничего не загружает. При выключении части её контуры и подписи сразу убираются. Завершение запроса может сохранить пригодные данные для следующего включения, но не возвращает выключенную часть на карту. Проверять актуальный выбор и жизнь экземпляра также после динамического импорта рендерера. При уничтожении карты поздние ответы не добавляют объекты и не меняют URL.

Расширить существующий рендерер так, чтобы он мог добавлять и удалять части независимо. Переключение одной части не пересоздаёт контуры соседних частей. Выбор участка и таймер остаются общими: выбор в другой части снимает прежнее выделение; выключение части с выбранным участком снимает его и завершает связанный URL-фокус. Все активные части используют существующие правила масштаба, статуса продажи и отображения нескольких кадастровых контуров позиции. Ручной выбор слоёв не перемещает камеру, кроме возобновления ожидающего прямого перехода после ошибки.

### 4. Минимальная обратная связь при ошибках

Не показывать текст «Загружаем…» и отдельный индикатор загрузки участков; чекбокс отражает выбор сразу и остаётся доступным для отмены. Отдельной кнопки «Повторить» и автоматических повторов нет.

Существующее краткое сообщение об ошибке сохраняется с указанием части, в доступной области рядом с контролом, в том числе при закрытой панели. При отказе доставки, разбора или применения данных снять выбор только этой части, убрать её частично добавленные объекты и не сохранять неудачный результат в успешный кеш. Пользователь может снова включить часть обычным чекбоксом. Это минимальное уточнение сохраняет различие ошибки и неизвестного номера из действующего `parcel-map`, выполняя просьбу убрать текст ожидания и специальное действие повтора.

При отказе прямой ссылки сохранить `p` и намерение фокуса. Следующее включение этой части повторяет исходный переход. Явное выключение части во время ожидающего или выполняющегося перехода отменяет намерение и удаляет соответствующий `p`; ошибка сама по себе его не удаляет. Успех другой части не очищает сообщение и намерение неудачной части.

### 5. Маршрутизация прямой ссылки по префиксу

После нормализации регистра и существующей проверки формы полного кода первые три символа определяют ровно один файл. В нём найти основной код или алиас. Только найденная позиция включает свою часть, фокусируется на точке подписи с нынешним масштабом появления номеров и выделяется на пять секунд. Через пять секунд удалить `p`, сохранив остальные параметры, hash и history state; часть и камера остаются. Повторное открытие ссылки повторяет действие; reduced motion отключает анимацию камеры.

Заведомо неверная форма кода не вызывает запрос участков. Корректный, но отсутствующий код требует только файла своего префикса; после успешного ответа `p` удаляется без показа этой части и перемещения камеры. Не загружать остальные части в попытке найти неизвестный код и не подключать Pagefind для разрешения ссылки. При существовании обоих параметров `p` и `h` сохранить нынешний приоритет перехода к участку.

В исследованном наборе все алиасы имеют префикс основной части. Чтобы один запрос по префиксу оставался достоверным, при подготовке данных проверять это условие вместе с принадлежностью позиции файлу. Межчастевой алиас не должен публиковаться как ссылка, которую карта молча считает неизвестной: остановить сборку с диагностикой кодов и вернуть такой случай на отдельное решение владельцу. Не угадывать новую связь и не добавлять запасной обход четырёх файлов.

### 6. Удаление общего feed и сохранение поиска

Владелец явно выбрал удаление `/map/data/parcels.json` вместо сохранения совместимости. Удалить маршрут и его URL-helpers, описание из `buildPlacesMarkdown`, запись `places:parcels-data` из реестра и соответствующие ожидания тестов. На старом адресе не создавать redirect или объединяющий ответ. Markdown-индекс остаётся входом для агентов; новых агентских каталогов участков или четырёх ссылок на UI-данные не добавлять. JSON мест относится к #858 и этим решением не затрагивается.

Сборщик Pagefind читает четыре подготовленных файла, проверяет их существующей Zod-схемой и объединяет перед общей проверкой уникальности кодов и алиасов. Отсортировать объединённый набор по основному коду, как в текущем loader, чтобы порядок добавления записей не зависел от UI-порядка частей. Содержимое, metadata, один результат на позицию и URL `/map/?p=<основной-код>` сохраняются. Отсутствие или повреждение любого файла останавливает сборку индекса вместо публикации неполного корпуса. Это применяется к production build и `search:prepare`, использующим один скрипт.

## Risks / Trade-offs

- При включении всех частей запросов станет больше, суммарная компрессия немного хуже. Сравнить реальные байты и готовность одной части и всех частей; не обещать ускорение всего SDK по размеру JSON.
- Одновременные запросы и быстрые переключения создают гонки. Проверить выключение до ответа, повторное включение во время запроса, обратный порядок ответов, отказ одной части и уход со страницы.
- Разбиение может незаметно изменить координаты или потерять записи поиска. Сравнить объединение новых файлов с исходным подготовленным набором и сохранить общий порядок индексирования.
- Новый контракт намеренно прекращает старый feed. Удаление и ссылки на него выпускаются вместе; четыре новых файла не объявляются приватными, хотя не рекламируются как агентский API.

## Migration Plan

1. Сначала опубликовать этот план в ветке `docs/862-split-parcel-map-layers` и draft PR с `Refs #862`. Владелец читает артефакты; текущая сессия не начинает реализацию.
2. В следующей сессии прочитать change, комментарии issue/PR и состояние той же ветки. Получить явное разрешение реализации подготовленных артефактов и сохранить отметку в issue со ссылкой на их коммит.
3. Реализовать новые данные, переключатель, прямые ссылки, миграцию поиска и очистку discovery в одном изменении. Обновить описание доставки в ADR-041 и skill `site-search`, не переписывая историю архивных changes.
4. Выполнить задачи приёмки. После готовности синхронизировать основные specs и архивировать change в этой же ветке; обновить тот же PR до реализации с проверками и `Closes #862`. Человеческое ревью и merge выполняет владелец.
5. Откат реализации возвращает весь набор изменений вместе: интерфейс, генерацию JSON, чтение индекса и публичное описание. Отдельно возвращать только старый маршрут недостаточно.
