## Context

Мотивация и объём описаны в [proposal.md](proposal.md). Исходная HTML-страница выводит адрес и часы, затем действия и `body` либо `summary`. `PlaceOpeningHours.astro` уже отвечает за полную неделю, перерывы и живой статус. `PlaceMap.svelte` рассчитан на общую карту: кластеры, временный фокус `?h=`, контуры по наведению и отступы под overlay-header.

Данные места содержат координаты, необязательные геометрию, маркер, адрес и ссылку на «Сарафан». GeoJSON Охотничьих прудов уже содержит два раздельных полигона. `@shelkovo/geo` предоставляет `calculateDistance`; новый расчёт геодезических расстояний не нужен.

Основа решения:

- [ADR-028](../../../docs/decisions/028-markdown-first-places-map.md): источник данных места, маркеры, геометрия и различие публичной карточки и общей карты.
- [ADR-034](../../../docs/decisions/034-native-css-architecture.md): app-owned tokens, общие роли типографики и локальные стили компонентов.
- [ADR-017](../../../docs/decisions/017-csp-inline-exceptions-for-astro-yandex-maps.md): подключение Яндекс Карт и CSP.
- [Дизайн-гайд](../../../docs/design/design-code-shelkovo.md): PT Serif / Fira Sans, плоские секции и сдержанные акценты.

Владелец рассмотрел локальное демо и попросил сохранить текущий вариант вместе с change в PR для визуального ревью. Это разрешение на публикацию предложения и демо; разрешение перенести решение в публичную страницу фиксируется отдельно после ревью артефактов.

## Goals / Non-Goals

**Goals:**

- Получить воспроизводимый визуальный ориентир для основной реализации и компактную композицию при разных наборах сведений.
- Использовать существующие данные и компоненты, сохраняя самостоятельную HTML-карточку при сбое карты.
- Отделить географическое соседство от редакционных упоминаний и ручной рекомендации маршрута.

**Non-Goals:**

- Редизайн «Сарафана», изменение общей карты, включение HTML-backlinks из #187.
- Маршрутизация, время пешего пути, геолокация посетителя, ручной список соседей и полный интерактивный картографический интерфейс внутри карточки.
- Изменение схем контента, Markdown/JSON-контрактов, метаданных или алгоритма расчёта часов.

## Decisions

### 1. Две колонки, начинающиеся на одной высоте

На широком экране левая колонка целиком включает breadcrumbs, заголовок с действиями, расписание и описание. Правая начинается на уровне breadcrumbs: карта, адрес при наличии, «Рядом». В демо переход к двум колонкам происходит от `60rem`; их отношение `1.2fr / 1fr`, высота превью — `20rem`. Это параметры визуального ориентира, а не новые глобальные tokens.

На телефоне порядок DOM естественный: левая колонка, затем карта с адресом и соседями. Превью имеет высоту `15rem`. Длинный заголовок переносится; при недостатке ширины группа действий может перейти на следующую строку без уменьшения общего размера H1. Внешние отступы и шрифты следуют существующей системе.

Отвергнут первый макет, где карта начиналась на уровне описания: при коротком тексте список соседей уходил слишком низко. Перенос «Рядом» в отдельную полноширинную секцию не выбран: поднятая правая колонка сохраняет географические сведения вместе.

### 2. Описание и метаданные

`body` остаётся основным текстом; `summary` служит fallback для места без `body`. Дополнительный lead из `summary` не вставляется. Расписание располагается перед описанием и использует `PlaceOpeningHours.astro`: кружок после «Время работы», обычный `title`, скрытая подпись, московское время и перерывы сохраняются.

Адрес принадлежит картографическому блоку и показывается подписью под превью, без лейбла «Адрес». Если адреса нет, пустая подпись не создаётся. Общая приписка «Границы показаны приблизительно» убрана по результату визуального обсуждения; `precision: approximate` в данных сохраняет исходный смысл геометрии.

### 3. Действия рядом с заголовком

Переход к `/map/?h=<slug>` и связанной карточке «Сарафана» оформляется отдельными кнопками-иконками рядом с названием, по паттерну календарных и VCF-действий. У каждой ссылки есть `title`, доступное имя, видимый focus и достаточная область нажатия. Условия показа остаются прежними: карта только при `showOnMap`, контакты только при `contact`.

В работающем превью есть штатное действие Яндекс Карт, поэтому второй переход под ним не выводится. При загрузке, ошибке API или без JavaScript сохраняется обычная ссылка с исходным `mapUrl`. Это выбранное владельцем уточнение исходного требования issue о ссылках: штатная кнопка ведёт в Яндекс Карты из текущего вида, а резервная ссылка и Markdown продолжают использовать сохранённый URL места. Стандартные логотип и атрибуция карты остаются видимыми.

### 4. Небольшой preview-компонент поверх действующего runtime

Превью получает координаты, существующий маркер и подготовленную геометрию напрямую из `Place`. Оно доступно и для публичного места с `showOnMap: false`, поэтому не должно получать свою точку только через JSON общей карты.

Используется тот же runtime Яндекс Карт и набор assets. Жесты карты отключены. Точка неподвижна; контуры видны постоянно, без hover, стрелки, пульсации и таймера подсветки. Начальный охват включает точку и все вершины всех полигонов, с запасом под иконку и элементы вендора; resize пересчитывает охват. Для места без геометрии нужен локальный обзор улиц вокруг точки. Соседи не расширяют кадр и не добавляют на превью дополнительные маркеры.

Общую полноэкранную `PlaceMap.svelte` не следует переносить в карточку целиком: её кластеры, highlight URL и overlay margins здесь не нужны. Демо использует небольшой Astro custom element с `behaviors: []`. Для основной реализации подходят тот же подход и штатный lifecycle; повторно используются runtime, конверсия геометрии и изображения. Общие helpers извлекаются только там, где действительно появятся два потребителя.

### 5. Автоматическое географическое соседство

На сборке кандидатами служат только места с `showOnMap: true`, кроме исходного slug. Расстояние вычисляется существующим `calculateDistance` между основными точками. Отбираются кандидаты не дальше 1 км, сортируются по расстоянию, затем по slug для устойчивого порядка; остаются первые три.

При совпадающих координатах разные slug остаются разными местами. Невидимое на общей карте место может иметь собственное превью и список видимых соседей, но само в чужие списки не попадает. При отсутствии кандидатов блока нет.

Видимый список содержит знакомые иконки и названия. По последним замечаниям владельца в нём нет горизонтальных разделителей и подписей «Планируется» / «Строится»; состояние передаётся доступным текстом ссылки. Расстояния не выводятся и не интерпретируются как длина пешего пути. Список не участвует в mention graph или backlinks и исключается из индексируемого текста карточки, как навигация.

### 6. Демо как ориентир, а не публичный маршрут

`apps/www/tests/place-card-demo/` — отдельная Astro fixture. Она читает настоящие Markdown и GeoJSON, валидирует frontmatter через текущую Zod-схему, использует mapper, renderer текста, компонент расписания, tokens и маркеры. В ней две страницы: Охотничьи пруды и Буржуйка. Демо-header даёт переключение примеров; основные header/footer приложения проверяются уже при переносе.

Снимки [preview/](preview/README.md) фиксируют исходные production-карточки и последнюю версию демо на desktop/mobile. Это материалы для человеческого ревью, не постоянные pixel-эталоны карты: картографическая подложка и текущий статус меняются.

Демо запускается командой из своего README на `http://localhost:4336/`. В этой среде API работает с `localhost`; обращение через `127.0.0.1` давало ошибку загрузки. Ключ берётся из корневого `.env` штатным способом и не сохраняется в исходниках или скриншотах.

## Risks / Trade-offs

- Дополнительная загрузка API на detail-страницах → фиксировать размер контейнера до инициализации, не блокировать HTML и проверить ошибки, клиентские переходы и освобождение карты при уходе со страницы.
- Контуры могут обрезаться или попасть под атрибуцию при узкой ширине → учитывать их целиком и проверить статические снимки после resize, особенно MultiPolygon.
- Близость через пруд или забор не означает доступный маршрут → отбор только по точкам, без обещания времени или пути пешком.
- Кнопка вендора зависит от успешной инициализации → исходный `mapUrl` доступен в HTML-fallback без JS и при ошибке.
- Пример с длинным названием переносит действия → сохранять реальный H1, доступные области нажатия и проверять 320/390 px, увеличенный текст и клавиатуру.

## Migration Plan

1. Владелец рассматривает proposal, specs, макет и скриншоты в PR. После явного разрешения реализации сохранить ссылку на коммит согласованных артефактов в #756.
2. Перенести выбранный вид в публичную HTML-карточку, реализовать preview и selector соседей, проверить сценарии и действующие контракты.
3. Дополнить ADR-028 описанием detail-preview и его отличий от общей карты; обновить дизайн-гайд только устойчивыми правилами страницы. Новый ADR для использования действующего runtime не требуется.
4. После реализации и приёмки синхронизировать основные specs и архивировать change. Для PR предложения архивирование преждевременно.
5. Откат основной реализации возвращает её коммит/PR вместе со specs и документацией; миграция контента не требуется.

Обязательная production-приёмка не предлагается: целевой результат проверяется на локальной сборке и визуальном ревью владельца. Публикация этого предложения использует `Refs #756`; завершённая реализация закрывает issue после выполнения критериев.
