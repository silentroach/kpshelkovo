# Design

## Context

Мотивация и согласованный объём описаны в [proposal.md](proposal.md). Технические решения ниже предложены для согласования этого change; согласование исследовательских вопросов само по себе не разрешает реализацию.

Проверенное состояние ветки:

- `/map/` монтирует `PlaceMap.svelte`, который получает `/map/data/places.json`, создаёт карту через общий runtime, добавляет контуры мест и кластеры маркеров. Существующий `?h=<slug>` выделяет место на пять секунд. Обработчик resize сейчас повторно вписывает все места после окончания выделения — это нужно учитывать для сохранения камеры участка.
- `lib/search/client.ts` получает документы Pagefind из HTML-индекса. `normalizeUrl` сохраняет только `h` и подходящий heading anchor. `SearchDialog.svelte` принимает общий `SearchClient`, использует готовые `SearchResult`, суммарное число результатов и увеличение лимита для догрузки.
- Astro-коллекции, явные mapper-ы и статические JSON-маршруты уже используются для мест. Низкоуровневая проверка Polygon/MultiPolygon есть в `lib/places/raw-geometry-schema.ts`; публичное представление мест содержит собственную sidecar-геометрию и не подходит для редакционной записи участка.
- В `docs/research/parcel-map/` сохранены исходные контуры в EPSG:3857, генпланы, основания двух подтверждённых соответствий, демо и `yandex-display.yaml`. Исследовательский снимок генпланов не содержит статусов, признаков и цен: их предстоит получить отдельно. Проверенный набор демо — 1588 нынешних контуров для 1589 обозначений; это контроль конкретного снимка, а не постоянное требование.
- `ops/nginx/kpshelkovo-online.conf` уже обслуживает `/map/data/` как статические данные с `try_files`, коротким кешированием и общими security headers.

Основания архитектуры:

- [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md) — Raw DTO → domain model → Public DTO.
- [ADR-025](../../../docs/decisions/025-static-full-text-search-with-pagefind.md) — Pagefind для содержательных HTML-страниц.
- [ADR-028](../../../docs/decisions/028-markdown-first-places-map.md) — места, их видимость и общая карта.
- [ADR-039](../../../docs/decisions/039-shared-yandex-maps-runtime-and-preview.md) — общее подключение Яндекс Карт и владение renderer-ами.
- [ADR-011](../../../docs/decisions/011-public-surface-registry.md) — публикация и обнаружение данных.
- [Дизайн-гайд](../../../docs/design/design-code-shelkovo.md) — семантические цвета, доступность действий и штатный интерфейс карты.

## Goals / Non-Goals

**Goals:**

- Один редакционный набор обеспечивает карту, точный поиск и повторное обновление, с раздельными представлениями для каждого потребителя.
- Работающий сайт использует статические ресурсы; сетевое получение первоисточников относится к локальной процедуре обновления.
- Проверенные правила идентичности и цены исполняются одинаково при первом наполнении и следующих запусках.

**Non-Goals:**

- Универсальный GIS-редактор, движок пространственного сопоставления и общий renderer всех карт сайта.
- Замена Pagefind, поисковый сервер, отдельный UI поиска участков и массовые HTML-страницы ради индексирования.
- Перенос редакционной модели мест на формат участков или расширение общего графа упоминаний участками.

## Decisions

### 1. Отдельный домен участков и Markdown-коллекция

Создать `apps/www/src/data/parcels/{shr,shv,shf,shp}/<основной-короткий-номер>.md`; номер в имени файла записывается в нижнем регистре. Например, `shr/l43.md` хранит нынешний участок с основным `SHR-L43` и алиасом `SHR-L44`.

Raw frontmatter:

- `code`, `aliases` — полные обозначения; часть и короткий номер выводятся из основного кода. Путь проверяется на соответствие ему.
- `cadastral_number`, `geometry` — нынешний кадастровый номер и GeoJSON Geometry Polygon/MultiPolygon в WGS84, пары `[longitude, latitude]`. Вершины переводятся из исходной CRS без упрощения и поправки отображения.
- `area_m2` — площадь НСПД, если она дана источником.
- `status` — `available`, `reserved`, `sold`, `unavailable`. При первичной неоднозначности без прежнего подтверждённого значения поле отсутствует; это отсутствие знания, а не пятый статус.
- `features` — значения закрытого словаря; `price_history` — упорядоченные наблюдения `{ on: YYYY-MM-DD, price: число }` по согласованному формату.

Markdown-тело хранится как редакционный текст. Обновление сохраняет его дословно, без перерендеринга и автоматического объединения заметок разных записей. Пока публичной карточки нет, тело не рендерится и не участвует в публичном графе упоминаний.

В `lib/parcels/` разместить raw-схемы, отдельные readonly domain types, mapper, loader, обновление и публичные adapters. Коллекция Astro читает только Markdown-файлы участков. Dataset проверяет уникальность кадастрового номера, основных кодов и алиасов во всём наборе. Обычные проверки координат и формы полей остаются в Zod, а не дублируются в specs. Общую проверку Polygon/MultiPolygon извлечь из схемы мест в app-owned модуль только в необходимом для двух потребителей объёме; оболочка приблизительного контура места остаётся у places.

**Выбор:** отдельная коллекция сохраняет различие между нынешним участком и публичным местом с карточкой. Sidecar как у places противоречил бы выбранному владельцем хранению геометрии во frontmatter; смешение участков с places изменило бы их маршруты, видимость, кластеры и граф упоминаний.

### 2. Рабочие снимки и основания связей отделены от записей

Рабочие данные обновления хранить в `apps/www/src/data/parcel-sources/`:

- `genplans/<part>.json` — проверенные нужные поля записей каждой части, исходные обозначения, кадастровые строки, URL и время получения.
- `nspd.ndjson` — исходные геометрии EPSG:3857, кадастровые номера, ID и площадь при наличии; `nspd.json` — URL, время получения, CRS, область и сведения о проверке ответа.
- `matches.yaml` — подтверждённые соответствия с полными кодами, нынешним кадастровым номером, исходными кадастровыми ссылками на момент подтверждения, основанием и явно выбранным основным кодом, когда он необходим.

Эти файлы не публикуются как runtime-данные. Старые версии остаются в Git, отдельный датированный архив всех выгрузок не нужен. Из генпланов сохраняются `id`, кадастровая ссылка, `status`, `location`, `objectprice`; сведения о собственниках, акциях, вторичной продаже, изображения и CSS меток для этого обновления не нужны.

URL и самостоятельные даты источников хранятся в снимках, с которыми запись связывается по своим кодам и кадастровому номеру. Повторение времени выгрузки в каждом Markdown-файле создало бы массовый diff без изменения сведений. Метаданные снимков описывают входы обновления; сохранение старого поля при конфликте отмечается в отчёте и не считается новым подтверждением этого поля. Для исследовательского кадастра переносится известная дата `capturedOn`; время сохранения файла `savedAt` не выдаётся за точное время сетевого запроса.

Существующие подтверждения из `capture.json` переносятся вместе с основаниями. Для L43/L44 фиксируется основной L43; для V43 Фореста — явная связь с нынешним номером, без догадки по площади. Если исходная кадастровая ссылка изменяется и противоречит основанию ручной связи, скрипт сообщает конфликт, а не применяет старое подтверждение поверх нового факта. Простое изменение геометрии того же кадастрового номера связь не отменяет.

Для объединённого участка подтверждение того, что цена конкретной исходной записи относится ко всему нынешнему контуру, при необходимости хранится здесь же как `price_source_code` и отдельное `price_evidence`. Пока такого основания нет, цена старых частей не используется. Подтверждение привязано к кадастровой идентичности и исходной связи; исчезновение других алиасов само по себе не превращает оставшуюся цену части в цену целого.

**Выбор:** отдельный небольшой реестр нужен для повторяемых исключений и их оснований. Географическое угадывание, скрытые overrides в скрипте и копирование исследовательского `capture.json` целиком в runtime не подходят.

### 3. Один локальный скрипт с двумя режимами

Добавить workspace-команду `pnpm parcels:update`, делегирующую app-owned `apps/www/scripts/parcels/update.ts`. Скрипт запускается штатным Node.js 24+ с поддержкой TypeScript; его типы и тесты включаются в соответствующие проверки приложения. Он использует установленные `yaml`, Zod, стандартные `fetch` и файловый API, без браузерной зависимости для обычного генплана.

Команды из корня workspace:

- `pnpm parcels:update genplans` — получить все четыре генплана, проверить и обновить их снимки и участки с последним принятым кадастром.
- `pnpm parcels:update genplans --snapshot <directory>` — обработать сохранённый набор снимков с его исходными датами для повторной проверки и воспроизведения результата.
- `pnpm parcels:update nspd --snapshot <directory>` — принять отдельно полученные `nspd.ndjson` и `nspd.json`, обновить контуры и соответствия с последними принятыми генпланами.

Пути аргументов разрешаются от каталога запуска. Параметры не меняют семантику режима; отдельного универсального import framework, расписания и автоматической публикации нет.

Получение генплана читает JSON из единственного присваивания `window['houses_data']`, без исполнения JavaScript. Поддерживаемые поля, полный ответ каждого генплана, уникальность кодов и сопоставления проверяются до замены рабочих файлов. Отсутствующее или неоднозначное присваивание, повреждённый JSON, HTML ошибки и неожиданно пустой ответ не принимаются как успешное исчезновение каталога. Сбой одной из четырёх страниц останавливает режим genplans целиком. Реальное опустошение источника требует явного разбора изменившегося формата, а не обхода проверки удаления.

Кадастровый режим не автоматизирует обход отказа доступа НСПД. Краткая инструкция `docs/parcel-updates.md` описывает проверенный браузерный запрос, получение снимка, проверку HTTP-ответа, CRS и области охвата. Повторная выгрузка использует сохранённую область; её изменение явно отражается в метаданных и отчёте. До принятия снимка проверяются отсутствие обрезанного ответа и покрытие запрошенной области; при сомнении сравниваются меньшие области. Это проверка пригодности нового снимка для удаления, а не обещание полноты всех номеров застройщика.

Обработка проходит три обычных шага: прочитать и проверить входы; вычислить новые записи и отчёт в памяти; записать только изменившиеся файлы. Ошибки формата обнаруживаются до записей и удалений. Нерешённые соответствия и неоднозначные известные сведения — отдельный результат обработки, а не ошибка формата; они не мешают однозначным изменениям. Каждый файл заменяется через временный файл и rename; удаления идут после успешной записи новых файлов. Скрипт завершает работу ошибкой при отказе получения, валидации или записи. Общей файловой транзакции нет: после прерывания записи проверяют частичный diff и восстанавливают согласованный набор перед повтором, как описано в инструкции. Публикацию завершает обычное Git-ревью.

**Выбор:** один CLI разделяет приобретение источника и общую обработку, сохраняя независимые режимы. Агент нужен при изменении источника или для редакционного решения, но не для регулярного разбора поддерживаемого формата.

### 4. Явное сопоставление сведений источника

Канонизация исходных номеров сохраняет подтверждённые замены кириллических `А` и `К` на латинские `A` и `K`; исходное написание остаётся в снимке. Это правило импорта, а не дополнительные варианты пользовательского поиска. Необычные новые обозначения требуют явной поддержки.

Статусы:

- «Свободен» → `available`.
- «Забронирован» → `reserved`.
- «Продан» → `sold`.
- «Снят с продажи», «Без документов», «Неразобранное», «Закрыто и не реализовано» → `unavailable`.

Последние три формулировки подтверждены renderer-ом источника в исследовании. Любое другое значение останавливает обновление.

Закрытое сопоставление `location`:

- «луговой» → `meadow`.
- «деревья на участке», «с лесными деревьями» → `trees`.
- «лесной участок» → `forest_plot`.
- «примыкает к лесу» → `forest_border`.
- «с видом на лес» → `forest_view`.
- «с выходом в лес» → `forest_access`.
- «с выходом к реке» → `river_access`.
- «с видом на лес у реки» → `forest_view`, `near_river`.
- «с выходом в лес и к реке» → `forest_access`, `river_access`.
- «у леса и реки» → `near_forest`, `near_river`.
- «с пляжем» → `beach`.
- «с прудом» → `pond`.
- «рядом с парком» → `near_park`.
- «в лесном парке» → `forest_park`.

Поддержанные формулировки сопоставляются целиком после удаления внешних пробелов. Неизвестная строка не разбирается по знакомым словам. Объединённый список признаков сортируется в одном порядке без дублей.

`objectprice` нормализуется в полную сумму рублей на raw-границе. Дата `on` выводится из времени получения соответствующего генплана по московской календарной дате. Кадастровый запуск не датирует старую цену сегодняшним днём: он использует дату принятого генплана. Повтор того же наблюдения и той же последней цены не увеличивает историю; несколько разных наблюдений в один день допустимы и сохраняют порядок. Снимок, более старый, чем уже принятый снимок этого источника, не принимается обычным обновлением; откат выполняется через Git.

При конфликте текущих статусов новая цена не добавляется на основании сохранённого прежнего статуса. Для добавления нужны согласованное текущее состояние продажи и подтверждённая цена целого. Накопленная история сохраняется по [parcel-records](specs/parcel-records/spec.md).

### 5. Обновление записей следует кадастровой идентичности

Сначала построить кандидатов из прямых и действующих подтверждённых связей, затем сгруппировать их по нынешнему кадастровому номеру и сопоставить с принятыми Markdown-записями. Один контур не дублируется под несколькими кодами. Порядок входов не определяет выбор основной записи.

- Для того же участка сохраняются основной код, редакционное тело и история, пока основной код присутствует в источнике.
- Если основной код исчез, оставшиеся подтверждённые обозначения выбираются в стабильном порядке по полному коду; первое становится основным, файл переименовывается. Алиасы, которых больше нет в генплане, удаляются.
- При объединении с сохранившимся кадастровым номером сохраняются редакционные сведения именно его записи. Заметки и цены присоединённой части не смешиваются автоматически со сведениями целого; её версия остаётся в Git, а удаление видно в отчёте.
- Для нового кадастрового номера объединения `matches.yaml` задаёт выбранную основную исходную запись. Без выбора группа остаётся нерешённой; исчезнувшие из принятого кадастра старые записи удаляются по согласованному правилу. После явного выбора сохранённое редакционное содержимое можно восстановить из предшествующей версии Git перед повторной обработкой.
- При подтверждённом разделении создаются новые записи с новыми соответствиями без специального переноса старых заметок и истории. Простая смена кадастровой строки не служит доказательством разделения или объединения.
- Если отсутствуют все обозначения или соответствующий контур, удаляется весь файл. Снимки и подтверждения не поддерживают «временно действующую» старую геометрию.

Сравнение геометрии производится по структуре принятых координат. Отчёт сообщает об изменении геометрических данных; перестановка вершин не объявляется доказанным изменением границы на местности. Топологическое заключение и пространственное угадывание не нужны для применения подтверждённого снимка.

Отчёт в stdout содержит даты источников и группы: добавлены, удалены, переименованы, изменена геометрия, изменены сведения, не сопоставлены, конфликтуют. Для спорного поля указываются код, исходные значения и сохранённое значение. Вместе с обычным Git diff этого достаточно для проверки; постоянный отдельный формат отчётной базы не вводится.

### 6. Два компактных публичных представления

Оба представления строятся из одного dataset через отдельные adapters и проверяются собственными Zod-схемами:

- `/map/data/parcels.json` — `{ parcels: [...] }`, где запись содержит `code`, `aliases`, `part`, исходную WGS84 `geometry` и производные `labelCoordinates`. Клиент получает настройку отображения отдельно из конфигурации приложения. Кадастровые номера, площади, статус, признаки, история, заметки и основания связей не нужны renderer-у первого этапа и в payload не попадают.
- `/map/data/parcel-search.json` — `{ parcels: [...] }` с `code`, `aliases`, `part`; геометрия и коммерческие сведения отсутствуют. Это внутренний поисковый build asset с точными обозначениями, а не новая полнотекстовая база.

JSON сериализуется компактно через существующий `createJsonResponse`. Оба маршрута строятся Astro статически. Runtime не импортирует raw dataset в клиентский bundle и не обращается к НСПД или генпланам.

Геометрический feed регистрируется в существующем slice раздела «Карта» с cache class `data`; ссылка и объяснение добавляются в `/map/index.md`. Поисковый словарь намеренно остаётся вне discovery по аналогии с внутренним индексом Pagefind. Корневой `llms.txt` кратко указывает возможность перехода по полному коду; отдельный llms-файл, публичный каталог всех номеров и карточки участков не создаются. Markdown генерируется существующим AST API.

Поддерживаемый публичный URL перехода — `/map/?p=<полный-код>`. Он относится к карте, а не создаёт новый HTML-route. Существующие count, ItemList и Markdown-список мест продолжают описывать места; участок не становится скрытым или видимым `Place`.

**Выбор:** объединение геометрии со словарём заставило бы поиск загружать контуры. Встраивание словаря в каждую страницу увеличило бы начальный HTML; искусственные карточки расширили бы продуктовый объём. Два статических ресурса дают необходимое разделение без сервиса.

### 7. Точный поиск компонуется с Pagefind через текущий SearchClient

Добавить app-owned `lib/search/site-client.ts`, использующий существующий Pagefind-клиент и узкий поиск номеров из `lib/parcels/`. `SearchDialog` получает этот клиент по умолчанию; его семантика диалога, клавиатурная навигация, plain-text `matchContext` и догрузка используются повторно.

Поток:

1. Обрезать внешние пробелы и привести регистр для сравнения номера. Только целый полный код вида `SHR-L43` либо целый короткий номер вида `L43` запускает загрузку словаря. Произвольный текст и одни цифры идут только в Pagefind.
2. Успешный fetch словаря совместно используется в текущем документе. Отклонённый promise сбрасывается для повтора; до номерного запроса словарь не загружается, даже при открытом поиске.
3. Сопоставить полные и короткие основные номера и алиасы точным равенством. Дедуплицировать по основному коду; несколько участков упорядочить по полному коду. Строка показывает основной код, полное название части Шелково и, при совпадении алиаса, пояснение `также <полный-алиас>`.
4. Сформировать обычный `SearchResult` с прямой ссылкой через helper участка, без `h`, excerpt HTML и sub-results. Эти результаты не проходят `normalizeUrl` Pagefind, поэтому существующий адаптер текстовых ссылок не приходится расширять произвольными параметрами.
5. Добавить текущую порцию Pagefind после точных результатов. Общий лимит применяется к объединению; лимит Pagefind уменьшается на число точных совпадений, с учётом существующего минимального лимита клиента. `total` учитывает обе группы, при догрузке точные совпадения не дублируются. Проверка актуальности запроса охватывает оба асинхронных источника, включая быстрые смены запроса и повторное открытие диалога.

Отказ словаря при номерном запросе проходит через существующую ошибку данных поиска с локальным повтором; он не превращается в нулевое совпадение. Обычные текстовые запросы словарь не затрагивают. Изменять веса, stemming, корпус HTML и `search_aliases` ради номеров не требуется; полезность объединённой выдачи всё равно проверяется вручную до/после по `site-search`.

**Выбор:** Pagefind остаётся владельцем полнотекстового поиска. Его custom records потребовали бы отдельного build pipeline и контроля stemming/точности/URL, а скрытые HTML-записи расходятся с ADR-025. Для точного равенства небольшого числа обозначений достаточно линейного прохода компактного словаря. Долговечное дополнение ADR-025 и отличие модели от ADR-028 фиксируются одним новым ADR в существующей серии при реализации; точные пути и алгоритмы остаются здесь.

### 8. Слой использует уже созданную общую карту

Добавить узкий модуль `components/places/parcel-layer.ts`, которому `PlaceMap.svelte` передаёт готовый экземпляр карты, SDK и настройки. Модуль владеет features, подписями и временным выбором участков; Svelte-компонент владеет переключателем, загрузкой, сообщением ошибки и жизненным циклом страницы. Общий runtime не получает доменных знаний.

Переключатель слоя — доступный checkbox в компактном overlay под header, вне штатных действий Яндекса. Ручное включение загружает payload, добавляет слой и сохраняет текущую камеру. Выключение снимает features, подписи и таймер выбора, сохраняя загруженные данные до ухода со страницы; повторное включение не требует нового запроса. При выключении во время fetch завершившийся запрос не включает слой обратно.

Обычные контуры оформляются одинаково через существующие нейтральные tokens; выбранный контур получает янтарный акцент. Контуры располагаются ниже маркеров мест, чтобы не перехватывать их действия. Подписи — HTML-кнопки с основным коротким номером и доступным именем по полному коду. По уточнению владельца от 23 сентября порог подписей — zoom 17 (примерно вдвое ближе исходного порога 16); при меньшем масштабе подписи убираются также из клавиатурной навигации. При приближении создавать подписи для видимой области, чтобы не добавлять весь каталог в Tab-порядок. Точка подписи вычисляется как центр bounds исходного контура, как в проверенном демо.

Выбор указателем или клавиатурой меняет только выделение и простую текстовую подпись полных кодов с `aria-live="polite"`. Повторный выбор перезапускает пятисекундный таймер; выбор другого участка снимает предыдущий. Завершение выбора не создаёт переход, панель сведений или возврат камеры. Кнопки поддерживают Enter/Space и видимый фокус; reduced motion отключает анимацию камеры. Шрифты используют действующий Font Budget.

Cleanup снимает listeners и таймеры, освобождает features и DOM-подписи. Асинхронное завершение после уничтожения компонента ничего не монтирует. Это расширяет существующий `onMount` с синхронным cleanup, не вводя второй экземпляр Яндекс Карты.

### 9. Поправка применяется только при отображении

Перенести `docs/research/parcel-map/yandex-display.yaml` в `apps/www/src/config/parcel-map.yaml` с сохранением `offset_east_m: 5.2`, `offset_north_m: 3.3`. Демо переключить на ту же рабочую настройку, чтобы не оставить две расходящиеся копии.

Применять проверенный `createDisplayOffset` из демо к WGS84-позициям перед передачей SDK: равномерный сдвиг в Mercator, метры на земле на средней широте исходного охвата слоя. Использовать одну функцию для всех вершин, подписей и bounds фокуса. Каждый результат считается от исходной геометрии; повторный render не сдвигает уже сдвинутые координаты. Исходные снимки, Markdown-геометрия, площадь и геометрический feed остаются без поправки. Публичные controls подбора не добавляются; форма остаётся исследовательским инструментом, настройка меняется через YAML.

**Выбор:** произвольная подгонка вершин или запись поправки в данные утратила бы различие между кадастром и положением на подложке. Единственный конфиг сохраняет принятое владельцем положение независимо от обновления источников.

### 10. Ссылка участка имеет собственный параметр и жизненный цикл

Использовать `p`, не перегружая `h`. Helper принимает только полный основной код либо полный алиас; поисковый результат формирует ссылку с основным кодом. Короткий номер разрешается только через поиск, потому что он может быть неоднозначным между частями.

При прямой ссылке сначала разрешить код через компактный словарь. Неизвестный или синтаксически неверный код удалить без изменения камеры и видимости слоя, не загружая геометрию. Для известного кода получить слой, включить его, вписать смещённый контур с запасом под UI и начать пятисекундное выделение после готовности показа. Ошибка любого запроса сохраняет намерение и параметр для повтора. Если словарь и геометрия разошлись из-за кеша при деплое, отсутствие уже найденной записи в payload считается ошибкой данных с повтором, а не неизвестным кодом.

Удаление `p` выполняется через `history.replaceState` с сохранением history state, остальных параметров и hash; старый таймер не очищает новую ссылку. При редком ручном сочетании `p` и `h` камера в этом переходе управляется `p`; обработка фокуса места не запускается одновременно, сам `h` не удаляется как побочный эффект. Генерируемые ссылки участков `h` не содержат.

Камера остаётся на участке после снятия выделения. В `PlaceMap` нужно отделить завершение таймера от повторного fit всех мест: resize после перехода к участку сохраняет текущую область, а новый экземпляр обычной карты начинает с принятого поведения мест. Повторная Astro-навигация по исходной ссылке создаёт новое действие; отсутствие `p` при новой загрузке означает выключенный слой. В localStorage и URL не сохраняется отдельный флаг включения слоя.

### 11. Приёмка и публикация

Обязательная production-приёмка для завершения этого change не требуется: проверка выполняется на production-сборке с настоящим SDK до перевода общего draft PR в готовность. Владельцу остаются человеческое ревью и merge. Если владелец захочет сделать production-проверку обязательным условием, это нужно согласовать до реализации.

Проверки привязываются к сценариям delta specs:

- Короткие тесты данных и обновления: неоднозначность, удаление, переименование, сохранность заметок/истории, повтор снимка, объединение/разделение, остановка до записи при ошибке формата.
- DOM/клиентские проверки: точное совпадение и алиасы, сохранение текстовой выдачи и догрузки, неизвестный код, retry, cleanup, таймер, reduced motion и совместимость фокуса мест.
- Реальный браузер: сеть до включения слоя, карта и поиск на desktop/mobile, выбранное положение контуров, клавиатура, клиентская навигация, resize, ошибки данных и повтор.
- До изменения поиска сохранить наблюдения для `SHR-L43`, `L43`, `L44`, другого регистра, совпадающего короткого номера разных частей, одних цифр, неизвестного номера и соседних обычных запросов. После изменения повторить их на production-индексе. Список реального контента используется для ручной приёмки, не как постоянная CI-матрица рангов.
- Проверить публичные adapters на отсутствие коммерческих и редакционных полей, стабильные ссылки discovery и успешную доставку JSON. Новые ресурсы same-origin; генпланы и НСПД не становятся браузерными CSP-источниками. Действующего nginx location `/map/data/` достаточно; если при реализации понадобится изменение deploy/CSP, синхронно проверить workflow, nginx и соответствующие инструкции.

## Открытые замечания владельца к приёмке (23 сентября 2026)

Эти пожелания записаны для обсуждения; конкретные решения и реализация по ним ещё не согласованы:

- Сделать границы участков мягче по цвету: нынешний контур выглядит слишком чёрным.
- Пересмотреть управление слоями: вместо checkbox «Участки» рассмотреть кнопку с выпадающим списком слоёв, как в Яндекс Картах.
- Не выводить обозначение выбранного участка рядом с переключателем слоя.
- Сделать подписи номеров внутри границ участков визуально приятнее.
- Обсудить размещение подписи на участке сложной формы: центр прямоугольника охвата может оказаться у границы или вне контура, а подпись — зайти на соседний участок (на снимке владельца пример K29/K30). Выбрать способ удерживать подпись в своём контуре и учитывать соседние подписи без заранее заданного алгоритма.
- Проверить наблюдение о загрузке и вычислении поправки в браузере; обсудить расчёт координат для отображения до их передачи клиенту, сохраняя исходные кадастровые данные без поправки.
- Обсудить более компактный геометрический JSON: плоский массив пар координат вместо вложенных массивов, массив записей вместо обёртки `parcels`, отсутствие `aliases` при пустом списке и устранение повторения `part`, если это окажется выгодно.
- Обсудить дополнительный уровень каталогов для редакционных записей участков: `[area]/[first-letter]/[name].md`, например `shr/l/l43.md` вместо `shr/l43.md`. При решении о переносе сверить пути записей и работу обновлятора; сейчас файлы не перемещать.
- Пересмотреть необходимость `parcel-sources/matches.yaml`: владельцу неясно, зачем нужен отдельный реестр подтверждённых соответствий. Разобрать, какие исключения и основания нельзя восстановить из снимков и записей участков, и нужен ли для них отдельный файл; до решения реестр не удалять.
- Проверить географические функции, написанные для участков: если они пригодны для повторного использования, обсудить перенос в существующий `packages/geo` вместо хранения в приложении. До обсуждения функции не переносить.

## Risks / Trade-offs

- **Неполный набор соответствий:** публикуется только подтверждённая часть; нерешённые номера отражаются в отчёте. В частности, покрытие Парка ниже остальных частей; оно не расширяется по близости меток.
- **Изменение внешнего формата:** проверка всей партии до записи останавливает неподдерживаемый ответ. Поддержка меняется явно по сохранённому источнику.
- **Деструктивные изменения из успешного снимка:** удаления приняты владельцем. Проверка области кадастра, отчёт и Git diff предшествуют публикации; ошибка источника не даёт пустой набор.
- **Сведения старых частей:** наличие основного кода не доказывает принадлежность цены целому. Подтверждение хранится отдельно; конфликт не обнуляет накопленную историю.
- **Много контуров и подписей:** геометрия загружается по требованию, подписи ограничены масштабом и видимой областью. На текущем наборе измеряются bytes, время первого показа и отзывчивость; тайловый сервис или spatial index вводятся только при доказанном ограничении.
- **Кеш ресурсов разных сборок:** точный словарь и payload строятся вместе; краткий кеш и обработка расхождения как ошибки с повтором не позволяют молча принять известный номер за отсутствующий.

## Migration Plan

1. После разрешения реализации сохранить согласованные артефакты в общей ветке и отметить разрешение ссылкой на коммит в родительском issue. Обновить там указатель на change; решения дочерних вопросов остаются историей обсуждения.
2. Подготовить модель и updater; перенести исследовательский кадастр и основания связей в рабочие пути с исходными датами. Получить свежий коммерческий срез генпланов и сформировать Markdown-набор. Его отличия от принятого снимка явно проверить, а не требовать прежнее количество файлов независимо от источника.
3. Перенести поправку, подключить статические представления, слой и точный поиск. Создать один ADR в следующем свободном номере серии об отдельном домене и дополнении Pagefind, актуализировать ссылки из исследования и эксплуатационную инструкцию.
4. Выполнить проверки и ревью всего diff общей ветки; синхронизировать основные specs и архивировать change. Обновить существующий PR результатами и оставшейся ручной приёмкой. Карта решений — родительская инициатива, PR сохраняет `Refs` на неё; её закрытие не подменяется завершением кода одного этапа.
5. Откат выполняется возвратом согласованного набора коммитов и повторной статической сборкой. Для отдельного неудачного обновления вернуть вместе рабочие снимки, соответствия и Markdown-записи; поправку менять только если она входила в это обновление. Серверное состояние или внешняя база для отката не нужны.
