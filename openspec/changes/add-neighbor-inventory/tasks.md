# Tasks

План подготовлен для согласования; разрешение реализации фиксируется отдельным шагом. Требования — в [delta specs](/openspec/changes/add-neighbor-inventory/specs/neighbor-inventory/spec.md), подход и контентное уточнение тестовой карточки — в [design](/openspec/changes/add-neighbor-inventory/design.md).

## 1. Общие контакты и модель данных

- [ ] 1.1 Выделить общие схему, raw/readonly-доменные типы, преобразование и форматирование способов связи внутри `apps/www`; подключить «Сарафан» и инвентарь к одним определениям. Проверить прежние телефонные случаи, Telegram URL и непустой набор способов связи адресными тестами; существующие тесты контактов должны проходить.
- [ ] 1.2 Добавить коллекции владельцев, видов и предложений, их Zod-схемы, доменные типы, mapper и loader. Проверить fixtures с несколькими владельцами/предложениями, тремя вариантами `price`, алиасом участка, неизвестными связями и снятием предложения; ошибки должны указывать исходник, а общие данные владельца обновляться во всех предложениях.
- [ ] 1.3 Добавить группы, маршрутные helpers, сортировку и отбор оглавлений. Проверить маршруты всех трёх уровней, стабильность якоря при редакционных изменениях, скрытие пустых видов/групп в оглавлениях и сохранение их страниц. Описать модель, ручное редактирование и снятие в локальных правилах `apps/www/src/data/inventory/AGENTS.md`; сверить примеры с реальной схемой.

## 2. Страницы каталога и фотографии

Проверить два отдельно отрендеренных body с одинаковыми заголовками, TOC, сносками и ссылками, в том числе encoded fragment и ссылкой на внешний контейнер предложения; проверить прежний результат без опции. Обновить README пакета и выполнить его адресные тесты вместе с тестами app-wrapper; сохранить отсутствие побочных эффектов при импорте.
- [ ] 2.2 Реализовать HTML трёх уровней, breadcrumbs, полный вывод предложений, три условия цены, редакционные body с устойчивыми префиксами и пустые состояния. Добавить приглашение только на главную, сохранив состав главного меню. Проверить рендер по образцу `contact-page.test.ts`: порядок и принадлежность предложений, ручные ссылки, контакты, выбранный участок, актуальность якорей и сохранение body после снятия последнего предложения.
- [ ] 2.3 Адаптировать общий `ContactMethods.astro` к нескольким вызовам на странице. Проверить уникальность ID и связи доступных заголовков у разных предложений, включая одного владельца; повторно проверить карточку «Сарафана» и её контактные действия.
- [ ] 2.4 Добавить необязательные фото предложения, размеры, `alt`, подписи и переход к подготовленной копии через существующий image pipeline. Проверить отсутствие фото и несколько фото у соседних предложений без смешения подписей; описать подготовку `ukogo/` в storage runbook и `public-media-publisher`, включая новые URL при замене. Сверить разрешённые источники с CSP и выполнить `pnpm skills:check` после правки skill.

## 3. Markdown, поиск и доставка

- [ ] 3.1 Построить Markdown companions всех уровней через AST API, подключить публичный срез, общий каталог ресурсов и корневой `/llms.txt`. Проверить стабильные URL, три варианта цены, контакты, участок, ручные ссылки, фотографии и пустой вид в Markdown, а также независимость сносок одинакового имени и сохранение ссылок на локальные разделы разных body. Не создавать полные snapshots документов или отдельный JSON API.
- [ ] 3.2 До изменения корпуса зафиксировать реальную выдачу по затронутым и контрольным запросам. Подключить к внутреннему поиску только виды с предложениями, а в sitemap — HTML всех уровней; проверить исчезновение и возвращение вида в индексе, неизменность внешнего режима пустой страницы и отсутствие дублирующих оглавлений. Выполнить `pnpm --filter @shelkovo/www test:search-quality` и ручное сравнение после на актуальной production-сборке по `site-search`; сохранить краткие результаты для PR.
- [ ] 3.3 Подключить HTML/Markdown-доставку `/ukogo/` в nginx по образцу «Сарафана». Выполнить `nginx -t` и разовые локальные HTTP-проверки настоящим nginx для трёх уровней, GET/HEAD, Accept negotiation, direct `.md` и отсутствующего маршрута; проверить MIME, обе оси `Vary`, ссылки alternate/describedby, robots и security headers. Сверить совместимость с существующим deploy workflow; при изменении самого потока обновить workflow вместе с конфигом.

## 4. Стартовое наполнение и общая приёмка

- [ ] 4.1 Уточнить у владельца участок и контакт демонстрационного владельца, добавить одну явно помеченную тестовую карточку с записью вида. Проверить обычной схемой, в HTML и Markdown; сохранить тестовый характер в видимом тексте. Остальные комбинации оставить в fixtures. Для фото, если оно включено в пример, выполнить публикацию и проверку media-origin по runbook. Новые русские тексты проверить по `humanizer-ru`.
- [ ] 4.2 Выполнить `pnpm lint`, `pnpm typecheck`, `pnpm test`, production-сборку и `pnpm openspec:validate`. Сборку из `test:search-quality` использовать как уже выполненную, если входы не менялись. При изменении клиентских импортов, загрузки или сборки сравнить клиентские бандлы до/после и сохранить актуальные отчёты по инструкции проекта.
- [ ] 4.3 Провести браузерную приёмку на телефоне и широком экране: прямые переходы главная/группа/вид, читаемые полные предложения, цены и фото, контактные действия, переход к выбранному участку, старый снятый якорь и пустой вид. Проверить клавиатуру, доступные имена, отсутствие горизонтального переполнения и регрессию «Сарафана». Штатный dev-стек запускать только с разрешения владельца; реальную карту проверять в штатной среде. Зафиксировать результат и закрыть свои браузерные сессии.
- [ ] 4.4 Перед завершением реализации вызвать `reviewer` для всего diff с точной базой, требованиями и актуальными проверками, разобрать замечания и упрощения. После правок провести адресный повтор; при недоступности reviewer выполнить самопроверку и `ponytail-review` с явным указанием fallback. Убедиться, что каждый сценарий change покрыт актуальной проверкой.

## Workflow follow-up

- После выполнения задач синхронизировать основные specs и архивировать change в той же ветке штатными workflows.
- После sync/archive выполнить `pnpm openspec:validate` и адресный повтор reviewer по документации; сохранить совокупный охват всего итогового diff.
- Обновить PR результатами реализации и проверок, оставшейся ручной приёмкой и ссылкой на архив; человеческое ревью и merge выполняет владелец.
