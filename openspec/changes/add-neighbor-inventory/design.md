# Design

## Context

Мотивация и объём — в [proposal](/openspec/changes/add-neighbor-inventory/proposal.md). Первая локальная реализация прошла приёмку с полными предложениями на странице вида. После осмотра владелец согласовал компактный список и отдельные подробные страницы: на телефоне одно текстовое предложение занимало 1336 px, а контакт находился ниже первого экрана. Этот design отражает пересмотренный вариант. Исходные опоры проекта:

- [Коллекции](/apps/www/src/content.config.ts) используют Markdown loaders и `rawMarkdownBody`. У «Сарафана» есть раздельные [raw-схема](/apps/www/src/lib/contacts/raw-schema.ts), [типы](/apps/www/src/lib/contacts/types.ts), [mapper](/apps/www/src/lib/contacts/mapper.ts), [loader](/apps/www/src/lib/contacts/load.ts), [маршруты](/apps/www/src/lib/contacts/routes.ts) и [публичный срез](/apps/www/src/lib/contacts/public-surface.ts).
- [ContactMethods](/apps/www/src/components/contacts/ContactMethods.astro) принимает контакты, необязательное местоположение и ID доступного заголовка. Его используют «Сарафан» и подробные предложения инвентаря; он подходит для общего блока контактов владельца.
- [Загрузчик участков](/apps/www/src/lib/parcels/load.ts) уже строит `byCode` для основных кодов и алиасов. Новому разделу нужна только ссылка выбора участка, не собственная карта или геометрия.
- [Фотографии новостей](/apps/www/src/lib/news/raw-schema.ts) используют `url`, размеры, `alt` и необязательную подпись. [NewsPhotos](/apps/www/src/components/news/NewsPhotos.astro) показывает адаптивные изображения со ссылкой на подготовленную копию; его типы и схема URL принадлежат новостям.
- [Nginx](/ops/nginx/kpshelkovo-online.conf) явно объявляет HTML/Markdown для корня, категорий и карточек «Сарафана» и отдельно перечисляет разделы обычных `.md`. Реестр не генерирует эти locations.

Основания: [ADR-013](/docs/decisions/013-raw-domain-public-data-boundary.md), [ADR-018](/docs/decisions/018-markdown-first-useful-contacts.md), [ADR-008](/docs/decisions/008-markdown-ast-generation.md), [ADR-009](/docs/decisions/009-markdown-accept-negotiation.md), [ADR-011](/docs/decisions/011-public-surface-registry.md), [ADR-021](/docs/decisions/021-public-section-files-in-s3.md), [ADR-023](/docs/decisions/023-news-images-in-public-s3.md), [ADR-025](/docs/decisions/025-static-full-text-search-with-pagefind.md).

## Goals / Non-Goals

**Goals:**

- Собрать статический каталог на действующих коллекциях и app-level helpers, с единым доменным снимком для HTML, Markdown, поиска и sitemap.
- Переиспользовать способы связи, сохранив поведение действующих карточек «Сарафана».
- Разделить идентичность владельца, вида и предложения; обновлять общие данные в одном месте.
- Дать владельцу устойчивую страницу всего его инвентаря на тех же данных, включая периоды без предложений.

**Non-Goals:**

- Универсальная движковая модель каталогов, отдельный backend, собственный поиск инвентаря и новый механизм публикации изображений.
- Общий JSON API инвентаря, vCard владельцев и интеграция владельцев с профилями `people`: для согласованного каталога достаточно HTML и Markdown.
- Перегруппировка главного меню. Состав навигации вернётся в обсуждение после наполнения.

## Decisions

### 1. Три независимые Markdown-коллекции

Использовать `inventoryOwners`, `inventoryKinds`, `inventoryOffers` в `content.config.ts`, с исходниками под `apps/www/src/data/inventory/owners/`, `kinds/`, `offers/`. Файлы лежат плоско; имя без `.md` служит устойчивым ID. ID владельца, вида и предложения входят в их публичные URL.

Редактор назначает ID владельца вручную: первая буква имени и фамилия в строчной латинице, без префикса посёлка. При коллизии добавляет следующие буквы имени; если этого недостаточно, выбирает свободный числовой суффикс `-2`, `-3` и далее. Ранее назначенные ID сохраняются, в том числе при исправлении имени или смене участка. Это редакционное правило из [локального AGENTS.md](/apps/www/src/data/inventory/AGENTS.md), без автоматического генератора ID и проверки транслитерации по имени в build. Существующие проверки формата, уникальности и ссылок остаются обязательными.

- Владелец: `name`, `parcel`, `contacts`.
- Вид: `title`, `group`, свободный body. Название обозначает одну вещь; английский slug использует соответствующее единственное число. Для слов без обычной формы единственного числа сохраняется естественная форма языка, например «Ножницы» и `scissors`. Форму выбирает редактор; автоматическое преобразование множественного числа не требуется.
- Предложение: `title`, обязательное краткое plain-text `summary`, `owner`, `kind`, необязательные `price` и `photos`, свободный body для характеристик, комплекта и условий. Модель включается в `title`; в карточке не нужно повторять название вида из H1. `summary` редактор пишет отдельно, без автоматической обрезки body; главное условие комплекта остаётся видно до перехода к подробностям.
- Цена на raw-границе — положительная сумма в объекте `{ value, period }`, литерал `0` или отсутствие. В домене — явное readonly-различение указанной цены, бесплатности и договорной цены. Проверять наличие/вариант, а не truthiness; `null` не используется.
- `photos` хранит непустой список при наличии: `url`, положительные размеры, `alt`, необязательная `caption`. Точная проверка полей принадлежит Zod-схеме и адресным тестам.

Новые `raw-schema.ts`, `types.ts`, `mapper.ts`, `load.ts`, `routes.ts`, `view.ts`, `markdown.ts` и `public-surface.ts` принадлежат `apps/www/src/lib/inventory`. Mapper явно переводит raw-данные в домен. Loader собирает индексы и проверяет ссылки на владельца, вид, группу и участок до публикации. Любая существующая запись владельца публикует его страницу, даже без предложений. Добавить владельцу публичные ссылки и доступ через индекс; выборку предложений строить из общего набора по `owner.id`. Не помещать предложения обратно внутрь доменного владельца: предложение уже содержит владельца, и обратная ссылка создала бы цикл.

Альтернатива — вложить предложения в владельцев — затрудняет независимое снятие вещи и редактирование body. Справочник видов в коде был согласован ранее, но заменён владельцем на Markdown ради свободного текста и ссылок. Группа остаётся небольшим справочником: её собственный редакционный body в этой версии не нужен.

### 2. Вложенные публичные URL без дублирования группы в исходнике

Начальные группы: `construction` — «Строительство и ремонт», `garden` — «Сад и участок», `home` — «Дом и уборка», в этом порядке. Название «Строительство и ремонт» совпадает с категорией «Сарафана». `construction` выбран владельцем; `garden` и `home` — технические значения для остальных уже согласованных групп. Их подписи и состав сверяются при наполнении.

Файл вида `kinds/circular-saw.md` с `group: construction` даёт `/ukogo/construction/circular-saw/`; предложение ссылается на него как `kind: circular-saw`. Полная страница предложения `offers/worx-wx530.md` получает адрес `/ukogo/construction/circular-saw/worx-wx530/`. Группа не повторяется в пути файла и в предложениях. После выбора английского slug владелец уточнил правило единственного числа; разовое переименование текущего `circular-saws` описано в Migration Plan.

Владелец получает `/ukogo/owners/<owner-id>/` и companion с `index.md`. Для стартовой записи это `/ukogo/owners/ikalashnikov/`. Сегмент `owners` зарезервирован для этих страниц; отдельный каталог `/ukogo/owners/` не нужен, входом служит имя владельца в карточке вида и в подробностях предложения. Ссылка владельца не зависит от его участка или видов инвентаря. Участок остаётся ссылкой на карту.

`getStaticPaths` строит страницы всех объявленных групп и видов, независимо от числа предложений. Оглавления выбирают только виды с предложениями и показывают их названия без счётчиков; пустая группа остаётся доступной напрямую с переходом в общий каталог. Для равных имён владельцев порядок предложений детерминирован по ID.

Маршрут владельца строит страницу для каждой записи `owners`, включая ещё не использованных владельцев. После снятия последнего предложения сохраняются имя, участок, контакты и сообщение об отсутствии предложений. Удаление записи владельца убирает его HTML и Markdown с обычной 404; оставшиеся ссылки предложений на удалённого владельца по-прежнему останавливают сборку. Отдельная история публикации для этого не вводится.

Якорь компактной карточки — `offer-<offer-id>`. Его ID задаётся контейнеру в списке; название и превью ведут на отдельную страницу предложения, а не на собственный fragment. Полная страница имеет устойчивый адрес по ID предложения; изменение заголовка, цены, summary и контактов не меняет ни URL, ни якорь списка. После удаления предложения обычная ссылка с отсутствующим fragment открывает страницу вида. Отдельная страница перестаёт генерироваться и отвечает обычной 404. Владелец подтвердил такое поведение без истории удалённых объявлений и специального fallback-редиректа.

Владелец выбрал вложенные URL вместо предложенных плоских адресов. Изменение названия сохраняет путь; перенос вида в другую группу меняет URL. Такой перенос после публикации потребует явного решения о сохранении старых ссылок. Автоматическую систему aliases/redirects ради возможных будущих переносов сейчас не вводим.

### 3. Общие способы связи внутри приложения

Выделить из контактов общий модуль `apps/www/src/lib/contact-methods/` с raw-схемой способов связи, raw- и доменными типами, mapper/helper-ами подготовки и форматирования ссылок. Оба раздела должны импортировать эти определения. Владелец инвентаря не становится карточкой «Сарафана» или профилем `people`.

Сохраняются пять существующих способов связи: `phone`, `telegram`, `whatsapp`, `email`, `website`; Telegram — HTTPS-ссылка. Перенести существующую нормализацию телефона, включая неполные и добавочные номера, без изменения контактных действий «Сарафана». Адрес, отзывы, vCard и прочие поля карточки контакта остаются в её собственном домене.

Переиспользовать существующий `ContactMethods.astro`. Вызывающий шаблон инвентаря передаёт ID заголовка на основе предложения или владельца; единственный вызов «Сарафана» сохраняет прежнее доступное имя и назначение блока. На странице владельца способы связи выводятся один раз в шапке. Проверить `aria-labelledby`, уникальность ID и клавиатурные ссылки; защитные проверки повторного использования контактного компонента сохраняются.

`parcel` разрешается через `loadParcelsData().byCode`; представление хранит основной код и ссылку `/map/?p=<canonical-code>`. Для этой связи не требуются ни загрузка карты в каталоге, ни отдельные координаты владельца. Альтернатива копировать контакты или кадастровые сведения в предложения отклонена в исследовании.

### 4. Серверные страницы и редакционный body

Добавить Astro-маршруты `pages/ukogo/index.astro`, `[group]/index.astro`, `[group]/[kind]/index.astro`, `[group]/[kind]/[offer]/index.astro`, `owners/[owner]/index.astro` и соответствующие `index.md.ts`. Общий layout, `Breadcrumbs`, роли заголовков, prose и ссылки следуют [дизайн-гайду](/docs/design/design-code-shelkovo.md) и [page meta](/docs/page-meta.md). Отдельная гидратация каталога не требуется.

Страница вида показывает все предложения компактно, по имени владельца и ID. Карточка содержит модель, цену, ручное summary, имя-ссылку владельца и участок. Способы связи находятся на подробной странице предложения и в шапке владельца; в карточках списка их нет. Название и превью ведут к предложению без отдельной ссылки «Подробнее». При наличии первого фото оно служит небольшим превью с полным кадром; отсутствие фото не оставляет пустого слота. На широком экране фото находится слева, сведения справа; на телефоне компактный верх с фото и моделью дополняется коротким текстом и владельцем. Модель использует `ui-card-title` (20 px, Fira Sans 600), цена под ней — 18 px / 1.5, вес 400, через 8 px. Горизонтальный промежуток между фото и текстом составляет 24 px на телефоне и 32 px от `48rem`. Разделитель есть только между соседними карточками. H1 сохраняет редакционный характер. Цвета, шрифты и главное меню не меняются, анимация не добавляется.

Подробная страница сохраняет полные характеристики, комплект, особые условия, ручные ссылки и все фотографии. Цена, владелец, участок и контакт находятся до длинного body; хлебные крошки ведут назад к виду без дублирующей нижней ссылки. Markdown сохраняет навигационные ссылки в начале документа. Вариант раскрытия полного body прямо в списке рассмотрен и отклонён владельцем в пользу отдельного адреса, удобного для пересылки. Общее напоминание о согласовании дат, передачи и оплаты не выводится ни в карточке, ни в SEO description.

Страница владельца использует его имя в H1 без автоматического склонения. Под заголовком находятся участок и единый блок контактов. Ниже идут только его действующие предложения, сгруппированные по видам; виды отсортированы по русскому алфавиту, предложения внутри вида по названию и ID. Заголовок вида ведёт на общий список этого вида. Переиспользовать компактную карточку с отключённой строкой владельца: имя и участок уже находятся в шапке. Виды имеют H2, модели внутри них H3 с прежней визуальной ролью `ui-card-title`; в общем списке вида модели сохраняют H2. Счётчики, полный body и галереи не добавляются. Контакты не повторяются в карточках. Хлебные крошки владельца ведут к «У кого есть»; страница предложения сохраняет путь через группу и вид, а к владельцу ведёт его имя в сведениях.

Body видов и предложений проходит существующий app-level Markdown pipeline с общим `SiteMentionRegistry`, как в KB. Упоминания раскрываются и валидируются; каталог не подключается как новый источник автоматических backlinks. Обычные ссылки на KB остаются авторскими. Владелец не обязан заполнять body вида, если пояснения пока не нужны.

Уже реализованный `idPrefix` в пакетном renderer и app-wrapper сохраняется: body вида и полной страницы получают устойчивые префиксы `kind-<kind-id>-body-` и `offer-<offer-id>-body-`. Карточки не рендерят полные body. Карта фактических HTML-целей остаётся единственным источником для ссылок companion; общей логике назначения ID не нужен второй slug-алгоритм.

В конце существующего HAST pipeline, до сериализации, собрать карту ID текущего фрагмента и добавить префикс к этим ID. По той же карте обновить ссылки `href="#…"` на собственные цели, ссылки оглавления, heading permalinks, прямые и обратные ссылки сносок и IDREF-атрибуты, включая `aria-describedby`, `aria-labelledby` и `for`. Учитывать percent-encoding fragment. Ссылки на контейнеры предложений, другие страницы и внешние URL, не входящие в карту локальных целей, сохраняются. Без `idPrefix` результат остаётся прежним. Это AST-преобразование, а не правка сериализованного HTML регулярными выражениями.

Проверить два body с одинаковыми заголовками, сносками и локальными ссылками вместе на странице: ID уникальны, каждая ссылка и возврат сноски работают внутри своего body. Простого накопления `reservedIds` между вызовами недостаточно для сносок; объединение всех предложений в один Markdown-документ смешало бы их независимые подписи сносок и разметку контактных компонентов.

Приглашение только на главной, под H1: «Хотите сдать инвентарь в аренду или дать попользоваться бесплатно? Напишите [silentroach](https://t.me/silentroach).» Только ник является ссылкой; HTML использует штатную иконку Telegram, доступное имя сохраняет назначение ссылки. Ссылка также присутствует при пустом каталоге. На группах, видах, страницах владельцев и полных предложениях приглашение не повторяется.

После замечаний владельца вводный текст использует `ui-copy ui-muted`, как в «Сарафане». Перед списком групп на главной расположен именованный `nav` с такими же компактными плашками: 🛠️ «Строительство и ремонт», 🌱 «Сад и участок», 🧹 «Дом и уборка». Навигация и блоки ниже используют один отфильтрованный набор непустых групп; пустой каталог не создаёт навигацию. Плашки ссылаются на существующие `#group-<id>` заголовков с отступом под закреплённую шапку; ссылки заголовков продолжают вести на страницы групп. Под заголовком проходит тонкая линия на ширину блока; текст подчёркивается только при hover/focus. Эмоджи заголовка вынесены в левое поле на широком экране и скрыты на телефоне, как в «Сарафане». Эмоджи декоративные, названия доступны скринридерам. На узком экране плашки переносятся строками. Верхний отступ содержимого составляет 32 px, отступ после навигации и между группами 40 px. В списках видов разделители находятся только между пунктами, без линии под последним или единственным пунктом.

### 5. Фото предложения используют существующую подготовку и media-origin

Фотографии остаются в `photos` предложения. Поддержать `ukogo/<offer-id>/<photo-name>.jpeg` в storage runbook и проектном `public-media-publisher`. Применять действующий JPEG-профиль с полным кадром, ориентацией, без увеличения, длинной стороной до 2560 и quality 90; метаданные, включая GPS, не сохранять. Иной снимок получает другое имя, без перезаписи опубликованных байтов.

Небольшой компонент фотографий инвентаря использует тот же Astro Image Service, что и новости: адаптивные производные, intrinsic-размеры, `alt`, подпись при наличии и обычная ссылка на web-master на полной странице. Превью карточки использует первое фото и ведёт к подробностям; полная галерея не повторяется в списке. `remotePatterns` покрывает все поддержанные пути публикации, а тесты проверяют разные URL производных, не только числа ширин. Типы и URL-ограничение новостей не становятся зависимостью домена инвентаря. Действующая политика позволяет повторно использовать опубликованный файл другого раздела по прежнему URL без копирования.

В схеме проверяется канонический media-origin и поддержанные публикационные пути фотографий, без query/fragment. После снятия предложения объект не удаляется автоматически. Перед реальной публикацией фотографии применяется проверка доставки по runbook. Существующий host уже используется сайтом; CSP сверяется для фактических запросов, а не расширяется заранее.

### 6. Один набор данных для поиска и внешней индексации

`SearchDocument` передаёт полная страница действующего предложения. В поисковое тело входят название вида, модель, summary и полный редакционный body. Контакты, цена, навигация и повторяющиеся подписи не используются как отдельный поисковый текст. Корень, группы, виды и страницы владельцев не передают поисковый документ: они служат оглавлениями. Результат по модели ведёт непосредственно к нужной вещи; скрытые полные тексты не добавляются на страницы списков ради Pagefind.

Все HTML-страницы каталога, владельцев и действующих предложений входят в sitemap, имеют self-canonical и разрешённую внешнюю индексацию. У каталога нет редакционного `updated_at`, поэтому `lastmod` не выдумывается из времени сборки. Снятие предложения убирает его подробную страницу из поиска и sitemap; внешний режим сохранённых страниц вида и владельца не меняется. Удаление записи владельца убирает его страницу из sitemap.

Приёмка релевантности следует [site-search](/.agents/skills/site-search/SKILL.md): до изменения индекса сохранить наблюдения по запросу вида, модели и соседним запросам; после сборки сравнить реальные результаты, snippets и переходы. Нужные запросы выбираются по тестовому наполнению и фактическому корпусу, без постоянной матрицы названий.

### 7. Markdown и доставка повторяют HTML-страницы

Генераторы используют `@shelkovo/markdown` AST API. Подготовленный редакционный body вставляется через `parseMarkdownFragment`; заголовки, списки, контакты, цены и ссылки строятся через `md`. Целые документы не собираются строковыми шаблонами.

Корень и группы дают такие же оглавления, виды — свой body и краткие карточки со ссылками на полные companions по названию и превью. В краткой карточке остаются цена, имя-ссылка владельца и участок; способов связи в ней нет. Полная страница предложения даёт summary, весь body, цену, имя-ссылку владельца, контакты, участок и все фото с URL, альтернативой и подписью. Companion владельца содержит имя, участок и контакты один раз, затем краткие предложения по видам без повторения сведений шапки. Имена ведут к companion владельца; названия видов и предложений к своим companions. Пустые вид и владелец сообщают об отсутствии предложений и сохраняют общую навигацию. Локальные ссылки редакционного body направляются к scoped-якорям его канонической HTML-страницы по фактической карте renderer; ссылки на карточки списка — к странице вида. Сноски остаются независимыми, обычные ссылки на KB и другие страницы сохраняются; не требуется угадывать slug Markdown-просмотрщика.

Добавить `inventoryPublicSurfaceSlice` по образцу контактов, подключить его в общий реестр, каталог публичных ресурсов и корневой `llms.ts`. Дополнить срез отдельной HTML/Markdown-парой владельца и уточнить назначение этих страниц в discovery. Собственный `llms.txt`, JSON feed и JSON Schema для этого каталога не нужны выбранному объёму.

В nginx сохранить exact-location корня и общий обработчик вложенных путей `ukogo`. Его действующая глубина уже покрывает `/ukogo/owners/<owner>/`, а обработчик `.md` покрывает новый companion; отдельный механизм доставки не требуется. Проверить фактическую выдачу новой пары: MIME, `Vary`, alternate/describedby, кеширование и security headers. Локальная проверка настоящим nginx охватывает GET/HEAD, прямой Markdown, negotiation, пустого владельца и 404 отсутствующей записи; существующие уровни проверяются на совместимость. Это разовая приёмка, не новый постоянный обход сайта в CI.

### 8. Проверки и стартовый пример

Домен проверяется на fixtures: один вид у разных владельцев, несколько вещей одного владельца, три варианта цены, известный алиас и ошибочная ссылка, снятие одного и последнего предложения. Проверки страницы добавляют повторяемые контакты, якоря, ручной body и фотографии. Пример тестирования рендера — [contact-page.test.ts](/apps/www/src/lib/contacts/tests/contact-page.test.ts); для URL карты — [parcel-url.test.ts](/apps/www/src/lib/parcels/tests/parcel-url.test.ts).

По просьбе владельца тестовая карточка заменяется реальным предложением: WORX WX530, Игорь Калашников, `SHR-L43`, Telegram `silentroach`, 500 ₽/сутки, пила с заряженным АКБ 2 А·ч и зарядка по запросу. Магазинное фото модели публикуется в S3 по runbook, помечается как фото модели и подключается только после проверки media-origin. Эти разовые данные запуска не попадают в долговечные specs; остальные комбинации остаются fixtures.

## Risks / Trade-offs

- Общий контактный модуль затрагивает «Сарафан» → сохранить его raw-контракт, телефонные случаи и существующий рендер; проверить обоих потребителей после выделения общего кода.
- Несколько body и блоков контактов на одной странице могут повторить ID → необязательный namespace для всего HTML-фрагмента с обновлением локальных ссылок и IDREF, отдельные подписи сносок в Markdown и явные ID контактов; проверять итоговый DOM и обе версии документа.
- Вложенный URL зависит от группы → явно учитывать сохранение опубликованных адресов при будущем переносе вида.
- Короткий ID владельца может совпасть с другим именем → редактор выбирает свободный вариант, сохраняет уже выданные ID; build проверяет уникальность. Префикс участка не используется, поэтому переезд не меняет ссылку.
- Пустая страница вида остаётся доступной внешним поисковикам → сохранять редакционный текст и явное состояние отсутствия предложений; не объявлять текущую доступность вещи.
- Запись владельца публикуется даже без предложений → создание файла владельца сразу означает публикацию его страницы; это указано в правилах редактора. Удаление последней вещи не удаляет контактные сведения владельца.
- Фото добавляют зависимость сборки от media-origin → хранить подготовленные файлы по стабильным URL, использовать существующие оптимизацию и cache pipeline.
- Вне меню каталог пока обнаруживается по ссылкам и поиску → это согласованная граница первой версии; решение о меню возвращается после наполнения.

## Migration Plan

1. После отдельного разрешения реализовать каталог и проверки в той же ветке. Публичных данных инвентаря для миграции нет; история исследования сохраняется как основание решений.
2. До первой публикации переименовать `owners/igor-kalashnikov.md` в `owners/ikalashnikov.md`, `kinds/circular-saws.md` в `kinds/circular-saw.md`, сменить название на «Циркулярная пила» и обновить `owner`/`kind` реального предложения. Новые адреса предложения и companions получают сегмент `circular-saw`; его собственный ID и медиа-ключ остаются прежними. Обновить рабочие ссылки и примеры; прежние результаты проверок в handoff остаются историей. Для неопубликованных адресов не вводить редиректы.
3. Добавить страницы владельцев, ссылки на них, companions и discovery; проверить пустую запись, удаление последнего предложения и удаление владельца. Политика стабильных ID начинает действовать с назначенных в этой итерации значений.
4. Выполнить приёмку и reviewer. После разрешения владельца завершить change штатными sync/archive workflows; текущая договорённость откладывает эти операции. До реализации и приёмки новые tasks остаются незавершёнными, основные specs не меняются.
5. Deploy использует существующий workflow, который доставляет static build и nginx-конфиг и вызывает `nginx -t` перед reload. Изменение структуры артефактов не требует другого deploy-потока.
6. Откат возвращает реализацию и её конфигурацию вместе. Уже опубликованные фото остаются неизменяемыми; их удаление — отдельное действие по действующему контракту.
