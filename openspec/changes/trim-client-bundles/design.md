# Design

## Context

Мотивация и объём — в [proposal.md](proposal.md). Исследование production и совпадающих локальных артефактов выявило четыре цепочки:

- `editorial-map.ts` → общий `@shelkovo/markdown` → Typograf и YAML. В исследованном чанке 80 778 байт, из которых около 2,2 КБ относятся к самой карте.
- `editorial-map-element.ts` → `EditorialMapDataSchema` → Zod и схемы полигонов. Чанк `raw-polygon-schema` занимает 86 444 байта при повторной проверке уже подготовленной геометрии.
- `opening-hours.ts` → `places/schema.ts` → общий `mentions` → инициализация unified/remark. В чанке 109 968 байт, собственный хвост часов работы и констант — около 881 байта.
- `formatPlaceStatus` из `places/view.ts` → `status/view.ts` → вычисление `CURRENT_STATUS_YEAR` при импорте → Luxon. Отдельный потребитель Luxon в браузере — дата поискового результата.

Новость без карты, мероприятия, фото и вложений загружает 204 129 байт собственного JS, из них 173 919 — цепочка редакционной карты; соответствующие размеры Brotli — 58 619 и 48 632 байта. Кроме того, в её CSS есть `EventWidget`, `MapPreview` и редакционная карта. Эти числа — исходное наблюдение, не будущие бюджеты и не обещание точного результата.

Стек: Astro 7, Vite 8/Rolldown, Svelte 5; Astro выполняет серверную и клиентскую сборки. `astro-compressor` уже создаёт `.br` и `.gz`. Корневая сборка проходит через Turbo, а `apps/www` после сборки копирует сайт в `dist/www`.

Применимые решения:

- [ADR-003](../../../docs/decisions/003-markdown-pipeline-layering.md): общие правила рендера и типографики принадлежат Markdown-пакету.
- [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md): исходные данные, домен и публичные представления имеют отдельные границы.
- [ADR-034](../../../docs/decisions/034-native-css-architecture.md): app-owned стили и владение оформлением компонентами.
- [ADR-039](../../../docs/decisions/039-shared-yandex-maps-runtime-and-preview.md): общий SDK, разные renderer-ы и жизненный цикл карт. Уточнение места подготовки текста и передачи данных общей карте внести в этот ADR при реализации.

## Goals / Non-Goals

**Goals:**

- Сделать улучшение наблюдаемым сначала на исходной сборке, затем после каждого самостоятельного исправления.
- Удалять ненужные импорты и повторную работу у источника; сохранять форматирование, геометрию, поведение карт, часов и поиска.
- Использовать штатные форматы анализатора, обычный Git diff и небольшую обвязку существующей сборки.

**Non-Goals:**

- Строить собственный граф зависимостей, универсальный CSS-анализатор, базу истории измерений или автоматическое решение о допустимости роста.
- Подменять очистку импортов ручной группировкой чанков, глобальным `sideEffects: false` или отключением валидации редакционных источников.

## Decisions

### 1. Один готовый анализатор, YAML в Git и HTML локально

Использовать `rollup-plugin-visualizer` как dev-зависимость. У него есть штатные `list` (YAML) и `treemap` (HTML), поддержка Vite/Rolldown и сортировка списка. BundleStats удобен встроенным сравнением, но для выбранного владельцем YAML достаточно Visualizer и Git; второй анализатор не нужен.

`pnpm bundle:analyze` выполняет актуальную production-сборку `@shelkovo/www` с opt-in анализом только клиентского выхода:

- `docs/bundle/client.yaml` — штатный список «чанк → исходный модуль → rendered». Пути обрезаются относительно корня workspace штатной настройкой `projectRoot`.
- `docs/bundle/assets.yaml` — короткий отсортированный список готовых JS/CSS из `dist/www/static`: байты файла, его `.br` и `.gz`. Для этого достаточно чтения размеров файлов и уже установленного YAML-сериализатора; разбор CSS не нужен.
- `.cache/bundle/client.html` — локальная treemap. Каталог игнорируется Git и находится вне публикуемого output. Отчёт доступен владельцу как локальный файл.

Подключение к клиентской фазе выполнять в Astro integration hook, чтобы серверная сборка не перезаписала клиентский отчёт. Команда запускает app build напрямую, обходя кеш корневой Turbo-задачи; обычный `pnpm build` отчёты не обновляет. Существующий build/search/compression pipeline используется целиком, без его второй копии в скрипте анализа.

Штатные имена чанков с хешами сохраняются. Агент сопоставляет исходные пути модулей и точки входа, а не считает смену хеша новой зависимостью. Самодельная стабилизация имён и алгоритм matching не нужны. `rendered` служит атрибуции состава; точные размеры передачи берутся из готовых файлов. Сжатые размеры отдельных модулей не складываются как сетевой вес чанка.

На первом запуске проверить содержательность отчёта на текущем Rolldown: видны реальные исходные модули и ненулевые размеры крупных зависимостей. Если атрибуции нужны source maps, включать их только для локального анализа и не включать в публикуемый сайт. Сравнение двух повторных запусков на одинаковых исходниках выявляет шум отчёта до начала очистки.

### 2. Разорвать тяжёлые цепочки импортов

Перенести общие константы дней недели, границ карты и прочие реально используемые клиентом значения в лёгкие модули без импорта схем и редакционных реестров. Уточнить импорты из `mentions`: читателю константы не нужна инициализация Markdown-процессора. Типовые зависимости оставить через `import type`.

Вынести `formatPlaceStatus` в лёгкий модуль, который используют клиент и build-time представление места. Вычисление текущего года статуса не должно выполняться из-за импорта карты. Проверить всех вызывающих эти helpers; исправление не ограничивается одним entry point. Существующие вычисления расписания и московского времени сохраняются.

Это предпочтительнее удаления нужных серверу библиотек или принудительных подсказок tree-shaking: причина — связность модулей и побочные эффекты, а не отсутствие библиотек в `package.json`.

### 3. Готовый текст и доверенный внутренний payload карт

Общий build-time helper готовит копию геометрии для показа: типографирует только видимые подписи точек существующими правилами `@shelkovo/markdown`. Клиент присваивает готовую строку через `textContent`. Оригинальные доменные строки, скрытые описания, публичная геометрия и исходные блоки Markdown не перезаписываются. При необходимости добавить в Markdown-пакет небольшой plain-text helper поверх действующей типографики, используя уже установленные средства экранирования/декодирования, без второго набора правил.

Подготовленное представление используется в трёх местах:

- HTML-renderer Markdown-карт сериализует его в `data-geometry`.
- `MapPreview.astro` получает подготовленную геометрию превью места.
- `/map/index.astro` передаёт выбранные места с подготовленной геометрией через уже существующий `PlaceMap.places`, явно выбирая нужные компоненту поля. Полный `Place` с body и backlinks не сериализуется.

Для общей карты удаляется больше не нужная ветка `dataUrl`/`fetchPlaces` и преобразование публичного DTO в клиенте. Публичный `/map/data/places.json` остаётся самостоятельной поверхностью для внешних потребителей с прежним контрактом. Так не требуется добавлять в него форматированные дубли подписей или менять смысл `iconCaption`. Пустой массив мест — корректное входное состояние, а не сигнал догрузить другой источник.

`EditorialMapDataSchema` и повторная проверка геометрии props удаляются. Проверка исходных GeoJSON и ошибки публикации остаются на сборке; `JSON.parse`, обработка ошибок и cleanup компонента сохраняются. Отдельно загружаемый по запросу слой участков остаётся самостоятельной сетевой границей со своей Zod-проверкой. Это не требование удалить Zod из любого клиентского чанка.

Выбор inline props вместо отдельного внутреннего endpoint использует существующий вход компонента и сокращает число форматов. Его стоимость — дополнительные байты HTML `/map/`; их нужно измерить вместе с исчезнувшим запросом данных и JS.

### 4. Дата поискового результата без Luxon

В клиенте поиска использовать лёгкий helper на `Intl.DateTimeFormat`, сохраняя русскую дату вида «день месяц год», московский часовой пояс и обработку отсутствующей даты. Если helper нужен другим клиентским потребителям, разместить его в `packages/format` с лёгким импортом; календарные операции на Luxon не переписывать.

Проверить дату без времени и timestamp около московской полуночи, а также формат без лишнего суффикса года. Корпус, порядок результатов и metadata поиска сохраняются; приёмка касается отображения даты, открытия поиска и переходов к результатам. Для этого этапа применять `site-search`.

### 5. Подключать renderer и CSS по наличию блоков

В шаблонах news/KB заменить безусловный импорт редакционной карты небольшим bootstrap: при наличии `editorial-map` в текущем документе он динамически импортирует регистрацию элемента. Повторять проверку при Astro-навигации; регистрацию самого custom element выполнять один раз. Имеющиеся карты начинают загрузку при входе на страницу, включая блоки ниже экрана, как требует печать.

У общего `map-preview` загружать поддержку редакционной геометрии только при наличии такой геометрии. Фоновые карты событий и поселков не должны получать этот renderer через общий preview.

Для стилей учитывать, что условная отрисовка Astro-компонента сама по себе не гарантирует условное подключение извлечённого CSS. Проверить emitted HTML и граф импорта. Стили конкретного блока, которые Astro подключает к пустому случаю, вынести в принадлежащий этому блоку stylesheet и подключать штатным внешним asset URL только вместе с его разметкой. Разделить оформление рамки Markdown-карты и общих геообъектов там, где у них разные потребители. Сохранить scoping/namespacing, каскад и print-правила по ADR-034.

Проверяемые отсутствующие блоки — редакционные карты, `EventWidget` и его `MapPreview`. Общий CSS layout не перепаковывается ради числа файлов. Динамическое подключение не должно давать неоформленную карту, терять стили при возврате или менять размеры контейнеров.

## Risks / Trade-offs

- **Хеши и границы чанков меняются после очистки** → сравнивать модули, суммарные JS/CSS-байты и реальные цепочки страниц; не суммировать уменьшение отдельных переименованных файлов как независимую экономию.
- **HTML общей карты становится больше из-за props** → записать до/после HTML, JS и запрос данных; передавать только поля клиентского представления и оценивать общий объём холодной загрузки.
- **Условные imports работают при прямом входе, но ломаются при навигации** → проверить переходы без карты → с картой → без карты → назад, несколько карт и отказ SDK.
- **Перенос типографики меняет экранирование или пробелы** → проверять подготовленные строки и `textContent`, включая HTML-подобный текст; значимые неразрывные пробелы показывать в snapshots видимым символом.
- **CSS выводится через другой импорт либо теряет локальность** → смотреть фактические stylesheet requests и layout в затронутых разделах, не принимать один лишь перенос файлов за результат.
- **Внешний SDK и аналитика доминируют в Network** → в сравнении явно указывать собственные JS/CSS, HTML/data и внешние запросы. Размеры бандлов не выдавать за доказанный выигрыш Lighthouse или сетевой вес всей страницы.

## Migration Plan

1. Продолжить в отдельной сессии в ветке `perf/trim-client-bundles` по issue [#838](https://github.com/silentroach/kpshelkovo/issues/838). Перед реализацией подтвердить разрешение владельца и зафиксировать связь с коммитом согласованных артефактов по проектному workflow.
2. Подключить анализатор и снять исходный YAML/HTML до исправлений. Сохранить исходный YAML отдельным коммитом в ветке при разрешённом commit; иначе сохранить локальную копию в `.cache/bundle/before/`. Для этой первой задачи исходный HTML тоже сохранить локально.
3. Последовательно убрать Markdown из часов, перенести подготовку карт, убрать повторную проверку встроенных данных, убрать лишний Luxon и исправить условные ресурсы. После каждого этапа запускать анализ, проверять ожидаемые исчезнувшие модули и кратко сообщать результат.
4. Перед сдачей сравнить итог с исходным baseline, сохранить актуальные YAML и открыть HTML для владельца. Для дальнейших задач исходный снимок берётся из Git; если ветка уже содержит изменения или baseline устарел, сначала снять локальное состояние до правки. Промежуточные отчёты не превращать в постоянно хранимую историю.
5. Обновить `docs/development.md`, короткое правило в `AGENTS.md` для изменений клиентского графа/сборки и затронутые архитектурные пояснения. Выполнить приёмку из `tasks.md`, затем штатные sync/archive и PR.

Откат возвращает код, настройку анализатора, lock-файл и YAML-снимки согласованным набором. Редакционные данные и публичные форматы миграции не требуют.
