# Proposal

## Why

Посетители загружают редакционные обработчики и код отсутствующих блоков: новость без карты получает около 174 КБ лишнего собственного JavaScript, а карты и превью — Markdown, Typograf, YAML и лишние импорты Luxon. Нужны исправление границ клиентского кода и простой локальный отчёт, чтобы видеть состав бандлов и сравнивать его прямо во время работы.

## What Changes

- Первым этапом подключить `rollup-plugin-visualizer` и команду `pnpm bundle:analyze`: штатное YAML-дерево клиентских JS-модулей в `docs/bundle/client.yaml`, локальная HTML-диаграмма и короткий список размеров готовых JS/CSS-файлов. Снять исходный baseline до очистки зависимостей.
- Убрать попадание Markdown через `opening-hours` и общие реэкспорты констант; отделить клиентские функции от модулей с редакционными обработчиками и вычислениями при импорте.
- Подготавливать текст подписей геометрии и типографику на сборке для Markdown-карт, превью мест и общей карты. Передавать компонентам готовое представление и убрать повторную Zod-проверку этих встроенных данных.
- Убрать Luxon из цепочки карты, где он нужен только неиспользуемому вычислению года, и заменить его использование для даты поискового результата лёгким форматированием с тем же результатом.
- Подключать клиентский renderer редакционных карт по наличию блока. Убрать из материалов стили отсутствующих карт и виджетов мероприятий; проверить прямой вход и клиентскую навигацию.
- После каждого этапа сравнивать состав и размеры; перед сдачей обновлять YAML-снимок в Git и объяснять существенную разницу. Закрепить порядок в инструкции разработки и агентских правилах.

## Capabilities

### New Capabilities

- `client-resource-loading`: загрузка ресурсов карт и виджетов только при наличии соответствующего содержимого; показ подготовленных редакционных подписей без передачи браузеру средств редакционной обработки.

### Modified Capabilities

Нет. Действующие контракты `map-geodata`, `markdown-service-blocks`, `site-maps`, `place-opening-hours`, `search` и `event-widget` служат условиями регрессионной проверки. Эксплуатация анализатора и разовый порядок очистки описаны в design/tasks, а не в продуктовых specs.

## Impact

- Основные области: `apps/www/src/components/maps`, `components/places`, `components/search`, `lib/geometry`, `lib/places`, `lib/mentions`, `lib/markdown`, шаблоны news/KB и `/map/`; точечные изменения `packages/format` и API типографики `packages/markdown` по потребности.
- Сборка и документация: `apps/www/astro.config.ts`, package scripts, lock-файл, `docs/bundle/`, `docs/development.md`, `AGENTS.md`, игнорирование локальных отчётов. Анализатор — dev-зависимость, отчёты не входят в публикуемый сайт.
- Задача: [#838](https://github.com/silentroach/kpshelkovo/issues/838), рабочая ветка `perf/trim-client-bundles`. Связанный [#629](https://github.com/silentroach/kpshelkovo/issues/629) исследует упаковку внешних ресурсов; это самостоятельное изменение про лишние зависимости и наблюдение состава, а не продолжение экспериментов с группировкой чанков.
- Границы: без CI-бюджетов и блокировки роста размера, собственного анализатора/движка сравнения, ручной раскладки vendor-чанков, изменения аналитики, шрифтов или внешнего SDK карт. Публичные JSON и Markdown-контракты сохраняются; отдельно загружаемый слой участков сохраняет свою runtime-валидацию.
- Приёмка выполняется на локальной production-сборке до PR: сравнение отчётов, функциональные проверки и браузерные сценарии. Отдельная production-приёмка для закрытия issue и архивирования change не требуется.
