# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md), issue — [#849](https://github.com/silentroach/kpshelkovo/issues/849). Исследование выполнено на `33b917770a3289972e6b1997b9a60e3b3fe4106c`; сохранённые отчёты `docs/bundle/` содержат Zod 4.5.4 в общем чанке `raw-polygon-schema`.

Три клиентских ребра удерживают проверку геометрии и Zod:

- `components/maps/editorial-map-element.ts` импортирует `EditorialMapDataSchema` и проверяет JSON из `data-geometry`.
- `components/places/PlaceMap.svelte` импортирует `EditorialPublicGeometrySchema` и повторно проверяет геометрию каждого места из `/map/data/places.json`.
- Тот же компонент лениво импортирует `ParcelMapPublicSchema` и проверяет весь `/map/data/parcels.json` при включении участков.

Все пути находятся внутри `apps/www/src`. Остальные runtime-потребители этих схем относятся к сборке, загрузчикам и инструментам обновления. Прецедент доверенного HTML-payload уже есть в `components/maps/map-preview.ts`: `JSON.parse` с приведением к `MapPreviewData`.

Применимые решения:

- [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md): границы Raw DTO → domain → Public DTO и явные доменные типы.
- [ADR-039](../../../docs/decisions/039-shared-yandex-maps-runtime-and-preview.md): общий runtime карт, сериализация геометрии и жизненный цикл компонентов.
- [ADR-041](../../../docs/decisions/041-parcel-records-and-exact-search.md): отдельные данные участков, их отложенная загрузка и подготовка публичного представления.

Действующие контракты геометрии и ошибок — `map-geodata`, `site-maps` и `parcel-map`. Конкретная граница доверия этого изменения зафиксирована в delta `site-maps`.

## Goals / Non-Goals

**Goals:**

- Удалить три клиентских ребра к схемам и сохранить проверку именно подготовленных данных, включая вычисленные координаты.
- Переиспользовать существующие схемы и типы, сохранив публичные форматы и build-диагностику.
- Сохранить рабочий повтор после обнаруженной ошибки загрузки или применения участка.

**Non-Goals:**

- Переносить места или участки из отдельных JSON-файлов в HTML, менять URL, режим загрузки слоя или условия подключения редакционных карт.
- Добавлять общий транспортный слой, версионирование payload, ручные валидаторы или альтернативную библиотеку схем.
- Расширять проверку всего payload мест: сейчас браузер проверяет только вложенную геометрию; остальные поля проходят существующие raw-схемы и типизированный адаптер.

## Decisions

### 1. Сборка владеет схемной проверкой собственных артефактов

В обсуждении владелец выбрал использование проверенных при сборке данных через JSON-разбор и тип результата. Решение распространяется и на HTML, и на два собственных статических JSON-файла. Отдельный `fetch` меняет обработку доставки, но не требует повторного исполнения схемы.

Клиентские `JSON.parse` и `response.json()` остаются внутри текущей обработки ошибок. Проверки успешности HTTP-ответа, отсутствующего HTML-payload и возможности построить кадр сохраняют своё прикладное назначение. Полную валидацию произвольного объекта после JSON-разбора клиент больше не обещает: лишнее поле или некорректное значение не обязаны приводить к прежнему Zod-отказу. Существующие адаптеры публичного представления не заменяются assertion к доменному типу.

### 2. Конечный HTML-payload проверяется перед сериализацией

Сейчас `parseEditorialGeometry` проверяет исходный GeoJSON, mapper собирает доменную коллекцию, а `expandPolygonGeometry` проверяет вычисленные контуры. Однако `lib/markdown/editorial-maps-html.ts` сериализует итоговую коллекцию без вызова точной `EditorialMapDataSchema`.

Переместить существующую схему из `components/maps/editorial-map-data.ts` в `lib/geometry/editorial-map-data-schema.ts` и вызвать её в `encodedGeometry` непосредственно перед `JSON.stringify`. Использовать проверенный результат, сохранив экранирование `<`, `>` и `&`. Это перенос существующей проверки; ограничения колец, оформления, цифровой метки и строгих объектов сохраняются.

Передать в конечную проверку контекст источника и номер `map`-вставки, доступные HTML-transform и `EditorialMapBlock.index`. Ошибка должна сохранять источник, номер вставки, путь поля и определимый ID объекта, включая `0`, по действующему `map-geodata`. Проверить это отрицательным тестом конечной сериализации: одной ошибки Zod без контекста материала недостаточно.

В `editorial-map-element.ts` использовать type-only импорт существующей `EditorialFeatureCollection` для результата `JSON.parse`. Схема остаётся согласованной с этим явным доменным типом; выводить доменную модель из raw-схемы не нужно.

### 3. Публичные JSON уже проверяются на нужной границе

- `lib/geometry/editorial-public.ts` проверяет конечную публичную геометрию через `EditorialPublicGeometrySchema` до публикации в `/map/data/places.json`. В клиенте убрать повторный `.parse`, передавать типизированную геометрию существующему public → domain адаптеру.
- `lib/parcels/map-public.ts` проверяет весь `ParcelMapPublicSchema` после объединения частей, display offset и вычисления точки подписи. В клиенте убрать динамический импорт схемы и пользоваться существующим `ParcelMapPayload` из `components/places/parcel-layer-types.ts`; его зависимость от схемы уже type-only.
- `scripts/build-search-index.ts` продолжает проверять подготовленные данные участков на сборке. Изменение корпуса поиска не требуется.

Обычный Zod и публичные схемы сохраняют текущий API для сборки и других build-потребителей. Геометрия, отверстия, ID `0`, оформление, скрытые описания и различие public/domain представлений не меняются.

### 4. Повтор не использует данные, на которых применение слоя завершилось ошибкой

При буквальной замене `.parse` на assertion ответ вида `{ parcels: [] }` может попасть в `parcelData`, после чего `data.find(...)` завершится ошибкой. Текущий catch не очищает кеш, поэтому retry повторит ошибку без нового запроса. Существующий тест `PlaceMap.test.ts` уже требует двух запросов и успешного восстановления после такого ответа.

В актуальной ветке обработки ошибки применения данных сбрасывать кеш неудачного ответа либо откладывать его фиксацию до успешного применения. Выбрать минимальную правку с учётом текущих проверок поколения/жизненного цикла: поздний ответ после выключения слоя или уничтожения компонента не должен менять актуальное состояние. Успешные данные по-прежнему переиспользуются при выключении и повторном включении.

Эта правка обеспечивает восстановление после обнаруженной ошибки, а не заменяет Zod ручной проверкой структуры. Параметр `p` при ошибке сохраняется, чтобы успешный повтор выполнил исходное действие.

### 5. Рассмотренные альтернативы

- **Общие схемы на `zod/mini`.** Штатный функциональный API позволяет убрать неиспользуемые возможности. Потребовалось бы перенести четыре схемы и адаптировать два build-потребителя, сохранив повторную проверку в браузере. После согласования доверия к собственным артефактам такая работа не нужна.
- **Отдельные Mini-схемы только для клиента.** Сохраняют classic API сборки, но дублируют контракт или требуют дополнительной конструкции для его описания. Повторная работа в браузере тоже остаётся.
- **Отделить JSON Schema exporter, сохранив classic на клиенте.** В установленном Zod 4.5.4 classic-конструкторы сами подключают JSON Schema methods/processors; перенос пользовательских вызовов не устраняет причину. У исследованных схем нет отдельного проектного exporter, который можно было бы вынести.
- **Доверять только HTML, а JSON проверять Mini.** Сохраняет две политики для артефактов одного build-конвейера. Владелец выбрал единую границу для всех трёх путей.

Документация Mini: <https://zod.dev/packages/mini>. Отличия установленной версии дополнительно проверены по локальному пакету; измерения документации не используются как обещание экономии сайта.

### 6. Приёмка опирается на готовый бандл и конкретные проверки поведения

До изменения импортов выполнить `pnpm bundle:analyze` и сохранить исходные отчёты для сравнения; после реализации повторить команду по [инструкции](../../../docs/development.md#анализ-клиентских-бандлов). Проверять модули и точки входа, а не имя чанка с хешем: в клиентском графе не должны остаться три схемы, общая полигональная схема и Zod, включая `to-json-schema` / `json-schema-processors`, через эти пути. По исходному графу других клиентских потребителей Zod нет.

Сравнить фактические JS/Brotli/gzip затронутых файлов с учётом общих чанков и ленивого слоя. Зафиксировать экономию в PR и актуальные `docs/bundle/client.yaml` / `assets.yaml`. Числовой процент заранее не задаётся; сумма `rendered` не считается сетевым весом, исчезновение старого имени файла само по себе не доказывает успех. Анализатор подтверждает состав и размеры собственного JS, не измеряет скорость страницы с внешним SDK.

Связанные проверки:

- Финальная HTML-сериализация принимает корректную подготовленную коллекцию и отвергает некорректную с источником, номером вставки, полем и определимым ID объекта; script-safe экранирование сохраняется.
- Генераторы публичных мест и участков продолжают отклонять недопустимую конечную геометрию, включая ошибку после подготовки координат. Использовать существующее покрытие; добавить только отсутствующую проверку конкретной границы.
- Компоненты показывают корректные данные и сохраняют fallback при отсутствии payload, ошибке JSON-разбора, HTTP/сети и SDK.
- Участки сохраняют отложенную загрузку, кеш успешных данных, прямую ссылку и восстановление после обнаруженной ошибки применения. Существующий тест неправильного wrapper и успешного второго ответа сохраняется.
- Тесты, целью которых было полное semantic rejection в браузере, перенести на build-границу; не считать случайный `TypeError` заменой схемного покрытия и не удалять вместе с ними проверки восстановления.

## Risks / Trade-offs

- Ошибка в подготовке данных после raw-проверки → применять конечную HTML-схему перед сериализацией, сохранять существующие публичные проверки и их отрицательные тесты.
- Синтаксически корректный сторонний или несовместимый ответ не обязательно будет отвергнут до renderer-а → согласованная граница доверия относится к собственным артефактам; ошибки доставки, разбора и обнаруженные ошибки применения проходят существующий fallback. Полная семантическая проверка произвольного ответа не обещается.
- Неудачный ответ может закрепиться в кеше участков → сохранять retry-тест и очистку неудачного кеша с учётом актуальности запроса.
- Случайный value-import схемы возвращает Zod → type-only импорты и проверка production-графа существующим анализатором.

## Migration Plan

После отдельного разрешения реализации сохранить baseline, перенести HTML-проверку и убрать клиентские импорты в одном изменении. Затем выполнить связанные тесты, `pnpm typecheck`, production-сборку через анализатор и ревью всего diff; синхронизация spec, архивирование и PR следуют проектному workflow. Данные и опубликованные URL не требуют миграции. Откат возвращает реализацию и отчёты вместе, восстанавливая клиентскую проверку.
