# Design

## Context

Причина изменения — в [proposal.md](proposal.md). Редакционный `iconCaption` проходит через `parseEditorialGeometry` к трём поверхностям: HTML-атрибут Markdown-карты, `MapPreview` карточки места и `/map/data/places.json` общей карты. Все используют `createEditorialMapObjects`, который сейчас импортирует `formatDynamicHtml` и превращает её HTML-результат обратно в текст. `@shelkovo/markdown` экспортирует и типографику, и генератор Markdown с импортом YAML. Отдельный импорт `formatPlaceStatus` через `places/view` и `status/view` способен удержать Typograf в чанке `/map/` после исправления общего renderer-а; конкретный результат нужно проверить по новой сборке.

В шаблонах новости и KB `editorial-map-element` подключён безусловно, хотя серверный `renderMarkdown(..., { editorialMaps: true })` уже определяет наличие итоговых `<editorial-map>`. Обе страницы используют Astro ClientRouter. Применимы [ADR-003](../../../docs/decisions/003-markdown-pipeline-layering.md) для единых правил типографики, [ADR-013](../../../docs/decisions/013-raw-domain-public-data-boundary.md) для независимых редакционного, доменного и публичного представлений, [ADR-028](../../../docs/decisions/028-markdown-first-places-map.md) для мест и JSON карты и [ADR-039](../../../docs/decisions/039-shared-yandex-maps-runtime-and-preview.md) для запуска Markdown-карты и повторной навигации.

## Goals / Non-Goals

**Goals:**

- Убрать Typograf/YAML из клиентской цепочки подписей, сохранив типографику и текстовую безопасность на всех трёх поверхностях.
- Сохранить проверку конечных данных до сериализации и самостоятельность публичного JSON от внутренней модели; без повторной схемной проверки в браузере.
- Не загружать код редакционной карты на статьях без карты, сохранив немедленный запуск всех карт на статьях с картами.

**Non-Goals:**

- Дробить `/map/data/places.json` на слои (#858) или менять навигационный Markdown-индекс и опубликованные карточки (#859).
- Оптимизировать клиентскую загрузку обычного превью без геометрии (#847), скрытые превью (#844), время готовности внешнего SDK или первый экран `/map/` (#393).
- Пересматривать редакционные правила Typograf либо типографировать скрытые описания и исходные блоки `map`.

## Decisions

### Отдельное подготовленное представление при сериализации

Добавить в `@shelkovo/markdown` узкий helper для типографики **обычной текстовой строки** с теми же правилами Typograf, что у `formatDynamicHtml`. Защищать буквальные `<...>`, `&...` и HTML-подобный текст от интерпретации как разметки; на выходе получать текст, не HTML. Использовать существующий механизм HTML-экранирования/декодирования через явную зависимость, если он требуется: не писать второй набор правил типографики и не использовать DOM браузера при сборке. Проверить кавычки, неразрывные пробелы, буквальные entity-последовательности, Markdown и опасные теги.

App-level адаптер получает доменную `EditorialFeatureCollection`, создаёт новое представление и подготавливает только `iconCaption` у `Point`. Исходная коллекция и скрытые строки остаются без изменений. Применять адаптер непосредственно перед сериализацией конечных данных в `editorial-maps-html.ts`, `PlacePreview.astro` и `toPublicEditorialGeometry`; проверять получившийся HTML payload и публичный DTO действующими Zod-схемами до публикации. В `/map/data/places.json` использовать прежнее имя `properties.iconCaption` для готовой строки — без параллельного поля. `fromPublicEditorialGeometry` только переносит подготовленную строку в display-геометрию, а общий renderer ставит `textContent` без типографа и HTML decoder-а.

Альтернатива — типографировать в raw mapper-е: меньше точек вызова, но доменная коллекция утратит исходную строку, от которой зависят другие представления. Отдельное публичное поле для готовой подписи сохранило бы точный старый JSON, но владелец выбрал готовое значение в существующем поле и отдельную будущую задачу по публичным поверхностям. Асинхронный клиентский импорт Typograf сохраняет тяжёлый код и затрудняет общий renderer; упрощённые регулярные выражения расходятся с правилами сайта.

### Убрать остаточный тяжёлый импорт общей карты

После переноса подписей проверить клиентский граф всех затронутых страниц. Если `/map/` продолжает получать Typograf через `formatPlaceStatus` → `places/view` → `status/view`, готовить необходимый статический текст места при построении payload карты, а не импортировать серверный view-модуль в `PlaceMap.svelte`. Время открытия/закрытия, viewport, кластеры и действия пользователя остаются динамическими: их нельзя вычислить при сборке. Выбор конкретного display-поля должен оставаться минимальным и не подменять публичные коды lifecycle-статуса; конечный payload по-прежнему проверяется при сборке. Совместимость остальной клиентской карты, включая сопутствующий Luxon из этого пути (#843), проверить фактическим отчётом, но не включать общий рефакторинг дат в change.

Альтернатива — вынести `formatPlaceStatus` в лёгкий клиентский модуль: это уменьшило бы граф импортов, но оставило бы подготовку неизменного текста в браузере вопреки принятой границе. Перенос всего JSON в HTML-пропсы также не нужен: добавляет HTML и меняет способ загрузки карты ради одной строки.

### Подключение редакционной карты только к материалам с картой

Использовать результат уже выполненного серверного Markdown-render-а для признака наличия сгенерированного `<editorial-map>` в конкретной новости или KB-странице. Подключать существующий bundled script регистрации custom element только для такого материала; не дублировать парсинг исходного Markdown и не использовать клиентский обход DOM для принятия решения о наличии карты. Условную вставку проверять по **собранному** HTML: способ размещения Astro `<script>` и deduplication могут отличаться от вида шаблона. При необходимости вынести script в небольшой Astro-компонент, который рендерится условно. Стили карты условно подключать только тогда, когда это действительно устраняет лишнюю доставку без влияния на общие стили; не превращать CSS в самостоятельную миграцию.

Альтернатива — безусловный маленький скрипт с проверкой `document.querySelector('editorial-map')` перед динамическим импортом. Он защищает от тяжёлого чанка, но каждую текстовую страницу всё равно заставляет загружать и запускать проверку присутствия, уже известного при сборке. Безусловное подключение готовой регистрации сохраняет текущую проблему #841.

## Risks / Trade-offs

- Публичный `iconCaption` перестаёт быть точной копией исходной строки → отметить несовместимость в PR и delta spec; сохранить редакционный GeoJSON и Markdown companion без изменений. Не выдавать будущий #859 за уже выполненную миграцию внешних потребителей.
- Буквальные entity-последовательности и псевдотеги могут измениться или исполниться из-за неверного экранирования → точечные тесты textContent, отсутствия DOM-узлов разметки и сохранения исходника, в том числе для публичного JSON.
- Удаление импорта renderer-а может лишь переместить Typograf/YAML в иной чанк → проверить `pnpm bundle:analyze` и сетевые запросы на `/map/`, странице места, новости с картой, обычной новости и простом превью; сравнивать суммарную передачу, не складывать модульные `rendered` как байты сети.
- Условный Astro-скрипт может не соответствовать ожиданиям на выходе сборки или при ClientRouter → проверить отсутствие map-кода в HTML/Network без карты и восстановление нескольких карт при переходах; если условный tag всё равно подключается, применить условный компонент вместо отказа от требования.

## Migration Plan

Опубликовать подготовленные HTML и JSON совместно с клиентским кодом, который больше не типографирует подпись повторно; не разносить несовместимые половины изменения по разным деплоям. До объединения PR выполнить локальную сборку, поведенческие проверки и сравнение бандлов; отдельная production-приёмка не требуется. При откате вернуть вместе форматирование, входы renderer-а и значение публичного поля. Разделение JSON по #858 и изменение агентского индекса по #859 остаются самостоятельными изменениями с собственной проверкой совместимости.
