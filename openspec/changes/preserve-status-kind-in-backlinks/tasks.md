Требования: [entity-mentions](/openspec/changes/preserve-status-kind-in-backlinks/specs/entity-mentions/spec.md). Подход и границы: [design](/openspec/changes/preserve-status-kind-in-backlinks/design.md).

## 1. Вид события в графе и публичном контракте

- [ ] 1.1 Передавать исходный `kind` через адаптер статуса и типы backlinks людей и мест; тестами адаптера и проекций подтвердить оба вида, будущий инцидент, короткие записи, повторы упоминаний и сочетание текста с `affected_places`, включая разные записи с общим календарным URL.
- [ ] 1.2 Обновить people JSON, JSON Schema, OpenAPI и описание в `llms.ts` на прямую передачу `incident` / `maintenance`; тестами публичного DTO и discovery проверить значения для обоих видов и валидацию payload через Zod по опубликованной схеме.

## 2. Подписи в HTML и Markdown

- [ ] 2.1 Расширить существующие форматтеры людей и мест, использовать вид backlink в Markdown места; тестами форматтера людей и Markdown обеих сущностей подтвердить правильную подпись для заголовков без названия вида, а у мест — с dataset статуса и без него. Прогнать проверки HTML-подборок мест, периода, состояния инцидента и отсутствия дополнительной подписи о завершении у работ; подтвердить скрытость HTML-упоминаний людей до #1284.
- [ ] 2.2 Подготовить изменённые подписи и пояснения через `humanizer-ru`, передать весь текст задачи `editorial-reviewer` по [протоколу](/docs/development.md#редакторское-ревью-текстов-сайта); исправить подтверждённые замечания и получить адресное повторное ревью изменённых фрагментов.

## 3. Общая приёмка

- [ ] 3.1 Выполнить `pnpm typecheck`, затронутые тесты статуса, mentions, people и places, затем `pnpm build`; в артефактах сборки проверить подпись работ в Markdown ВЗУ Фореста и согласованность people JSON с JSON Schema и OpenAPI. Сценарий людей с плановыми работами подтвердить тестовыми данными из задач 1–2.
- [ ] 3.2 Выполнить `pnpm openspec:validate`, сверить весь актуальный diff с требованиями и провести [цикл reviewer](/docs/development.md#ревью-изменения-в-opencode): исправить подтверждённые проблемы, обосновать отклонения и получить адресный повтор. При недоступности агента провести самопроверку и `ponytail-review` всего diff с указанием ограничения.

## Workflow follow-up

- После приёмки повторить отбор требований, синхронизировать основные specs и архивировать change в той же ветке; выполнить `pnpm openspec:validate` и адресное ревью итоговых документов.
- Обновить связь change с issue и подготовить PR с `Closes #1266` по действующим разрешениям на публикацию.
