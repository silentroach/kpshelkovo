# Design

## Context

Причина изменения — в [proposal](/openspec/changes/remove-news-photo-background/proposal.md#why), исходная задача — [#1065](https://github.com/silentroach/kpshelkovo/issues/1065).

Визуальная задача: житель читает новость с телефона и сразу различает заголовок, дату, автора и источник. Основа — существующий спокойный редакционный дизайн сайта, PT Serif/Fira Sans и светлые семантические цвета. Снимок текущей шапки на 390 px подтверждает наложение метаданных на светлое затухание фотографии; исходные снимки сохранены в [приёмке палитры](/openspec/changes/archive/2026-10-14-refine-site-color-roles/acceptance/).

Наблюдения по коду:

- [Страница статьи](/apps/www/src/pages/news/[year]/[month]/[entry]/index.astro) содержит две разметки шапки. Только фотошапка использует повторный `getEntry`, вычисление размеров обложки, `Image`, `news-hero-*` и `NewsMeta variant="prominent"`.
- `cover` проходит через [raw-схему](/apps/www/src/lib/news/raw-schema.ts), [loader](/apps/www/src/lib/news/load.ts), [типы](/apps/www/src/lib/news/types.ts), [публичный адаптер](/apps/www/src/lib/news/public-dto.ts), [публичную схему](/apps/www/src/lib/news/public-schema.ts), [discovery](/apps/www/src/lib/news/discovery.ts) и [Markdown](/apps/www/src/lib/news/markdown.ts). Это самостоятельное поле публичного API, а не только CSS-эффект.
- Единственный редакционный `cover` задан в [новости о дамбе](/apps/www/src/data/news/articles/2026/04/river-restriction.md); локальный JPEG размером 1280×720 показывает подтопленный проезд и полезен материалу.
- Обычные изображения в body уже поддержаны app-level Markdown renderer; пример — [новость о гостевых пропусках](/apps/www/src/data/news/articles/2026/08/guest-passes-disputed-debt.md). `eagerImages: true` обеспечивает загрузку для печати без предварительной прокрутки.
- [BaseLayout](/apps/www/src/layouts/BaseLayout.astro) уже поддерживает корректное текстовое social preview при отсутствии `image`. Фотографии из `photos` сейчас включаются в JSON-LD, но не становятся social preview автоматически.

Владелец явно подтвердил: полностью удалить `cover` из данных и всех схем, не поддерживать обратную совместимость и не менять версии схем; фотографию можно вставить в текст новости. Текстовое social preview входит в предлагаемый подход и согласуется вместе с change.

## Goals / Non-Goals

**Goals:**

- Свести статью к одному существующему варианту шапки и убрать все потребители обложки, включая печать и машинные представления.
- Использовать имеющийся Markdown/media pipeline для снимка, сохранив его доступность в HTML, Markdown и JSON body.
- Проверить удаление поля на каждой границе по [ADR-013](/docs/decisions/013-raw-domain-public-data-boundary.md).

**Non-Goals:**

- Новые правила выбора social image, новый тип изображения, автоматическое извлечение картинок из body или замена `cover` другим редакционным полем.
- Переработка галереи `photos`, общесайтовой палитры, шрифтов, маршрутов новости или её исторического содержания.

## Decisions

### 1. Оставить обычную шапку единственным вариантом

Развернуть текущую ветку без `hasHeroCover` в безусловную разметку. Удалить фотошапку, связанные импорты и получение raw-записи, вычисления размеров, `--with-cover`, наложения и локальные цвета. Удалить вариант `prominent` из `NewsMeta`, поскольку других его потребителей в новостях нет. Сохранить списоковый вариант метаданных и действующую раскладку новостей с мероприятиями.

Из [print.css](/apps/www/src/styles/print.css) удалить только исключения фотообложки; обычное изображение подчиняется общим правилам печати. Владение стилями следует [ADR-034](/docs/decisions/034-native-css-architecture.md), печать существующего DOM — [ADR-037](/docs/decisions/037-content-print-css.md).

Подбор другого затемнения отклонён владельцем в issue. Сохранение скрытого варианта шапки оставило бы ненужные ветки и данные.

### 2. Удалить поле через все слои

Удалить `cover`/`cover_alt` и image-зависимость новостной raw-схемы, адаптировать её подключение в content config и тестах. Удалить типы обложки, поля полной/списковой модели, mapper, публичные типы и re-export, Zod-описание и Markdown-строку «Обложка». JSON Schema и OpenAPI должны следовать обновлённой публичной схеме.

Не оставлять deprecated-поле, fallback, aliases или отдельный адаптер совместимости. По решению владельца `NEWS_PUBLIC_PAYLOAD_SCHEMA_VERSION` и остальные версии сохраняются. В PR явно указать удаление поля и доступность изображений через body/`photos`.

### 3. Перенести снимок в обычный Markdown body

Подготовить имеющийся JPEG и опубликовать его через `public-media-publisher` по [runbook](/ops/storage/public-media.md) с ключом `news/2026/04/river-restriction/flooded-dam.jpeg`. Сохранить полный кадр без увеличения, удалить встроенные метаданные, GPS не переносить. Проверить свободный ключ либо совпадение опубликованных байтов, затем MIME, размеры и SHA-256 через media-origin.

После успешной публикации поставить Markdown-изображение после абзаца с рекомендацией объезда, перед поздним уточнением ОК Комфорт. Сохранить существующий alt «Подтопленная дамба у КПП Шелково Ривер». Удалить поля обложки и локальный JPEG после проверки всех ссылок. Галерею `photos` для этой одиночной иллюстрации не создавать.

Это использует действующую инфраструктуру [ADR-023](/docs/decisions/023-news-images-in-public-s3.md) и app-level рендер [ADR-003](/docs/decisions/003-markdown-pipeline-layering.md). Локальный относительный URL не подходит: body новости рендерится отдельным Markdown pipeline, а публичным представлениям нужен действующий URL изображения. Вставка в body предпочтительнее галереи по указанию владельца.

### 4. Использовать штатное текстовое превью

Убрать передачу `image` и `imageAlt` из страницы новости в `BaseLayout`. Сохранить заголовок, описание, канонический URL и `type="article"`; layout выдаёт `twitter:card=summary` без `og:image`/`twitter:image`. `NewsArticle.image` формировать из `photos` с сохранением удаления дублей; для новости только с body-изображением поле отсутствует.

Автоматический выбор первой картинки потребовал бы нового правила для всех новостей и, для body, дополнительного извлечения изображений. Текстовый fallback уже работает у новостей без обложек и позволяет полностью убрать специальную поддержку.

### 5. Синхронизировать действующие инструкции

Обновить [правила новостей](/docs/news.md), [дизайн-гайд](/docs/design/design-code-shelkovo.md), [news-maker](/.agents/skills/news-maker/SKILL.md) и пояснение body-фотографий в [storage runbook](/ops/storage/public-media.md). В ADR-023 отметить прекращение локального `cover`, сохранив историческое обоснование и актуальное правило галереи. Убрать устаревшие формулировки про обложку из сценария `news-authorship` и требования печати без изменения их гарантий. Архивные changes и отчёты сохраняют историю.

## Risks / Trade-offs

- У потребителя JSON может быть собственная зависимость от `cover` → удаление явно согласовано владельцем без совместимости и смены версии; проверить согласованность DTO, JSON Schema и OpenAPI.
- Превью бывшей фотообложки станет текстовым → это явно описано в proposal; изображение останется доступным внутри новости и её Markdown/JSON body.
- Подготовленная фотография должна быть доступна до выпуска страницы → добавлять media URL после проверки опубликованного файла; при конфликте ключа остановиться по runbook.
- Общий `NewsMeta` и печатный stylesheet используются шире статьи → проверить новостной список и печать одной страницы KB наряду со статьями; общие цвета и link-примитивы менять только при подтверждённой необходимости.

## Migration Plan

1. После согласования change и разрешения реализации сохранить артефакты коммитом в рабочей ветке, связать issue с change и коммитом разрешения.
2. Опубликовать снимок, затем одним изменением перенести его в body и удалить всю поддержку обложки.
3. Выполнить адресные тесты, typecheck, lint, production build и браузерную приёмку 320/390/1440 px. Проверить длинную шапку, Tab-фокус, фактические коэффициенты контраста, печать и публичные представления.
4. Провести полный reviewer-проход, разобрать находки и адресно повторить ревью. Синхронизировать specs, архивировать change и проверить итоговые изменения перед PR по проектному workflow.
5. Откат — возврат всего PR; опубликованный неизменяемый JPEG сохраняется, пока нет отдельного запроса на его удаление.
