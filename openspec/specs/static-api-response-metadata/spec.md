# static-api-response-metadata Specification

## Purpose

Сохранять HTTP-метаданные статических endpoints при публикации, чтобы клиенты могли правильно читать документы, обнаруживать связанные контракты и скачивать файлы без знания внутренних деталей сборки.

## Requirements

### Requirement: Публикация сохраняет метаданные каждого статического endpoint

Каждый существующий prerendered endpoint текущей опубликованной сборки сайта SHALL публиковаться с объявленным media type и параметрами `Content-Type`, а также объявленными `Link`, `Content-Disposition`, `X-Robots-Tag` и `Vary`, если они заданы ответом. Правило SHALL применяться и к конкретным URL параметризованных маршрутов. `GET` и `HEAD` одного URL SHALL возвращать одинаковые метаданные представления; `HEAD` SHALL не возвращать тело.

#### Scenario: Документ имеет специализированный media type с параметрами

- **WHEN** клиент получает документ, для которого endpoint объявляет media type и параметры, например `charset` или `profile`
- **THEN** опубликованный `Content-Type` сохраняет этот media type и все объявленные параметры
- **AND** в ответе нет второго конфликтующего `Content-Type`

#### Scenario: Endpoint публикует файл для скачивания

- **WHEN** клиент запрашивает существующий календарный файл или vCard с объявленным `Content-Disposition`
- **THEN** ответ сохраняет disposition и имя файла из endpoint
- **AND** `GET` возвращает исходное содержимое, а `HEAD` — те же метаданные без тела

#### Scenario: Документ задаёт правила индексирования

- **WHEN** endpoint объявляет `X-Robots-Tag` для документа
- **THEN** опубликованный ответ сохраняет эти директивы

#### Scenario: Ответ задаёт Vary

- **WHEN** endpoint объявляет `Vary` для документа
- **THEN** опубликованный ответ сохраняет перечисленные условия выбора представления

#### Scenario: Параметризованный endpoint выпускает новые URL

- **WHEN** опубликована сборка с новыми конкретными URL существующего параметризованного endpoint
- **THEN** каждый такой URL получает объявленные для его ответа метаданные без отдельного ручного правила публикации

### Requirement: Media type соответствует виду API-документа

Статические JSON-ленты и контракты разделов `/815/compare/`, `/news/`, `/status/`, `/people/` и `/815/regulation/` SHALL публиковаться с единственным `Content-Type`, соответствующим виду документа: `application/json` для данных, `application/schema+json` для JSON Schema и `application/vnd.oai.openapi+json` для OpenAPI. `GET` и `HEAD` одного URL SHALL возвращать одинаковые media type; параметр `charset` не меняет вид документа.

#### Scenario: Запрос JSON-ленты

- **WHEN** клиент запрашивает существующую JSON-ленту раздела через `GET` или `HEAD`
- **THEN** ответ содержит один `Content-Type` с media type `application/json`

#### Scenario: Запрос JSON Schema

- **WHEN** клиент запрашивает существующую JSON Schema раздела через `GET` или `HEAD`
- **THEN** ответ содержит один `Content-Type` с media type `application/schema+json`

#### Scenario: Запрос OpenAPI

- **WHEN** клиент запрашивает существующий OpenAPI-документ раздела через `GET` или `HEAD`
- **THEN** ответ содержит один `Content-Type` с media type `application/vnd.oai.openapi+json`

### Requirement: Discovery-связи сохраняются при статической публикации

Основная JSON-лента и её JSON Schema и OpenAPI в каждом из указанных разделов SHALL публиковать в `Link` связи `service-desc` на свои контракты и `api-catalog` на каталог раздела. Цели SHALL быть абсолютными каноническими URL с корректными media type. Публикация SHALL сохранять объявленные обработчиком связи и их параметры без дублирования; `GET` и `HEAD` одного URL SHALL возвращать одинаковый набор связей.

#### Scenario: Клиент обнаруживает контракты из ответа

- **WHEN** клиент получает основную JSON-ленту, её JSON Schema или OpenAPI
- **THEN** `Link` содержит `service-desc` для соответствующих JSON Schema и OpenAPI и `api-catalog` для каталога раздела
- **AND** каждая цель — абсолютный канонический URL с media type целевого документа

#### Scenario: Обновление объявленных discovery-связей

- **WHEN** опубликована сборка с изменёнными discovery-связями обработчика API-документа
- **THEN** ответ на этот URL содержит новый набор связей с объявленными параметрами
- **AND** в ответе нет дополнительно сохранённых устаревших или дублирующих связей

#### Scenario: Проверка discovery через HEAD

- **WHEN** клиент запрашивает API-документ через `HEAD`
- **THEN** ответ без тела содержит тот же набор `Link`, что `GET` этого URL

### Requirement: Публикация метаданных сохраняет действующую политику доставки

Применение метаданных статического endpoint SHALL сохранять установленную для его URL политику кеширования, базовые security headers сайта и дополняющие связи обнаружения и условия `Vary`, предусмотренные политикой доставки. Оно SHALL NOT создавать конфликтующие значения или дубли связей. Обслуживание HTML с согласованием Markdown через `Accept` и доступность сохраняемых прежних статических ресурсов SHALL сохраняться независимо от генерации текущих endpoints.

#### Scenario: Документ получает метаданные endpoint

- **WHEN** сервер отдаёт статический документ с метаданными endpoint
- **THEN** ответ также содержит базовые security headers сайта и следует установленной для этого URL политике кеширования, включая отсутствие явного cache-control там, где он не задан
- **AND** заголовки не дублируются и не конфликтуют

#### Scenario: Markdown имеет дополняющую ссылку на путеводитель

- **WHEN** клиент запрашивает Markdown endpoint, для которого политика доставки предусматривает `describedby` на путеводитель и `Vary: Accept`
- **THEN** ответ сохраняет эту связь и условие выбора представления вместе с заголовками endpoint

#### Scenario: HTML запрашивается как Markdown

- **WHEN** клиент запрашивает HTML-страницу с подходящим `Accept: text/markdown`
- **THEN** сервер сохраняет согласование представления и предусмотренные для него метаданные

#### Scenario: Клиент использует сохраняемый ресурс прежней сборки

- **WHEN** клиент запрашивает прежний версионированный статический ресурс в пределах установленного срока хранения
- **THEN** ресурс остаётся доступным с предусмотренной политикой кеширования, даже если его URL отсутствует среди endpoints текущей сборки
