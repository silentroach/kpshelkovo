# Внутрисайтовый поиск

## Назначение

Оценивай пользу поиска по реальной выдаче Pagefind. Автоматические тесты проверяют работу клиента и правила индексирования; релевантность меняющегося корпуса оценивай вручную через существующий интерфейс сайта.

Архитектура поиска описана в `docs/decisions/025-static-full-text-search-with-pagefind.md`, поисковые записи участков — в `docs/decisions/041-parcel-records-and-exact-search.md`. Основные файлы:

- `apps/www/src/lib/search` — клиент, типы и поисковые контракты;
- `apps/www/src/layouts/BaseLayout.astro` — Pagefind root и metadata;
- `apps/www/tests/search-quality.test.ts` — интеграционные проверки загрузки, переходов, догрузки и состава production-индекса;
- `apps/www/scripts/build-search-index.ts` — сборка индекса HTML и поисковых записей участков: читает четыре файла данных карты `/map/data/parcels/{shf,shv,shp,shr}.json`, проверяет каждый и уникальность кодов и алиасов в объединённом наборе; общего `/map/data/parcels.json` нет.

## Проверка до изменения

При изменении релевантности, правил корпуса, алиасов или движка:

1. Выбери затронутые запросы и несколько соседних контрольных формулировок по задаче.
2. До правки просмотри их в существующем поисковом интерфейсе. Для исследования можно использовать dev-индекс, проверив его свежесть; изменения индексирования и движка принимай по актуальной production-сборке. `pnpm dev` запускай только с разрешения владельца.
3. Определи лучшую целевую страницу по пользе читателю. Предпочитай актуальную справочную страницу устаревающей новости, если она точнее отвечает на запрос. Отметь существенные URL, их порядок, snippets и highlights для сравнения после правки.
4. Проверь `title`, `summary`, body, теги и текущую выдачу. Pagefind применяет русский stemming, поэтому отсутствие точной словоформы в исходнике еще не означает, что нужен алиас.

Исходную выдачу просматривай до редактирования, а не восстанавливай по памяти. Проверки технической правки, которая сохраняет релевантность и корпус, выбирай по затронутому поведению.

## Выбор исправления

Сначала исправляй естественный видимый текст, если материал действительно не называет важное для читателя понятие. Используй `search_aliases` только когда пользовательская формулировка уместна для поиска, но не для текста страницы.

Не добавляй алиас, если:

- целевая страница уже находится в подходящей позиции;
- словоформа уже покрывается stemming;
- алиас повторяет `title`, `summary`, body или теги;
- запрос слишком общий и несправедливо связывает понятие с одной страницей;
- материал не отвечает на запрос или содержит только косвенное совпадение;
- формулировка придумана «на всякий случай» и не подтверждена сценарием, аналитикой или речью жителей.

Добавляй минимальную полную формулировку запроса. Не переноси в поле все возможные синонимы и опечатки.

## Как индексируются алиасы

`search_aliases` — необязательный массив во frontmatter поддержанных коллекций. Raw DTO переводится в `searchAliases`, шаблон передает его как `SearchDocument.aliases`, а `BaseLayout` публикует `aliases` как Pagefind metadata.

Не добавляй алиасы скрытым текстом в `data-pagefind-body`: он может попасть в snippet. Алиасы не должны становиться SEO description, keywords, JSON-LD, публичным Markdown или текстом результата. При этом они не секретны: metadata видна в публичном HTML и индексе.

## Проверка после изменения

1. На обновлённом индексе просмотри выбранные запросы и контрольные формулировки. Сравни пользу целевых страниц, порядок результатов, snippets и highlights; проверь, что полезные прежние результаты не исчезли и не опустились без причины.
2. Для каждого алиаса подтверди пользу для исходного пользовательского намерения. Если улучшения нет или Pagefind уже находил страницу в подходящей позиции, удали алиас. Фиксированная позиция сама по себе не служит критерием пользы.
3. Проверь, что snippet состоит из настоящего содержимого страницы и не показывает служебную формулировку.
4. Выполни `pnpm test`, `pnpm typecheck` и `pnpm --filter @shelkovo/www test:search-quality`. Последняя команда включает production-сборку с индексом.
5. Кратко запиши в PR существенный результат ручного сравнения, когда оно относится к задаче: запросы, целевые URL, польза правки и влияние на соседние формулировки. Отдельный отчёт выдачи не нужен.

Набор запросов определяется задачей. Постоянная матрица реального контента, полные snapshots, точные количества результатов и автоматические ограничения рангов не используются. Обычное пополнение материалов по действующим правилам не требует такой ручной приёмки.

## Проверка материалов

При аудите коллекции не заполняй `search_aliases` массово. Для каждого кандидата отдельно покажи:

- исходный запрос;
- выдачу до изменения;
- выбранный целевой URL и почему он лучший;
- выдачу после изменения;
- влияние на соседние контрольные запросы;
- причину оставить или удалить алиас.

Лучше добавить несколько доказанных алиасов, чем покрыть все материалы предположительными ключами.
