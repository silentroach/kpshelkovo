# Public Media Publisher

## Intent

Публикуй переданные файлы в публичном S3-хранилище безопасно и воспроизводимо. Сохраняй исторические редакции, не перезаписывай существующие объекты и выдавай стабильные ссылки через `media.kpshelkovo.online`.

## First Steps

- Прочитай `docs/decisions/021-public-section-files-in-s3.md` и `ops/storage/public-media.md`.
- Если меняешь материал сайта, прочитай `AGENTS.md` его раздела.
- Убедись, что локальный файл и целевой раздел-владелец известны.
- Для изображения продолжай, только если это исходный PNG-скриншот публичного реестра для KB по ADR-021, фотография новости по ADR-023 или иллюстрация отзыва по ADR-024. Для другого сценария или формата остановись и запроси отдельное решение.
- Считай бакет полностью публичным. Если файл содержит секретные, персональные, внутренние или ограниченные данные, не загружай его.
- Используй уже настроенные credentials. Не ищи, не печатай и не добавляй их в команды или файлы репозитория.

## Key Selection

- Первый сегмент key обозначает раздел-владелец. Для базы знаний используется `kb/`, для промо-раздела `/815` - `815/`, для новостей — `news/`, для отзывов — `reviews/`.
- Внутренняя структура key не обязана повторять URL раздела.
- Если файл нужен нескольким разделам, сохраняй исходного владельца и используй один публичный URL.
- Для документов по умолчанию сохраняй историю: новая редакция получает новый датированный key.
- Используй дату снимка `YYYY-MM-DD`: самую раннюю подтвержденную дату, когда проект видел эту редакцию.
- Для новой редакции бери дату получения в `Europe/Moscow`; для переноса используй дату первого подтверждающего Git-коммита, если связь с этой редакцией доказуема.
- Не используй filesystem creation date, S3 `Last-Modified` или автоматически дату внутри документа.
- Если существующий материал уже ссылается на тот же документ, сначала сравни переданный файл с опубликованным объектом. Одинаковые байты сохраняют прежние дату, key и URL.
- Недатированный изменяемый key допустим только по явному требованию пользователя.
- Текущие PDF промо-раздела `/815/regulation` хранятся под недатированными ключами `815/regulation/<filename>.pdf` и не считаются историческим архивом. Не перезаписывай конфликтующий объект: сначала сравни SHA-256.
- Для оферт сохраняй установленную схему `kb/ok/offer/<snapshot-date>/<slug>.pdf`.
- Для подтверждающих скриншотов публичных реестров базы знаний используй `kb/<topic-path>/<snapshot-date>/<semantic-name>.png`. Материал должен ссылаться на публичный первоисточник, а исходный PNG публикуется без изменений.
- Для фотографий новостей используй `news/YYYY/MM/<article-slug>/<semantic-name>.jpeg`. Ключ неизменяем, а статья хранит URL, фактические `width`/`height` подготовленного JPEG, `alt` и опциональную подпись.
- Для иллюстраций отзывов используй `reviews/YYYY/MM/<review-slug>/<semantic-name>.jpeg`. Ключ неизменяем, изображение вставляется в авторский body Markdown с содержательным `alt`; GPS не восстанавливается.
- Не используй `404.html` и `_media/*`, которые зарезервированы nginx.
- Если подходящая storage-схема еще не определена, предложи короткий key и согласуй его до загрузки вместо создания новой таксономии молча.

## Publication Workflow

1. Документы, скачиваемые вложения и PNG-скриншоты публичных реестров для KB публикуй без изменения содержимого. Фотографию новости или иллюстрацию отзыва сначала подготовь точной командой из `ops/storage/public-media.md`: примени ориентацию, не увеличивай, ограничь длинную сторону 2560 пикселями, сохрани progressive JPEG в sRGB с quality 90 и удали метаданные.
2. Перед публикацией KB-скриншота вручную проверь всю видимую область и встроенные метаданные. Не загружай снимок с персональными данными, данными учетной записи, секретами, сессионными идентификаторами или другой непубличной информацией; не очищай безопасный исходник автоматически.
3. По умолчанию не переноси никакие EXIF/IPTC/XMP-данные в подготовленный JPEG. Для отзывов GPS не восстанавливай. Для новости верни только широту и долготу GPS, если место съемки само является публичным предметом новости и публикация координат осознанно одобрена; не сохраняй время съемки, устройство и остальные GPS-поля.
4. Проверь итоговые размеры и метаданные изображения, затем определи MIME-тип по содержимому, размер и SHA-256 именно публикуемого файла.
5. Проверь точный key командой `s5cmd head` через endpoint `https://s3.regru.cloud`.
6. Если объект существует, скачай его во временный каталог и сравни SHA-256. Не считай ETag контрольной суммой SHA-256.
7. Если SHA-256 совпадает, не загружай файл повторно и переходи к публичной проверке.
8. Если SHA-256 различается, остановись: не перезаписывай и не удаляй объект.
9. Если key свободен, убедись, что другой процесс не публикует тот же key, затем загрузи файл через `s5cmd cp --no-clobber` с явными `Content-Type` и `Cache-Control`, указанными в runbook. `--no-clobber` не дает атомарной гарантии create-only.
10. После `cp` обязательно скачай файл через `https://media.kpshelkovo.online/<key>` и проверь статус, MIME-тип, размер и SHA-256. Для KB-скриншота, фотографии или иллюстрации также повторно проверь размеры и метаданные. Это обязательная проверка и успешной загрузки, и возможного незаметного пропуска существующего объекта.
11. Только после успешной проверки добавляй публичный URL в материал сайта, если это входит в задачу.

Для временных скачиваний используй `/private/tmp/opencode`, а не репозиторий. Удаляй временные копии после успешной проверки, если они больше не нужны.

## Replacement And Deletion

- Не заменяй датированный объект по тому же key.
- Не удаляй старый объект при публикации новой редакции.
- После явного запроса на удаление найди известные ссылки, покажи пользователю один точный key и затронутые материалы, затем получи отдельное подтверждение.
- Удаляй только этот буквальный key командой `s5cmd rm --raw`; не используй wildcard или `--all-versions`.
- После удаления проверь S3 и media-origin с учетом того, что nginx может отдавать прежний успешный ответ из кеша до 10 минут.
- Если существующий объект конфликтует с новым содержимым, сообщи key, оба SHA-256 и остановись.
- Не создавай совместимые копии, редиректы или новые варианты key без конкретной необходимости или решения пользователя.

## Public Contract

- В материалах и ответах используй только URL `https://media.kpshelkovo.online/<key>`.
- Не публикуй `https://kps-public.s3.regru.cloud/<key>` как постоянную ссылку.
- Не добавляй query string для версий: nginx его не передает в S3.
- Помни, что прямой endpoint провайдера остается публичным; nginx не является границей доступа.

## Final Response

Кратко укажи:

- S3 key;
- публичный URL;
- размер, MIME-тип и SHA-256;
- был объект загружен или уже существовал с тем же содержимым;
- прошла ли проверка через media-origin;
- для KB-скриншота — итоговые размеры и результат проверки видимой области и метаданных;
- для фотографии или иллюстрации — итоговые размеры, примененный лимит/quality и результат проверки метаданных, включая решение по GPS;
- какие материалы сайта обновлены.

Никогда не показывай credentials.
