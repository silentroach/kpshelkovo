# Project Issues

- Репозиторий проекта: `silentroach/kpshelkovo` (`https://github.com/silentroach/kpshelkovo`). Для issue и pull request используй `gh` с явным `--repo silentroach/kpshelkovo`.
- Если создаешь issue от имени агента, добавь label `ai`.
- Выбор маршрута, согласование, владельцы информации и завершение определены в разделе «Жизненный цикл изменений» корневого `AGENTS.md`. Прочитай его перед работой с задачей.
- Для решения issue обычно создай отдельные worktree и ветку; явная просьба работать в текущей копии имеет приоритет. Коммиты оформляй по Conventional Commits с `Refs #<number>`; первую строку можно писать по-английски, поясняющее body — по-русски. Соблюдай действующие разрешения на commit, push и PR.
- Для OpenSpec-задачи укажи issue в change, а в issue — имя change и ссылку на его путь в рабочей ветке. После разрешения реализации оставь короткую отметку со ссылкой на коммит согласованных артефактов. Для архивированного change обнови ссылку на архив.
- Перед PR проверь весь актуальный diff, требования текущего change и затронутые основные specs; для короткого пути — запрос или issue. В PR укажи change, результаты проверок и оставшуюся ручную приёмку.
- Готовый PR пометь `ai`. Используй `Closes #<number>` только для задачи, критерии которой выполнены; если согласована production-приёмка, используй `Refs #<number>`. Родительские инициативы связывай через `Refs`, не закрывая их PR одного этапа.
- Заголовок pull request пиши на русском: кратко и по существу, без префиксов и scope из Conventional Commits.
- Описания issue и pull request пиши по-русски простым человеческим языком: сначала объясни, что видел пользователь и почему это было проблемой, затем — как это исправлено. Не перегружай текст внутренними деталями, канцеляритом и формальными формулировками; технические детали оставляй только там, где они помогают понять решение или риск.
- Собственную проверку выполняй до PR. Формальное человеческое ревью и merge оставь владельцу; не одобряй свой PR от его имени.
