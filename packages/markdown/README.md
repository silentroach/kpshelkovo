# @shelkovo/markdown

Общий серверный пакет для Markdown-рендера, извлечения текста и генерации Markdown через mdast. Строковая типографика принадлежит [@shelkovo/typography](/packages/typography/README.md); Markdown-пакет подключает её через AST-адаптеры.

## Разметка для авторов

Это справочник редакционного Markdown сайта и общего пакета. Базовые возможности и оглавление работают в `@shelkovo/markdown`; [расширения приложения](#расширения-приложения-appswww) подключает обёртка сайта. Frontmatter и правила конкретной коллекции задаются её локальными инструкциями.

### Текст, ссылки, списки и код

```markdown
## Подключение услуги

**Главное условие** и _дополнительное пояснение_.
[Инструкция](/kb/services/gas/) и [документ](https://example.com/document.pdf).

- Первый шаг
  - Уточнение шага
- Второй шаг

1. Подать заявку
2. Получить ответ

> Дословная цитата.

Синтаксис в коде: `:toc-omit[Приложение №]`.
```

Непустая строка отделяет абзацы. Вложенные списки сохраняют иерархию; нумерованный список Markdown продолжает последовательность, поэтому для юридических пунктов с собственной нумерацией сохраняйте исходную запись и сверяйте результат. Поддержаны GFM-ссылки, ссылки по определению, зачёркивание и списки задач. Ограждённый блок с языком, например `js`, показывает код буквально. Содержимое кода не становится директивами или упоминаниями.

Таблицы Markdown запрещены: используйте обычные списки и подзаголовки. Произвольный raw HTML не является авторским API и отбрасывается при HTML-рендере. Для оформления служат поддержанные конструкции, а не вставки HTML. Текст вне кода типографируется при HTML-рендере; вручную подменять обычные пробелы не требуется.

### Заголовки и якоря

Заголовки задаются через `#`–`######`. HTML-рендер вычисляет ID из полного текста заголовка и различает повторы, добавляет ссылку на раздел. Меняя заголовок, учитывайте внешние ссылки на его якорь. Для существующей цели скопируйте фактическую ссылку из готовой страницы, а не угадывайте slug по типографированному тексту.

### Обычное оглавление

Поставьте `[TOC]` отдельным абзацем в нужном месте:

```markdown
[TOC]

## Подключение

### Подача заявки

## Оплата
```

Результат: «Содержание», ссылки «Подключение» с дочерней «Подача заявки», затем «Оплата». Список автоматически строится по заголовкам второго–шестого уровней; H1 в него не входит. Оглавление не нужно поддерживать вручную после добавления разделов. Без `[TOC]` список не вставляется.

### Группы и короткие подписи оглавления

```markdown
[TOC]

## Термины и определения

### Обозначения

::toc-group[Договор]

## 1. Общие положения

### 1.1. Участники

## 3. Оплата

::toc-group[Приложения]

## :toc-omit[Приложение №] 1: Перечень услуг

### Сезонные работы
```

Видимое содержание:

- Перед группами: «Термины и определения» с подразделом «Обозначения».
- «Договор»: «1. Общие положения» с подразделом «1.1. Участники», затем «3. Оплата».
- «Приложения»: «1: Перечень услуг» с подразделом «Сезонные работы».

В теле остаётся полный заголовок «Приложение № 1: Перечень услуг». Его ID совпадает с ID того же заголовка без `toc-omit`; сокращение подписи не меняет цель перехода. Одинаковые короткие подписи допустимы: цели определяются полными заголовками. Авторские номера, в том числе пропуски, сохраняются, а не пересчитываются по числу пунктов.

- `::toc-group[Название]` — отдельная строка между верхнеуровневыми ветвями оглавления. Начинает группу до следующего маркера или конца документа; не создаёт заголовка или якоря в теле. Пустая группа не выводится. Число групп и пунктов произвольное.
- `::toc-group` без подписи начинает отдельную группу без названия. На страницах KB несколько групп образуют колонки на широком экране и идут последовательно на узком. Именованные и неназванные группы можно смешивать; `::toc-group[]` и подпись из одних пробелов остаются ошибкой.
- До первой группы пункты остаются вводными вместе со своими подразделами. Отдельного сброса группировки и вложенных групп нет.
- `:toc-omit[Фрагмент]` используется внутри заголовка. Фрагмент скрывается только в подписи TOC, но остаётся в полном заголовке, извлекаемом тексте и вычислении якоря. Произвольного второго названия `toc-label` нет.
- Маркер не должен отделять подраздел от его родителя. Например, группа между `## Раздел` и его `### Подраздел` — ошибка. После исключений подпись должна оставаться непустой. Некорректная известная аннотация останавливает обработку с указанием места в исходнике.

Имена `toc-group` и `toc-omit` — проектные расширения, а не стандарт Markdown. Сторонний просмотрщик может показать их буквально. Публичный Markdown companion вместо них получает обычные абзацы с названиями групп и вложенные списки ссылок; полные заголовки сохраняются. Повторная подготовка не добавляет второе оглавление. Неизвестные директивы остаются обычным Markdown. Чтобы показать пример известной конструкции буквально, поместите её в inline-код или fenced code.

Пример двух групп без дополнительных заголовков оглавления:

```markdown
[TOC]

::toc-group

## Выполнено

## План

::toc-group

## Просрочено

## Отменено
```

В companion неназванные группы становятся отдельными списками без абзацев с названиями.

### Изображения

```markdown
![Вход со стороны улицы](https://example.com/entrance.jpg 'Вход в здание')
```

У отдельного изображения непустой `title` становится видимой подписью. У изображения внутри текстового абзаца он остаётся всплывающей подсказкой. `alt` описывает смысл изображения; подпись дополняет, а не заменяет его. Публикация адресов и файлов подчиняется правилам соответствующей коллекции и публичного media.

## Расширения приложения `apps/www`

Эти возможности подключает приложение: HTML проходит через `@/lib/markdown/render`, а companions готовятся отдельными app-адаптерами с общими AST-преобразованиями. Низкоуровневый пакет сам по себе не раскрывает доменные упоминания, карты или редакционные callout и не добавляет значки файлов.

### Ссылки на файлы

В HTML сайта файловый обработчик добавляет к обычной Markdown-ссылке на PDF штатный значок. Пакетный `render` без app-обёртки оставляет обычную ссылку; companion сохраняет её текст, URL и `title` без значка. Архивные URL задаются автором и не вычисляются из даты документа.

### Ссылки на Telegram

В HTML сайта Telegram-ссылки автоматически получают штатный декоративный значок. Это работает для обычных ссылок, ссылок по определению и автоссылок, включая сообщения, приглашения и `tg:`.

Простая подпись `[@Resident_Name](https://t.me/resident_name)` отображается как `Resident_Name`: начальный `@` снимается, если подпись без учёта регистра совпадает с username прямого HTTP(S)-адреса без query и fragment. Завершающий `/` допустим. Ник без `@` уже подходит. Подписи вроде `[чат праздника](https://t.me/example_chat)`, видимые URL, вложенное форматирование и подписи ссылок на сообщения или приглашения сохраняются.

Значок не заменяет доступное имя ссылки и не меняет URL, `title` или способ открытия. Пакетный `render` без app-обёртки и Markdown companion сохраняют авторскую ссылку, включая начальный `@`, без SVG.

### Ссылки на Яндекс Навигатор

В HTML сайта ссылки со схемой `yandexnavi:` автоматически получают декоративный значок навигационной стрелки. Обычные ссылки, ссылки по определению и явные автоссылки оформляются одинаково. Название сервиса в подписи или HTTP(S)-адресе само по себе значок не добавляет.

Пишите обычную Markdown-ссылку с понятной подписью: `[Маршрут в Яндекс Навигаторе](yandexnavi://build_route_on_map?lat_to=55.062483&lon_to=37.708384)`. Обработчик сохраняет исходные URL, параметры, `title` и вложенное форматирование. Значок не озвучивается скринридером и скрывается при печати. Пакетный `render` без app-обёртки и Markdown companion сохраняют обычную ссылку без SVG.

#### Маршрут от текущего местоположения через остановки

Для поездки по заданным остановкам используйте `yandexnavi://build_route_on_map`:

- Не задавайте `lat_from` и `lon_from`: началом будет текущее местоположение водителя.
- Передавайте все остановки, включая место сбора, парами `lat_via_0` / `lon_via_0`, `lat_via_1` / `lon_via_1` и далее. Индексы начинаются с нуля и идут подряд в порядке посещения.
- Финиш задавайте парой `lat_to` / `lon_to`; не дублируйте его в `via`.
- Координаты остановок берите на дороге у согласованного места подъезда. В GeoJSON пары записаны как `[долгота, широта]`: значение `lat` берётся вторым, `lon` первым. Сохраняйте публичную точность не более восьми знаков после запятой.

Пример с двумя остановками и отдельным финишем:

```text
yandexnavi://build_route_on_map?lat_to=55.062483&lon_to=37.708384&lat_via_0=55.069083&lon_via_0=37.738282&lat_via_1=55.06729903&lon_via_1=37.74148255
```

Если место сбора передать через `from`, оно станет фиксированным началом маршрута, а следующая остановка получит номер 1. Чтобы место сбора было первой нумерованной остановкой, передавайте его через `via_0` без `from`. Такой вариант красного маршрута Хеллоуина владелец проверил в Навигаторе; ОС и версия приложения не зафиксированы. Для новых маршрутов проверяйте состав и порядок точек на телефоне перед публикацией.

Ссылки передают координаты, но не авторские названия остановок или готовую линию дороги: путь между точками Яндекс рассчитывает сам. Формат и ограничения внешних запусков разобраны в [исследовании](/docs/research/2026-10-30-yandex-navigator-routes.md).

### Упоминания

Используйте `@slug` для канонического имени, `@slug:gen` для формы родительного падежа или `[председателю](@slug)` для авторского текста ссылки. Поддержаны `nom`, `gen`, `dat`, `acc`, `ins`, `prep`; нужная форма должна существовать в данных сущности. В ссылочной форме падеж задаётся видимым текстом, не суффиксом адреса. Неизвестное упоминание и отсутствующая форма вызывают ошибку сборки. Подробности — в [правилах упоминаний](/apps/www/AGENTS.md#entity-mentions).

### Примечания, предупреждения и источник цитаты

```markdown
> [!NOTE]
> **Добавочные отличаются**
>
> Пояснение со [ссылкой](https://example.com/).

> [!WARNING]
> **Перед началом работ**
>
> Проверьте условия подключения.

> [!NOTE]
> **Уточнение**
>
> Пояснение по сообщению компании.
>
> [!SOURCE]
> [Автор сообщения](https://example.com/message)
```

Маркер NOTE или WARNING занимает первую строку цитаты. Необязательный заголовок — отдельный абзац, целиком выделенный жирным; без него используются «Примечание» или «Внимание». Автор задаёт второстепенное оформление сопроводительного абзаца через `[!SOURCE]` на отдельной первой строке абзаца непосредственно внутри NOTE/WARNING; роль не определяется по словам абзаца. Вне этих блоков маркер остаётся обычным текстом. Обычная цитата без маркеров остаётся цитатой. В companion сохраняются содержание, ссылки и заголовки обычным Markdown.

### Оригинал распознанного документа

В KB NOTE с единственной файловой ссылкой в заголовке получает компактное тёплое оформление со штатным значком PDF:

```markdown
> [!NOTE]
> **[Оригинал от 09 июня 2026](https://example.com/original.pdf 'Оригинал документа (PDF)')**
>
> Текст распознан автоматически и может содержать неточности.

[TOC]
```

Это рецепт существующего NOTE, а не отдельная директива или поле документа. Дату редакции и URL задаёт автор по документу; дата каталога архивной копии не заменяет дату редакции. Отдельный вводный повтор этой даты под исходным H1 не нужен. Юридический текст, прочие даты и реквизиты сохраняются. Для оферт используйте [промпт](/prompts/oferta.md), параметры оформления — в [дизайн-гайде](/docs/design/design-code-shelkovo.md).

### Сравнение редакций

````markdown
```change
- Прежняя формулировка.
+ Новая формулировка.
```
````

Блок `change` сопоставляет старый и новый текст. Доступны явные режимы `change inline` и `change block`; без них представление выбирается по объёму изменений. Обе стороны должны содержать текст. Это расширение сайта, а не обычный diff с исполняемым кодом.

### Редакционные карты

````markdown
```map https://example.com/map
{"type":"FeatureCollection","metadata":{"name":"Схема прохода"},"features":[{"type":"Feature","id":0,"properties":{"iconCaption":"Вход"},"geometry":{"type":"Point","coordinates":[37.75,55.05]}}]}
```
````

Полный GeoJSON находится в ограждённом блоке `map`; необязательный HTTP(S)-адрес пишется сразу после `map`. HTML-преобразование включено опцией `editorialMaps: true` для новостей и KB; без неё блок остаётся кодом. Companions новостей и KB сохраняют блок с публичной точностью координат и подписью. Формат, геометрия, оформление и ограничения — в [руководстве редакционных карт](/docs/editorial-maps.md#вставка-в-новость-или-справку). Карта статьи не создаёт карточку места, а её JSON не разбирается как упоминания.

## Публичный API

- `render(markdown, options?)`
  Рендерит Markdown в HTML. Выполняет preprocessors до парсинга, применяет GFM, отбрасывает raw HTML и типографирует текстовые узлы. Markdown-таблицы отклоняет с ошибкой. В `apps/www` body markdown проходит через `@/lib/markdown/render`, чтобы сработала доменная обработка приложения.

- `MarkdownPreprocessor`, `MarkdownAstTransform`, `RenderOptions`
  Preprocessor принимает Markdown-строку и возвращает строку. `options.preprocess` принимает одну функцию или последовательность функций. `options.transform` получает целый mdast `Root` после построения авторского `[TOC]` и функцию `reserveId(base)` для ID вставляемых элементов. Code nodes ещё содержат `lang` и `meta`; transform может изменить дерево на месте или вернуть другое `Root`. Авторские ID заголовков резервируются первыми, `options.reservedIds` защищает ID окружающей страницы. Затем документ рендерится как единое целое: GFM-ссылки по определению и заголовки продолжают работать. `eagerImages: true` задаёт изображениям `loading="eager"`; по умолчанию используется `loading="lazy"`. Options пакета универсальны, доменная логика остаётся в приложении.

- `options.idPrefix`
  Необязательный префикс всех ID готового HTML-фрагмента: заголовков, сносок, подписей задач и элементов, добавленных AST-transform. В конце HAST pipeline та же карта целей обновляет локальные `href="#…"` (включая percent-encoded fragments), TOC, heading permalinks, прямые и обратные ссылки сносок и IDREF-атрибуты (`aria-describedby`, `aria-labelledby`, `for` и другие). Ссылки на цели вне фрагмента, другие страницы и внешние URL сохраняются. Без префикса и с пустой строкой HTML не меняется. Вызывающий код выбирает уникальный устойчивый префикс для каждого body; `reservedIds` продолжает резервировать исходные, ещё не префиксированные ID и не заменяет namespace для нескольких body.

- `renderWithMetadata(markdown, options?)`, `RenderedMarkdown`
  Выполняет тот же рендер и возвращает `{ html, localIds }`. `localIds: ReadonlyMap<string, string>` содержит исходные ID заключительного HAST и соответствующие ID в HTML; без `idPrefix` это тождественная карта. Карта включает автоматически созданные цели сносок, но не цели окружающей страницы. Генератор companion может направить авторскую локальную ссылку на каноническую HTML-страницу: декодировать fragment, найти его в `localIds` и добавить к URL закодированный итоговый ID. Отдельно вычислять slug или повторно разбирать HTML не требуется. API не изменяет mdast-сноски companion: при объединении независимых Markdown-body их definitions/references нужно изолировать отдельно. В `apps/www` использовать `renderMarkdownWithMetadata` из общей app-обёртки, чтобы карта учитывала тот же pipeline, что и body сайта.

- `createMarkdownDocument({ frontmatter, children })`
  Создаёт mdast `Root`. Если передан `frontmatter`, добавляет YAML-узел первым. Объект сериализуется через `yaml` с блочными коллекциями, отступом в два пробела, без директив и переноса строк по ширине; кавычки определяются содержимым значений. Состав публичных полей выбирает вызывающий код.

- `serializeMarkdownDocument(document)`
  Сериализует mdast `Root` в Markdown: ATX-заголовки, списки через `-` и `1.`, ограждённые блоки кода, GFM и финальный перевод строки. Отдельный абзац `[TOC]` заменяет содержанием по заголовкам `h2`–`h6`. Markdown-таблицы отклоняет с ошибкой.

- `parseMarkdownFragment(markdown)`
  Парсит существующий редакционный Markdown в `readonly RootContent[]` с поддержкой GFM. Позволяет вставлять его в документ с сохранением разметки. YAML frontmatter из фрагмента удаляется.

- `expandTableOfContents(document)`
  Разворачивает `[TOC]` в подготовленном mdast `Root`, например после `parseMarkdownFragment`, и возвращает дерево с оглавлением. При объединении независимых body позволяет развернуть каждое оглавление до общей сериализации. Использует то же назначение авторских ID, что HTML renderer: учитывает вложенные заголовки, повторы и зарезервированные GFM-цели сносок. `toc-omit` сокращает подпись, но ID строится из полного заголовка. Финальный `serializeMarkdownDocument` превращает служебные контейнеры оглавления в обычные списки и абзацы.

- `md`
  Тонкие фабрики mdast-узлов: `heading`, `paragraph`, `text`, `link`, `list`, `listItem`, `inlineCode`, `code`, `blockquote`, `thematicBreak` и `yaml`. Строковые аргументы заголовков, абзацев и ссылок означают обычный текст; для форматирования передаются узлы. Можно использовать стандартные mdast-узлы напрямую. Типы входов и параметров экспортируются из пакета, их определения — в [generate-types.ts](/packages/markdown/src/generate-types.ts).

- `resolveMarkdownResourceReferences(children)`
  Разрешает reference-ссылки и изображения по definitions, превращая их в обычные узлы `link` и `image`, затем удаляет definitions. Это позволяет делить редакционный документ на самостоятельные фрагменты без потери адресов. Меняет вложенные узлы переданного дерева.

- `extractFirstMarkdownText(markdown)`, `extractMarkdownText(markdown)`
  Извлекают соответственно первый непустой читаемый блок или весь читаемый текст. Пропускают блоки кода, raw HTML, YAML и definitions; используют image alt и текст inline-кода. Схлопывают пробельные символы, включая NBSP, в обычный пробел и обрезают края. Возвращают `undefined`, если читаемого текста нет.

- `rehypeTypograf()`, `satteriTypograf()`
  Плагины типографики для внешних rehype- и Satteri-pipelines соответственно. Общий адаптер преобразует безопасный HTML из `formatTextHtml` пакета `@shelkovo/typography` в узлы дерева, сохраняет пробелы по краям текстового узла и пропускает код, другие защищённые элементы и уже созданные обёртки диапазонов. Диапазон обрабатывается внутри одного текстового узла; через границу ссылки или выделения он не собирается.

## Граница типографики

Адаптеры используют общие правила и наборы `TYPOGRAPHY_SKIP_TAGS`, `TYPOGRAPHY_WRAPPER_CLASSES` из `@shelkovo/typography`. Контракт диапазонов, кавычек, повторной обработки и CSS hooks описан в [README типографики](/packages/typography/README.md#общие-правила-и-htmlcss-контракт). CSS для создаваемой разметки принадлежит приложению.

Строковые `formatText`, `formatTextHtml`, `formatDynamicHtml` импортируются напрямую из корня `@shelkovo/typography` и на сервере, и в клиентском коде. Markdown-пакет не реэкспортирует их и не предоставляет прежний subpath `@shelkovo/markdown/typography`; его корневой вход загружает серверную AST-инфраструктуру.

## Пример генерации

```js
import {
  createMarkdownDocument,
  md,
  parseMarkdownFragment,
  serializeMarkdownDocument
} from '@shelkovo/markdown';

const editorialBody = 'Описание с **редакционным выделением**.';
const document = createMarkdownDocument({
  frontmatter: { title: 'Справка' },
  children: [
    md.heading(1, 'Справка'),
    md.list([md.listItem([md.paragraph([md.link('/kb/', 'База знаний')])])]),
    ...parseMarkdownFragment(editorialBody)
  ]
});

const markdown = serializeMarkdownDocument(document);
```

Ссылки и списки здесь создаются узлами; парсер обрабатывает только готовый редакционный текст.
